**Existing basis and remaining user problem:** safe historical comment acceptance already recovers through the validated atomic settlement. Historical accepted streams with conflicting data/UTF-8 suffix semantics stop as `accepted_evidence_conflict`, preserving raw/native/staging/pointers, original usage/time and committed tool effects without resending. Synthetic file-Store and Runtime cases establish that this state is real and that preservation works. No affected live Nursing task or real-route incidence has been established. The current app does not provide a general, supported resolution workflow for that conflict; a user who encounters it may need technical diagnosis before useful work can continue. A safe stop is an appropriate preservation boundary, but it is not a complete recovery experience.

**Potential value:** reduce manual forensic work and recover useful task progress when the evidence supports a specific next action. This is a separate capability improvement, not proof that the current shared completion rule should be replaced. Possible next actions must be distinguished: reuse a result whose compatibility can actually be established, retain a conflict while continuing from an explicitly chosen preserved state through a new request, or remain stopped when integrity/effects cannot be resolved. These are design candidates, not currently available actions or permission to perform them.

**Meaningful increments and tradeoffs:** first consider a read-only diagnostic presentation using the existing evidence: exact request/attempt, failing rule, raw/native/staging linkage, committed and pending tool effects, saved versions, known/unknown usage and available preservation/export information. It could make an informed decision easier without creating another inference or changing acceptance. Only add a case-specific resolution action when its preconditions and effects can be stated and verified. A generic "force accept/retry" button or blanket automatic salvage would hide materially different risks, including duplicated model work, repeated tools and inconsistent context/history. A full resolution state machine is not selected merely because it is more general.

**Preservation requirements for the selected objective:** preserve original acceptance and conflict evidence rather than rewriting history; retain frozen requests, consumption and useful products; never synthesize acceptance from raw-only terminal bytes; distinguish immutable integrity/provenance failures from compatibility of historical validation rules. Determine the state of already committed effects before any continuation, preserve idempotency across interruption/reopen, and leave unresolved effects explicit. A new model request needs applicable authorization and a new traceable identity; it must not masquerade as the old reply or reset consumption. The selected state must remain consistent with graph/context/handoff responsibilities. Do not ask the user to repair SQLite manually or silently discard earlier work. The objective is adopted; a concrete recovery transition is not yet an effective contract or implemented action.

**Selection rationale and remaining alternatives:** the user has now prioritized understandable diagnosis and supported recovery before real Nursing validation. This supersedes the initial deferral based on the existing preservation guard, unknown live incidence, additional semantic/verification work and competing delivery validation. A production failure is not a prerequisite for selection. Broader recovery for corrupt evidence or unknown tool effects remains an open alternative, to revisit when a concrete case establishes enough evidence for a safe transition; it must not silently become part of the first supported class.

**Proposed first implementation method:** extend the existing task/evidence UI with a read-only diagnostic projection, then add an explicit preserve-and-replan action only for intact historical evidence with known tool-effect outcomes. Ordinary Continue and unknown-compaction recovery do not establish this transition: reconciliation currently stops on an accepted-evidence conflict. A resolution must therefore have its own durable identity linked to the exact request, task revision and document head, with a defined graph/context projection that can be recovered after interruption. Specify the disposition and model-visible representation of unstarted calls without executing them, retain completed receipts and useful document versions, and distinguish resolution selection from dispatch of a new request. A stale view, duplicate click or reopened process must not duplicate effects. This is a proposed design for discussion, not a selected schema or an instruction to mutate an existing task. It favors reuse of the existing ledger/immutable evidence and explicit transitions over a generic repair engine; storage restructuring remains available if concrete atomicity requirements justify it.

**Proportionate evaluation:** start from retained synthetic conflict Stores, not a real task mutation. Compare the existing controlled stop with a proposed diagnostic/resolution path for the user's ability to understand the conflict and preserve/continue useful work. Check conflicts before tool dispatch and after a committed tool, partial metadata/graph publication, repeated/reopened resolution, valid historical comments and genuine corrupt evidence. Require stable raw/native/staging/usage/time, no unintended inference or duplicate effect, and source-led saved/reopened/exported results. Measure intervention reduction or successful supported recovery rather than merely the existence of a button. Local mechanism selection, actual route validation and live recovery authority remain separate.

### Recovery transition discussion (2026-10-29)

Recorded 2026-10-29, Asia/Hong_Kong (UTC+08:00), against source `b36ad63` and the four existing uncommitted discussion documents. The supplied external commentary, headed "I have fully inspected the project source" in Chinese, proposed read-only diagnostics, operation reconciliation, publication of missing acceptance pointers for normal history, separate compaction handling, and a local resolution transaction before dispatch. Its original is the user attachment `f374af8f-3d87-44fb-a388-c51e5ed04b07/Pasted text.txt`; that attachment is optional provenance, not required to understand this account. Its asserted complete review is the reviewer's claim. This conversation checked the relevant local code, not a new whole-project audit or runtime experiment.

**Assessment agreed by the human:** the API evidence gap, avoidance of mutating `Nexus.reconcile()`, known-effect tool handling and separation of resolution from dispatch are useful. A truly read-only path must also avoid write-capable Store/Runtime initialization. Integrity checks must include frozen protocol, task/request/attempt ownership, descriptors, native reconstruction and exact staged projection, not just matching chunk hashes. Restricting initial support to finish-boundary conflicts is coherent; other decoder failures are not thereby proven storage corruption. Populating `accepted_ref` for conflicting staged acceptance would conflate historical evidence with current successful validation. Use an explicit resolution and a distinct historical projection instead. `catalog.sqlite`, immutable files and `graph.sqlite` cannot be declared one atomic transaction under current wiring; a committed catalog decision must support replayable graph projection. `needs_agent_revision` is a status and `invalid_revision` is a reason, not synonyms; interruption is not necessarily malformed structure. Context settlement keys belong to their actual coordinator transition, and compaction does not universally increment normal-batch sequence. Clearing an active report for re-planning must retain its original receipt and delivery facts. These corrections change the proposed implementation method, not the selected recovery-before-Nursing priority.

**Next proposed scope, not yet an adopted transition contract:** support a complete staged/native object with intact provenance and a recognized historical finish-boundary conflict, with every local effect established or confirmed not started. Apply this to both published acceptance and staging-only gaps without rewriting either original acceptance state. Diagnose raw-only evidence, other receive failures, corrupt/contradictory records and unknown effects explicitly; do not offer this recovery action for them. This is an initial supported class, not a claim that broader recovery is impossible or unimportant.

| Evidence/effect case | Proposed local action and successor basis |
| --- | --- |
| Complete evidence passes the current criterion | Report compatible evidence; preserve existing ordinary validated settlement/reuse. No conflict override is needed and diagnosis performs no settlement. |
| Eligible normal conflict, no tool started | Preserve candidates; durably pair each call with a truthful not-started result. Record one resolved historical batch and re-plan from current saved work. |
| Eligible normal conflict, some or all tools committed | Verify and retain each actual receipt/effect; only settle confirmed unstarted calls as not started. Include the batch once, regardless of checkpoint retries. |
| Started tool with uncertain outcome or inconsistent receipt | Explain the exact unknown/inconsistency; no automatic replay or false not-started receipt. This action remains unavailable. |
| Eligible compaction conflict, no committed handoff | Preserve candidate text and the previous handoff/history; record the choice to re-plan. Do not promote the candidate handoff or append compaction to normal history. |
| Eligible compaction conflict, committed handoff with a checkpoint gap | Validate archive, committed receipt and original basis, then recover exactly that committed transition. Do not re-evaluate the old acceptance using today's capacity or apply it twice. |
| Resolution committed, graph projection unfinished | Complete the same recorded projection before new dispatch; do not create another resolution or increment again. |
| Missing/corrupt/contradictory evidence, no accepted staging, or unsupported decoder conflict | Preserve and explain; do not disguise it as the supported historical finish-boundary case. |

Published-pointer versus staging-only state is an independent dimension of the eligible rows, not a reason to omit one from acceptance. Likewise test both normal/compaction protocols and the meaningful operation/context/handoff boundaries without requiring an unbounded Cartesian matrix.

**Proposed model-facing history:** introduce one batch-reading responsibility that distinguishes current validated acceptance from resolved historical evidence. Normal assembly, exact reference collection, capacity estimation, compaction and handoff archive construction all use that same distinction. For eligible normal batches, retain validated native call identities and matching actual/not-started results as historical facts, with an explicit recovery explanation that the old batch cannot authorize further tool execution. No new assistant reply is fabricated. The original candidate/text/usage/version references remain accessible, and the current user instructions, document head and active policy remain authoritative. Do not rely solely on transient `continuation_feedback`: the resolution link must survive later tools, compaction and reopen. A compact prose-only recovery summary is an alternative, but cannot replace complete originals or silently break tool pairing and reference/coverage accounting. Exact internal history schema and protocol presentation still need design; a new generic history framework is not required.

**Proposed context and report treatment:** recover already committed policy effects using their exact recorded basis. An interrupted uncommitted batch gets an explicit ineligible disposition explaining recovery interruption; its saved intents remain available for explicit reselection, with no partial admission or automatic fallback to an older proposal. Complete but uncommitted proposals also need an explicit resolution policy; the recommendation is to require reselection rather than silently apply a conflicted batch. Distinguish that recommendation from the existing structural-invalidity rule. Preserve unrelated effective policy and committed work. Retain report receipts and delivery versions while removing the old report's authority to immediately terminate this newly requested planning step. The resolution must account for any pre-existing pending context proposal rather than indiscriminately clearing context state.

**Proposed persistence and stale-view contract:** inspection yields an evidence/basis identity, not execution authority. Under the existing task lock, validate the exact request/attempt, graph checkpoint, head, instructions, effective policy and relevant evidence again. Changed facts require a fresh diagnosis before the first commit. Prepare immutable receipt content, then atomically publish the catalog resolution and the associated catalog effects; mere staged files are not a committed choice. Record the exact original basis and intended graph changes, rather than calculating fresh increments during replay. Publish the graph through its supported checkpoint API. If catalog commits first and the process exits, recover that projection without replaying tools or sending a request. If graph already reflects or has advanced beyond this resolution, never roll it back. Legitimate later amendments/settings/head changes do not revoke a committed choice: finish its projection while preserving newer service facts, then evaluate current settings/instructions before any new frozen request. Checkpointer implementation details require the installed framework's official guidance before coding.

**Proposed user flow and local acceptance:** show the conflict and preservation facts, with one local "Preserve work and prepare to re-plan" action when eligible; it needs no provider credential. After successful local resolution, allow inspection/export/amendment and a separate ordinary Continue. Display pending projection as incomplete recovery rather than claiming readiness. No first-version combined resolve-and-send control is needed. Acceptance must cover actual UI/API use, unchanged diagnosis reads, stale selection, duplicate resolution, staged-but-uncommitted files, catalog/graph crash gaps, both acceptance publication states, known/unknown effects, committed/uncommitted context and handoff, subsequent normal and compaction inputs, and source-led save/reopen/export. Demonstrate unchanged accepted pointers/original evidence/usage/time and no repeated local effects. Local checks use isolated evidence and scripted responses; they establish no real-route success. The exact first supported conflict class and model-facing historical representation are the next design choices; implementation and Nursing execution are not started by this discussion.

### Second recovery commentary assessment (2026-10-29)

The next external response (user attachment `cc944004-2a38-4855-846e-02fcf0f26504/Pasted text.txt`) accepted the pointer/transaction/key corrections and proposed four diagnostic classes, N-1/N-2/C-1/C-2 transitions, a shared `Context.batch_reply` and prepare/catalog/graph phases. This is useful design input, not adopted implementation authority. The following source-based assessment was recorded under the continuing discussion-record authority; no runtime reproduction or code change was performed. The selected recovery-before-Nursing order is unchanged.

- **Retain the direction:** an on-demand no-write diagnostic, explicit resolution distinct from acceptance, known-effect eligibility, normal/compaction-specific transitions, shared history reads and catalog-authoritative graph recovery fit the objective. Compatible staging should be described as validated evidence awaiting publication where applicable, rather than claiming that a read-only diagnosis has already completed acceptance settlement.
- **Correct phase A publication:** `Store.blob(key=...)` registers its catalog alias immediately. `Dispatcher.reconcile` can promote an existing unfinished operation using `result:<operation>` without a conflict-resolution commit check. Therefore preparing recovery-specific not-started results under their final aliases can expose uncommitted choices to an existing consumer (particularly an existing `skipping` operation), or reserve an immutable alias that blocks a later retry with a changed basis. Stage under unique/content-derived candidate identities; publish final aliases, operation settlement and the resolution authority together in the catalog commit. The same rule applies to `conflict-resolution:<K>` and other authoritative recovery aliases. Existing raw evidence and original candidates remain unchanged. This concerns the proposed new recovery path, not a newly reproduced defect in the current bounded R13 repair.
- **Preserve immutable context history:** an existing `context-proposal:<K>` cannot be rewritten; `Store.blob` rejects different bytes at that reference. Applied, superseded and previously ineligible dispositions are distinct historical facts. Do not replace every non-applied disposition with a new recovery reason. Record a new linked recovery decision for still-uncommitted intent where needed, preserve the original proposal and existing settled outcomes, and account for a pre-existing unrelated pending proposal before clearing `context_waiting`. A recovered `context_feedback` needs the structure expected by its readers, not merely a resolution reference or a nominal `context_commit` marker. The recommendation to require explicit reselection of complete but uncommitted conflicted intent remains a proposal from the preceding discussion.
- **Make graph idempotency explicit:** store the original basis and exact intended successor, not a recipe that appends K or increments the current counters whenever called. Distinguish the original checkpoint, already-projected successor and later progress. A repeated API call after projection must identify the existing resolution even though pending no longer names K; it must not append again, drop newer history or overwrite later instructions/head/policy. Catalog-committed projection recovery must precede reconciliation of K, but finding a resolution row alone does not authorize an arbitrary graph rewrite.
- **Use one actual catalog transaction:** the current `event_once` starts its own transaction. Calling it inside another write transaction is not a supported composition: it can reject nesting with a shared handle or contend on a separate writer. Publish an event/receipt through the same transaction-aware primitive, or derive a separately deduplicated notification from the committed resolution. Only the committed resolution/effects are transition authority. Also settle verified staged operation results into complete operation records in that commit when necessary, not only newly skipped calls; Context currently requires `operation.status == done`.
- **Carry recovery provenance through every representation:** the shared reader should return an explicit ordinary/resolved classification, staging/native and resolution references, not only a reply fallback. Resolved classification takes precedence even if the historical `accepted_ref` already exists. Preserve resolution provenance through normal history, compaction entries, retention previews and handoff archives, independent of transient continuation feedback. The current source has seven direct acceptance-pointer reads in `context.py`, including the `original_refs` retention preview; the review's six named consumer locations must not become an exhaustive implementation checklist. Actual dependency search and behavioral checks govern coverage.
- **Avoid misleading diagnostic labels:** matching hashes establish agreement with stored descriptors, not semantic or physical perfection. Native/reconstructed mismatch is a saved-evidence contradiction whose cause may be unknown; parser failure does not itself prove disk corruption. Diagnostic results should separately expose storage/provenance integrity, reconstruction/native consistency, receive-rule compatibility, acceptance publication and recovery eligibility. First-version supported eligibility can remain narrow without forcing all other outcomes into a misleading label. Preserve original request/attempt usage/time rather than the review table's ambiguous allowance for missing-field repairs; separately display validated saved facts and publication status.

The next useful step is to incorporate these boundaries into one coherent target design after the remaining scope/reselection choices are settled, rather than start another broad audit. Required distinguishing checks include exit after candidate preparation but before catalog commit, changed-basis retry, catalog-before-graph exit, repeated resolution after graph advancement, staged-result operation recovery, prior context dispositions and continued compaction/archive provenance. They are proposed checks, not passing evidence.
