### User question, preference and clarification

The user questions why a model request must stop at a fixed duration when Codex can work on one task for an hour, asks how 600 seconds and Codex's timeout are determined, and then considers the documented stream-idle approach more reasonable: if data keeps arriving, is the model still working? The assistant supports evaluating continued waiting while useful generation is observable, while distinguishing the following facts:

- A whole agent task may contain many model requests and tool operations. Its duration does not establish the maximum duration of one request.
- A total request deadline measures elapsed time from the request's start. An inactivity timeout measures the interval since activity as defined by that implementation. A stream can exceed five minutes in total without exceeding a five-minute inactivity interval; the exact events that reset that interval must be specified.
- Incoming new text, reasoning-summary or tool-argument deltas are evidence of generation/delivery progress. A created/in-progress status is a different signal. Transport bytes, proxy buffering or a keepalive alone do not establish continued model generation; these examples do not assert that the current Nexus route emits such keepalives.
- Progress does not prove correctness, completion or successful delivery. Conversely, silence does not prove that a model stopped working, especially before the first visible output or with a non-streaming response. Incomplete tool arguments must not be executed.
