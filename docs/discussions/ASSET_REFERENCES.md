## Readable filenames and later search (2026-11-08)

**User question and boundary.** After AR-S1, the user questioned the hash-only filename rule because these images may later be searched and meaningful names could make them easier to match. The user explicitly requested discussion first and an English reply. This reopens the filename policy; it selects no filename format, naming tool, specification replacement or implementation. AR-S1's hash-only destination clause remains the preceding proposal, not a settled response to this new objective.

**Inspected basis.** `Evidence.image` currently computes SHA-256 from the bytes and uses it both in the internal blob record and the visible `asset_path`. `Documents.edit` additionally enforces a hash-shaped asset basename, but the saved `assets` map separately records `ref`, full `sha256` and provenance. File manifests also store full hashes independently of their keys. Thus the visible basename and byte identity are coupled by current implementation/policy, not by an inherent integrity requirement. Supporting descriptive names would require coordinated registration/validation/fixture changes; it is not an export-only string substitution.

**Recommendation for discussion.** Separate internal byte identity from the human-readable filename. Keep the full SHA-256 for object storage, deduplication and verification. Use a source-grounded description, a useful page/figure locator and a short disambiguator in the registered display filename. For example, the illustrative path `assets/新聞基本屬性-p012-a3f9c2d1.png` contains searchable topic words while the manifest retains the full hash. This is an example, not a chosen naming grammar or a claim that the suffix is collision-proof. The registry must detect conflicts and allocate a distinct stable path without overwriting; the shortened suffix never replaces full-hash verification.

| Option | Search/use effect | Tradeoff |
| --- | --- | --- |
| Hash filename with a separate friendly label | Keeps current paths; labels can help a viewer/search system that explicitly indexes them. | Does not meet filename-based discovery when browsing or searching exported files. |
| Description-only filename | Provides directly searchable names without a hash-looking suffix. | Needs a deterministic collision/version policy for repeated captions, different crops and unrelated images with the same description. |
| Description plus source locator and short disambiguator | Provides meaningful filename terms and a compact distinction between similarly named images. | Recommended starting point. Requires naming, collision handling and stable registration; exact suffix/locator syntax remains open. |

Filename terms directly address searches that use filenames. For later semantic/content retrieval, source captions, alt text and provenance should remain available too; useful names should not be treated as an entire search system or a promise about any particular indexer's ranking. The user has not yet specified an external search engine or knowledge-base ingestion contract, and none is investigated or selected here.

**Preserved guarantees and decisions still needed.**

- Prefer names based on an actual caption, heading or inspected image content, with source language retained when useful, including Chinese. Do not invent unsupported subjects or force English translation. Source-language versus translated/bilingual labels remains a user-facing naming choice; source-language names are the initial recommendation.
- The agent can suggest a name; the app validates a portable filename and resolves collisions. When useful meaning is not known yet, use an honest page/figure fallback. Do not require semantic naming before source/image access. Whether an optional extraction/render argument or a later registration action supplies the name remains a design choice, not a selected extra tool.
- Treat the chosen relative path as a stable registered reference. Use it consistently in Markdown, saved inventory, preview and ZIP. Do not rename only during export, rewrite old immutable versions or silently change existing links. A later naming change would require an explicit new mapping/version with consistent references; the exact rename/alias capability is still open.
- Full-hash object deduplication can remain independent of display filenames. Identical bytes used under different semantic names require an explicit alias/export policy rather than an assumption that equal bytes imply equal descriptions or provenance.
- Revisit AR-S1's hash-only grammar, URI/filename handling and affected acceptance together if readable naming is selected. Names must stay bounded by supported filesystems and the declared destination, without discarding meaningful source language. Existing long-path limitations do not justify inventing a silent truncation rule.

The proposed meaning of canonical would be a task-registered, safe, stable relative asset path whose bytes/provenance are verified, rather than a requirement that its basename contain the full hash. This is a proposed amendment to AR-S1, not an adopted rule. The following exchange refines the locator/title choices; the inclusion/save/reopen/export outcome and original A03 preservation remain intact.

### Printed labels and a short source title

In the subsequent 2026-11-08 exchange, the user preferred printed page numbers if feasible, raised incorrect bookmarks as a concern, and suggested adding the book/article title to improve search. They also identified two risks: excessive filename length and an incorrect title supplied with the uploaded PDF. They selected discussion first and specification only. This expresses a locator preference and a title proposal, not agreement on all naming mechanics.

The [existing page-identity requirement](../PRODUCT_REQUIREMENTS.md#page-identity-and-logical-structure) already distinguishes visible printed labels from physical positions and explicitly excludes bookmarks, viewer labels and inferred offsets as evidence of the printed label. The [document schema](../design/DOCUMENT_MODEL.md#q1-document-schema-and-commit) preserves strings such as Roman labels and the distinction between `unknown` and `none`. Source inspection confirms that `Evidence.create_job` currently derives the task name from the uploaded filename; that value is not evidence of a bibliographic title. Source observation is possible through the existing text, image and OCR access, but no reliable automatic title/page recognition result was established in this discussion.

The recommendation is to prefer a source-confirmed printed label, retain physical provenance, and use a clearly identified physical-page fallback when the printed label cannot be established. A confirmed figure label can provide an additional useful locator; it must not be fabricated. Incorrect bookmarks may affect navigation hints but must not decide the filename label. Reading a header/footer can establish a printed label even when bookmarks are wrong; cropped or unreadable labels can still remain unresolved.

For titles, a short source-grounded alias offers a better balance than repeating the entire bibliographic title or depending only on a containing folder. A full title can dominate each filename, while a folder's context disappears when an image is copied out. A short alias provides useful standalone terms, with the complete observed title and its basis retained in metadata. An alias is a display abbreviation, not a replacement bibliographic fact. Missing title pages, article collections and conflicting headings can leave the source work uncertain; title omission is preferable to turning the upload filename or PDF metadata into a false title. No external bibliographic lookup or routine user naming step is proposed.

The [draft naming amendment and discriminating acceptance](../batches/R01CAL-A03-DELIVERY-01/spec.md#consolidated-discussion-agreement) records that exchange's proposed behavior separately from AR-S1's preceding hash-only target. The subsequent exchange below revises the recommendation; the earlier examples are retained as prior proposals. There was no implementation or runtime verification in this exchange.

### Format-neutral locators and source distinction

In the next 2026-11-08 exchange, the user described possible future conversion of non-PDF formats, rejected a PDF-specific filename locator, found `print` too long, and questioned whether title abbreviations were needed if full titles survive in metadata. Several books can share an abbreviation such as "journalism". The user explicitly agreed that physical PDF positions remain in metadata even when filenames use printed labels, and that printed labels must not be calculated from assumed offsets. The [spec's agreed source-position guarantee](../batches/R01CAL-A03-DELIVERY-01/spec.md#readable-filenames-and-source-locators) records that narrow agreement. The instruction remains discussion first; future-format support is a naming constraint, not an instruction to build new converters.

**Revised assistant recommendation.** Omit the title abbreviation by default. Use `description[-locator]-short_id.ext`, with a source-grounded description for readable search terms and a short identifier that distinguishes the asset's source occurrence. This replaces the assistant's earlier preference for a title abbreviation; it is not yet a user-adopted grammar. Full title, source identity, physical location, printed-label observation and complete image/source hashes remain separate metadata concepts. Unknown titles remain unknown.

| Locator candidate | Proposed meaning | Limit |
| --- | --- | --- |
| `p58` or `piii` | Confirmed printed/source page label, retaining the exact label in metadata | Never use the same prefix for an unconfirmed physical index. Filename escaping remains open. |
| `i12` | One-based source-page index when the printed label is unresolved or absent | Format-neutral spelling, but currently defined for sources with stable pages; metadata records the unit type. It is not a page number invented for reflowable content. |
| `f4-2` | Figure identifier actually present in the source | Optional; an output-local image counter must not impersonate a source figure number. |
| Omitted locator | No appropriate stable page/figure label | Preserve the format's actual locator in metadata when support is designed; do not force every future source into pagination. |

A compact suffix can combine source identity, asset identity and occurrence provenance into one registered identifier. A prefix of only the image-byte hash cannot distinguish the same image reused in two books. Source distinctions therefore must not rely on the title, abbreviation, upload filename or display description. Full identities stay in metadata; short identifiers require conflict detection and must not be advertised as globally collision-free. A title correction or upload-file rename should not by itself allocate a different source identity. Identity across different editions, regenerated files or format conversions is not established by this proposal.

Illustrative distinct-source names are `新聞基本屬性-p58-a3f9c2d1.png` and `新聞基本屬性-p58-b72e91c4.png`. The suffixes identify different source occurrences; they do not imply different image bytes or let a person read the book title from the name. Exact identifier derivation, length and registration remain open.

Alternatives have different benefits: a separate short source code plus asset code makes grouping by source possible from filenames alone but adds length; an author/year/title prefix provides human clues but needs additional source verification and still is not unique. A source folder can group an intact export, but its context is lost when a file is copied out. For the stated compact-name preference, recommend the single source-aware suffix and full source details in accompanying metadata; keep the alternatives available if identifying the book by filename alone becomes a requirement.

The metadata must be included in the saved version and export and be resolvable from the asset path/identifier. This does not claim that the current image file contains embedded bibliographic metadata. If only a PNG is copied and the accompanying metadata is left behind, its title cannot be recovered from an opaque suffix alone. Full-title search requires the later index to ingest that metadata; filename-only search can still use the image description. Embedded metadata or per-image sidecars remain separate possible delivery choices, not silently selected capabilities.

At that point the compact locator semantics, source/occurrence identifier policy, metadata carrier and length/escaping/collision rules remained open. Proposed counterexamples included two books sharing an abbreviation and identical image bytes, different occurrences with the same printed label, and an unchanged source whose filename/title is corrected. The subsequent exchange below rejects a missing page locator and reliance on accompanying metadata. Save/reopen/export still must retain the same registered names and metadata mapping without inference. No prototype, provider operation or production change was authorized by this discussion.

### Embedded provenance, required pages and readable codes

In the subsequent 2026-11-08 exchange, the user required the full title and source information to remain with an image copied alone, requested an embedded-metadata/sidecar comparison, and explicitly prohibited a companion file. The user also required a page number, with a figure number allowed in addition, and said the example hash-like suffixes still looked random. They asked how identifiers should be assigned and for an explanation of separate source and asset codes. The [spec's portability/page constraints](../batches/R01CAL-A03-DELIVERY-01/spec.md#standalone-embedded-provenance-and-faithful-image-bytes) own these selected outcomes and planned acceptance; no implementation was requested.

**Format evidence, checked 2026-11-08.** [Adobe's XMP specification overview](https://developer.adobe.com/xmp/docs/xmp-specifications/) describes embedded extensible metadata, including JPEG storage, and the separate sidecar alternative. The [W3C PNG textual-information specification](https://www.w3.org/TR/png/#11textinfo) defines Unicode-capable `iTXt` and registers `XML:com.adobe.xmp` for XMP; this permits Chinese title/provenance text inside the PNG itself. Thus embedded metadata is technically feasible for the PNG/JPEG delivery formats. This is standards evidence, not a tested implementation or a guarantee that every viewer/search engine exposes every property.

| Comparison | Embedded metadata | Sidecar metadata |
| --- | --- | --- |
| Copy only the image file | Metadata travels inside the file when its bytes are copied | Metadata is left behind unless the separate file is copied too |
| Rename/move | Metadata stays inside the image | File association must be maintained |
| Image file bytes | Adding metadata changes container bytes and its hash; it need not alter the image's encoded picture data | Image bytes can remain unchanged |
| Editing provenance | Writes a new image-file representation | Can update the metadata file separately |
| Fit to this request | Recommended | Excluded by the no-companion-file constraint |

The proposed carrier is embedded XMP, using common descriptive properties where their meaning fits and explicit provenance fields for source-title/page/region/identity facts. A readable citation/description should accompany structured details inside the same packet; an opaque identifier alone is not self-contained source information. Bibliographic title, image description and image creator are different fields. PNG's built-in `Source` keyword means the device that created the image, so it must not be casually repurposed as a book citation. Exact field mapping and reader support remain to be designed. The complete observed title, established author/edition/publication facts, printed label, physical source page, figure label, source-file identity and relevant crop/render provenance are candidate contents. Unknown facts stay explicitly unresolved; embedding does not establish a title absent from the available source.

The intended guarantee is ordinary file copy/rename, not arbitrary transformation. A screenshot or pixel-only copy creates a different image; other software can drop metadata on re-export. For example, [Adobe's export options](https://helpx.adobe.com/mena_ar/media-encoder/desktop/encoding-and-exporting/export-settings-reference.html#export_and_thin_xmp_metadata) allow XMP inclusion, filtering or omission. Embedded does not mean visible in every properties dialog or automatically searchable. The app should expose its provenance and planned acceptance must include an independent reader with no project store or companion file.

**Byte preservation consequence.** The [current image contract](../design/PDF_EVIDENCE.md#pdf-coordinates-and-image-delivery) preserves original streams and sometimes uses unchanged embedded JPEG bytes as the display asset. Metadata embedding introduces a distinct deliverable representation whose container bytes differ. The proposed repair must retain the original separately, preserve image encoding/pixels, color/alpha/orientation information, and record the derivation honestly. Prepare and register the enriched bytes before immutable publication; export copies that selected version rather than enriching it at export time. Embedded source/original hashes must be distinguished from the final delivered-file hash, which belongs in the version manifest; a file must not try to contain its own final-byte hash. The representation and metadata-update boundary remain design work, not a silent relaxation of existing byte-fidelity rules.

**Revised naming recommendation.** Replace the opaque suffix with a persistent catalogue code: `S023` identifies a source in the user's library; `A004` identifies a registered asset occurrence/rendition within that source. These are assigned numbers, not title abbreviations or compressed hashes. Full source/asset identities remain embedded. All images from one source share its `S` code; `A` distinguishes multiple assets even when descriptions, page labels or figure labels repeat. Put `S` first if source grouping by filename is useful. Examples:

```text
S023-p58-新聞基本屬性-A004.png
S023-p59-新聞價值-A005.png
S024-p58-新聞基本屬性-A001.png
S023-p58-f4-2-新聞基本屬性-A004.png
```

The last example adds a confirmed figure label to the required page locator. `A004` is an application identifier and must never masquerade as source Figure 4. Proposed allocation: assign an unused source serial once on registration, reuse it for the same registered source despite upload-file renames/title corrections, and persist an unused asset serial when registering a distinct occurrence/rendition. Do not recompute codes from sort order or reuse them after deletion. Sequential codes improve legibility and grouping but do not tell the reader the book's title; the embedded citation supplies that meaning. They are unique only within a defined library, not globally. Independent libraries may both allocate `S023`; merging/export collision handling must compare full embedded identities and never overwrite on code equality. Exact library boundaries, reimport/edition matching, asset-version identity and cross-library conflict handling remain open.

For paginated sources, keep the proposed `p58` for an observed printed label and `i12` as an explicit physical-page fallback. The user's mandatory-page rule supersedes the earlier figure-only or omitted-locator suggestions. Future formats with no stable pages now need a deliberate pagination policy before they can meet this requirement; no page number is invented and no new importer is selected here. The compact prefixes and catalogue-code grammar remain assistant recommendations. The next design work is to reconcile the embedded representation, readable identifiers and mandatory page locator with save/reopen/export, including standalone copying.

### Preservation, source-authored labels and deletion

In the next 2026-11-08 exchange, the user annotated three statements: preserving the original image, the application asset code `A004`, and the shared source code `S023`. They asked what preservation means, preferred the source's original wording/identifier when available with numbering as a fallback, and raised eventual deletion of the source. They explicitly requested discussion first. The second comment is interpreted here in its asset-identifier context as referring to an actual source figure label/name; this interpretation is explicit rather than an assertion that the user chose a precise filename grammar.

**Preservation clarification.** The intended boundary is non-destructive conversion and metadata enrichment: keep source evidence unmodified in the working store, create the enriched deliverable separately, and check its picture data against the corresponding pre-embedding extracted/rendered image. This does not claim that a crop/render equals the whole original page or that every source-to-display conversion preserves encoded bytes. It also does not require a duplicate next to the exported image, embedding the entire book in that image, or a new perpetual-retention rule. The [existing storage policy](../ARTIFACT_STORAGE.md#preservation-and-cleanup) preserves current task data and leaves product retention/garbage collection unselected. Explicit future deletion and its scope are separate from preservation during ordinary conversion; this discussion neither deletes data nor introduces automatic cleanup.

The standalone output keeps its full established citation/provenance inside itself. Removing the source or project later must not make an independently retained exported image unable to disclose that information. Losing the source does remove the ability to re-extract from or directly recheck that source; a hash/citation identifies it but cannot reconstruct its contents. Deleting an app task/version is not a promise that that deleted task can still reopen. Existing saved versions and independent exported copies have distinct lifetimes.

**Source-first visible identifiers.** The assistant agrees with the user's preference and revises the unconditional `A004` recommendation: when the source supplies a usable figure label/name, use its source-language form in the filename and retain its exact wording in embedded metadata. For example, a source label `圖4–2` could yield `S023-p58-圖4–2-新聞基本屬性.png`; it does not need an additional visible asset serial merely because the app has an internal asset identity. A useful source caption/name can supply readable words even without a figure number. When no usable source label exists, a clearly application-generated number such as `A004` can identify the asset: `S023-p58-新聞基本屬性-A004.png`. Descriptions still follow source evidence and the [caption/agent-description distinction](../design/FIGURE_DELIVERY.md#required-outcome). Page locators remain mandatory. Actual duplicate source labels or multiple renditions may require an additional distinction, but source labels must not be silently changed into newly invented source numbering; the exact collision/variant spelling remains open.

**Deletion and source codes.** `S023`, if retained in the eventual naming design, is a persistent accession code, not the twenty-third item in a live sorted list. The proposed behavior is to leave gaps: deleting source `S023` does not renumber `S024`, rename exported files or allocate `S023` to the next source in the same continuing library. A monotonically advanced allocation counter can prevent reuse without keeping a hidden copy of a deleted book or requiring its bibliographic record for exported-file lookup. This remains a proposal, not an implemented deletion/catalogue capability. A complete library reset or merge of independent libraries needs explicit namespace/conflict handling; serials alone are not global identities.

The embedded full citation and source identity make the exported image independent of the surviving catalogue entry. Thus a later missing `S023` record does not erase its exported image's title/source facts, although the filename code alone still does not express the book title. Whether the visible `S` code is useful enough to retain remains open; it helps grouping and avoids repeated title abbreviations but is not necessary for reading embedded provenance. The [spec clarification](../batches/R01CAL-A03-DELIVERY-01/spec.md#readable-filenames-and-source-locators) records the narrowed interpretation and planned counterexamples. No retention duration, deletion action or final code scheme is selected.

The assistant recommends preserving the ordinary readable name and adding a small copy suffix only when a different registered asset actually needs the same name. This is a proposed exception for collisions, not renewed support for routine source/asset codes.

| Option for an actual collision | Benefit | Cost or limitation |

| Collision-only copy suffix | Short, predictable, requires no new source interpretation; recommended default | The suffix distinguishes files but does not explain their source. Embedded provenance does. |

The first registered asset keeps its existing name. Later conflicting assets receive an available suffixed name, checked against the full registry including already suffixed names. Once assigned, the name remains stable across further saves, reopen and export; adding/removing another image does not renumber it. Allocate before saving references, not by silently renaming files during export. Retained registrations referenced by saved versions cannot be reassigned to different assets.

The [collision policy and acceptance](../batches/R01CAL-A03-DELIVERY-01/spec.md#collision-only-allocation-and-identity) now incorporates the subsequent agreement and correction below. Such external renaming does not repair links in a separately retained Markdown document. ### Language-sensitive punctuation and portable filenames

#### T2 — Path serialization and precise reference edits

The registered path and a link's transport spelling are distinct. [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/#links) permits angle-delimited destinations and specifies rules for bare spaces/parentheses; it does not require one particular non-ASCII URL-rendering choice. [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.html#section-2.4) distinguishes URI delimiters from encoded component data and warns against repeated percent encoding/decoding. The inspected installed `markdown-it-py==4.2.0` source uses `mdurl` for link normalization; parser handling cannot be assumed to leave destination bytes untouched.

| Option | Effect and cost |
| --- | --- |
| Readable Unicode destinations with minimal escaping and angle brackets | Easier to inspect in raw Markdown, but requires more context-specific rules for literal percent signs, entities, punctuation and raw HTML. |
| One URI-encoded destination form generated from the exact registered path | Longer/less readable raw destinations, but straightforward consistent generation across Markdown and HTML. Actual filenames remain readable. Recommended. |

Recommend keeping the literal directory separator in `assets/`, then UTF-8-percent-encoding basename bytes except URI-unreserved ASCII characters. Use uppercase escape digits for output. Supply the exact filesystem `asset_path` and ready-to-use link destination together so neither the user nor the agent must manually calculate escapes. For example, `assets/News framing-p58 (2).png` is referenced as `assets/News%20framing-p58%20%282%29.png`; a literal `%` becomes `%25`. The 180-byte limit measures the actual basename before URI encoding. Markdown and HTML perform their own syntax/attribute escaping around that URI without changing its decoded path. Existing valid authored spellings need not be reformatted wholesale, but must resolve through the supported parser to the exact task/version binding.

Separate URI components before decoding. Decode the asset basename once with strict UTF-8, use no form-style plus-to-space conversion, and require the exact registered spelling/case. Reject malformed escapes, decoded separators/traversal, extra directories, queries/fragments and unregistered paths; do not perform fallback host-file lookup or a second decode. A literal filename containing the characters `%2F` can be represented as `%252F`: after one decode it remains literal text, never another path separator. Record the accepted spelling matrix before implementing, including entity handling by the parser and exact matching of noncanonical input; the output encoder is not permission for general path normalization.

For corrections, whole-document parse-and-reserialize can change unrelated prose/whitespace; global text replacement can alter code examples or unrelated occurrences. Recommend parsing the complete document to identify effective references and retaining exact source spans for their destination text. Update only those spans, including the controlling cross-block definition and supported raw-HTML attribute values, then reparse to verify the new bindings and preserve unrelated bytes. [The parser's documented `Token.map`](https://markdown-it-py.readthedocs.io/en/latest/api/markdown_it.token.html#markdown_it.token.Token.map) provides line ranges, not a ready-made exact destination-edit map. A focused parser-integrated span collector is therefore real engineering work, not a claimed existing capability. Ambiguous mapping fails the operation with the candidate retained; it never falls back to global replacement or manual routine user repair.

Discriminators: spaces/parentheses, Chinese text, percent-looking filenames, HTML entities, inline and cross-block references, identical text inside code, case-only mismatches and encoded traversal. The same selected binding must survive save/reopen/export without double decoding or changing the underlying filename.

### Basis and official guidance

[AR-T2-01](../batches/R01CAL-A03-DELIVERY-01/verification.md#ar-t2-01--large-image-data-url-navigation-blocks) owns the actual full-byte embed success and large-link navigation failure, source identities, retained fixture and causal limits. These are the relevant integration boundaries, rather than the save, naming or metadata-writer lifecycle.

Applicable current official guidance and the pinned Electron version were checked before comparing methods:

- [File API access restrictions and lifetime](https://w3c.github.io/FileAPI/#url) describe storage-key checks for Blob access and exempt top-level Blob navigation. The Blob origin follows its creator, and revocation/lifetime require explicit ownership. This is a current draft rule, not an observation of the installed Electron binary.
- [HTML sandboxing](https://html.spec.whatwg.org/multipage/browsers.html#sandboxing) explains the opaque origin and disabled scripts retained by the empty sandbox. It distinguishes internal resource loading from handing a custom protocol to external software.
- [Electron 45.0.0 protocol documentation](https://github.com/electron/electron/blob/v45.0.0/docs/api/protocol.md) provides a session-specific `handle` returning a Response and requires privileged scheme registration before readiness. Its bundled-file directory mechanism is experimental and is not a fit for the proposed dynamic, verified inventory.
- [Electron 45.0.0 scheme privileges](https://github.com/electron/electron/blob/v45.0.0/docs/api/structures/custom-scheme.md), [frame-navigation events](https://github.com/electron/electron/blob/v45.0.0/docs/api/web-contents.md#event-will-frame-navigate) and [request context](https://github.com/electron/electron/blob/v45.0.0/docs/api/web-request.md#webrequestonbeforerequestfilter-listener) supply the privilege, navigation and caller checks. The protocol callback alone is not a frame-identity API. Optional or missing request/frame fields cannot be treated as authenticated ownership.
- [Electron 45.0.0 security guidance](https://github.com/electron/electron/blob/v45.0.0/docs/tutorial/security.md) supports restrictive CSP, sandboxing, validated IPC senders and constrained navigation, and prefers controlled custom protocols over exposing `file:` access.

The recommendation below is an inference from these APIs and the inspected application boundary. Neither Blob behavior nor the proposed protocol's empty-sandbox behavior has been exercised in this discussion.

Blob's small patch advantage does not settle its opaque-frame behavior; a protocol's extra registry is justified only if it stays narrow and enforces the selected inventory. ### Proposed resource and isolation boundary

Use one derived mapping for selected preview `a.href` and `img.src` targets, so repeated references share one immutable payload and one lifetime. Preserve the authored link/embed roles. An illustrative URL is `pdfmd-preview://snapshot/<lease>/<asset-key>`; its name is not a new public document format. The lease is an unguessable, app-issued capability for one loaded generation, and the asset key is an opaque table key, not a filename to join to disk.

The document engine remains the authority for task/version registration, integrity, supported image type and reference assessment. Its selected-version read would make the complete verified image buffers and their binding metadata available to the trusted desktop host through the existing authenticated internal boundary. Main retains those same bytes, checks their declared length/hash at transfer, and returns only the derived bound preview and selection metadata to the renderer. Do not reread mutable task blobs, resolve against head, regenerate images or accept renderer-supplied file paths. Preserve distinct occurrence identities even when immutable payload storage is deduplicated.

Main registers an internal resource handler on the actual window session. Each active entry binds the owning window/session, job, version, load generation, asset identity, validated PNG/JPEG MIME, full length and SHA-256 to the immutable buffer. A request must match an issued URL and the active lease exactly; query/path/encoding variants, other assets, revoked leases and unrelated callers fail. Use the supported request context and frame-navigation guard for caller checks; an opaque `null` origin or a matching scheme prefix is insufficient. This is a resource service, not a path router, directory mount, remote proxy or OS protocol association.

Return a normal full image Response with validated Content-Type, `nosniff` and no-store behavior. No redirects or file/network fallback are needed. Unknown/unavailable resources fail with an honest outer diagnosis rather than substituted content. Repeated references do not justify repeated encodings of the payload. No arbitrary image-count/byte quota is proposed; real allocation/transport failures must be reported without silently dropping bytes.

The proposed scheme uses standard URL behavior, a secure context classification and CORS enforcement, without CSP bypass, service workers, renderer Fetch API support or unnecessary privileges. Permit it explicitly in the derived parent `frame-src` and preview `img-src`; do not add it, Blob, data or file URLs to source-sanitizer schemes. Source custom URLs must not mint or acquire a lease. Keep `sandbox=""`, `contextIsolation`, process sandboxing, disabled Node integration, the validated main-frame IPC boundary and denied permissions/windows/downloads. The scheme is separate from the trusted app shell. Constrain navigation to an issued image URL in the registered preview frame; main-frame, unrelated-frame and external navigations stay blocked. If future implementation cannot establish this internal load in the empty sandbox, return the concrete observation to this choice rather than adding sandbox permissions.

### Snapshot lifecycle and Return

A `(job, version)` pair is necessary but not sufficient: retries and late responses can target the same pair. Use a load generation shared by the trusted host/renderer lifecycle. Beginning another load invalidates the prior lease and removes its derived frame/action. A selected response can activate only if its job/version/generation still matches the latest intent; a late response is discarded and cannot register or reactivate resources. Pending/failed loads, task/version changes, editor entry and window/session destruction release the lease and buffers. Coordinate this with the existing document-session guards rather than creating another independent selection owner.

The lease belongs to the loaded snapshot, not to a particular image decode or Return remount. Keep it alive during image viewing, ordinary tab changes and Return while that snapshot remains ready. Return increments the frame revision and restores the cached matching bound HTML, reestablishing its frame guard, without reading the version again, consulting head, inferring or saving. The newly mounted frame may request image bytes from the same in-memory resource table; that is not a new document/version read. Do not release the resources on the first image `load` or every iframe remount.

Lease revocation prevents new authorized resource requests; it does not erase bytes already delivered to Chromium or guarantee that every in-flight response is aborted. Removing the old frame and rejecting late generation results preserve the UI identity boundary. No-store and unique per-generation URLs prevent a reusable stale address from becoming a new selection. ### Concurrency, engine copies and host memory (discussion, 2026-11-11)

**User decisions.**
- Several saves and preparations must be able to run at once; serializing them would make progress too slow.
- Cross-platform limits (the untested POSIX fallback) are deferred.

**Engine-side copies, as explained to the user.** The bounded worker limits only the writer process. On the current save path the engine also holds image bytes in memory, with nothing capping them:
- the source image read for preparation (`store.bytes`);
- the worker's output read back for its hash check;
- the enriched object read again into `payload` for the version files;
- each retained original stream;
- the `files` dict, which keeps every member of the version in memory while hashes are computed and files written.

For one 103 MiB PNG this measured about 580 MiB in the engine. Because `payload` accumulates every referenced image and original of a save, engine memory also grows with the total size of all images in one save, and with every save running at once. With concurrency selected, this uncapped engine-side growth is the larger risk.

**Proposed engine change (not selected).** Keep files as the authority and stream instead of loading:
- verify and copy the store object to the worker's input with chunked hashing and `shutil.copyfile`;
- register the worker's output by streaming hash and an atomic move into `objects/`;
- write version members by streamed copy, not a hard link, so a version copy stays an independent recovery source;
- compute manifest hashes in chunks;
- check image signatures from the first bytes only.

Engine memory per save would then be roughly constant, independent of image size and count. This does not touch the qualified writer. The worker's own roughly five copies come from `primary_xmp.py` and could only be reduced by changing and requalifying it.

**Host memory proposal (open).**
- **Declared minimum host:** Windows x64 with 8 GB RAM and 4 logical cores; 16 GB recommended for large images.
- **Writer pool:** sized at engine start from physical RAM as `clamp(30% of RAM, 1.5 GiB, 8 GiB)`. That gives about 2.4 GiB on 8 GB and 4.8 GiB on 16 GB.
- **Per-worker ceiling:** `min(2 GiB, pool)`.
- **Admission control:** a worker starts only when its full memory budget fits in the unreserved pool and fewer than `max(1, cores − 1)` workers are running. Otherwise it waits in a queue, and its wall timer starts at launch, not while queued. Typical default-DPI images (budget 256 MiB, actual use 20–50 MiB) can then run about nine at once on an 8 GB host, which is more than its cores. A 100 MiB image (budget about 864 MiB) runs about two at a time. Reserving the full limit, not the expected use, means a pathological packet cannot push the host into paging.
- **Parallelism:** the creates within one save would be prepared in parallel through the same pool, alongside other tasks' saves.
- **Small hosts:** an image whose budget exceeds the pool is rejected as `over_budget`, with the host limit named.

Open choices: the minimum RAM (8 or 16 GB), the pool fraction, the parallelism cap, and whether the engine-copy streaming comes before enabling parallel preparation. The recommended order is streaming first, because parallel saves multiply the uncapped engine copies.

**Decided 2026-11-11: streaming first, then the pooled parallel writers.** The user accepted that order, with the proposal's defaults: an 8 GB minimum host, a pool of 30% of RAM within 1.5–8 GiB, at most logical CPUs − 1 workers, and per-worker reservation of the full limit. These are named constants in `xmp_worker.py` and remain open to change. The 2 GiB per-worker ceiling still applies on large hosts, and on a host whose pool is smaller than the ceiling, the pool is the limit. See the [fresh-save measurements](../batches/R01CAL-A03-DELIVERY-01/verification.md#t3b-streaming-and-writer-pool) and [subsequent review](../batches/R01CAL-A03-DELIVERY-01/verification.md#t3b-streaming-and-writer-pool-review) for the scope of the memory and concurrency evidence.
