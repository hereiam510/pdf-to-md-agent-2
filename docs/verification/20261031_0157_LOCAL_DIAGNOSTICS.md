## Diagnostic detail API typing implementation (2026-10-30)

### Effective boundary and rationale

`src/renderer/types.ts` now defines `DiagnosticDetail`, `DiagnosticRecordResult` and `DiagnosticRecordArgs`. The successful envelope contains the view/task/capture metadata, selected identity/record, `DiagnosticLink[]` and limitations. Optional projections describe fields actually produced by request, operation, version and generic detail paths. A shared envelope is sufficient because these are independently available read facts; a large kind-specific union would add coupling without strengthening the selected response/state boundary. Attempt entries distinguish an observed record from local unavailability, with original record/receive content kept unknown. Only summary fields already checked by `record_summary`, fields constructed by the projection, and success-only link facts receive concrete structure. Publication pointers, raw usage, arbitrary operation results, related records and raw descriptor contents acquire no validated-fact guarantees.

The concrete `diagnosticRecord` overload makes the existing unparameterized API call return `DiagnosticRecordResult`, rather than the unrelated APIs' legacy default. `server.diagnostic_read` supplies `unavailable` or `stale`, with task, reason and `refreshable=true`; other HTTP/auth/query errors reject the promise through the unchanged desktop `call`. No new JSON status is invented. `TaskDiagnostics` uses `DiagnosticDetail | null` state and stores only after `status='ok'`; generation rejection, observation invalidation, errors and private-view cleanup retain their existing order. Link/operation/related/attempt callbacks infer their types from state. The initial compiler failures exposed raw dynamic access and nullable navigation inside callbacks; these now use scoped raw display reads and a local callback guard, without a whole-detail cast.

Raw attempt status/transport/usage and result-parent observations remain unknown. The renderer reads only own object fields, then displays string/number values or JSON for another observed shape; absent/null values keep the existing unknown labels. Complete attempts/results/original records remain retained, and failed-link raw observations cannot supply navigation. This small display narrowing avoids declaring arbitrary JSON to be a checked domain object. The existing unrelated evidence state/API defaults are outside this maintenance scope. There is no runtime response decoder: TypeScript declarations and an invoke overload do not validate HTTP/IPC bytes. `diagnostics.py` integrity/provenance/role checks, independent request/attempt and commit/version checks, `server.py` errors and recovery authority remain responsible for runtime truth and are unchanged.

This follows the installed versions' supported [TypeScript discriminant narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions), [specific overload signatures](https://www.typescriptlang.org/docs/handbook/2/functions.html#function-overloads) and [React nullable hook-state typing](https://react.dev/learn/typescript#typing-usestate), retrieved before implementation. Callback-only annotations would leave API/state unchecked. A general decoder/schema-generation framework could additionally validate transport payloads, but is outside this task and unnecessary to protect the selected static contract. No alternative requiring dependency/backend/recovery changes was adopted.
