# Rebuild contracts

These contracts consolidate the agreed boundaries and the final recommended tradeoffs in EVT-1166. The [implemented first-version contracts](#implemented-first-version-contracts) below select the exact schemas and transitions for Q1–Q3. The earlier mechanism examples remain explanatory. Additional mechanisms from the discussion retain their status in the reference records.

Detailed local explanations accompany these contracts: [document engine](design/DOCUMENT_ENGINE.md), [context and evidence](design/CONTEXT_AND_EVIDENCE.md), and [execution and delivery](design/EXECUTION_AND_DELIVERY.md). These explain data shapes, sequencing, examples and failure cases without requiring the chat export. Illustrative field names do not silently close open schema choices.

## 1. Document updates and candidate references

### Identity and original content

Keep source identities, derived evidence identities, received candidate identities, committed document versions and operation identities distinct. A content hash establishes byte identity, not ownership, scope, whether the agent saw the data, or whether it remains in the current document. An unqualified path, mutable `head`, timestamp or hash alone must not ambiguously select a source/version.

Preserve complete received native responses/tool arguments before framework parsing or tool schema validation can discard useful content. An accepted response and an executable tool call are later states. Framework tool middleware may run after native JSON parsing. Malformed calls may never reach that middleware. Retention therefore begins in the Nexus receiving layer, with dispatch-layer retention as an additional boundary.

Preserve what was actually received. Do not claim missing trailing content was saved. A rejected or incomplete call remains non-executable. A candidate reference identifies exact original content and its source operation/version/range. A repaired new request has its own identity.

### Edits and validation

The first version should support exact reuse of complete candidate content, pure insertion/append and partial page-map updates. Preserve unchanged body and metadata by default.

Apply a local metadata patch in this sequence:

1. Merge it into the explicitly named base version.
2. Validate the resulting complete map/structure.
3. Conditionally commit against the expected head.

A stale base must not silently become today's latest version. Do not require the model to regenerate all prose or resend a full map merely to repair one entry.

A referenced prior candidate is usable even if a later save exists. Adoption in an ancestor records historical use, not proof that every part survives in the current version. Unused candidate material need not all be adopted or explicitly rejected before a task can complete.

Distinguish reusing content from replaying operations. A `block_ops` object can delete/reorder/replace content. Copying its prose differs from executing that operation sequence against a changed base. Operations need applicability checks against the intended base. Literal patching must have defined target and match semantics. Unique byte matching prevents ambiguous replacement but does not establish semantic correctness.

The agent can choose a larger reconstruction when the source requires it. Local-edit support is an ergonomic capability, not a mandate to use the smallest edit. Logical output blocks do not dictate a token/chunk/storage size or require a complex semantic dependency graph.

### Commit and replay

Recommended body authority: immutable version files. SQLite owns version registration, head/pointers and the unique operation receipt. Stage the file payload. Validate it before the metadata commit that makes it visible. Define cleanup/reconciliation for files without a committed registration. Do not maintain a second independently mutable body as an equal authority.

Operation retries return the original committed receipt and its produced version. A newer head does not invalidate that receipt and must not be rewound. A receipt describes the historical operation. It is not a fresh selection/update of the current document. Validation rejection, successful commit and failure to build/return a model-facing projection are distinguishable outcomes.

No memory-only lock is a durable uniqueness guarantee. The first version uses one active writer per task plus persistent operation identity and short metadata transactions. SQLite ordering does not automatically serialize parallel graph-state `Command` updates. Graph policy updates must have a defined single writer.

### Partial-content salvage boundary

Preserving malformed originals is required. Automatically indexing complete subobjects from an incomplete response is a deferred useful option, not a first-version dependency. If added, automatic indexing must satisfy these conditions:

- Identify closed exact source spans within one attempt/call.
- Handle escapes, duplicate keys and array order.
- Preserve the original hash/span.
- Create a new valid operation for reuse.

Tolerant parsing that closes strings/braces, synthesizes defaults or merges attempts is not proof of a complete original subobject. Extractability is not source correctness.

## 2. Context capacity and handoff

### Two coordinated responsibilities

Evidence management controls what source results, images, OCR and saved content are loaded, kept, released and precisely retrieved. History compaction reorganizes older conversation/work history and continuation state. They share a capacity budget but are not the same operation.

The agent judges relevance and semantic continuation needs. The app observes capacity and requires organization when necessary. The app may prioritize releasable content. It does not judge semantic necessity from high OCR confidence, small text differences, completed page counts or storage presence.

Protect effective user requirements and later amendments, unresolved dependencies and useful work. Save unsaved useful material before removing it from input. Exact originals and references remain retrievable. Latest drafts and unfinished candidates may be partly released. They need not wait for a successor version or stay entirely resident.

### Assembled-request budget

Configure effective capacity and output reserve for the selected route/model. Assess the actual assembled request, including instructions, schemas, native message overhead, images, tool results, draft arguments and continuation state. An estimate is not an exact provider token count. Unknown native/image costs require explicit conservative handling. Unknown does not mean zero.

Do not infer the model's nominal window from a local estimate of a rejected request. A provider refusal may reflect endpoint limits, route mismatch, output reserve, image encoding or another error. Only supported diagnosis should trigger context-specific re-preparation. Generic HTTP 500/502 alone is not overflow evidence. Transport replay and context-changed re-preparation are distinct request operations, both charged to persistent task budgets.

For newly evaluated unfrozen input, `Route.estimation_profile` defaults to `bpe_proxy_v1`: the shared estimator counts every character of canonical complete native JSON in consecutive 8,192-character BPE chunks with native image objects replaced by fixed placeholders using bundled `o200k_base`/`tiktoken==0.14.0`. It reserves the BPE count plus `ceil(count/4)`, 1,024 native/proxy units and the configured allowance for each still-present native image; output reserve is separate. It is a local request proxy, never an alias-inferred tokenizer or exact upstream count. The margin is not a proved bound or compaction percentage. `utf8_fallback_v1` is explicit, or used observably when the pinned counter/data cannot load; it reserves normalized UTF-8 bytes plus 1,024 and configured images. Unknown protocol, mismatched native payload or unsupported modality stops with `capacity_configuration`; missing image allowance is never zero. Request byte/hash, route fingerprint, method/version/data hash, scope, fallback cause and cost components travel with new capacity observations. Capacity remains configured, not a discovered Nexus window. [The context guide](design/CONTEXT_AND_EVIDENCE.md#capacity-accounting) owns rationale, data lifecycle and limitations.

The new estimator does not rewrite old frozen payload/route/meta, replay policy, receipts, accepted handoff/transition settlement or consumed usage. Ordinary legacy-task settings saves preserve an absent estimation-profile field; an explicit profile change is permitted for future decisions, like capacity settings, while frozen requests retain their old route. New unfrozen decisions and still-eligible waits use the current method; a committed `needs_agent_revision` never revives. Inspection labels a new assessment of an old frozen payload separately from its recorded capacity; a historical preview requires exact assembler reproduction. No counter data is fetched during conversion. Working feedback reports a self-inclusive conservative reservation, which can be slightly larger than the final proxy because printed numbers affect their own BPE cost.

### Release and rolling compaction

Prefer releasing saved content that is currently unnecessary, then compact older work history when needed. This is an ordering guide, not a mandatory field preset, permanent history-retention rule or unconditional immediate release after saving. Large authored arguments in assistant tool calls can dominate context just as tool results do.

Retain an immutable native journal. Build a separate valid model-input projection, keeping tool-call/result pairing and provider-required native items intact. Do not execute the projection as an original call. The app computes exact covered message/range identities and revision anchors rather than asking the summarizer to reconstruct bookkeeping.

A compaction request may cover only a fitting portion of history. Preserve uncovered history. Its result may be valid progress even if the total context is still above the normal-send threshold. Check reduction on the assembled context, including summary/reference overhead. Do not require each partial compaction to reach the final target. No fixed recent `K`, universal percentage, fixed two/three-summary guarantee or claimed 90% saving is selected.

Each compaction request has frozen input, task/step identity, attempt records, budget and cancellation checks through the same Nexus service. It cannot be a hidden untracked model call inside `prepare_step`. Apply a successful result against its intended history revision/coverage boundary.

On failure, preserve original records. Reassess the context. Do not silently erase input. Do not send the same oversized normal request.

### Continuation content

The recommended first-version handoff is self-sufficient for continuing the task: effective requirements, task/scope, current saved version, unfinished work/dependencies, useful candidate/evidence references and necessary cautions. It need not duplicate complete originals. It does not claim semantic losslessness merely because message IDs or schema validation pass.

A delta-only summary can omit information from an anchor only if it explicitly preserves that dependency. Do not adopt such summaries otherwise. The first-version recommendation avoids that dependency. Working notes, continuity snapshots, document state and recovery receipts can share references but have different purposes and lifecycles.

### State and caching

Keep small context policy in graph state as the single executor's policy authority, following EVT-0878. An additional external policy-version/activation system is unnecessary. Graph state should not retain transient hydration as messages.

Tools can report intents. One settlement writer applies them at a safe boundary and records the processed accepted batch. Any independent deltas still need explicit conflict rules. `max(policy_rev)` can silently discard parallel changes and is not a merge algorithm.

A global journal scan must not resurrect compacted tool history or old policy states. Service-owned request budgets, committed documents and external-effect receipts remain durable outside rollback of that graph state.

A model input view records what the app assembled for a request. Attempt records separately establish dispatch. Neither proves what the model understood. Request identity, attempts, accepted tool-batch identity, tool execution, message visibility and semantic source coverage are distinct. Stable IDs must survive retries and resume. Using a new recovery checkpoint as an accepted batch's identity can cause duplicate dispatch.

Prefer stable instructions, schemas, ordering and appendable prefixes where practical. Updating/removing tail-injected state also changes the prior request prefix. Putting dynamic state last does not guarantee cache preservation. Cache considerations cannot force useless history to remain resident, and smaller input cannot alone establish lower whole-task cost.

## 3. Persistence, recovery and stop behavior

### State ownership

Use one authoritative record for each of these:

- Frozen model request and its attempts.
- Accepted native reply.
- Pending tool batch/progress.
- Operation receipt.
- Document version.
- Export intent.
- Effective compact context policy.

Exact record placement remains an implementation choice. A four-module/six-table sketch is not a complete specification. Specify which graph state is authoritative and which can be rebuilt from durable receipts.

Recovery of the same request uses the frozen input. A fresh context policy or newer head can influence a later request, not silently mutate the old request. Persist attempt/budget consumption before dispatch. Reuse a complete accepted saved reply before deciding to call the model again. Do not concatenate partial replies from separate attempts or execute incomplete JSON.

### Recovery boundaries

| Durable boundary | Required behavior on re-entry |
| --- | --- |
| A frozen request exists. No accepted reply exists. | Reconcile attempt/budget/cancellation state. Same-request replay keeps frozen input. Q3 permits a distinct request for explicit failed-request Continue or an amended, never-sent request. |
| A complete reply is accepted. Its tool batch remains unfinished. | Reconcile the same batch. New human amendments supersede unstarted calls with paired unexecuted receipts; completed effects remain. Do not silently omit calls or advance before settling them. |
| The tool committed. Its response/projection/checkpoint is missing. | Return/reconstruct the historical receipt and its necessary current-batch effects without repeating the local commit |
| The entire batch settled. Graph continuation remains incomplete. | Restore the necessary deterministic graph/context effects, then prepare the next request at a safe boundary |
| Local external effect remains unknown | Stop with preserved work and a specific unresolved outcome. Do not blindly replay an OCR/script/process operation. |

A `ToolMessage` alone may not reproduce a tool's graph `Command`/context-state effect. Conversely, replay must not reapply stale policy over a newer settled state. Reconciliation is scoped to the accepted pending batch and explicit effect identities. A call can finish after another call with a higher creation sequence. Creation order and `max(event_seq)` are not a completion timeline. Define causal/application progress rather than inferring it from wall-clock timestamps.

Graph checkpoints, SQLite commits and immutable external files do not form one atomic transaction. Define visibility and reconciliation at these limited boundaries. First-version single-writer recovery does not promise arbitrary historical-job migration, exactly-once remote generation or unconditional recovery from every hard crash.

### Shared limits and transport behavior

Normal and compaction sends use one durable budget/cancellation gate, including direct entry and resume paths. Limits survive restart and graph rollback. Distinguish request inactivity from whole-job active time. Define wait/backoff accounting. Do not reset attempts, turns or time allowances on resume or hide nested SDK/proxy retries.

When bounded unknown-outcome model replay is enabled, it need not demand routine human proof that the remote generation stopped. Preserve possible duplicate inference, remote overlap and unknown usage/cost. Local abort, timeout or later success does not prove remote cancellation, original-generation continuation or zero cost. Eligibility/limits/default values need configuration. Old experiment values are not new defaults.

Streaming and non-streaming share accepted-response/tool/persistence semantics. Preserve native candidate information with safe handling of errors and sensitive fragments. A transport fragment is evidence, not automatically an executable native response. Respect explicit cancellation. Respect user questions. No routine reminder may override them.

### Stop, task completion and export

Execution stop reason, agent content-completion claim and package consistency are separate records. A question for the user can enter a waiting state. A second no-tool answer is not automatically a question. Bounded continuation feedback is now implemented as specified in Q3 below. It asks the model to express an existing necessary question through `report(waiting)` without assuming a user answer; it does not certify completion or require a conversion method.

Saved versions remain exportable by the host without further model use. Partial work retains a draft/partial label. Explicit version selection determines Markdown, JSON, HTML, assets and ZIP. Neither a mutable head nor a newly generated summary may change that selection during export.

Verify actual intended members and bytes. A manifest identity alone does not establish actual ZIP/file consistency. The export directory and ZIP are separate publication effects. A single rename cannot atomically publish both. Re-entry must preserve unrelated outputs and reconcile known output identities before repeating publication. A finalizer node cannot guarantee packaging after every crash/cancellation/exit.

### Desktop progress and process boundary

Persist important results/receipts. Allow coalescing or dropping obsolete progress events. A bounded queue cannot simultaneously promise lossless unlimited events and never block when the consumer stops. Avoid coupling durable tool completion to UI stdout consumption. A reconnecting UI should read committed state.

Protocol output and diagnostics require a deliberate process/channel boundary, but mandatory first-line `os.dup2` was not established as the universal remedy. Native libraries, callbacks, threads and process shutdown need proportionate implementation checks. These considerations do not require a new distributed infrastructure or a separate network research phase before document/context contracts can be written.

## Implemented first-version contracts

These are the selected executable contracts, with Q1 and Q3 updated for version-bound editing, local candidate reuse and explicit continuation boundaries. They close Q1–Q3 at the design level. [CURRENT_STATE](CURRENT_STATE.md) records which behavior was tested. New connections default to [streaming progress waiting](#streaming-progress-waiting); saved legacy routes and frozen requests retain their explicit non-streaming total-deadline interpretation.

### Q1: document schema and commit

`schema.py` defines `Document` with `title`, `scope`, ordered `blocks`, a complete physical-page `pages` map, `claim` (`partial` or `complete`), and `known_gaps`. Each block has a stable task-local `id`, exact `markdown`, physical `pages`, and optional `source_note`. Each page has `printed`, `disposition`, and `note`. Disposition is `unprocessed`, `included`, `outside_scope`, or `omitted_non_content`. Printed labels remain strings; `unknown` and `none` have different meanings.

`edit_document` requires `base_version` and `expected_head`. The base supplies content; the expected head is the commit precondition. Default `mode="edit"` requires both identifiers to match, including null/null for an initial document. A mismatched ordinary edit fails with repair guidance and retains its candidate. The agent may explicitly choose `mode="rebuild"` to start from another task-owned saved version or a null (empty) base. This requires no separate human approval and imposes no reconstruction-size limit. Both modes still compare `expected_head` with the actual head inside the commit transaction. A stale expected head fails without silently rebasing or overwriting newer work. The saved document envelope records `edit_mode`, `parent` (the content base), and `expected_head`; the receipt also identifies the mode. These establish the requested operation, not semantic correctness.

Omitted content and metadata remain unchanged relative to the named base. `replace_blocks` replaces the full ordered list; top-level `reuse_candidate` copies a block list at a task-owned candidate's RFC 6901 JSON Pointer. These alternatives cannot be combined. Neither replays the candidate's old operation.

Sequential `operations` support `insert` after an existing ID (null means beginning), `replace`, `delete`, and `patch`. Each insert/replace supplies exactly one non-null content source: `blocks` or `reuse_candidate: {ref, pointer}`. A local candidate pointer selects one `Block` or a list of `Block` objects, such as `/operations/0/blocks` or `/operations/0/blocks/0`. The resolver checks task ownership, candidate kind, pointer syntax and block schema. It copies only those blocks, without importing other operations or rejected metadata. Existing target, unique block ID, page and asset checks still apply to the merged result. Candidates remain reusable after later versions are saved. Invalid inputs retain their new candidate and leave head unchanged. An empty block list is allowed as an explicit operation, not mistaken for a missing content source.

Patch offsets are zero-based, half-open Unicode code-point positions in the current block after earlier operations in this request. `expected` must match exactly. `page_updates` merges only supplied page fields before validating the entire result. The tool schema exposes the page fields, disposition values, edit modes and candidate-content choices to the model.

Every accepted call's raw argument string is retained as `candidate:<request>:<call-index>` before domain validation. Reuse works after rejection or a later save. The full native response is retained earlier, before native parsing. Invalid and truncated calls remain non-executable.

The document core writes immutable version files, flushes them, then commits the version registration, head and original operation receipt in one SQLite transaction. Unregistered prepared/version directories remain preserved but invisible; there is no automatic destructive cleanup. A replay returns its original receipt/version without rewinding a newer head. The whole Markdown document is parsed together, so cross-block references and footnotes can resolve. Preview sanitization does not rewrite saved Markdown. Image links must name registered local assets; version files and exports preserve those bytes.

`complete` is an agent content claim with structural checks: no known gaps or unprocessed pages, output provenance for included pages, and a note for outside-scope/non-content pages. These checks cannot establish source fidelity. Partial versions can be saved and exported at any time.

The desktop treats a selected version as ready only after loading content with the matching task and version identity. Pending/failed reads hide the previous content and disable editing/export; failed reads have a local retry. Late responses for previous selections are ignored. An edit session captures the loaded base, expected head, mode and draft blocks together. It remains bound to them if the head advances. Save uses the session's captured fields; a conflict retains the draft and the backend candidate. Version/task switches are disabled while editing until save or explicit discard. Historical versions offer **Rebuild from this version**, with an explanation that later content is not included. Manual saves remain partial claims. Export always targets the loaded saved version; unsaved edits are excluded and identified as such in the editor.

### Exact saved-document and evidence access

`read_document` resolves an omitted `version_id` to the current head once for that operation; an explicit ID stays immutable. Its full result is the saved **version envelope**, with `content.blocks`, `content.pages`, `assets`, `originals` and provenance. `edit_document` accepts `Edit` operations against the content, not that envelope. Select `/content/blocks`, `/content/blocks/11`, or `/content/blocks/11/markdown` directly. A range requires a selected string or array; the root envelope is an object. Invalid paths/ranges return actionable structure guidance and preserve the original arguments. No index-first step is required.

Optional `view="index"` returns the exact version, block IDs/pages, Unicode character and UTF-8 byte counts, and exact pointers. It does not include block bodies or certify fidelity. The index does not take content selectors; use its version/pointers in a full read. Full and raw reads remain available, including on the first access. A smaller read leaves earlier full results in history unless an explicit policy or the existing compaction/admission rules change their projection.

Read results distinguish three facts in `completeness`:

| Field | Meaning | Twelve-block `/content/blocks`, range `[11,12)` |
| --- | --- | --- |
| `root` | The whole saved root is returned in the named access representation | false |
| `target` | The JSON Pointer target (before range selection) is entirely returned | false |
| `selection` | The valid requested selection is entirely returned | true |

An unsliced target or explicit `[0,12)` has `target=true` and `selection=true`, but still `root=false` when the pointer selects a field. A full root has all three true. The retained `complete` field aliases root completeness only; document `claim="complete"` is a different fact. `total` is measured before slicing. String ranges use Unicode code points; arrays use item indexes; raw/Base64 reads use original-byte offsets. `original_bytes` describes the stored original and `returned_bytes` describes selected content under `returned_size_basis`, excluding receipt/native-envelope escaping. Neither is a provider token count.

Metadata indexes have root/target false and selection true. Native-image reads identify a complete saved image selection, not proof that its pixels were included in a model request: actual projection reports `pixels_delivered`. Index reads do not inject image pixels. Unsupported selectors on indexes, native images or raw JSON fields are rejected rather than ignored. All completeness facts concern access, not PDF scope, model understanding or source fidelity.

### Working-evidence feedback and optional preview

Every newly assembled normal input contains one compact `Working context feedback` summary: current head, representation counts, actual document-read bodies, native-image count, total local input estimate, output reserve and remaining allowance. It counts its own emitted bytes and all tool descriptions. Numeric rendering uses monotonic whitespace width to avoid self-cost oscillation at a digit boundary. Unknown-result reservations remain separate admission metadata; the summary describes the actual emitted payload, not future results. It does not select, release or silently change evidence.

`inspect_context` is optional. Its detailed inventory describes the **frozen normal input that produced the current response**, including full/selected/index/raw results, reference-only projections, authored tool arguments, assistant text, pins and handoff summaries. `release_ref` names the exact history-result/argument/pin representation; `ref` identifies its underlying source when available. Edit commit receipts are not document-read bodies. The inventory can be read whole or with explicit zero-based item ranges. Component costs are labeled native-envelope deltas, not an additive breakdown or a semantic-relevance judgment.

The tool deliberately excludes **all results of its current response batch**, including preceding reads or edits. It reports both the snapshot head and current head, input request/payload identities and active-policy identity. Optional `changes` accepts agent-selected `pin`, `release`, and `notes` against that snapshot active policy. It uses the production normal assembler and estimates the resulting hypothetical input; it does not import pending intent, apply a policy, consume a model request, or guarantee the later batch's admission. New results, outcomes, settings and head changes can alter that later input. This is information for ordinary agent work, not a mandatory preview or confirmation-only turn.

New frozen normal requests retain a compact context/anchor snapshot outside graph hydration. An exact preview is available only when the current assembler reproduces the recorded payload; older requests without that snapshot or changed assembly recipes cannot claim an exact reconstruction. Read-only inventory remains available from the actual frozen payload. Tool capture and immutable receipts still persist normally; their replay returns the same observation. No original receipt/frozen input, policy eligibility, head or consumed budget is changed by inspection. Normal whole-batch coordination remains the only policy activation path.

### Q2: context transitions

Graph state holds request IDs, the handoff reference, history revision, the current compact policy projection, pending/disposition references and compact response-correction entries. Immutable proposal and settlement objects retain complete revision and decision content. Catalog commit/disposition/current-policy records establish formal effects; graph state recovers those effects rather than making a second policy decision. Full native responses, candidates, evidence, feedback and frozen inputs remain in immutable external objects. Request assembly is transient. Native call/result pairs and required reasoning items remain in the projection. Released authored arguments become explicit archive references only in that projection; execution always uses the original accepted call.

The current portable estimator charges the UTF-8 byte length of the complete assembled non-image payload, plus 1,024 units and a configured allowance per native image. It then reserves configured output capacity. This is a conservative heuristic, not provider token usage or a proven upper bound for every route. Missing image allowances block a pixel request. Capacity values must be configured for the route; a generic HTTP failure does not change them.

`context_update` lets the agent release/pin exact saved objects and replace continuity notes. Release changes input retention, not storage. The model-facing `pin` array contains explicit selections: `{"ref":"...","view":"index|image|full|raw"}` with optional `json_pointer`, `start` and `end` for precise content. `index` injects reference, kind, byte size, provenance and a retrieval instruction; it makes no full-content claim. `image` injects saved native pixels and requires a vision route with a configured image allowance. `full` injects complete JSON/text, or an exact field and/or half-open string/array range. A candidate's full root view preserves its authored UTF-8 syntax; root ranges use Unicode characters. `raw` injects Base64 bytes, optionally a half-open byte range; it cannot use JSON Pointer. An encoded `image_stream` also has byte semantics for `full`. Display-image files require `image`, `raw` or `index`, rather than treating image metadata as full pixels. Index/image views reject selectors. Invalid selections reject the update. Bare references from retained calls/checkpoints keep the existing kind-derived full/image representation; new tool guidance asks for explicit selections.

Several selections of the same reference in one update are retained together and replace that reference's prior selections. Other references stay pinned. Release removes all selections of the named reference; a subsequent pin in the same update takes precedence. Pins hydrate in a separate transient section independently of their original history. Historical occurrences identify the selected representation instead of duplicating the entire body, and `body_in_context` is false when only an index or partial selection is pinned. Pinning a result does not recursively load referenced objects. Image pixels are explicitly absent from text-only compaction requests and restored in normal input; a new image pin on a text-only route is rejected.

**Save first; admit the complete accepted batch.** `ContextRevisions` validates structure, source identity, representation and range while retaining exact arguments and each original result. A valid call returns `context_saved`, `admission={"applied":false,"status":"saved"}` and `policy_unchanged=true`; `ok=true` acknowledges saved, structurally valid work only. Capture does not measure an intermediate policy's capacity or activate it. All context calls in one complete model response compose in accepted call order into a single immutable `context_proposal`. Its operation IDs, batch, base, instruction basis, candidate policy and validation errors remain readable. `context_waiting` references that proposal, not an assumption that it has applied. Full known tool results, rather than placeholders for later tools, are available before whole-policy admission.

Omitted `notes` preserves the chosen base's notes; supplied notes replace them completely, and `""` clears them. Within each update, release precedes pin; a later pin restores the selected reference with its stated representation. A later update can change the same reference or notes again. Intermediate excess such as `pin Y` before `release X` does not reject the first call when the final candidate may fit. By default a new batch extends the still-eligible pending candidate, otherwise the active policy. Explicit `base={"kind":"active"|"pending","ref":"expected-base"}` selects a different current base; ordinary updates may omit `ref`, while a supplied stale reference conflicts. A pending base must remain eligible.

Any structurally invalid context call makes the entire batch's context revision ineligible for automatic application, including a formerly pending candidate it attempted to revise. The coordinator records `needs_agent_revision` with reason `invalid_revision`. It does not apply the valid subset or automatically fall back to the older pending policy. All raw calls, diagnostics and candidates remain readable. This rule does not roll back successful document edits, image extraction or other non-context effects in the batch. Merely exceeding capacity is not a structural error.

**Explicit reuse creates a new revision.** `reuse` is an array of source selections: `{"ref":"saved-source","operations":["operation-id"],"fields":["notes","pin","release"]}`. A source can be a context proposal, an original context-call candidate, or a context tool result. Proposal sources require exact operation IDs; selected operations retain source order, not the order of the ID list. `fields` selects context fields and defaults to all three. Reuse entries run in request order, followed by the current call's newly supplied fields. Reuse requires explicit `base.kind` and `base.ref` from the current anchor's `context_policy_ref` or eligible `context_candidate_ref`. It copies selected operations/fields onto that current base, never implicitly replaces it with an entire old policy. After an ineligible result, a subsequent call must explicitly select its base. New instructions use a new revision's instruction basis; the old source basis and disposition are unchanged. Malformed raw content stays readable, but only explicitly selected, structurally valid content can be reused. All selections are revalidated.

**One coordinator makes the formal decision.** `ContextUpdates` first recovers a committed result. At an applicable unfrozen boundary it checks instruction validity and structural validity, then compares the final candidate's complete normal input with the active-policy input using the same settled history and specific prospective `applied` outcome. This includes task instructions, handoff, native pairing/reasoning, schemas, images, result presentation and output reserve. A fit with no additional unselected body deferrals commits the complete candidate without compulsory compaction. An update cannot manufacture immediate success by making previously visible evidence individually too large. Explicit releases and selected representations remain agent choices.

The separate mandatory-content projection includes system/task material, current source/scope/instructions/head/policy anchor, selected pins, tools, native framing and configured images/output. It retains both unreserved proxy cost and admission reservation. These are not provider-token lower bounds: deleting history/handoff or removing a margin does not prove actual minimum cost. Current profiles return `proof_available=false`, `necessary_cost_lower_bound=null`, `proved_excess=false`. A fitting projection proves neither complete admission nor semantic sufficiency. Specific-result admission and final-handoff acceptance still use the complete prospective outcome; an unknown-outcome reserve is planning only.

**Confirmed necessary-content excess requires agent revision (policy B).** For a valid, complete, still-eligible candidate, proven excess under current settings commits `needs_agent_revision` with reason `required_content_exceeds_capacity` before attempting diagnostic delivery. This rule applies even if that candidate used to fit or the active policy cannot currently carry the diagnostic. The active policy and all useful work stay unchanged. Later capacity increases cannot reactivate this candidate; the agent may explicitly reuse selected content in a new revision. Capacity observations made before a disposition commits can be reevaluated using current settings. New instructions supersede an uncommitted candidate instead of rewriting its basis.

When the mandatory reservation itself does not fit without a supported proof, use `necessary_estimate_uncertain`. If a complete active-policy diagnostic fits, commit `needs_agent_revision` with that uncertainty reason, retaining the previous policy; otherwise keep the candidate eligible with a named uncertainty wait and explicit retry condition. This is a transfer of choice, not confirmed excess. Missing image/modality/protocol configuration remains `capacity_configuration`; a fitting diagnostic may transfer choice as `unknown_capacity_agent_choice`. Both committed transfers remove automatic eligibility and survive later capacity/estimator changes. No current profile generates a new confirmed-excess disposition solely from an estimate.

When the mandatory reservation fits and history/handoff prevents complete admission, try the actual compaction request. A fitting plan preserves eligibility and records `context_check.reason=compaction`; every compaction and post-handoff continuation must pass its own full reservation. Other temporary blocks retain their reason, basis and retry condition. Continue/reopen reevaluates unfrozen eligible waits, never a committed disposition.

**Disposition and delivery are independent.** Recover committed decisions before evaluating current estimates/settings; checkpoint the decision/wait before selecting the next request. Diagnostic continuation uses the unchanged active policy and exact recorded outcome. An uncertain active mandatory reservation stops as `necessary_estimate_uncertain`, preserving work and explaining that actual token excess is unconfirmed. A future independently supported proof may use the existing `feedback_capacity_blocked`/policy-B boundary. Compaction feasibility always uses its actual instructions, schemas and selected history, not a failing normal template. A waiting label does not establish successful continuation.

Compaction normally uses active notes and selections. Only explicit releases from a still-eligible pending candidate may reduce a labeled transient compaction view; this does not commit any part of that policy. A candidate needing revision or superseded by new instructions supplies no release/notes/pin shortcut. Shorter pending notes or selections are not presumed semantically equivalent. Final handoff validation targets either the eligible candidate plus its exact prospective applied outcome, or the active policy plus the committed diagnostic. Partial compaction must show strict complete-input reduction; a final pass must also permit that target's normal continuation. Handoff-only compaction is available when history is empty. Existing request/time/correction limits remain authoritative; no progress, interruption or exhaustion preserves old history, useful candidates and consumption.

The accepted tool batch always reaches `coordinate`, including a batch with `report`; a valid report may then terminate the invocation after local coordination without another model call. Stop before batch completion preserves captured calls without applying a partial revision. Direct Continue resumes the original batch. New instructions retain committed policy/document effects, skip unstarted old tools according to Q3, and supersede uncommitted context intent. Saved-but-unapplied context work is not a committed policy effect. A report can end with an eligible wait or a saved disposition; its receipt does not imply context activation.

**Commit before graph recovery.** An immutable `context_decision_candidate` stages the prospective settlement. One short catalog transaction validates the evaluated task/active policy, registers the final `context_settlement` alias, writes its `context_commit` marker and candidate `context_disposition`, and updates `context_policy` only for an applied result. These record kinds use the existing generic records catalog; they are not independent policy schedulers. A staged file alone proves neither disposition nor application. The immutable settlement records source basis, evaluation, exact result and graph changes. Re-entry recovers the committed decision/event before any current-settings decision, including across the commit/checkpoint gap. Formal needs-revision/superseded results cannot revive, and applied policy cannot be applied twice or retroactively rejected.

Original capture/error receipts never change. Request projection adds a later `context_outcome` only when the actual native result projection already provides the matching operation's result; otherwise it includes a separate bounded result/reference message. Presence of the batch ID in history alone is insufficient. Full diagnostics remain behind the exact settlement reference. Unknown outcome planning reserves the measured native envelope; `outcome_reserve` is a local estimate, not provider tokens. Frozen input records the selected representation and outcome. Freezing means preparation, not send or model comprehension; a frozen request wins over new coordination and stays byte-for-byte unchanged, with its original replay policy and consumed budgets. Checkpoints contain policy/references rather than hydrated bodies. A dispatcher without runtime context cannot apply updates, and actual new requests still pass the complete capacity gate before freezing.

Normal assembly first tries the complete selected input. If it does not fit, the app assesses each unpinned, unreleased argument/result/image against the required anchor, current handoff, pins, feedback, tool schemas and its native batch scaffold. Other unprotected bodies can become references only when that replacement reduces the measured complete native input. Short arguments or results stay verbatim when their references would be larger; JSON escaping, protocol envelopes and image metadata are included in the comparison. Only a body that cannot fit in this input is capacity-deferred; no text is silently sliced and no fixed field subset is selected. If that scaffold itself cannot fit, normal assembly leaves this case to compaction. This is a mechanical size decision, not a judgment that the body is irrelevant. Multiple individually fitting bodies that overflow in aggregate are not automatically evicted. The complete assembled request is checked again before freezing; remaining history pressure uses compaction.

A deferred result records `body_in_message=false`, `body_in_context=false`, its exact result/candidate references, saved byte size, original warnings and coverage, result keys, and a full-read tool argument. For a saved evidence selection, `source_view` preserves its source reference, pointer/range and original selection metadata; `body_in_message=false` distinguishes that saved selection from delivered evidence. `value_keys` supplies navigation for an object-valued selection, not a fidelity claim. Nested and outer warning/coverage fields are retained separately when both exist. Authored arguments become explicitly labeled `archived_arguments_ref` projections. Omitted pixels keep their image reference and an absence notice. Full/raw/field/range access remains available from the complete immutable originals; a later oversized full read may also need deferral. Exact field/range reads are selectable without a compulsory summary, index, OCR or script stage. Frozen normal-request metadata records the before-admission estimate, selected capacity deferrals and pinned references; graph state does not acquire the hydrated bodies.

Compaction selects a fitting oldest complete batch prefix. A pin does not stop that prefix: its complete selected object is independent of the history and survives application of the handoff. Normal and compaction assembly share per-object projection logic, but measure their own actual envelopes. Compaction measures the anchor, previous handoff, pins, correction feedback, already selected batches and the proposed batch. It first defers individually unfit objects, then, if aggregate pressure remains, defers the object with the largest measured saving until the segment fits or no improving projection remains. It retains fitting objects in the same batch, never slices their text, and does not re-project earlier selected batches or silently release pins. This size-based compaction projection does not change normal admission's rule against evicting individually fitting bodies under aggregate pressure. Frozen compaction metadata and the handoff archive record each affected request and exact deferred references; their semantic relevance remains unresolved.

Once an older selected prefix offers body reduction and only the newest complete batch remains, the planner checks whether that batch has an actual result/image retention benefit beyond context-control receipts. It previews its normal continuation with real handoff framing and known previous handoff content, or known task/source/head facts when no handoff exists. That target includes an eligible candidate policy and its specific applied outcome where applicable. If the target fits without capacity deferrals, selection stops before consuming that batch, even if its text-only compaction projection would also fit. Frozen `retained_normal_target` metadata records the suffix and projection. This is a planning target, not an early policy application or permission to send. The actual replacement handoff must subsequently fit that target without introducing evidence deferrals. The preference keeps fresh tool results available for normal reasoning; it does not automatically pin them, impose page batches, promise model understanding or retain history permanently.

When no such fitting target exists, the preceding rolling-compaction behavior remains: a later batch that fits alone but cannot join the selected prefix stays uncovered when that prefix offers body reduction in normal input. The app compares each selected batch's normal projection with only reference substitutions that reduce that complete native envelope. Normal admission and prefix progress share this positive-saving principle; a longer archive reference for a short argument cannot hide the saving from another body. With no positive body saving, compaction attempts to include a per-object projection of the next batch in the actual remaining space. There is no fixed minimum prefix/summary size, field whitelist or semantic usefulness claim. Actual handoff acceptance still checks the complete target input, including replacement of the previous handoff. A proven impossible necessary target or a compaction request with no fitting segment stops explicitly and preserves pins and work; normal-template overflow alone is not such a proof. No larger route capacity is inferred.

The summary request uses the same frozen-request service, budgets and cancellation gate. Its six fields are `task`, `current_state`, `unfinished_work`, `dependencies`, `references`, and `cautions`, each a string or string list. The replacement must carry needed facts from its predecessor. The app records exact covered request IDs, source references, deferred bodies and history revision independently of the summary text. Text-only compaction projections explicitly label `pixels_delivered` as current-request-only; ordinary normal image envelopes retain their existing representation and cost. Missing pixels in a text-only compaction do not prove that earlier normal requests lacked them; neither historical submission nor a summary proves visual comprehension or fidelity. Summary guidance preserves recorded findings and their uncertainty instead of turning current absence into a claim of historical non-delivery.

A handoff applies only to the matching prefix/revision and only if it reduces the entire normal input, including its own references. Without a declared retained normal target, a partial reduction can apply while uncovered history remains, even if another compaction is needed. When a retained target is declared, the actual handoff must fit that complete continuation without new evidence deferrals. A handoff covering the last history batch must also produce fitting normal input; otherwise it is archived but rejected, preserving the previous active history/handoff for bounded correction. This prevents the demonstrated oversized-input/empty-history dead end without demanding that every partial pass reach the final target. A schema, revision, reduction or request failure leaves the previous context active. Model-authored schema/reduction/final-capacity failures and unexpected compaction tool calls receive bounded correction feedback; state conflicts and storage faults are not treated as model mistakes. A new fitting compaction request includes the diagnostic and original covered history. Rejected candidate text is considered only after selecting that history and is included only if the complete payload still fits; it cannot displace selected evidence. Otherwise its exact reference and omission status remain explicit. Compaction tools are never dispatched. Original handoffs and their archive links remain retrievable. Schema validity, net reduction and fitting capacity do not prove semantic completeness.

An application receipt, not the existence of a handoff archive, establishes that a handoff was applied. If that receipt committed before the graph checkpoint, re-entry first checks the same prefix/revision and immutable archive. It then recovers the original transition using the receipt's historical before/after estimates; it does not recalculate those historical facts from a changed amendment or document head. The receipt must still match the covered requests and archive reference. Rejected or merely archived candidates have no successful application receipt and must undergo normal validation. After recovery, `prepare` assembles and checks current input with the latest amendments/head. A previously accepted transition neither grants capacity for new input nor authorizes another model send. Pins, uncovered history, original bytes and task consumption remain intact.

### Q3: execution, recovery and delivery

Chat Completions `tool_calls` may be absent, null, or an array. Absent/null means no executable calls; non-array non-null values are rejected. This interpretation does not rewrite the original native message. A nonempty text-only reply still follows its normal continuation or compaction contract; empty, refused, truncated or invalid calls do not become executable. See the official [Chat Completions response schema](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create). Actual Nexus route validation remains separately recorded in CURRENT_STATE.

`catalog.sqlite` owns jobs, requests, attempts, operation receipts, committed context dispositions/effects, version registration and exports. `graph.sqlite` owns LangGraph checkpoints with synchronous durability. External immutable objects own the retained bytes. A cross-process file lock permits one task executor; manual editing uses the same lock. Independent jobs can run separately. These stores do not form a shared transaction.

Request identity is `<job>:<sequence>:<revision>`; member operation identity appends the accepted call index. Same-request re-entry uses frozen bytes. An accepted reply wins over a new send. One validated, idempotent Nexus settlement publishes an already saved `accepted:<request>` pointer and its actual attempt metadata in one catalog transaction, and also repairs older states whose pointer exists but attempt settlement is missing. Complete matching re-entry preserves original time/usage; contradictory provenance or known metadata is rejected without partial publication. Immutable evidence is saved first, outside this transaction. [The execution guide](design/EXECUTION_AND_DELIVERY.md#accepted-result-settlement) owns field authority and validation order. The dispatcher similarly reconciles `result:<operation>` before repeating work. A committed document can reconstruct its missing projection from the atomic original receipt. Captured context calls reconstruct the same ordered revision; only a committed Q2 settlement establishes its policy effect. An interrupted OCR/script operation without a settled result stops as `local_outcome_unknown`.

Each frozen request records `instruction_basis`, the hash of its ordered user amendments. Tool writes and head changes alone do not supersede their own batch. Before each uncompleted call, compare that basis with current amendments. When they differ:

- A completed operation returns its original receipt. Committed document/context effects are not undone or repeated; a saved context call without policy commitment is preserved as content and follows Q2's uncommitted-revision rules.
- An unstarted operation saves its original candidate and a durable `skipping` marker, then a paired result with `ok=false`, `skipped=true`, `execution="not_started"` and reason `superseded_by_user_amendment`. The candidate remains available for the agent's next decision. Every accepted call retains its native result pairing.
- A started operation without a recoverable receipt cannot be labeled unexecuted. It stops as `local_outcome_unknown`, with original files retained. This increment does not add general local-effect reconciliation.

After the batch settles, coordination restores committed context effects before evaluating outstanding intent. New amendments supersede an uncommitted revision without changing its original instruction basis. An old `report` receipt remains historical but cannot terminate new instructions. The next model request contains the latest amendments and outcomes; the agent chooses its method, tool and reconstruction scope. A plain Continue without an amendment resumes the original accepted batch. A same-text new amendment is still a new entry in the ordered amendment list.

The user's Start/Continue API permits a new request after `http_error` or `rejected` (including a complete transport carrying a truncated or malformed native reply). No calls from a rejected reply execute. An amended prepared request with no send attempts can also be superseded. Before graph advancement, an immutable `continuation:<old-request>` receipt stores the reason, diagnostic, retained native-response reference when available, attempt IDs and next revision. Graph state carries its reference; the supported LangGraph state-update path resumes through coordination before preparing new input. Re-entry recovers this recorded choice instead of requiring another click. Normal or compaction input carries the continuation feedback. Old requests, accepted history, candidates and versions remain available; old frozen bytes are never rewritten.

Plain process re-entry does not independently authorize a new request after an HTTP/rejected failure. Ordinary Continue and new amendments cannot move `unknown` or `in_flight` requests to a new ID: their frozen input and replay gate remain authoritative. The explicit unknown-compaction choice below is a separate, request-scoped authorization. Accepted local bytes take precedence over a fresh send. HTTP failure is not proof of zero cost or remote cancellation. Error bodies are withheld to protect credentials; status/diagnostic and unknown usage remain recorded.

**Explicit interrupted-compaction recovery.** The desktop offers **Resume context organization** only for the graph's current `unknown` compaction without locally accepted bytes or an already recorded continuation. The action sends `recover_compaction_request` with that exact request ID. Under the task lock, the server validates the choice before changing instructions/settings or clearing cancellation; a stale or unrelated ID cannot authorize another successor. This is a human decision to permit a replacement despite unknown upstream completion/cost, not a new automatic retry default or an assertion of remote cancellation. Normal unknown model requests and unknown local tool effects are outside this action.

Runtime records `continuation:<old-request>` with reason `explicit_compaction_recovery`, the selected request, its original payload reference and attempts, and the next history revision before advancing the graph. The old request, native/partial bytes, attempt, route and replay policy stay unchanged. A crash after the receipt but before its checkpoint recovers that same transition; after graph advancement a stale click cannot create another transition. Locally accepted bytes, including a response saved before its request pointer, win over replacement. The subsequent request is assembled and capacity-checked from current valid state. Context policy, saved documents, original receipts, correction episodes and consumed request/time allowances are not reset. One explicit choice permits one successor transition; if that successor is also unknown, ordinary Continue cannot recursively authorize another replacement. It requires a separate explicit choice. A successful replacement can then continue ordinary task execution.

Attempts and request-budget consumption commit before dispatch. Defaults are 80 model attempts, 7,200 active seconds, no automatic transport retry, and no unknown-outcome replay. Optional bounded transport replay applies only on re-entry. Each newly frozen request stores its `replay_policy` (`replay_unknown`, `max_attempts_per_request`) alongside its original route and payload. Its original gate governs subsequent attempts even if task-level values differ. Preserved pre-snapshot requests use the task recovery policy, which settings updates cannot change after any request is prepared. Normal, compaction and response-correction calls share current task total allowances. Active-time and cancellation checks also precede new tools and poll network/child-process waits. A local stop never establishes remote cancellation or known cost.

### PDF coordinates and image delivery

`inspect_pdf` uses PyMuPDF **unrotated page points, top-left origin** for `rect`, text/image bounding boxes and extraction content. `rotated_rect`, `rotation`, `rotation_matrix` and `derotation_matrix` separately describe the displayed page. A CropBox offset does not change the contract to absolute PDF coordinates. Native extraction fields and complete originals are retained; coordinates are not rounded or rewritten inside extracted content.

`render_page(region=...)` and `ocr_page(region=...)` accept that same unrotated frame. Omit the region for the complete visible page. Rendering converts the region to the rotated page rectangle internally and keeps the source page orientation. The result records both `region` and `rotated_region`, actual integer `pixel_origin`, dimensions, DPI, `page_to_pixel` and `pixel_to_page`. Each mapping is a six-number affine matrix `[a,b,c,d,e,f]`: `x'=a*x+c*y+e`, `y'=b*x+d*y+f`. Pixel coordinates refer to the saved image's top-left origin; pixel centers are at half-integer positions. The transform uses MuPDF's actual raster origin, including fractional-clip rounding. OCR output boxes remain image pixels and can be mapped back with `pixel_to_page`. OCR recognition quality is not established by a correct crop.

`extract_image` separates a display image from original encoded PDF streams. The unchanged source PDF remains authoritative. Before deriving the display image, the app retains exact `xref_stream_raw` bytes for the image and any SMask as task-owned `image_stream` objects. Each stream records its source hash/reference, xref, filter, object dictionary, role and extraction version. These are encoded PDF streams, not a claim that every stream is a standalone image file; color-space and other indirect dependencies remain in the source PDF.

The returned `asset_path`/`image_ref` selects a native-dimension display asset. Compatible unchanged embedded JPEG bytes stay unchanged. Other cases decode the PDF image directly and use PNG; CMYK converts to RGB before a source soft mask is composed, and JPX is delivered as a browser-readable PNG. The app does not publish the RGB JPEG that `Document.extract_image()` may reencode from CMYK. Provenance records `representation`, `original_bytes_equal`, `original_ref`, `originals`, color conversion, source/display bit depth, mask xref, decoder version and actual steps. PNG encoding is lossless for the decoded samples; it does not make preceding color conversion lossless. The bounded verified image cases use 8-bit components. Higher-depth decoding is explicitly warned about and retains encoded originals; preservation of high-depth display precision and arbitrary PDF image/color semantics is not certified by these checks.

A stencil (`ImageMask`) is a coverage component whose appearance depends on the page graphics state. Default extraction returns `representation="stencil_mask"`, `display_semantics="coverage_only"`, explicit warnings, `image_ref` and original streams, **without an `asset_path`**. The component remains readable as native pixels or exact bytes but is not registered as a faithful deliverable figure. `occurrences` lists each placement on the selected page, with zero-based occurrence number, unrotated region, image-to-page transform and retrieval arguments. The same xref can have different paint colors at different occurrences.

The agent may select `extract_image(page, xref, occurrence, dpi)`, call `render_page` for its chosen region, or use another source-led method. An explicit occurrence uses the shared page renderer and produces a registered PNG of that region with page rotation, paint, background and overlapping content preserved. Provenance identifies `rendered_occurrence`, source image kind, source/xref, selected occurrence and region, any page clipping, DPI, affine mappings, original streams, decoder and a warning that the crop is not an isolated embedded image. `original_bytes_equal=false` distinguishes rendered appearance from the retained stream. No occurrence is chosen automatically. Native extraction dimensions do not describe this DPI-selected rendered crop.

Images support native display-pixel reads and exact `view='raw'` byte ranges. Encoded stream `full`/`raw` reads return Base64 bytes with half-open byte ranges, while `index` exposes metadata. JSON Pointer remains available for structured evidence; a pointer on a binary stream is rejected explicitly. No summary gate, compulsory extraction method, resampling rule or agent tool quota is added.

Saving a document includes only its referenced display assets and their associated original image/mask streams. The version's `originals` map records their provenance and portable paths, `originals/<xref>-<hash>.<extension>`. Xref preserves source-object identity even when distinct streams have identical bytes. The manifest covers these files, and reopening and ZIP export verify them with the same immutable-version machinery as Markdown and images. Original streams are not inserted as broken preview images. The complete source PDF remains in the task store; it is not automatically copied into the delivery ZIP.

### Existing-task settings and active-time accounting

The authenticated `POST /jobs/{job}/settings` API changes a stopped task under the same cross-process task lock used by execution and editing. Start/Continue may also explicitly supply settings. Validation and a `task_settings` before/after record commit with the job update in one catalog transaction. Settings writes never change attempts, known active seconds, amendments, saved versions or frozen requests. Empty/omitted fields retain their effective values; invalid or disallowed changes reject the entire update.

Before any request is prepared, validated route/limit settings can be changed. Once a request exists or any attempt is consumed, only `context_tokens`, `output_tokens`, `image_tokens`, `timeout_seconds`, `wait_policy`, `max_requests` and `max_active_seconds` can change. Capacity and waiting settings apply to newly prepared requests; an existing request, including a never-sent prepared one, retains its original route, bytes and applicable replay limit. A waiting-policy change applies to both normal and compaction requests in that task until explicitly changed again; it is not a one-successor override. Changing settings sends nothing, does not authorize unknown-outcome replay, add per-request replay attempts or extend a correction episode. Protocol, endpoint, model, vision mode, generation parameters, recovery and correction policy changes are outside this existing-task update contract.

The desktop's **Task limits** dialog edits the supported capacity, waiting and budget values for the selected task and displays effective values and consumed usage. **Response waiting** selects streaming progress waiting or the legacy complete-response deadline. The legacy **Request deadline (seconds)** range is 1 through 3,600, including fractional seconds, with an unchanged legacy default of 180. The streaming defaults and independent timers are specified below. Connection settings supply defaults for an unconfigured task; Continue on a configured task uses its saved settings. Updating connection defaults does not silently replace them. GET job responses include effective route/limits, per-request frozen route/replay policy, and recorded unknown active-time intervals.

For a legacy route with missing/null `wait_policy`, the request deadline measures total monotonic elapsed time in the exchange; incoming body data does not restart it. The HTTP client uses the same frozen value for read/write/pool waits and `min(30, timeout_seconds)` for connection establishment. Stop and the persistent active-time budget remain independent interruption gates. A stopped task's new settings cannot mutate the selected old request: explicit unknown-compaction recovery uses its existing durable choice and prepares a distinct successor with the current route. Re-entry recovers that choice rather than granting another successor; locally accepted reply bytes still win.

Each new attempt has a small `transport` observation, separate from native-reply and handoff acceptance. It records `deadline_seconds`, `connect_timeout_seconds`, `settled`, `stop_cause`, safe exception type, header/first-body/last-body/complete-body elapsed seconds, received body bytes, `body_complete` and elapsed exchange seconds. The existing attempt `http_status` is set from observed headers even if the successful body later times out. A missing header time/status means not observed, not proof that the upstream sent nothing. Body counters measure decoded bytes received from a successful HTTP response, not wire bytes, tokens, generation progress or billed usage. Arbitrary non-success error bodies and authorization/header values are not stored.

`stop_cause` distinguishes `complete`, `http_error`, `request_deadline`, connect/read/write/pool timeout, other transport timeout/error, user Stop and active-time exhaustion. `body_complete=true` means successful-body EOF, not valid native output or an accepted handoff. False means successful-body reading started but did not finish; null means it did not start, including withheld HTTP-error bodies. First/last body times remain null when no nonempty success-body chunk was observed. Partial successful bodies remain archived and cannot execute tools. Unknown upstream completion, cancellation and usage remain unknown.

The deadline is checked at successful-body EOF as well as during pending waits. A late complete body cannot bypass the check because a synchronous segment prevented the polling task from running. Its exact bytes are retained as a complete `native_response` with `within_deadline=false`, without an accepted reply or executed tools; the request remains at the unknown-outcome recovery gate. It is not mislabeled as a partial body. This is local receipt/acceptance evidence, not a measurement of upstream completion time. A timely complete body followed by a transport-close failure is likewise preserved with its observed completeness; it does not silently create acceptance.

Legacy receive observations settle when the exchange exits and are saved with the attempt, not continuously journaled per chunk. A hard termination can leave the initial `settled=false` record; its initial null/zero fields are not a final measurement. Older attempts have no such observation and are not backfilled or reinterpreted. Accepted-response reconciliation recovers already committed acceptance without inventing missing transport observations. Streaming observation checkpoints are specified below. A generic complete-response rejection and a complete but unacceptable handoff retain their existing failure/correction rules; changing a waiting policy neither accepts them nor resets their correction budget.

### Streaming progress waiting

An explicit route `wait_policy` selects `stream: true` for newly frozen normal and compaction requests. Its fields are `first_progress_seconds` (default 600), `idle_progress_seconds` (default 300), and nullable `total_seconds` (default null). Present numeric values must be finite and in 1-3,600 seconds. These intervals are adjustable engineering starting points, not measured sufficient durations or provider limits. New UI connections use this policy with no total cutoff; existing saved routes without a policy remain legacy until explicitly changed. Streaming and `stream_options` are controller-owned, not arbitrary generation parameters. CC requests ask for terminal usage with `include_usage`; unavailable usage is not invented.

First-progress waiting starts when the exchange starts, not when input is frozen. Headers, bytes, created/in-progress states, tool identifiers, usage, empty deltas and keepalive comments do not reset it. A valid decoded non-whitespace addition to text, reported reasoning/summary or tool arguments establishes generation progress; all whitespace remains in the saved content. After first progress, the idle interval is measured from the last qualifying addition. A done snapshot can count only a previously unseen consistent suffix. Repeated equal text additions are preserved; they are not inferred duplicates. Protocol sequence-number duplicates are handled by exact event identity, not content guessing. The app does not assess usefulness, correctness or fidelity to reset these clocks.

An optional explicit total deadline runs independently and can stop continuing generation; it is absent by default and never inferred from the legacy `timeout_seconds` field when streaming is selected. Stop and the persistent active-time budget remain independent existing controls. The receiver checks expiry before a newly arrived event can refresh progress, including synchronous receive segments that prevent the poller from running. Silence only establishes lack of observed progress; hidden reasoning, buffering, upstream generation and cost remain unknown. HTTPX read timeout is disabled for streaming because the app owns these waits; connect uses `min(30, first_progress_seconds)`, and write/pool waits use 30 seconds. These connection/upload/resource bounds do not become a hidden total generation deadline. Generation waiting ends at a timely complete terminal; response/client cleanup is separately bounded to five seconds and cannot demote that result to an idle timeout. Cleanup completion, safe error type and elapsed time are recorded separately. This bound concerns closing local resources after reception has ended, not stopping continuing generation.

The attempt-local `StreamDecoder` handles SSE framing and complete native reconstruction. CC requires a single finished choice and `[DONE]`; terminal usage before `[DONE]` is retained. Responses requires a consistent completed response snapshot, retaining its native output and encrypted reasoning. HTTP 200, a tool name, partial JSON or EOF alone cannot authorize execution. A complete protocol terminal can end receiving without waiting for gateway EOF. Length/content-filter, refusal, malformed/inconsistent events, failed/incomplete response terminals and invalid native tools do not execute. Runtime's handoff validation and bounded corrections still apply after native acceptance. No timer event forces a tool, representation choice, context update, retry, model switch or extra model call.

First acceptance and saved replay validate the same entire received prefix at their receive boundary. Fully received SSE non-data fields/comments and a recognizable unfinished colon comment are harmless; all received UTF-8 must be complete. Pending data, an unfinished non-comment line, invalid/incomplete UTF-8 or any extra dispatched data after terminal rejects new acceptance. Keep every received byte; later chunks never read by the client are not evidence. EOF without terminal remains unknown. Historical acceptance satisfying this rule can be recovered atomically without changing raw/native/staging facts. Historical accepted stream semantics that conflict with it stop explicitly as `accepted_evidence_conflict`, retaining pointer, attempt, original usage/time and committed tools, with no automatic resend or rollback. Integrity/provenance and native validation still apply; raw-only terminal bytes cannot become acceptance. [The execution guide](design/EXECUTION_AND_DELIVERY.md#received-prefix-completion-rule-2026-10-28) explains comments, fields, UTF-8, chunk cuts, EOF and historical disposition.

Every nonempty decoded successful-body chunk is saved as an immutable `stream_chunk` before interpretation, with request/attempt/index and receipt elapsed time. New object files are flushed/fsynced before their FULL SQLite registration commit; repeated identical bytes can reuse a content address. `stream_receive` checkpoints headers, observations and a fixed-field durable-prefix cursor (count, bytes, SHA-256 and last reference), without rewriting the cumulative chunk list. The receive scope reuses one thread-confined SQLite handle, preserving separate FULL commits and fresh Stop/budget SELECTs. A hard stop between registration and observation can leave extra durable chunks beyond that cursor. `Store.read_stream` verifies request/task/attempt identities, contiguous numeric order, every object's length/hash, checkpoint prefix and any published aggregate. It returns the entire durable suffix without inventing observation or acceptance. Legacy list checkpoints remain readable without migration. The records are per attempt and never concatenated across retries. Complete protocol settlement reconstructs and verifies the exact aggregate before acceptance. An unaccepted incomplete protocol can archive its exact received bytes and already committed constituent identities from a matching cursor, labeled `chunk_validation=registration_only`; strict evidence/recovery reads still verify the entire sequence. The `raw_stream` keeps its once-written constituent manifest. The separate `assembled_response` links `source_stream_ref`, protocol, request and attempt; it is not represented as the original upstream full JSON. `accepted_response.native_ref` selects the assembled response and `stream_ref` selects the raw stream. Accepted streaming recovery verifies these evidence relationships before returning acceptance. Partial or rejected content remains useful evidence, not an accepted tool batch. A failure before accepted-response persistence does not imply acceptance merely because terminal bytes are recoverable; the existing unknown/local-recovery boundary remains conservative. [The execution guide](design/EXECUTION_AND_DELIVERY.md#implemented-streaming-receive-persistence) owns writing/recovery details and the distinction between process-kill evidence and untested OS/power-loss faults.

Receive observations retain the frozen wait policy, exchange elapsed time, headers/status, first/last body and valid event times, first/last progress times, received bytes, event/progress counts, terminal event/time and protocol completion. Progress count counts receive chunks containing a qualifying addition; it is not tokens or a semantic work measure. Earlier valid events in a chunk remain observed even if a later event in that same chunk rejects the response. `body_complete` still means HTTP EOF, so a valid terminal may have `protocol_complete=true` and `body_complete=false`. Missing observations and usage remain unknown. Original SSE error bytes from an HTTP-success stream are private evidence; arbitrary error messages/headers are not echoed in public diagnostics. HTTP non-success bodies remain withheld as in the legacy path. The job API and desktop expose an allowlisted latest-attempt timing/count/status projection, not raw fragments or headers; receive progress is explicitly distinguished from saved conversion progress.

Stops distinguish `first_progress_timeout`, `progress_idle_timeout`, explicit `total_deadline`, legacy `request_deadline`, `stream_incomplete`, `stream_error`, HTTP/transport failure, user Stop and active-time exhaustion. A stream disconnected before a terminal remains unknown; malformed/error terminal output is rejected without partial tools. No automatic fallback to non-streaming or another protocol occurs. Settings alone never grant replay. Accepted-response staging still wins after a pointer/checkpoint interruption; re-entry restores its stream/native references without sending again or charging another attempt. Existing unknown requests keep their frozen input/policy and require their existing authorized recovery path.

See [Nexus/CLIProxyAPI signal evidence](reference/NEXUS_STREAMING_SIGNALS.md) for pinned source observations, current-route limitations and official HTTPX/protocol guidance. Local scripted checks establish mechanisms and preservation; actual forwarding, latency, summary quality and autonomous conversion require separately authorized real-route evidence.

`active_seconds` is known monotonic elapsed time within active invocations, including model/tool waits, not CPU time or a provider bill. `ActiveTime` checkpoints at preparation, tool boundaries and request entry, and approximately once per second while polling network/child-process waits. Each short transaction adds the measured delta and advances `active_since`, the last durable wall-clock observation. In-process budget checks include the not-yet-checkpointed monotonic delta. Normal shutdown settles the remainder and clears the active marker. User waiting between invocations is not active execution.

After hard termination, restart atomically preserves any stale marker as an `active_time_gap` record and starts a new interval. The record retains both wall observations, their signed difference, `active_seconds=null` and `budget_policy=known_active_only`. The wall span is not an active-duration measurement; clock changes can affect it. All previously recorded consumption remains charged. The uncertain tail is neither charged as all downtime nor recorded as zero work. The budget uses known active seconds, and the UI/API disclose the unmeasured intervals. A crash during a long uncheckpointed in-process operation can leave a substantial unknown tail; this policy is not a strict lifetime-work or cost bound. Gap creation and marker replacement commit together, preventing duplicate settlement on re-entry.

A no-tool answer is retained in history and schedules application continuation feedback. `report` selects `complete`, `partial`, or `waiting`; completion requires an explicit structurally complete saved version. An existing question must be reported as waiting, without inventing a user answer. The run stop reason, selected version's claim and export verification remain separate. Reopening does not itself resume or spend inference. The user can resume, reply, or export saved work.

`max_response_repairs` defaults to 2 and can be configured for new tasks in Connection settings; zero disables automatic corrections. It bounds correction requests following consecutive text-only normal replies and, independently, consecutive invalid handoffs. A settled normal tool batch clears the normal counter; a valid applied handoff clears the compaction counter. This is not a detector of semantic progress in arbitrary tool loops. The default is an adjustable engineering choice, not a measured optimal number or a quota on source-reading methods.

Each failure retains immutable `repair:<request>` feedback with its original accepted-response reference, diagnostic, count and basis (current document head and user amendments). Graph state carries a reference to that record. A correction changes context and receives a new request identity; it is not a resend of the accepted response. A restart or plain Continue does not reset the count. A new user amendment or edited document head starts a new correction episode at `prepare`; consumed attempts and time never reset. Exceeding the correction allowance yields `response_repair_exhausted`, preserves all work, and sends no further request. Reopening an exhausted episode alone cannot replenish it.

Handoff archives use `handoff:<request>` identities. `response_correction`, `context_compacted` and `request_continued` events have transactional deduplication receipts in `catalog.sqlite`. These cover replay after feedback/handoff/continuation persistence but before graph checkpoint completion. Applied handoffs recover their historical acceptance under Q2, including after a new amendment; global receipt immutability is not relaxed. The graph and catalog still do not share a transaction. General unknown-effect reconciliation and semantic no-progress detection remain separate. Capacity admission and independent pins are specified in Q2; they do not change recovery budgets or authorize new inference.

Export takes an immutable version and an explicit external ZIP path. It verifies actual ZIP names and bytes against that version, publishes without replacing an existing unrelated file, and reconciles an existing known export. Markdown, structured document, preview, manifest and assets come from that version. It needs no model call. The local filesystem must support the current exclusive hard-link publication operation; other filesystem publication strategies are unverified.
