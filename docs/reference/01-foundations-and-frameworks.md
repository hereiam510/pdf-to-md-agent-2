# Foundations, research, and framework decisions

This reference preserves the substantive discussion from **EVT-0002 through EVT-0414**, including attachments **ATT-01 through ATT-06**. It records why the rebuild direction changed, not a second implementation backlog. The controlling later correction is **EVT-1148 / EVT-1166**: a small **Python LangGraph `StateGraph` with SQLite** is the preferred rebuild baseline; responsibilities are settled, but implementation and proof are not. The remaining V1 contracts concern document edits and candidate references, context capacity and handoff, and persistence, recovery, and stopping. Earlier Pi, Deep Agents, `create_agent`, filesystem-only, and custom-controller rankings below are historical.

This document explains the decisions and their reasons without requiring the old project or conversation export. The repository's discussion-source archive supplies the cited original text and attachment material when a reader needs exact wording. `EVT` identifies an exported event and `ATT` an attachment; these are provenance labels, not application APIs or runtime object IDs. [SOURCE_INDEX.md](SOURCE_INDEX.md) explains their origins and lookup. Links to public documentation preserve the conversation's research trail. They were not freshly checked for this documentation rebuild, and their historical versions are not dependency pins.

Status meanings used throughout:

- **Agreed direction:** a product principle accepted in the discussion, subject to the later bounded consolidation.
- **Observed-v1:** an observation reported and checked in the old project discussion. It is not a new implementation claim for this repository.
- **Proposal/open:** a historical option, research lead, or illustrative implementation; it does not become a V1 requirement by appearing here.
- **Corrected/rejected:** a claim, prescription, or ranking that was withdrawn, narrowed, or superseded. The useful reasoning is preserved with its correction.

## Reading this reference on its own

For the effective product and responsibility boundaries, start with [PRODUCT_REQUIREMENTS](../PRODUCT_REQUIREMENTS.md), [ARCHITECTURE](../ARCHITECTURE.md), and [CONTRACTS](../CONTRACTS.md). This reference supplies the reasoning behind them. The final framework choice is explained at [P1-098](#p1-098); the three bounded open contracts are [P1-099–101](#p1-099). The earlier proposals remain here because their corrections explain constraints that a simple implementation must still respect.

Several terms had distinct meanings in the discussion:

| Term | Meaning in this reference |
|---|---|
| Agent / runtime / harness | The agent is the model making task decisions. The runtime or harness surrounds those decisions with requests, tool execution, state, capacity handling, and continuation. A framework can supply parts of that machinery; it does not replace source interpretation. |
| Nexus route | The configured connection from this app through the user's Nexus gateway to an upstream model service. The particular historical subscription path was Nexus → CLIProxyAPI → subscription accounts. A model alias or OpenAI-shaped request format does not identify every upstream feature. |
| Active context / complete record | Active context is what a particular model request actually contains. The complete record includes durable original messages, results, and files that may be absent from that request. The model does not know a file's contents merely because it receives its path. |
| Evidence / artifact | Evidence is source material or an actual tool-produced result used to reason about the PDF, with its scope and provenance. An artifact is prepared or saved output, such as reconstructed document content. Reading output successfully does not prove that it faithfully represents the evidence. |
| Offloading / release / retrieval | Offloading preserves content outside model input. Release removes a selected representation from later active input while preserving the original and a retrieval route. Retrieval supplies that original, or an explicitly selected part, again. These actions do not automatically preserve the agent's unrecorded interpretation. |
| Summary / handoff / compaction | A summary condenses earlier content. A handoff describes enough effective task, work, unresolved issues, and references to continue. App-owned compaction changes future request assembly using retained content and such continuation material; producing a summary alone changes no future input. |
| Context checkpoint / graph checkpoint | The old application's context checkpoint started a new working context with continuation material. A LangGraph checkpoint persists graph execution state for continuation. Either can exist without the other: persisting a huge history does not shorten it, and shortening input does not by itself provide crash recovery. |
| Candidate / committed version / head | A document candidate is received prepared content, including content that failed validation. A committed version is an immutable saved document result. The head is the current version pointer. A proposed context assembly can also be called a candidate; it is a different object from candidate document content. |
| Operation receipt | A durable record of the result of one identified operation, used to recognize a completed local effect after interruption. It is not a quality certificate, a fresh command to republish, or proof of what an upstream model did after a client disconnect. |
| Protocol / adapter / frozen request | Chat Completions and Responses are alternative wire formats. An adapter preserves their actual images, tool exchanges, and applicable native items. A frozen request preserves what was selected and encoded for one request so resuming that same request does not silently substitute a new context. |

These definitions unpack the discussion's responsibilities rather than prescribe new class names or database tables. **Sources: EVT-0137, EVT-0249, EVT-0318, EVT-0382, EVT-0414, EVT-1166.**

## Product purpose and the starting evidence

<a id="p1-001"></a>
**P1-001 — Delivery is the purpose.** **Status: agreed direction.** The agent completes the conversion; the app provides reliable tools. A user should supply a PDF and scope, then receive complete, readable, reusable Markdown and faithful source images with little manual handling. Product progress means useful delivery, less user work, reliability, recoverability, and reasonable whole-task cost. Tool counts, test counts, document counts, a success flag, and a polished screen do not substitute for these outcomes. The initial review used an actual PDF or complete natural section and its reading, search, or editing purpose as the next useful delivery question. **Sources: EVT-0053; EVT-0001.**

<a id="p1-002"></a>
**P1-002 — Independent desktop delivery remains part of the product.** **Status: agreed direction.** The intended application is an independent Electron, TypeScript, and React desktop app that runs its own agent and supports configurable Chat Completions and Responses connections. Independence from the Codex or ChatGPT UI does not mean an offline model. The old headless Python core and an external assistant successfully using tools did not prove installed desktop readiness. At the start, UI integration and Windows packaging were absent; the later consolidation still treats them as required delivery work if “delivery” means an installable app, without making every backend unknown a prerequisite. **Sources: EVT-0021, EVT-0053, EVT-1166; EVT-0001.**

<a id="p1-003"></a>
**P1-003 — Fidelity and reading form.** **Status: agreed direction.** Preserve substantive wording, numbers, names, units, punctuation, symbols, meaningful emphasis, glyph distinctions, superscripts and subscripts, headings, paragraphs, lists, footnotes, meaningful side content, reading order, and cross-page relationships. Reflowing columns, lines, typefaces, or spacing is acceptable; guessing, paraphrasing, normalizing meaningful characters, or dropping difficult content to make it look readable is not. Tables retain values, intentional blanks, headers, groups, spans, and relationships rather than being forced into a simple pipe table. Figures retain panels, captions, and important searchable labels. Pure decoration and repeated non-substantive running matter may be omitted; uncertain substantive content is preserved or made explicit. **Sources: EVT-0382, EVT-0414; EVT-0001.**

<a id="p1-004"></a>
**P1-004 — Images, page identities, and one-version outputs.** **Status: agreed direction.** Sources stay intact. Extract complete native images at their original size and encoding when possible; an existing JPEG is legitimate, and PNG alone proves no fidelity. Faithful lossless crops or renders are legitimate for vector, composite, or scanned content, with page, region, and rendering provenance. Do not silently resize, redraw, whiten, reduce color or bit depth, or add lossy recompression. Physical PDF positions and visibly printed labels are separate; printed `none` differs from `unknown`, Roman labels remain, and viewer labels or inferred offsets are not evidence. The full map distinguishes outside-scope and unprocessed pages without splitting sentences or tables merely to insert markers. Markdown, document JSON, safe HTML, assets, and ZIP must correspond to the same specified immutable version and use portable relative links. **Sources: EVT-0047, EVT-0053, EVT-0382, EVT-0414, EVT-1166; EVT-0001.**

**Page-label example.** In the observed delivery, physical PDF page 12 carried printed label `68`. That one correspondence does not authorize assigning every page a fixed offset: front matter, inserted plates, or an unprinted page may break it. `none` means the page was established to have no printed label; `unknown` means its label has not been established. Both differ from a page outside the requested scope or still unprocessed. The point of keeping these states separate is to show what the output covers without guessing labels or damaging a continuing paragraph to force a marker. **Sources: EVT-0047, EVT-0053; EVT-0001.**

<a id="p1-005"></a>
**P1-005 — Method autonomy and full access.** **Status: agreed direction.** The agent may choose extraction, OCR, visual reading, scripts, or combinations, including re-OCR of a damaged existing text layer. It chooses pages, regions, DPI, language, and reconstruction scope. Neither a framework nor the app should impose a page-by-page conversion pipeline, compulsory text-first reading, OCR, scripts, preview, or a fixed unit of repair. Full first-call and later full/raw/field/range/native-pixel access remain available without hidden truncation or a summary gate. Discoverable shapes, sizes, pointers, warnings, coverage, and omissions help selection. Disk availability is not evidence that the model has seen, understood, or remembered the content; a path or base64 text is not visual input. Full access also cannot make an arbitrarily large object fit in one request. **Sources: EVT-0137, EVT-0249, EVT-0265, EVT-0297, EVT-0318, EVT-0382, EVT-0414; EVT-0001.**

<a id="p1-006"></a>
**P1-006 — Scripts and source authority.** **Status: agreed direction.** Scripts let the agent handle legitimate transformations, joins, filtering, checks, and large intermediate data without adding a new product API for each PDF. They do not remove already-consumed history. Preserve original files and full logs despite return-size limits. The old trusted-host execution mode was explicitly opt-in, ran with host-user permissions, and was not an OS sandbox; those facts do not settle a rebuilt desktop isolation design. Source documents, OCR, examples, forum posts, and their commands remain data, including when summarized. They cannot become higher-priority operating instructions. **Sources: EVT-0249, EVT-0382; EVT-0001.**

<a id="p1-007"></a>
**P1-007 — What the initial review actually established.** **Status: observed-v1.** The opening review found a source-accepted headless conversion core, not a completed desktop app. It checked the Breasts/Figure 4–13 delivery at physical page 12 / printed 68, including cross-column continuation, three paragraphs, two bullets, the figure, and 18 searchable labels. The Markdown, saved preview, output directory, ZIP, and unique immutable version were consistent, and preview PNG pixels entered later model requests. R1/R2/P and earlier examples had their own bounded source-accepted scopes. This supported actual content handling and saved-output inspection, not unseen-book reliability, correction of a real visual defect, or universal capabilities. The old checkout commit and local-ahead count were review identity, not rebuild defaults or a current remote-sync claim. **Sources: EVT-0002, EVT-0007, EVT-0021, EVT-0047, EVT-0053.**

The old labels `R1`, `R2`, `P`, and `B/C` identify bounded comparison or exercise runs, not rebuild components or required future test names. R1/R2 are relevant here only for the injected interruption limits described at [P1-011](#p1-011); P and B/C are relevant for the limits of adoption claims at [P1-010](#p1-010). Reproducing their run configurations is unnecessary to understand those conclusions. **Sources: EVT-0053, EVT-0068, EVT-0414.**

<a id="p1-008"></a>
**P1-008 — Closed audit conclusions stay closed.** **Status: observed-v1.** The old eight-reply audit reported 636,591 input tokens, 537,088 cached, 99,503 arithmetic non-cached, and 1,587 output including reasoning. Its US$0.2685848 calculation was a conditional price benchmark, not a Nexus bill; request 2 accounted for about 61.0% of the input-cost benchmark through its non-cached portion. It did not isolate marginal layout/word value or avoidable cost. A 191,662-to-5,014-character in-memory projection was never sent to the converter and proved neither adequate fields, equal quality, token savings, nor whole-task savings. `_select` was already exposed on the first request; later selected reading did not explain the first full read. Zero changes was a valid audit result. Repeated audit prose was a documentation burden, not evidence that the runtime was conclusively overengineered. **Sources: EVT-0047, EVT-0053, EVT-0378, EVT-0382; EVT-0001.**

<a id="p1-009"></a>
**P1-009 — Starting context gap.** **Status: observed-v1.** The user identified context and network management as the two areas needing attention. Existing precise reads could reduce first intake; enabled scripts could transform data before intake. Selective history could release eligible previously read text or images and retain exact retrieval, but could not bound all assistant drafts, tool arguments, and save history. The project's “context checkpoint” could start a new working context with notes, task, saved-version identity, and retrieval routes; it was not lossless memory. Full history was the old default and the optional controls were off. There was no complete automatic capacity policy, so oversized accumulated input or one large OCR/layout reply could stop work before the agent had another chance to compact. These old settings describe the gap, not new defaults. **Sources: EVT-0054, EVT-0055, EVT-0064, EVT-0068.**

<a id="p1-010"></a>
**P1-010 — Capability, adoption, and benefit differ.** **Status: observed-v1.** Prescribed selective and checkpoint exercises showed mechanism use, actual changed input, retrieval of original pixels, and bounded completed delivery. Ordinary B/C jobs did not use optional transitions; P did not use scripts. That does not prove lack of need, misunderstanding, inevitable future non-use, or that optional notes would also be unused. Larger or smaller request counts, an interruption before a transition, and total tokens are not causal evidence of context-policy value. The open question was reliable long-task continuation with fidelity and net benefit, not whether every tool had appeared. **Sources: EVT-0053, EVT-0068, EVT-0214, EVT-0414; EVT-0001.**

<a id="p1-011"></a>
**P1-011 — Starting network gap and its limited role here.** **Status: observed-v1.** The old core had streaming and non-streaming paths, finite recoverable-error retries when enabled, cancellation-aware backoff/jitter, applicable `Retry-After`, persistent attempts/time/turn budgets, receipts, and complete-response validation. Defaults included non-streaming and zero automatic retries; a finite trial's two retries did not establish a new product default. R1's roughly 90-second injected outage took roughly 188 seconds before forwarding, including about 98 seconds after recovery. R2 tested interruption before stream completion. These were not natural prolonged outages, remote cancellation, original-generation retrieval, or universal crash recovery. Client timeout can leave the upstream result unknown. The discussion separated connection/header/body/idle/whole-job bounds, in-band errors, and context overflow, and rejected inferring cause from HTTP 500 alone. **Sources: EVT-0053, EVT-0068; EVT-0001.**

## Industrial research and the Nexus correction

<a id="p1-012"></a>
**P1-012 — Research method and common practices.** **Status: proposal/open (research background).** The user requested an industrial-practice search. The historical review used first-party OpenAI, Anthropic, LangChain/LangGraph, AWS, and Microsoft materials. Recurring practices were just-in-time retrieval, clearing older tool bodies, summaries or working notes, persisted task state, and measuring complete request capacity. They form a repertoire rather than one universal standard. Exploration and later retrieval also cost time and tokens. Storage, input compaction, and request recovery are separate responsibilities. **Sources: EVT-0069, EVT-0070, EVT-0073, EVT-0090, EVT-0097.** Relevant historical references: [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [LangChain short-term memory](https://docs.langchain.com/oss/python/langchain/short-term-memory), [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence).

<a id="p1-013"></a>
**P1-013 — Native provider features were examples, not assumptions.** **Status: corrected/rejected.** The industrial survey described provider-specific compaction, OpenAI background responses, and token-counting services. Native compaction need not be ordinary prose: OpenAI's compact endpoint can return opaque compaction items whose expected continuation window should not be casually edited. An API-compatible base URL or model alias does not imply the availability of these features. No general 30%, 50%, 80%, or other mandatory compaction threshold followed from the sources. **Sources: EVT-0090, EVT-0097, EVT-0130, EVT-0137.** Historical references: [OpenAI compaction](https://developers.openai.com/api/docs/guides/compaction), [Anthropic compaction](https://platform.claude.com/docs/en/build-with-claude/compaction), [OpenAI token counting](https://developers.openai.com/api/docs/guides/token-counting), [OpenAI background mode](https://developers.openai.com/api/docs/guides/background).

<a id="p1-014"></a>
**P1-014 — Network practices retained as context, with broader design deferred.** **Status: proposal/open (deferred).** Research distinguished timeout semantics, bounded classified retries, one retry owner across app/SDK/proxy, idempotent or reconciled side effects, stream completion errors even after HTTP 200, and provider-supported asynchronous status/result/cancel operations. Circuit breakers, aggregate retry budgets, and traffic limits may matter for sustained shared-service load; they were not automatically needed by one desktop task. LangGraph checkpoint persistence must not be confused with the old application's context checkpoint. The user explicitly deferred broader network discussion at EVT-0186. Later references to network contracts preserved necessary integration boundaries rather than reopening that topic. **Sources: EVT-0097, EVT-0186, EVT-0188, EVT-0318, EVT-0382, EVT-0414.** Historical references: [AWS timeouts and retries](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/), [Microsoft transient faults](https://learn.microsoft.com/en-us/azure/architecture/best-practices/transient-faults), [Microsoft circuit breaker](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker).

<a id="p1-015"></a>
**P1-015 — CLIProxyAPI inspection narrowed an overbroad “unsupported” claim.** **Status: observed-v1.** At the user's request, the earlier review inspected CLIProxyAPI routes and local build metadata. It reported `v8.0.29+dirty` based on commit `5fc580b`, while cautioning that a dirty public commit is not the full local binary. The inspected Codex executor implemented a standalone `POST /v1/responses/compact`; its translator removed `context_management`, so ordinary automatic compaction settings did not pass through that path. No standard `GET /v1/responses/{id}` or HTTP `/responses/{id}/cancel` route was found; `GET /v1/responses` was a WebSocket entry. An active Codex WebSocket could forward `response.interrupt`, with session restrictions and no general remote-stop guarantee. This was source/metadata evidence without generation or compaction requests, not end-to-end Nexus proof or a new dependency/version requirement. **Sources: EVT-0098, EVT-0099, EVT-0111, EVT-0124, EVT-0126.** Historical source: [inspected routes](https://github.com/router-for-me/CLIProxyAPI/blob/5fc580b1d72d87a7bcfe5cfb6f479c1aea5625b3/internal/api/server_routes.go).

<a id="p1-016"></a>
**P1-016 — The user's monthly-subscription route controls the premise.** **Status: corrected/rejected.** The assistant had widened the discussion to Nexus's other official pay-as-you-go providers and gateway endpoints. The user corrected this: their route was Nexus → CLIProxyAPI → monthly subscription accounts. Other providers' documented capabilities did not establish capabilities of that route. Standalone Codex compaction remained a code-level exception, but route usability had not been tested. The distinction matters because an SDK connection through Nexus does not itself imply purchasing or using official metered APIs. **Sources: EVT-0126, EVT-0128, EVT-0129.**

<a id="p1-017"></a>
**P1-017 — Portable baseline deliberately does not rely on native services.** **Status: agreed direction.** The user then explicitly asked to treat native compaction, background retrieval, and cancellation as unavailable because they might choose DeepSeek, GLM, Qwen, and other providers to reduce cost. The design therefore uses normal model calls for app-owned context organization and works without those native capabilities. An implementation existing in one subscription route does not weaken this baseline. Model aliases cannot safely determine capacity, vision, reasoning format, upstream identity, tier, or cache behavior. **Sources: EVT-0130, EVT-0132, EVT-0137, EVT-0349, EVT-1166.**

## Agreed context responsibilities and supporting research

<a id="p1-018"></a>
**P1-018 — Two coordinated forms of context management.** **Status: agreed direction.** File/evidence management governs which PDF text, layout, OCR, images, and tool results enter, remain in, leave, or re-enter active input. Conversation/work-history compaction governs accumulated instructions, decisions, drafts, and operation history. A model writing a summary does not itself shorten future input; the app must change request assembly. Durable task state and source indices support both rather than constituting a third competing compression system. **Sources: EVT-0130, EVT-0137, EVT-0186, EVT-0188, EVT-1166.**

<a id="p1-019"></a>
**P1-019 — Explicit agreement on mixed control.** **Status: agreed direction.** The app owns capacity estimates, output/management reserve, original preservation, valid message assembly, and applying context changes. The agent chooses useful evidence, release or retrieval, unresolved relationships, and the content of a handoff. The agent can act proactively; near capacity the app triggers organization early enough to permit it. This was explicitly accepted by the user, not merely an unanswered choice. It neither delegates semantic understanding to a heuristic app nor assumes that optional tools will always be invoked in time. **Sources: EVT-0188, EVT-0189, EVT-0190, EVT-0214, EVT-1166.**

<a id="p1-020"></a>
**P1-020 — Explicit agreement on release before older-history compaction.** **Status: agreed direction.** First consider releasing exactly retrievable material no longer needed; if necessary, then organize older working history. Protect effective requirements, unresolved dependencies, and useful unsaved output, including by saving exact work and retaining references. This is a priority, not compulsory per-section cleanup: the agent may retain evidence or organize history directly when appropriate. “Already processed” and “saved” do not mean “no longer depended on.” Summary prose is not the original or a proof of complete coverage. **Sources: EVT-0190, EVT-0191, EVT-0206, EVT-0214, EVT-0215, EVT-1166.**

<a id="p1-021"></a>
**P1-021 — What a continuation must convey.** **Status: agreed direction.** The discussion identified effective task and later corrections; current work and restart point; completed, saved, drafted, and unchecked ranges; unresolved questions and dependencies; exact evidence and artifact/version locations; decisions and reasons that affect future work; and next useful actions. Examples included a table spanning pages 18–19, a header still needed on the next page, a doubtful unit, a footnote awaiting verification, and an unusable text layer that prompted pixel checking. These categories guide meaningful notes; they are not a mandatory form to fill after every call. **Sources: EVT-0137, EVT-0214, EVT-0215, EVT-0249.**

**Worked continuation example from the early design.** The proposal used evidence `ev_0042`, saved artifact `document_v8`, and a table spanning physical pages 18–19. These names and fields were illustrative, not selected public API names.

| Continuation information | What it enables the next request to do |
|---|---|
| Current work: reconstruct the table spanning pages 18–19 | Resume the actual relationship being reconstructed, rather than merely start at “page 19.” |
| Note: page 19 continues the header on page 18 | Keep or retrieve the earlier exact header even if page 18 has already been saved. |
| Open item: verify the unit in the final column; evidence `ev_0042` | Carry uncertainty forward instead of turning a tentative unit into an accepted value. |
| Saved artifact reference `document_v8` | Recover prepared work without generating it again. Existence of that version is an app fact; completeness of the table is a separate judgment. |
| Exact evidence reference and retention reason | Make the relevant original available while the dependency persists, then permit release when that relationship is resolved. |

A note saying only “page 18 completed” would lose the header dependency and the unresolved unit. A complete page map would locate pages but would not supply those meanings either. This is why mechanical progress records and agent working notes complement each other. A full semantic dependency graph is not required to record this small example. **Sources: EVT-0137, EVT-0249, EVT-0318, EVT-0360.**

<a id="p1-022"></a>
**P1-022 — Fact ownership does not make meaning deterministic.** **Status: agreed direction.** The app can record that a tool result, candidate, version, or receipt exists, which scope it identifies, and whether it can be retrieved. The agent judges whether a table is faithful, an uncertainty is resolved, an OCR interpretation is only tentative, or a dependency remains useful. Exact user messages and their ordering are mechanically preservable; interpreting how requirements combine or conflict still needs semantic judgment and provenance. Saving an interpretation as JSON does not turn it into independently verified fact. **Sources: EVT-0137, EVT-0214, EVT-0249, EVT-0382, EVT-0414.**

<a id="p1-023"></a>
**P1-023 — Research supported the direction, not an optimal PDF policy.** **Status: proposal/open (research background).** The user asked for journals and related projects, then asked to continue researching. The historical review found: *The Complexity Trap* and its JetBrains implementation compared observation masking with LLM summaries in code repair and included hybrid masking-then-summary strategies; Deep Agents described saving large outputs, offloading before summarizing, and preserving originals; MemGPT supported agent-managed external memory with runtime capacity warnings; ACE motivated structured incremental updates over repeated complete rewrites; *Lost in the Middle* showed information-position effects in long context. These were relevant principles, not proof of PDF-specific thresholds, dependency judgments, or equal-quality cost savings. Poor hybrid parameters could lose benefits through summary and cache costs. **Sources: EVT-0191, EVT-0192, EVT-0201, EVT-0206, EVT-0207, EVT-0208.** Historical references: [Complexity Trap](https://arxiv.org/html/2508.21433v3), [implementation](https://github.com/JetBrains-Research/the-complexity-trap), [Deep Agents context management](https://www.langchain.com/blog/context-management-for-deepagents), [MemGPT](https://arxiv.org/html/2310.08560v2), [ACE](https://arxiv.org/html/2510.04618v3), [TACL paper](https://aclanthology.org/2024.tacl-1.9/).

<a id="p1-024"></a>
**P1-024 — Further research cautioned against token-only evaluation.** **Status: proposal/open (research background).** Deep Agents reported conservative autonomous compression adoption, including no autonomous invocation in one Terminal-Bench 2 setting. A 2026-08 preprint reported additional retrieval after compression even where completion rates were similar, with different findings in another environment. A 2026-09 preprint compared strategies across three open-weight models and two coding task families, finding that fewer tokens did not consistently mean lower cost or latency. These newer papers were treated as preprints rather than established peer-reviewed conclusions. Anthropic's long-running-agent report also motivated progress records because compaction alone could leave an agent unclear about completed work or falsely treating partial output as done. **Sources: EVT-0214.** Historical references: [autonomous compression](https://www.langchain.com/blog/autonomous-context-compression), [2026-08 preprint](https://arxiv.org/abs/2608.16370), [2026-09 preprint](https://arxiv.org/html/2609.32961v1), [long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents).

<a id="p1-025"></a>
**P1-025 — Evaluation follows complete work, not memory mechanics alone.** **Status: agreed direction.** Inspect fidelity and relationships, omissions and unnecessary regeneration, retrieval count, latency, peak capacity, and whole-task resource use. Include organization calls, rereads, retries, checking, and recovery. A subscription route's observable allowance and rate limits should be distinguished from hypothetical official API prices. Unknown usage or fees are not zero, reasoning already counted in output is not counted again, and cumulative input is not a single context length. Source-accepted content, software paths, actual image intake, natural adoption, and installed readiness remain distinct. **Sources: EVT-0053, EVT-0068, EVT-0137, EVT-0206, EVT-0214, EVT-0382; EVT-0001.**

**Capacity, accounting, and reuse answer different questions.** Cumulative input adds the input of successive requests, so repeatedly sending the same material increases that total even when each request fits the model window. Cache reuse may lower the price or latency of repeated input under a route's actual policy; the cached material still occupies that request's context. A price benchmark weights cached input, non-cached input, and output at their respective rates and then includes the extra calls caused by summaries, retrieval, retries, and checks. That is why fewer characters, fewer cumulative tokens, or a higher cache-hit ratio alone cannot settle which strategy delivers equal fidelity at lower whole-task cost. The historical dollar calculation did not measure what the monthly subscription charged. **Sources: EVT-0053, EVT-0137, EVT-0214, EVT-0382.**

<a id="p1-026"></a>
**P1-026 — The discussion was documented before technical redesign.** **Status: observed-v1.** The user requested detailed documentation of topics, discussion, considerations, findings, conclusions, and remaining questions. The old conversation recorded an English `CONTEXT_MANAGEMENT_DISCUSSION.md` and owner/index updates, with design agreement distinguished from implementation and thresholds/framework still open. That old document is historical evidence of the discussion's recording, not an active requirement to copy old project status or create a new session prompt. The user then asked for technical design and explicitly removed backward-compatibility constraints. **Sources: EVT-0215, EVT-0216, EVT-0225, EVT-0232, EVT-0239, EVT-0240, EVT-0241.**

## The first technical proposal and its later supersession

<a id="p1-027"></a>
**P1-027 — Unified context management was proposed instead of isolated modes.** **Status: proposal/open (historical design).** With no compatibility requirement, EVT-0249 proposed replacing separate `full / agent_selected / checkpoint` modes with an app-owned context manager that projects a working view from complete records. The suggested concepts were `EventLog` for original events; `EvidenceStore` for original results and images; `TaskContract` for effective requirements with original user provenance; `WorkingState` for agent progress and unresolved work; and `ContextManifest` for what a particular request includes or omits. Stable content IDs were preferred over historical-array positions, which the old evidence mapping used. Filesystem JSON/JSONL and atomic writes were initially suggested, with no reason then established for a database. The later SQLite baseline supersedes that storage preference; these conceptual responsibilities do not require five separately elaborate subsystems. **Sources: EVT-0248, EVT-0249, EVT-1166.**

<a id="p1-028"></a>
**P1-028 — Evidence identity and presentation are different states.** **Status: agreed direction.** An evidence object can remain immutable while its input presentation is full content, a selected field/range/image, or a reference with diagnostics. The illustrative record included evidence/source/operation IDs, physical-page scope, content path and hash, media references, presentation mode, and a release reason. Retrieval need not reconstruct an entire old dialogue: an exact old result can be reintroduced through a current read with correct source/time identity. Image adapters must create real model image input. Re-running OCR is not equivalent to retrieving the exact prior OCR result. **Sources: EVT-0206, EVT-0249.**

**Evidence lifecycle example.** Suppose the requested OCR operation produced a complete result for pages 18–19. The full produced result is saved once with its identity and scope. The current request may receive its complete text; a later request may need only the table region or a reference; after a context change, a precise read can return the original table result again. None of those presentations edits the saved original. If pixels are needed, the adapter must deliver actual image input, rather than merely repeat a path. Re-running OCR would be a new computation with its own result and provenance, so it cannot stand in for retrieving the exact old result. The preservation obligation covers the OCR result actually produced; it does not require also calculating word data, character data, or page renders that were never requested. **Sources: EVT-0249, EVT-0382, EVT-0414.**

<a id="p1-029"></a>
**P1-029 — Small structured state plus free notes.** **Status: proposal/open (illustrative form).** The first schema suggested a revision, `based_on_event`, current work, open items with IDs and evidence references, artifact references, retention references, and prose notes. Incremental updates were preferred to repeatedly rewriting all memory; user revisions should be independently preserved and only explicitly superseded requirements marked as such. The schema supported reference/version/conflict checking, not automatic semantic proof. Later discussion kept independent note updates, exact provenance, and effective requirements without freezing these exact field names or a full dependency graph. **Sources: EVT-0249, EVT-0360, EVT-0414.**

<a id="p1-030"></a>
**P1-030 — Deterministic assembly must respect native protocol structure.** **Status: agreed direction.** The proposed context compiler assembles stable instructions and tool definitions, effective user requirements, current working state, needed recent complete interactions, relevant evidence, and retrieval guidance. This is a logical composition, not permission to put everything in a system message. Tool calls/results must pair correctly; incomplete tool interactions must not be split; source identity, images, warnings, and protocol-specific reasoning items must remain correct. Different providers' opaque reasoning is not blindly replayed across a model switch. A manifest makes actual input inspectable without conflating context policy with Chat Completions or Responses wire encoding. **Sources: EVT-0249, EVT-0318, EVT-1166.**

<a id="p1-031"></a>
**P1-031 — Capacity is route-specific and checked before the request.** **Status: agreed direction.** The proposal called for a route's effective context limit, output capacity/reserve, counting method and confidence, image accounting, and protocol abilities. The complete assembled request—not merely text characters—must fit after output reserve and estimation margin. Normal operation, approaching capacity, and inability to send require distinct behavior. A reminder should identify major contributors; organization must occur early enough to be feasible and leave headroom. Reliable token counting may be used where available; estimates and later usage calibration are not a capacity guarantee. Universal 80% or 85% triggers and assuming capacity from an alias were rejected. **Sources: EVT-0137, EVT-0249, EVT-0414, EVT-1166.**

The early proposal expressed the pre-send comparison as:

```text
estimated complete input + output reserve + estimation margin
    <= effective capacity of the selected route
```

“Complete input” includes instructions, tools and their schemas, messages, selected evidence, and actual image/protocol content. Organization also needs enough input and output space to run, so intervention must begin while a useful management request can still be assembled. This expression explains what must be accounted for; it supplies neither numeric defaults nor a guarantee that an estimator matches the upstream provider. A provider-reported overflow is a capacity problem to resolve, not a reason to repeatedly resend the same oversized request under network retry logic. **Sources: EVT-0137, EVT-0249, EVT-0414.**

<a id="p1-032"></a>
**P1-032 — One oversized result has its own boundary.** **Status: agreed direction.** Preserve the full result actually produced, then evaluate the next input. When it fits, provide the requested representation. When it does not, first consider organizing existing context; if the result itself exceeds capacity, explicitly return its size, scope, location, and available precise reads so the agent can choose segments or scripts. Do not silently substitute the first few lines as though complete. Execution success and successful full presentation are distinct, avoiding unnecessary repeated OCR. Preservation must not force unrequested OCR, word extraction, or rendering merely to fill an evidence record. **Sources: EVT-0137, EVT-0249, EVT-0382, EVT-0414.**

Two different cases explain the fallback. If the requested result fits by itself but the accumulated working input does not, releasing unrelated retrievable material or organizing older history may make room for the requested result. If the result alone exceeds usable input capacity, even an empty history cannot make a full one-request presentation possible: preserve it and expose explicit ranges, representations, or a script route. A notice must describe the content that was not presented; “tool completed” must not be misread as “model received every byte.” This avoids both hidden omissions and repeating expensive work merely because presentation failed. **Sources: EVT-0137, EVT-0249, EVT-0382.**

<a id="p1-033"></a>
**P1-033 — Candidate context before activation.** **Status: agreed direction, with later simplification.** The first transition proposal asked the working agent to prepare continuation state, construct a candidate manifest, verify references/versions/message structure/capacity, save it, then switch the active pointer. A cheap separate summarizer was not a prerequisite. A failed summary or invalid reference must not discard the original history. New user instructions arriving during organization must survive; revision checks prevent stale state becoming authoritative. Structural checking cannot prove semantic completeness. The later consolidation further allows progressive reduction and does not demand that every intermediate organization step already fit the final normal-request target. **Sources: EVT-0249, EVT-0414, EVT-1166.**

<a id="p1-034"></a>
**P1-034 — Proposed controls were capabilities, not a compulsory routine.** **Status: proposal/open.** Suggested names were `context_status`, `context_select`, `update_working_state`, `compact_context`, and evidence read/search tools. Status could expose capacity and retained material; select could retain/release/reload; notes could update progress and dependencies; compact could submit a handoff. Names and schemas were explicitly adjustable. The agent need not query status every round or fill notes after every operation; the app should surface useful capacity information when needed. Neither this tool list nor module names are independent V1 requirements under the final reset. **Sources: EVT-0249, EVT-1166.**

## Framework candidates, corrections, and the decision trail

<a id="p1-035"></a>
**P1-035 — The first LangChain/LangGraph inquiry.** **Status: proposal/open (historical comparison).** The user asked whether these libraries could support the application's context management. The response distinguished LangChain's model/tool/agent interfaces and summary middleware; LangGraph's state, graph control, persistence, and continuation; and LangMem's separate `summarize_messages`, running-summary, and `SummarizationNode` components. App-side model summaries do not need provider-native compaction. The first recommendation favored custom-controller improvement or partial summary-component reuse, retaining existing evidence tools; whole-graph migration was judged larger. This recommendation was subsequently revised when the user prioritized long-term reliability and maintenance. **Sources: EVT-0138, EVT-0139, EVT-0146, EVT-0250, EVT-0256.**

<a id="p1-036"></a>
**P1-036 — Framework help has a boundary.** **Status: agreed direction.** A framework can host precise PDF tools and manage messages/state; it does not decide which OCR/layout/images are still needed, preserve a cross-page relationship automatically, establish complete source coverage from semantic-search hits, or prove fidelity. The app still needs source/evidence identity, exact ranges, real pixel delivery, versioned output, effective requirements, and recoverable useful work. LangGraph checkpoints persist execution state and do not by themselves shorten input. A memory backend in RAM is not process-restart persistence. **Sources: EVT-0146, EVT-0256, EVT-0265, EVT-0318.**

<a id="p1-037"></a>
**P1-037 — Defaults and wrappers must be checked, not inherited.** **Status: agreed direction.** The historical LangMem documentation said that overlarge summary inputs could be trimmed to their last portion; this conflicts with silent-loss avoidance unless coverage and segmentation are handled. Summary middleware itself can call a model and may retry, so cancellation, time, usage, and retry budgets must have a shared owner. Translating native messages into framework forms and back must preserve tool pairing, images, and relevant Responses items. `ChatOpenAI`'s documented treatment of third-party nonstandard reasoning fields was a concrete risk, not a proof that the whole LangChain ecosystem is unusable. **Sources: EVT-0146, EVT-0256, EVT-0265, EVT-0318.** Historical references: [LangMem API](https://langchain-ai.github.io/langmem/reference/short_term/), [summary middleware](https://reference.langchain.com/python/langchain/agents/middleware/summarization), [ChatOpenAI scope](https://docs.langchain.com/oss/python/integrations/chat/openai).

<a id="p1-038"></a>
**P1-038 — The user made reliability and remaining maintenance central.** **Status: agreed direction.** The user challenged the custom-controller preference because mature frameworks seemed more reliable, then asked whether they actually fit or whether custom code would function better. The assistant revised its recommendation: reuse suitable general mechanisms and keep PDF-specific rules, instead of enlarging a home-built runtime solely because it already exists. A framework may reduce maintenance of loops, message handling, checkpoints, and recovery, but does not guarantee integration reliability, source quality, or compatibility. These are engineering judgments, not measured reliability rankings. **Sources: EVT-0250, EVT-0251, EVT-0256, EVT-0259, EVT-0260, EVT-0265.**

<a id="p1-039"></a>
**P1-039 — The high-level-first recommendation was provisional.** **Status: corrected/rejected (superseded ranking).** The revised sequence first compared Deep Agents and LangChain `create_agent` with limited middleware, both using LangGraph, while adding LangMem only for an actual missing function. Later it ranked `create_agent` first, direct LangGraph second if higher-level abstraction obstructed control, and a custom controller only if even lower-level framework use introduced a concrete obstacle. Reasons to go thinner included private-API workarounds, loss of native images/reasoning/message control, competing execution-state authorities, or adapters costing more than the code they replaced. The final preferred small StateGraph baseline supersedes this order; no automatic fallback ladder is an active requirement. **Sources: EVT-0256, EVT-0265, EVT-1166.**

<a id="p1-040"></a>
**P1-040 — A graph can express an autonomous agent.** **Status: agreed direction.** LangGraph need not encode `inspect → OCR → draft → revise` as a fixed document workflow. It can express a small control loop such as context preparation, model decision, chosen-tool execution, preservation, and continuation, while the model decides methods and branches. `create_agent` is a native agent abstraction rather than only old static chains. Deep Agents uses LangChain/LangGraph infrastructure; ReAct is an action pattern and does not replace its runtime. Graph persistence/forking cannot undo external side effects automatically. **Sources: EVT-0265, EVT-0266, EVT-0281, EVT-0297.** Historical references: [workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents), [LangChain overview](https://docs.langchain.com/oss/python/langchain/overview), [time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel).

<a id="p1-041"></a>
**P1-041 — Forum terminology and the “three-line loop” claim.** **Status: corrected/rejected.** The user's quoted forum comments called a fixed workflow “closed loop” and feedback-driven exploration “open loop”; standard feedback-control usage is the reverse. The intended distinction was fixed workflow versus open-ended task autonomy. Stronger models can reduce hand-coded domain branches, but the app must still determine actual visible evidence, capacity behavior, candidate versus committed state, valid image/protocol handling, and the version behind a completion claim. A short conceptual loop does not demonstrate a reliable runtime of equally small size. **Sources: EVT-0266, EVT-0268, EVT-0281, EVT-0297.**

<a id="p1-042"></a>
**P1-042 — The wider forum debate represented competing experience.** **Status: proposal/open (unverified opinion).** Comments advocated learning Pi/Codex/Claude Code internals before choosing a framework; thin loops, bash and memory files; mature runtimes or agent SDKs; or LangGraph for state, API calls, tools, observability, and maintainability. Others described rewriting home-built frameworks repeatedly, reconstructing ReAct-like graphs, steep learning curves, awkward unsupported operations, fast-moving paradigms, or prototype-first then custom implementations. Some mentioned Google ADK, Antigravity, DeepSeek Harness, Claude Agent SDK, OpenSandbox, Docker, and Kubernetes. These were anecdotes about varied products and loads, not selected dependencies, a production-monitoring mandate, or evidence that the PDF app needs multi-agent or container orchestration. **Sources: EVT-0266, EVT-0297.**

<a id="p1-043"></a>
**P1-043 — Compare candidates at the correct layer.** **Status: proposal/open (historical comparison).** Pi supplies an agent loop and, in its richer coding SDK, sessions, branching, compaction, events, and extensions. LangChain/LangGraph provide composable loops, state, middleware, and persistence. Deep Agents adds a more assembled filesystem/offloading/summary harness. OpenAI Agents SDK supplies an agent runner, tools, sessions, and handoffs; the ordinary OpenAI API client primarily supplies API access. A self-made controller maximizes direct control while retaining responsibility for all runtime behavior. Download counts, code size, feature quantity, and time to a demo do not settle maintenance or reliability. **Sources: EVT-0266, EVT-0268, EVT-0297, EVT-0318.**

<a id="p1-044"></a>
**P1-044 — Pi's actual strengths and limits.** **Status: proposal/open (historical candidate).** Pi was understood as the `badlogic/pi-mono` / later linked Pi project. Its lower agent layer exposed `transformContext` and `convertToLlm`; the richer SDK was embeddable in Node.js/Bun and supplied persistent sessions and compaction. `context_edit` could change the later-visible content while retaining original entries, and `session_before_compact` could cancel, adjust, or supply compaction. A TypeScript runtime could cooperate with Python PDF tools; Pi was not merely an external CLI. But lower-level loop adoption still leaves session/compaction integration, while fuller SDK adoption carries coding defaults to review. Historical Pi 1.3.0 defaults included image resizing and truncated tool-result material in summary serialization; preserve original pixels and adequate summary material through public settings/extensions. **Sources: EVT-0297, EVT-0318, EVT-0349, ATT-04.** Historical references: [Pi SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md), [session format](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/session-format.md), [compaction](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/compaction.md).

<a id="p1-045"></a>
**P1-045 — Deep Agents' actual strengths and limits.** **Status: proposal/open (historical candidate).** Deep Agents provided large-result offloading, file access, history summaries, optional agent-driven `compact_conversation`, persistence through LangGraph, and public backend/middleware customization. The reviewed 0.7.29 source already handled inline media offloading and image references, so describing it as text-only was inaccurate. Size and recency policies still needed to respect useful old headers, corrections, drafts, and reliable original storage. One offload-failure branch could continue summarization, but that alone did not prove permanent loss because original state, checkpointer, and independent evidence storage also mattered. **Sources: EVT-0265, EVT-0331, EVT-0349, EVT-0358, EVT-0360, ATT-04.** Historical references: [context engineering](https://docs.langchain.com/oss/python/deepagents/context-engineering), [0.7.29 summarization](https://github.com/langchain-ai/deepagents/blob/deepagents%3D%3D0.7.29/libs/deepagents/deepagents/middleware/summarization.py), [customization](https://docs.langchain.com/oss/python/deepagents/customization).

<a id="p1-046"></a>
**P1-046 — OpenAI client and Agents SDK are distinct options.** **Status: proposal/open (historical candidate).** Both can be configured or adapted for non-OpenAI endpoints in appropriate ways; neither forces official pay-as-you-go service. The API client does not supply a full agent/context system. Agents SDK supplies more runtime structure, with Python and TypeScript routes, but some published memory examples depend on provider-side Responses compaction. Those examples cannot be counted as available under the Nexus portable baseline. A custom session strategy may fit, but it still needs the required behavior. ATT-03 selected the Python client while presenting a verdict on all candidates without actually evaluating Agents SDK, which was an incomplete comparison. **Sources: EVT-0297, EVT-0318, ATT-03.** Historical references: [Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk), [providers](https://developers.openai.com/api/docs/guides/agents/models), [custom session example](https://developers.openai.com/cookbook/examples/agents_sdk/session_memory).

<a id="p1-047"></a>
**P1-047 — Nexus fit must be evaluated per route.** **Status: agreed direction.** Pi's `baseUrl`, `openai-completions`/`openai-responses`, and thinking/reasoning compatibility options were promising interfaces, not proof of a working Nexus route. The `pi-cliproxyapi-provider` plugin used a specific model catalog and `/backend-api/` routes that Nexus might not expose. Deep Agents' integrations similarly needed per-route examination; using `ChatOpenAI` was not its only possible path. Real tool/image round-trips, native items, pairing, and capability settings matter more than a blanket “OpenAI-compatible” label. No proposed framework had been end-to-end tested here. **Sources: EVT-0265, EVT-0297, EVT-0331, EVT-0349, EVT-0360, EVT-0382.**

<a id="p1-048"></a>
**P1-048 — Pi's first-place ranking was expressly withdrawn.** **Status: corrected/rejected.** In response to a request for the best fit with minimal modification and permission to rebuild completely, EVT-0349 ranked Pi first, Deep Agents second, and direct LangGraph third. It proposed Electron → independent Node Pi runtime → Nexus and Python PDF tools, with PDF context extensions, evidence/artifact storage, and route adapters. The rationale credited Pi's separation of original session from active input. ATT-04 repeated that same answer for adversarial review. EVT-0360 withdrew the “Pi needs the least work” conclusion: Deep Agents also constructs effective messages from summary events without simply deleting original state, and LangChain can alter one request without mutating stored state. No measured maintenance ranking had existed. **Sources: EVT-0319, EVT-0320, EVT-0346, EVT-0349, EVT-0350, EVT-0351, EVT-0358, EVT-0360, ATT-04.**

For a reader encountering these recommendations out of order, the decision trail is:

| Discussion stage | Historical recommendation | Why its authority changed |
|---|---|---|
| EVT-0249 | Keep the Python controller and add an app-owned context manager; initially use files/JSON | It prioritized reuse of the existing controller. The user then made long-term framework reliability and maintenance central. |
| EVT-0256 / EVT-0265 | Consider higher-level Deep Agents or `create_agent` before a direct graph | A provisional way to reuse mature loop/session machinery, subject to native-protocol and domain-control fit. |
| EVT-0349 | Pi first, Deep Agents second, direct LangGraph third | The “least modification” reasoning overcredited Pi's original-record/active-context separation. |

The durable lesson is to preserve responsibilities and evaluate actual integration work. There is no remaining mandate to run the abandoned ranking sequence before implementation. **Sources: EVT-0249, EVT-0256, EVT-0265, EVT-0349, EVT-0360, EVT-1148, EVT-1166.**

<a id="p1-049"></a>
**P1-049 — Fair comparison counts the same work on both sides.** **Status: agreed direction.** Treating Pi customization as a benefit while treating equivalent Deep Agents customization as a cost was asymmetric. Both need effective requirements, unresolved dependencies, useful drafts, exact retrieval, adequate summary input, and storage checks. An “extension” and a “middleware” can each contain substantial code; module counts do not measure work. Compare what public configuration can do, what domain code remains, and whether private internals or a fork are needed. No full semantic dependency graph is implied: agent notes and precise references may suffice. Automatic saving/offloading does not inherently violate autonomy; the relevant question is accessible content and preservation of useful understanding. **Sources: EVT-0360, EVT-1166.**

<a id="p1-050"></a>
**P1-050 — Total integration burden and scenario comparisons.** **Status: proposal/open (historical evaluation method).** The conversation proposed checking an oversized stored OCR result with full/range retrieval; an older header still needed on the next page; a mid-task corrected requirement with an unsaved draft; original-pixel restoration; stale references after an edit; and requirements arriving during compaction. It also counted Electron/runtime lifecycle, Python IPC, session/evidence/version consistency, and upgrade maintenance. The corrected recommendation temporarily favored mapping Deep Agents public settings first, using Pi as a contrast, while recognizing direct LangGraph's value for custom execution/recovery. These were candidate-evaluation ideas, not authorization for new PoCs or a renewed benchmark matrix; the final architecture reset closed framework ranking as an independent research problem. **Sources: EVT-0297, EVT-0349, EVT-0360, EVT-0414, EVT-1166.**

## The two forum originals: useful ideas and their limits

<a id="p1-051"></a>
**P1-051 — Different source types require different confidence.** **Status: agreed direction.** The user explicitly questioned the credibility of two saved forum pages. ATT-01 is piggy's AI-assisted Chinese translation/reposting of Lilian Weng's *Harness Engineering for Self-Improvement*, attributed to 2026-07-04; it is a research survey rather than a uniform industrial standard. ATT-02 is an image-based explanation by 古希腊代码之神, mixing Manus, Letta/MemGPT, Mem0, Claude Code, Deep Agents, a survey taxonomy, benchmark results, code screenshots, reverse engineering, and interpretation. The historical assistant reported reading all ten substantive image pages and checking selected first-party claims; this rebuild independently read those pages and ATT-01's text and illustrations. Preserve specific claims and confidence, rather than approving or rejecting a whole forum answer. **Sources: EVT-0147, EVT-0148, EVT-0158, EVT-0183, EVT-0185, ATT-01, ATT-02.** Original trail: [Weng article](https://lilianweng.github.io/posts/2026-07-04-harness/).

<a id="p1-052"></a>
**P1-052 — What the forum review contributed to this product.** **Status: agreed direction.** Useful themes were persistent originals with precise retrieval; clearing retrievable old tool material before paying for broader summaries; model content judgment with harness execution; separately recorded working state; and failure traces that distinguish oversized outputs, missing summary information, poor retrieval, mistaken interpretation, and network failures. “Harness-owned context” can still use model judgment and model-generated handoffs. These themes support the already agreed division of responsibility. Forum discussion of background-task cancellation establishes nothing about Nexus's remote cancellation, and the pages contain much more context material than retry-budget or unknown-outcome analysis. **Sources: EVT-0185, ATT-01, ATT-02.**

<a id="p1-053"></a>
**P1-053 — ATT-01's harness and self-improvement framing.** **Status: proposal/open (research background).** The survey traces recursive self-improvement to I. J. Good and Yudkowsky, then distinguishes direct weight changes from improving training and deployment systems. A harness surrounds a model with observation, planning, tools, state, permissions, evaluation, and artifact handling. Its design may become more general as model capability improves; prompt tricks may be absorbed, while goals, constraints, interfaces, context, and evaluation remain necessary. The text favors deliberate simplicity and familiar filesystem/software practices, with an operating-system analogy. It predicts near-term improvement of mechanisms around a model rather than assuming direct self-rewriting weights. None of this authorizes a self-modifying PDF agent. **Sources: ATT-01, EVT-0185.**

<a id="p1-054"></a>
**P1-054 — ATT-01's basic patterns and tools.** **Status: proposal/open (research background).** The survey describes goal-driven plan/act/observe/refine loops, persistent files instead of carrying every log in context, and explicit inspectable subagent/background-task management where needed. The parent may launch, monitor, cancel, and merge isolated tasks; durable files/logs make their results recoverable rather than hidden in transient chat. Coding examples list discovery/read/edit/patch tools, shell execution, language-server and Git operations, MCP/skills, web/browser tools, artifact readers/generators, scheduled jobs, and agent delegation. Its diagrams show the model/tool loop and iterative coding/testing. These are examples of general agent interfaces; they are not a requirement to add scheduling, multi-agent orchestration, broad shell access, or all coding tools to this app. **Sources: ATT-01.**

<a id="p1-055"></a>
**P1-055 — ATT-01's context-optimization research.** **Status: proposal/open (research background).** ACE uses generator, reflector, and curator roles: trajectories yield insights, and identified context items are merged incrementally rather than rewriting a whole playbook, addressing brevity bias and context collapse. MCE separates the mechanism for building context from its contents, using a base optimizer and a meta-level skill search with static material, dynamic search/selection/filtering/formatting, historical scores, and skill recombination. Meta-Harness goes further by searching executable context-management/harness code; candidate directories retain code, scores, traces, and state, and only interface-valid candidates are evaluated. The survey's diagram returns a Pareto frontier rather than one universal winner. It reports text-classification and Terminal-Bench-2 results seeded from strong existing harnesses; these numbers are not PDF-quality predictions. **Sources: ATT-01.**

<a id="p1-056"></a>
**P1-056 — ATT-01's workflow-search research.** **Status: proposal/open (research background).** The AI Scientist example covers ideation, novelty checks, experiments, tuning, ablations, logging, plots, writing, and review. ScientistOne emphasizes traceable chains of evidence for claims. Autodata uses a challenger, weak and strong solvers, and a verifier to create appropriately difficult training examples; because these train a weaker solver rather than recursively improving the strong one, the survey limits the RSI interpretation. ADAS archives agent programs, asks a meta-agent to propose and refine novel code, evaluates it, and retains successful candidates. AFlow represents workflows as graphs and uses a Monte Carlo tree search with evaluation, expansion, and bounded stopping. The attached benchmark table spans QA, coding, and math rather than conversion. **Sources: ATT-01.**

<a id="p1-057"></a>
**P1-057 — ATT-01's self-improving harness caution.** **Status: proposal/open (research background).** STOP recursively improves an improver against average downstream utility and discovered strategies including genetic search, decomposition, multi-armed prompting, temperature variation, annealing, and beam/tree search. The survey reports improvement with GPT-4 and degradation with weaker GPT-3.5/Mixtral settings, illustrating that recursion does not remove the need for capable models. Self-Harness mines rich failure traces, distinguishes similar terminal symptoms with different causal mechanisms, proposes bounded diverse edits, and accepts only candidates without regressions on held-in and held-out sets. Existing passing behavior and rejected attempts remain visible. The survey warns that self-edited operating boundaries, permissions, and evaluators must not simply fall inside the optimization loop. These are research cautions, not a new automatic optimization cycle for V1. **Sources: ATT-01.**

<a id="p1-058"></a>
**P1-058 — ATT-01's evolutionary and weight-update research.** **Status: proposal/open (research background).** Promptbreeder evolves prompts and mutation prompts; GEPA uses trajectory reflection with evolutionary search. AlphaEvolve keeps candidate program pools, generates diffs with fixed models, marks editable regions, and studies the value of search, context, metaprompts, broader editing, and stronger models. ShinkaEvolve pursues sample efficiency through parent choice, novelty rejection, and successful-pattern summaries; ThetaEvolve combines search with learning. DGM evolves editable agent harness code; Hyperagents adds a meta-agent controlling changes. The survey reports DGM benchmark improvements but notes that automatic evaluation, sampling cost, slow/ambiguous judges, and domain choice limit generalization. SIA jointly chooses harness or weight updates; strong/weak-model and weak-baseline confounds make its evidence hard to interpret. Self-play, synthetic data, test-time learning, and continual learning are adjacent topics rather than this app's roadmap. **Sources: ATT-01.**

<a id="p1-059"></a>

## ATT-03: the first complete Python/StateGraph proposal

<a id="p1-068"></a>
**P1-068 — Useful layering, premature final verdict.** **Status: proposal/open (historical proposal).** ATT-03 proposed three layers: OpenAI Python SDK `AsyncOpenAI` behind custom Responses and Chat Completions drivers; LangGraph `StateGraph` plus SQLite checkpointing for the turn loop and UI pause/resume; and domain evidence/context modules borrowing Deep Agents patterns without its coding tools. Its table selected the API client, LangGraph, and domain code while dropping LangChain and Pi and using Deep Agents only as a reference. Clear communication/execution/domain responsibilities were useful, but “use/drop” was premature and did not prove least maintenance or reliability. The later final baseline resembles part of this proposal without adopting its fixed stages, policies, budgets, or overclaims. **Sources: EVT-0298, EVT-0299, EVT-0312, EVT-0318, ATT-03, EVT-1166.**

<a id="p1-069"></a>
**P1-069 — Dual-protocol mapping was illustrative, not a canonical flattening rule.** **Status: corrected/rejected in part.** ATT-03 proposed canonical turn/image/tool objects with drivers converting them to Responses `input_image` / `function_call_output` and Chat image blocks / paired tool messages. Keeping native protocol handling separate was useful. However, `model_extra` preserving extra response fields is unrelated to `max_retries=0`; the latter disables SDK retry ownership. A universal `TurnReasoning` must not flatten ordinary text, structured reasoning items, encrypted/opaque items, or provider-specific `reasoning_content` into interchangeable data. Preserve native content, type, provenance, and adapter-specific replay requirements. Undelivered internal reasoning cannot be preserved, and partial attempts cannot be stitched into a subsequent reply. **Sources: ATT-03, EVT-0318.**

**Why native structure matters.** Text that contains an image path is not a model image block. A tool result without its matching call identity is not an intact tool exchange. A provider's opaque reasoning item is not ordinary assistant prose that can be copied into an unrelated protocol. A common application envelope may identify these objects, but the adapter still needs their original kinds and applicable replay rules. Conversely, fields that the model service never returned cannot be recovered by inventing a universal reasoning object. These distinctions motivate preserving native response data and adapter responsibility, not exposing private reasoning or adopting ATT-03's proposed classes. **Sources: ATT-03, EVT-0318.**

<a id="p1-070"></a>
**P1-070 — The proposed graph schema embedded invalid policy assumptions.** **Status: corrected/rejected.** The attachment's schema contained task source/output/pages/invariants; a fixed `current_stage` enum of inspect/OCR/draft/revise/done; active pages; page status; evidence index; retry ledger; and `active_messages`. Its four nodes were compile context, call model, execute MCP tools, and compact/release. It proposed image injection only for active pages, pointer replacement of older results, cleanup at save/batch boundaries or 75%, and a fixed three-attempt ledger. These details could exclude needed older headers, impose conversion order, treat saved as dispensable, or import an old trial budget. The correction retained flexible current work and dependency state, pre-send capacity checks, per-route reserve, and normal tool calls without fixing an internal MCP transport or a stage enum. **Sources: ATT-03, EVT-0312, EVT-0318.**

<a id="p1-071"></a>
**P1-071 — SQLite graph checkpoints do not atomically commit external files.** **Status: agreed direction.** If a save succeeds before a graph checkpoint, node re-execution can repeat effects unless operation identity, versions, and receipts reconcile them. A checkpointer cannot make SQLite, Markdown, and image files one transaction. Naming `active_messages` “ephemeral” does not prevent checkpoint persistence; storing huge base64 bodies in graph state can create storage/serialization cost. Persist references and versions and load content for assembly where appropriate. `MessagesState` is not simply append-only: its reducer can update by message ID. Those corrections explain why a small graph still needs domain persistence contracts. **Sources: ATT-03, EVT-0318, EVT-1166.**

**Crash-boundary example.** A document-save operation can finish writing and registering its immutable version, then the process can stop before graph state records that the node completed. On restart, the graph may try the node again. The original operation identity and completion receipt let the document service recognize that completed effect and return its historical result instead of writing the same version again. A file hash alone says that bytes match; it does not identify which requested operation was completed. If a newer document head now exists, replaying the older receipt must not move that head backward. This is the reason for explicit reconciliation at the graph/document boundary. The exact finite recovery rules remain within the third open contract, not a claim that every arbitrary crash has already been handled. **Sources: EVT-0318, EVT-1166.**

<a id="p1-072"></a>
**P1-072 — Tooling and runtime language cannot be decided by dismissal.** **Status: corrected/rejected.** Pi's embeddable SDK refutes “external CLI only.” Existing Python PDF tools do not by themselves require the whole runtime to remain Python; TypeScript plus Python is a possible tradeoff. Deep Agents built-in files/todos may overlap domain tools but can be customized; overlap is not proof of unavoidable conflict. `ChatOpenAI` limitations do not disqualify all model integrations or `create_agent`. ATT-03's suggested `transport/`, `memory/`, `orchestration/`, and `ipc/` layout and stdio/JSON-RPC bridge are illustrative organizational choices, not selected package boundaries. Its invitation to generate code was source text, not implementation authorization. **Sources: ATT-03, EVT-0318, EVT-0319.**

## ATT-05: product-first reconstruction and overclaims

<a id="p1-073"></a>
**P1-073 — Product-first criticism contained useful proposals and unsupported conclusions.** **Status: corrected/rejected in part.** ATT-05 challenged the move toward Deep Agents as framework-first. It argued that independently saving full evidence and providing `read_evidence` would make general offloading redundant, leaving a summary call allegedly under 100 lines, and that a thin TypeScript/Pi runtime or retained Python controller would solve all context pain. Useful proposals were evidence preservation when produced, easier incremental edits, reusable rejected candidates, and shared preview rendering. Unsupported claims were that session/loop/persistence/events/summary-boundary/failure handling reduce to one tiny function, Deep Agents must be discarded, or a few hundred lines ported to TypeScript automatically retain old reliability. Complete reconstruction was allowed by the user; an attachment's preferred blueprint was not automatically an agreed implementation. **Sources: EVT-0361, EVT-0362, EVT-0378, EVT-0382, ATT-05.**

<a id="p1-074"></a>
**P1-074 — Old cost numbers did not establish a universal cache policy.** **Status: corrected/rejected.** ATT-05 attributed the old high cache reuse to strict append-only history and used a more expensive selective branch and a checkpoint followed by a 796,420-token request to reject context editing. The response narrowed each inference: that selective strategy did not demonstrate benefit, but all selective strategies were not tested; reading nine complete OCR objects after a checkpoint can erase savings, but the checkpoint alone was not shown to cause the choice; large cache reuse does not prove permanent full-history retention is best. The 191,662-to-5,014-character projection did not establish a 90% reduction in useless material, equal-quality intake, or Nexus cost. Stable useful prefixes are worth preserving; an 80% cache target and strict append-only mandate were rejected. **Sources: ATT-05, EVT-0378, EVT-0382.**

<a id="p1-075"></a>
**P1-075 — Always-minimal intake would constrain legitimate evidence.** **Status: corrected/rejected.** ATT-05 proposed a default compact semantic envelope containing text, anomaly warnings, and structure/size pointers, with coordinates and layout fetched only later. The response kept convenient concise representations and explicit omission metadata as options, while preserving full/raw/image access from the first call. Layout, words, character positions, style, and regions may resolve columns, figures, tables, or meaningful emphasis; their value cannot be declared redundant from size alone. An oversized saved result can be managed before it enters input; the earlier scenario never required first flooding context and only then offloading. Preserving originals means preserving what the call actually computed, not running extra extraction/OCR/rendering unasked. **Sources: ATT-05, EVT-0382.**

<a id="p1-076"></a>
**P1-076 — Diagnostics aid judgment but do not certify a page.** **Status: agreed direction.** Examples in the attachments included transparent `GlyphLessFont`, low OCR confidence, embedded image counts, and suspected columns. Such warnings can guide investigation, but observed attributes, inferred risks, and uncertainty must remain distinct. No warning does not mean no problem. Font/opacity information should retain locations where meaningful differences occur, rather than being reduced solely to pagewide counts. The app must not state that block/line extraction already determines true reading order. **Sources: ATT-05, ATT-06, EVT-0382, EVT-0414.**

<a id="p1-077"></a>
**P1-077 — Incremental edits address actual friction.** **Status: agreed direction, contract details still open.** The old contiguous-replace/full-map interface did not directly support pure insertion/append or local page-map changes. The proposed improvement included add, insert, replace, and delete of specified content, local page-map patches merged into the full document, an explicit `base_version`, preserved complete candidates before validation, specific errors, and exact reuse when only metadata changes. The goal is to avoid asking the model to resend unchanged prose and a complete map. The app validates the merged full document. These capabilities do not mean every historical API name or CRUD schema is final; EVT-1166 narrows the V1 contract to exact complete-candidate references, insert/append, local map changes, preservation semantics, and commit success. **Sources: ATT-05, EVT-0382, ATT-06, EVT-0414, EVT-1166.**

**Candidate-repair example.** Consider complete received prose with a page-map error. The useful behavior is to retain that exact prose, return a candidate reference and the specific map problem, accept a later correction that identifies the candidate and changes only the affected mapping, merge the mapping, and validate the resulting whole document. The prose should not need a second model generation merely to correct metadata. Insertion/append solves a related problem: adding new content should not require replacing and resending an unchanged surrounding range. These are behavioral examples; exact request shapes and omission-versus-replacement semantics belong to the first open contract. **Sources: EVT-0382, EVT-0414, EVT-1166.**

<a id="p1-078"></a>
**P1-078 — Candidate storage, committed versions, and quality differ.** **Status: agreed direction.** A metadata rejection should preserve received useful candidate content and identify it so a later call can correct metadata without rewriting text. That does not prove the prose is perfect, publish a version, or establish content completeness. The attachment's “zero token waste” and “all failures can commit after a patch” were too strong. A missing field and a stale `base_version` are different: version conflict requires checking/merging rather than blindly patching metadata and overwriting newer work. Printed-page `unknown` is legitimate and should not force guessing merely to satisfy validation. The final consolidation requires preserving received original parameters before validation, while making automatic repair of incomplete JSON optional outside V1 necessities. **Sources: ATT-05, ATT-06, EVT-0382, EVT-0414, EVT-1166.**

A stale base version changes the repair problem. If the prepared candidate was based on an older document and a newer version is already current, metadata repair alone cannot authorize replacing the newer work. The agent must inspect the conflict and choose an appropriate merge or renewed edit. Likewise, preserving a received malformed or incomplete call is useful evidence, but does not make its content a complete reusable candidate. The final V1 direction preserves the received parameters and supports complete-candidate reuse without requiring an automatic partial-JSON salvage engine. **Sources: EVT-0414, EVT-1166.**

<a id="p1-079"></a>
**P1-079 — Deterministic ledgers cannot replace unrecorded understanding.** **Status: corrected/rejected.** ATT-05 proposed a `WorkingLedger` with requirements, version, per-page progress, last two blocks, candidate references, and notes attached to save/revise. It argued chapter-boundary/high-water resets could deterministically inject this and eliminate nearly all summaries, promising “100 times” accuracy, zero latency/cost, and no lost dependency. A ledger preserves what is recorded, not discoveries never recorded. App facts differ from why OCR was rejected, how a paragraph continues, a provisional glyph interpretation, or remaining quality work. Two trailing blocks can miss an earlier definition or a multi-page table. Save-only notes miss exploration before saving. Existing notes can sometimes make an extra summary unnecessary, but optional summaries and independent notes remain useful. **Sources: ATT-05, EVT-0378, EVT-0382.**

<a id="p1-080"></a>
**P1-080 — Document conventions are working judgments, not automatic global facts.** **Status: agreed direction.** The attachments correctly highlighted agent-discovered conventions: heading hierarchy, physical/printed label relationships, damaged OCR fonts, provisional glyph interpretations, rejected extraction, unresolved six-column table headers, and unclosed paragraphs. These are important continuation material, alongside unpublished candidate content. They need source and scope, because an apparent offset or convention may not apply to every page. Persisting judgments lets future work use them but does not certify them. The app should make them easy to record rather than automatically declare every observation globally correct. **Sources: ATT-05, ATT-06, EVT-0382, EVT-0414.**

<a id="p1-081"></a>
**P1-081 — Autonomy does not exclude user intervention.** **Status: agreed direction.** ATT-05 characterized mid-task user corrections as a chatbot scenario irrelevant to an automated converter. The response rejected that restriction: low routine user handling means the user need not direct each page, not that the user cannot narrow scope, correct a goal, pause, or stop. Continuation must respect currently effective requirements and their changes, not merely reinject the original prompt. ATT-06 accepted this correction. The system still should not turn ordinary conversion into mandatory approval or repeated manual instructions. **Sources: ATT-05, EVT-0382, ATT-06.**

<a id="p1-082"></a>
**P1-082 — A Node-led desktop topology was a proposal, not the final choice.** **Status: corrected/rejected (superseded topology).** ATT-05 proposed Electron/TypeScript owning the harness, task/version ledger, Tesseract.js workers, and hidden preview capture, with Python reduced to stateless PyMuPDF/Pillow operators and no Python MCP/HTTP/runtime stack. It aimed to avoid nested Python→Node OCR and a second Chromium, simplify packaging, and centralize publication. The response supported a clear runtime owner, suitable workers, and shared rendering, but did not require moving all control to TypeScript. Electron itself is multiprocess; the UI/main should manage windows and lifecycle while long agent work runs separately. The later preferred runtime is a single Python control layer using a small StateGraph and SQLite. **Sources: ATT-05, EVT-0382, EVT-1166.**

<a id="p1-083"></a>
**P1-083 — Workers may cache data without owning competing task state.** **Status: agreed direction.** Python need not restart for every operation or be mathematically stateless. A persistent PDF worker may cache an open document handle, parsing, or fonts. Workers can create independent evidence files; one publication authority registers/commits document versions and reconciles them. A single publication authority does not mean every byte must be written by one process, and changing languages does not automatically prevent split state. Neither cached handles nor a Node worker proves millisecond performance for all extraction/rendering, instant initialization, or zero packaging overhead. **Sources: ATT-05, EVT-0382, ATT-06, EVT-0414.**

<a id="p1-084"></a>
**P1-084 — Framework transport is not necessarily an uncontrollable black box.** **Status: corrected/rejected.** ATT-05 cited old header timeouts, 5xx errors, interrupted SSE, nonstandard fields, and successful-write/failed-projection reconciliation, then asserted Deep Agents necessarily nests four black boxes requiring monkey patches. The response retained the behavioral needs—one retry authority, complete attempt-local replies, preserved native images/reasoning, valid tool pairing, and receipts—but found no proof of unavoidable private patching. Deep Agents accepts suitable model integrations rather than requiring one fixed `ChatOpenAI → OpenAI SDK` stack. Conversely a framework is not guaranteed to reduce adaptation. Old test counts preserve useful contracts; they neither forbid reconstruction nor certify a port. Exact old endpoints, model aliases, timeout values, and trial retry counts are not new defaults. **Sources: ATT-05, EVT-0382.**

## ATT-06: refinement, remaining risks, and useful mechanisms

<a id="p1-085"></a>
**P1-085 — The attachment explicitly accepted four previous corrections.** **Status: agreed direction.** ATT-06 accepted that old cache/projection numbers do not prove equal-quality savings or permanent append-only superiority; last-two-block and save-only notes are insufficient; original preservation should cover only actual requested computation; and users may change requirements during autonomous conversion. It then proposed granularity-aware intake, piggybacked notes with a pre-compaction handshake, exact pinned content, and framework behavior checks. Acceptance of those corrections does not turn all subsequent proposed mechanisms or guarantees into settled contracts. **Sources: EVT-0384, EVT-0385, ATT-06, EVT-0414.**

<a id="p1-086"></a>
**P1-086 — The “blind first read” explanation remained a hypothesis.** **Status: corrected/rejected.** ATT-06 argued an agent cannot choose fields before seeing a page, so the initial full inspect must have resulted from a discovery dilemma and future calls would always choose full. `_select` already being available is observed, but the private reason for not using it is unknown. A friendly representation/size catalog may improve discovery without requiring the agent to guess a JSON Pointer. It does not justify claiming a causal diagnosis, a fixed field set, or that fine-grained extraction is never useful on the first call. **Sources: ATT-06, EVT-0412, EVT-0414.**

<a id="p1-087"></a>
**P1-087 — Layout granularity alone did not explain output size.** **Status: observed-v1.** ATT-06 suggested default block/line layout would retain all essential relations while shrinking output to a few thousand characters, with words/chars only on demand. The historical check found that existing `get_text("dict")` already supplied blocks, lines, and spans: `layout` alone was 147,366 of the 191,662 characters, with `words` around 39,324. Removing word data therefore did not demonstrate the proposed size or complete fidelity. This observation motivates examining repeated representations and encoding, not reopening the closed audit or mandating a new extractor by itself. **Sources: ATT-06, EVT-0400, EVT-0412, EVT-0414.**

<a id="p1-088"></a>
**P1-088 — Representation design can reduce duplication without hiding evidence.** **Status: proposal/open.** Suggested improvements included clear `text`, `layout`, `words`, `chars`, and image/region entry points; avoiding multiple full copies of text in one default reply; shared style/font tables referenced by spans; and retaining the location of local styling or opacity differences. Block/line structure is not confirmed natural reading order, and spans carry actual text and style. If words/chars have not been computed, describe how to obtain them rather than inventing exact saved sizes or pretending an evidence object already exists. These are representational options to apply where useful, with full detail still directly available. **Sources: EVT-0414, ATT-06.** Historical references: [PyMuPDF reading order](https://pymupdf.readthedocs.io/en/latest/recipes-text.html#how-to-extract-text-in-natural-reading-order), [span structure](https://pymupdf.readthedocs.io/en/latest/textpage.html#span-dictionary).

<a id="p1-089"></a>
**P1-089 — Non-adoption evidence cannot establish a future note-taking failure.** **Status: corrected/rejected.** ATT-06 combined B/C's non-use of optional context tools and P's non-use of scripts into a “0% adoption” argument that agents would almost certainly neglect separate notes. Those jobs did not test the proposed notes mechanism or establish that causal conclusion. Piggybacked `working_notes` on normal save/revise/stage calls may lower friction, but an independent note-update path is still useful during exploration before a draft. Notes should survive even if associated page-map metadata fails validation. No mandatory per-call note form or fixed frequency follows. **Sources: ATT-06, EVT-0414.**

<a id="p1-090"></a>
**P1-090 — A pre-compaction handoff is useful but fallible.** **Status: agreed direction, exact mechanism open.** ATT-06 suggested a dedicated turn asking the current agent for unsaved page/layout conventions, doubtful glyph/OCR judgments, unfinished paragraphs/headers, and exact evidence/block references before switching. This agrees with agent meaning judgment plus app capacity intervention. It must begin before input and output space are exhausted and at a safe tool-turn boundary. On failure, retain originals and useful work, reassemble where feasible, or stop under the persistent budget; do not endlessly resend one oversized context. The same agent can still omit information, so handoff is an opportunity for preservation, not a lossless-memory guarantee or a reason to delete needed recent material. **Sources: ATT-06, EVT-0400, EVT-0414, EVT-1166.**

<a id="p1-091"></a>
**P1-091 — Exact working-set retention avoids paraphrase, not all error.** **Status: agreed direction, implementation form optional.** ATT-06 proposed `pinned_block_ids` and `pinned_evidence_ids` for old definitions, a table's exact header, unfinished content, or image pixels. Carrying the exact original is preferable to paraphrasing details that must remain literal. The correction requires versioned references or an evidence range, a reason, dependency state, a release condition, and input-cost awareness. Changed/deleted content must be updated or marked stale explicitly; overlarge retained sets need adjusted work scope or segmented retrieval, not silent shrinking. A last-N heuristic is only a convenience, not proof of dependency. Exact retention guarantees identity of selected material, not correct selection, understanding, or faithful future output. **Sources: ATT-06, EVT-0400, EVT-0414.**

**Stale-retention example.** EVT-0414 asks what should happen when retained table header `blk_089` is corrected. An unversioned block ID cannot tell the next request whether it is using the pre-correction or corrected header. The retention record therefore needs to identify the intended version or exact evidence range and make a change or invalidation visible. Retention can end once the cross-page table is reconstructed and checked; the original is still recoverable. If all retained items no longer fit, the agent must narrow or segment the next work, rather than receive a silently shortened item that was promised to remain exact. This illustrates version and capacity semantics, not a compulsory pinning subsystem or fixed record schema. **Sources: EVT-0414, EVT-1166.**

<a id="p1-092"></a>
**P1-092 — Context transactions have mechanical and semantic limits.** **Status: agreed direction.** A candidate context can be checked for object/version existence, hashes, registered references, preserved user-revision records, native protocol validity, and capacity. It cannot mechanically prove no important dependency was never recorded, that requirements have been correctly interpreted, or that fidelity will persist. EVT-0414 proposed recording requirement/artifact/notes revisions and evidence references, rechecking before commit, and persisting the candidate before pointer activation. If requirements or artifacts change during organization, reassemble the affected parts. Under the final simplified contract, failed organization preserves originals and intermediate reduction is allowed; the exact manifest/schema machinery remains proportionate implementation work. **Sources: ATT-06, EVT-0414, EVT-1166.**

<a id="p1-093"></a>
**P1-093 — Durable indices need not all be in every request.** **Status: agreed direction.** ATT-06 proposed injecting the full page map, candidate list, evidence index, notes, and pinned material. The response cautioned that those records themselves can grow beyond useful input. Keep the complete records durably accessible, while active input contains relevant items, progress context, unresolved work, precise references, and query routes. This also applies to saved drafts and the latest artifact: durable authority is separate from what must be repeated in every model request. The final consolidation expressly permits portions of current versions or unfinished candidates to leave active input while exact originals remain retrievable. **Sources: ATT-06, EVT-0414, EVT-1166.**

<a id="p1-094"></a>
**P1-094 — Artifact state and review evidence are separate dimensions.** **Status: agreed direction.** ATT-06's one-way `CandidateStaged → VersionPublished → SourceVerified → export` diagram conflated storage with content judgment. Store candidate and committed immutable version state separately from what source/range/content was checked on which version and what remains uncertain. Reopen success proves readability; preview success proves a preview was obtained. Neither establishes full-source acceptance. A local table review does not cover an entire section; changes to headers, page mappings, or images can affect prior review applicability. Draft partial output should still be exportable with clear labeling. No compulsory review count, approval gate, or permanent global “verified” flag follows. **Sources: ATT-06, EVT-0400, EVT-0414, EVT-1166.**

A source check should therefore read as a scoped claim—for example, the header and values of a specified table were checked on a specified saved version—rather than a permanent badge on the document. Reopening that version demonstrates access to its saved content. Obtaining a preview demonstrates that rendering succeeded. Inspecting the preview may support a reading-form judgment, while comparing the relevant source supports fidelity. These facts can coexist without certifying the rest of the chapter, and a later edit can change which earlier checks still apply. This separation permits an explicitly labeled partial draft to be exported while useful work continues. **Sources: EVT-0414, EVT-1166.**

<a id="p1-095"></a>
**P1-095 — Same-version preview is the outcome; one screenshot method is not.** **Status: agreed direction.** Shared UI/agent rendering can reduce divergence and duplicate browser resources. Electron `capturePage()` and DOM/block-based CDP capture were useful options; target block IDs or source-page mappings can locate a table or figure. The outcome still depends on the same version, HTML/CSS, font resources, viewport, zoom, asset readiness, and coordinate interpretation. Visible-area limits, clipping containers, huge blocks, and font/image loading may require bounded region capture. Do not promise all content fits one screenshot or byte-identical appearance merely because Chromium is shared. Preview pixels assess reading output; exported source images retain their own quality/provenance. **Sources: ATT-05, EVT-0382, ATT-06, EVT-0414.** Historical references: [Electron capturePage](https://www.electronjs.org/docs/latest/api/web-contents#contentscapturepagerect-opts), [CDP protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json).

<a id="p1-096"></a>
**P1-096 — Proposed framework touchstones test behavior, not one lock layout.** **Status: corrected/rejected in part.** ATT-06 proposed four checks: preserving dual-protocol images/reasoning, candidate context validation and rollback, persistent retry/stream isolation with receipt reconciliation, and candidate retention/local mapping merge. Those behaviors are useful integration boundaries. Requiring the framework and tool layer to share one document lock is not itself a product requirement. The agent plans, the runtime owns model/tool lifecycle, the document service owns evidence/candidates/versions/receipts, the context module owns assembly/capacity, and the adapter owns wire differences. A normal tool call can enter a short document transaction; model inference, OCR, and an entire turn should not be enclosed by that lock. **Sources: ATT-06, EVT-0414.**

<a id="p1-097"></a>
**P1-097 — Mechanism proposals did not complete design or authorize implementation.** **Status: corrected/rejected.** ATT-06 declared disagreements fully converged and offered precise JSON schemas or immediate framework tests. EVT-0414 accepted the useful direction—layered evidence, early handoff, versioned exact working material, and candidate reuse—but still identified capacity, stale-version, semantic, and quality-state behavior to resolve. It retained optional summaries and independent note updates, and suggested examining those boundary scenarios before freezing an oversized schema. Later EVT-1148/1166 expressly stopped round-by-round expansion: the residual work is three bounded contracts, not indefinite discovery of more mechanisms. **Sources: ATT-06, EVT-0414, EVT-1148, EVT-1166.**

## Controlling consolidation and how to use this reference

<a id="p1-098"></a>
**P1-098 — Final architecture responsibilities supersede framework ranking.** **Status: agreed direction.** The controlling final consolidation prefers a small LangGraph `StateGraph` plus SQLite under one Python control layer. The agent chooses methods freely. One Nexus request service covers normal reasoning and organization with persistent budgets/cancellation, native protocols, and frozen requests; it does not rely on native compaction, remote result retrieval, or remote cancellation. The document/evidence core preserves source, evidence, received candidates, and immutable versions with precise reads, local edits, previews, and specified-version export. Context keeps evidence use separate from history organization. Recovery uses original calls and historical receipts, does not regenerate saved content, reset budgets, duplicate commits, or regress the head. Execution stop, content-completion claims, and export consistency remain distinct. This is design agreement, not an implemented/proven product. **Sources: EVT-1148, EVT-1166.**

<a id="p1-099"></a>
**P1-099 — The first remaining contract is edits and candidate references.** **Status: proposal/open (V1 contract).** The final observed trigger was a complete candidate rejected for page-map nonconformance and later regenerated with a wording regression; it supported exact reuse, not a proven compaction cause. The recommended V1 tradeoff is complete-candidate references, insertion/append, local page-map changes merged then validated against the complete document, immutable version files as body authority, and SQLite as registration/pointers/receipts rather than a separately mutable duplicate body. Preserve incomplete calls; automatic block salvage is not necessary for V1. Closure means specifying original identity, updated fields, untouched-field preservation, and successful commit, with three intelligible cases: page-map-only repair, insertion, and reuse of a rejected candidate without rewriting. **Sources: EVT-1166.**

<a id="p1-100"></a>
**P1-100 — The second remaining contract is capacity and handoff.** **Status: proposal/open (V1 contract).** The final observed evidence was large inspect/OCR intake and an existing checkpoint that reduced input and retrieved earlier evidence; universal savings and lossless continuation were unproven. Overflow after release and a delta-summary anchor losing information were hypotheses, not observed project failures. The recommended tradeoff uses configurable route capacity/output reserve over the whole request, releases persisted material not currently needed, then organizes older history; latest output and unfinished candidates can be partly referenced rather than fully repeated. V1 uses a self-sufficient handoff, not a delta-only summary. Reduction can be progressive; normal requests must fit the final capacity, originals survive failure, and budget exhaustion stops explicitly. No fixed recent K, required replacement draft, universal percentage, or promise that two or three passes always suffice. **Sources: EVT-1166.**

<a id="p1-101"></a>
**P1-101 — The third remaining contract is persistence, recovery, and stopping.** **Status: proposal/open (V1 contract).** Existing saved-work continuation and injected R1/R2 failures were observed; arbitrary crashes and natural prolonged outages were not. Tool commit before graph checkpoint and an old receipt replayed after head advancement are boundary scenarios requiring finite rules, not grounds for a general distributed system. The recommended design keeps one active task writer, unique authority for requests/tool-batch progress/versions/receipts, frozen input for resuming the same request, and newly assembled input only after a completed tool-result batch. Completed operations return their historical receipt; unreconciled local effects stop with preserved work; a real user question waits. Saved versions can export independently and partial output stays draft. Automatic reminders and packaging on every exit are not V1 prerequisites. Closure specifies behavior at request-saved, reply-accepted, tool-committed, and graph-recorded boundaries. **Sources: EVT-1166.**

<a id="p1-102"></a>
**P1-102 — Reopening is tied to a real contract blocker.** **Status: agreed direction.** Framework names, module counts, table counts, old trial reserves, whole-book/provider matrices, and hypothetical optimization ideas are not independent current tasks. The architecture contracts must be consistent and have clear ownership; implementation is then checked proportionately with offline checks and an authorized PDF or full-section delivery. Independent desktop UI/backend integration and Windows packaging remain required if an installable product is the intended output, but do not reopen context architecture. Revisit a corresponding design only when implementation or actual delivery exposes a blocker that would violate a settled contract. This reference preserves reasons and discarded possibilities so that the new repo can remain traceable without importing old current-state documents or closed jobs as instructions. **Sources: EVT-1148, EVT-1166.**
