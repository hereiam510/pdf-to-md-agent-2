### 3. 按優先順序排列的審查發現（依產品影響與證據強度排序）

#### 第一優先：現有缺陷與造成缺陷的架構／狀態問題

##### 發現 1 

$$P1・已重現缺陷$$

：`Context.compact_request` 入口誤用含 `outcome_reserve` 的正常輸入門檻，阻斷歷史壓力下的縮減型更新（R1）

* **具體依據**：`src/pdfmd/context.py:477-481`、`517-520`；`src/pdfmd/context_updates.py:83-100`；證據：`evidence/capacity-rereview/reproduce.py`、`guard-control.py`、`findings.json`、`guard-control.json`。
* **觸發條件與失敗機制**：
* 當活動政策 `A` 的正常核心估算 `old_core` 落在 `[allowance - 312, allowance]` 區間時，原本正常請求合規（`fits=True`）。
* 同批讀入新證據並呼叫 `context_update` 將 10.5KB `full` pin 降級為 `index`/`range` 或縮短 10.5KB `notes` 時，`preflight` 因歷史超量將其存為 `context_waiting`。
* 進入 `coordinate` -> `resolve()` -> `compact_request()` 時，第 517 行呼叫 `self.normal(job, {**state, "history": [], "handoff": None})`。由於 `state["context_waiting"]` 非空，`normal()` 自動加上 312 units 的未來正常續工預留 `outcome_reserve`，導致 `old_core + 312 > allowance`，在壓縮請求還沒開始組裝前就拋出 `StopRun("capacity_blocked")`。


* **使用者影響**：Agent 主動縮小 pin 視圖或精簡筆記以緩解容量壓力時，任務反而直接卡死停機，要求人工介入調整容量。
* **根因判斷與未知部分**：
* **根因**：將「未來正常續工輸入的核心檢查（含 `SYSTEM`、工具 schema、圖片像素與 `outcome_reserve`）」錯誤放在「組裝 `COMPACT` 壓縮請求」的入口，且疊加了不屬於壓縮請求的 `outcome_reserve`。
* **邊界風險（原碼推導支持）**：在固定容量下，移除第 517 行的錯誤 `outcome_reserve` 守衛、保留完整舊政策即可完成壓縮（已由 `guard-control.json` 證實）。但若使用者在暫停時調低了 `context_tokens`，使舊政策的 10.5KB `full` pin 連實際 `COMPACT` 請求都放不下，而待處理提案已將該 `full` pin 改為 `index`，此時不借用暫態縮減視圖就會停在 `capacity_blocked`。


* **建議改善方向與驗證方式**：
* **改善方向**：`compact_request` 只檢查實際組裝出的 `COMPACT` 請求本身是否 `fits`（以及是否有可壓縮的區塊與進度），不再於第 517 行用舊政策加 `outcome_reserve` 跑 `normal()` 空殼守衛；候選政策能否進入正常請求，由 `resolve()` 針對**候選政策 `Q**` 檢查。不加入一般化的「暫態採用較短 `notes`／`pin`」，以避免拆散語義依賴；若舊政策因使用者調低容量而連 `COMPACT` 都放不下，則誠實回報 `capacity_blocked` 等待設定調整。
* **驗證方式**：雙協定測試驗證 `full`→`index`、`full`→`range`、縮短 `notes` 在固定容量下保留完整舊政策完成壓縮並正式生效；以及當實際 `COMPACT` 請求真的放不下時明確停在 `capacity_blocked`。



##### 發現 2 

$$P2・已重現缺陷$$

：`Context.apply_handoff` 驗收最後一段 handoff 時使用未知 `reserved_outcome` 而非實際結算投影，造成 60-byte 誤拒（R2）

* **具體依據**：`src/pdfmd/context.py:625-640`、`src/pdfmd/context_outcomes.py:10-14`、`src/pdfmd/context_updates.py:74-82`；證據：`evidence/capacity-rereview/findings.json`（finding `2a`）。
* **觸發條件與失敗機制**：最後一段歷史壓縮完成時，`apply_handoff` 第 631 行在未清除 `context_waiting` 且未指定實際結算回饋下呼叫 `admission()`，觸發 311 bytes 的 `reserved_outcome("superseded", ..., "x"*64)`，比下一步 `resolve()` 的實際 `applied` 結果（251 bytes）多出 60 bytes，導致落在該 60-byte 區間內的合法 handoff 被拋出 `HandoffRejected`。
* **使用者影響**：觸發無謂的壓縮重試並消耗 `max_response_repairs` 與請求配額。
* **根因判斷**：各決策點未共用同一個「目標狀態續工計畫」建構器。
* **建議改善方向與驗證方式**：
* **改善方向**：建立共用的目標續工預覽方法——當評估候選 `Q` 在某個 `handoff` 下能否准入生效時，`apply_handoff` 與 `resolve` 必須建構完全相同的目標狀態（包含該次結算實際會採用的結果呈現方式：若原始批次仍在活躍歷史中則投影於 tool output，若已被壓縮涵蓋則附加尾端 outcome 訊息）。
* **驗證方式**：雙協定單元測試驗證最後一段 handoff 在 `apply_handoff` 中的估算值與下一步 `resolve` 及 `prepare` 的正常輸入估算值完全相等（0-byte 誤差）。

##### 發現 4 

$$P2・原碼支持的架構／契約風險$$

：逐筆 `preflight` 准入與雙軌生效路徑造成中間超量誤拒、語義依賴撕裂及權威分散

* **具體依據**：`src/pdfmd/context.py:149-203`、`src/pdfmd/runtime.py:62, 154-207`、`src/pdfmd/context_updates.py:28-103`。
* **觸發條件與機制**：
1. **中間超量誤拒**：同批次分兩筆呼叫 `[pin(Y), release(X)]` 時，第一筆在 `preflight` 因中間狀態 `X+Y` 超量而被 `context_rejected` 拒絕。
2. **語義依賴撕裂**：同批次 `[Call A: 改 notes 指向圖 Y, Call B: pin 圖 Y 失敗（結構錯誤或超量）]` 時，現行程式自動保留 `Call A`、跳過 `Call B`，導致筆記與實際綁定脫節。

* **建議改善方向與驗證方式**：
* **改善方向**：採納「以完整批次候選修訂為原子提交單位 ＋ `tools -> coordinate -> END / prepare` 單一結算入口」（詳見第 4 節具體架構設計）。
* **驗證方式**：雙協定測試覆蓋 `[pin(Y), release(X)]` 中間超量最終合規、`[notes(Y), pin(Y)無效]` 整組不生效、同批含 `report` 結算後終止、以及 `tools` 與 `coordinate` 間隙中斷重開。



#### 第二優先：可靠自主轉換所需的能力缺口

##### 缺口 1 

$$P2・原碼支持的續工缺口$$

：Agent 缺乏明確放棄／重置待處理候選（從有效政策 `A` 重新開始）的工具契約與修改閉環

* **具體依據**：`src/pdfmd/tools.py:42-45`、`src/pdfmd/context.py:150-151`、`src/pdfmd/context_updates.py:83-103`。
* **問題與影響**：
1. 當 `context_waiting` 存在時，`context.py:151` 強制將新呼叫疊加在 `waiting["policy"]` 上。若待處理候選 `Q` 因包含過多項目而無法通過准入，或 agent 想放棄 `Q` 直接基於目前有效政策 `A` 重建，目前工具沒有明確的 `base` 選擇。
2. 若 `Q` 的核心 `core["fits"]` 已經不合規（例如 `Q` 本身要求的 pins 超過正常容量上限，無法靠壓縮歷史解決），系統在 `A` 可行的前提下將 `Q` 標為 `rejected`（或需要修改），必須確保下一輪請求能以有效政策 `A` 加上清楚的拒絕／待修改診斷送達 agent（若 `A` 當時因歷史過長放不下，則先以 `A` 執行壓縮，壓縮後再將拒絕診斷送達 agent），形成完整的自主修正閉環。


* **建議改善方向與驗證方式**：
* **改善方向**：在 `context_update` 工具 schema 中新增明確的 `base: Literal["pending", "active"] = "pending"` 參數（避免模糊的 `"current"`）：
* `base="pending"`（預設）：在目前待處理候選 `Q`（若無 `Q` 則為有效政策 `A`）之上順序組合。
* `base="active"`：明確放棄尚未生效的待處理候選 `Q`，直接以目前有效政策 `A` 為基底建構新候選。若同批次後續呼叫再次指定 `base="active"`，則重新以 `A` 重置本批工作候選。
* **失敗不復活規則**：若某次新修訂因結構無效或容量超限失敗，且 agent 在該修訂中已明確指定 `base="active"` 放棄舊 `Q`，舊 `Q` 應標記為已被撤回／取代，不得因新修訂失敗而偷偷復活自動生效（若未指定 `base="active"` 而是跨回合新增修訂失敗，也應明確告知 `Q_prev` 的狀態，不暗中提交未預期組合）。


* **驗證方式**：腳本化 Runtime 測試驗證：當 `Q` 無法准入時，系統透過正常或壓縮路徑將回饋送達 agent，agent 使用 `context_update(base="active", ...)` 成功放棄舊 `Q` 並提交新政策生效。

#### 第三優先：有實際價值的新功能與改善機會

##### 改善機會 1：在 `Context.group` 與 `ContextUpdates` 實作「感知歷史覆蓋的結算結果投影（Coverage-Aware Settlement Projection）」

* **解決甚麼具體問題**：同時滿足「單一 `coordinate` 結算權威」「原始工具回條 `result:<op>` 永不改寫」以及「常規無壓力更新不必多塞一則尾端 `Deferred context update outcome` user 訊息」，並修正我上一輪報告忽略的「批次已被壓縮覆蓋時 tool output 不在請求中」的漏洞。
* **現有能力為何不足**：現行 `Context.normal`（`context.py:469-471`）只要 `state.get("context_feedback")` 非空，就無條件附加尾端 user 訊息；而 `control_result`（`context_outcomes.py:17-34`）只看靜態 `result:<op>` 內容，不知道該提案後來在 `coordinate` 已經結算。
* **具體機制設計**：
1. **原始回條保存驗證事實**：在 `Runtime.tools` 中，每筆 `context_update` 的 `result:<op>` 不可變 blob 記錄該筆驗證結果與所屬批次候選 ID（例如 `candidate_revision: "<batch_key>"`），不宣稱已生效。
2. **單一結算紀錄**：在 `coordinate` 中，`ContextUpdates` 對批次候選寫入唯一的 `context-settlement:<key>` blob（記錄 `proposal_ref`、`source_request: "<batch_key>"`、`status: "applied" | "rejected" | "superseded"`、`changes`）。
3. **感知覆蓋的投影（Coverage-Aware Projection）**：
* 當 `Context.normal()` 組裝請求時，檢查目前的 `context_feedback`（指向最新的 `context-settlement:<key>`）：
* **情況 A（`source_request` 仍在當前活躍 `state["history"]` 中，尚未被壓縮進 `handoff`）**：`Context.group()` 在渲染該批次的 `context_update` tool output 時，透過 `control_result` 直接將該 `context-settlement:<key>` 的最終狀態投影進 tool output 中，並明確標示：
`{"admission": {"status": "applied", "applied": True, "scope": "batch_candidate_revision", "settlement_ref": "context-settlement:..."}, "full_result_ref": "result:<op>"}`（清楚表達是**該操作所納入的整組批次修訂已提交**，而非單筆中間政策曾獨立生效）。同時，因為結果已包含在本次請求的活躍 tool output 中，`normal()` **不再重複於尾端附加 `"Deferred context update outcome"` user 訊息**！
* **情況 B（`source_request` 已被壓縮進 `handoff`，不再位於 `state["history"]` 中，或該結算是在跨越壓縮／等待後才發生）**：此時原 tool output 已不在正常請求訊息列中，`normal()` 便在尾端附加 `"Deferred context update outcome"` user 訊息，確保結算結果 100% 送達模型！
* **清除時機**：不因「預計會投影」就提前清除 `context_feedback` 指針；與現行規則一致，保留至下一個工具批次實際結算時才更新，確保任何重試或壓縮都不會遺失通知依據。




* **如何驗證改善是否成立**：
1. 測試同批兩筆 `context_update`（先寫 `notes="A"` 再改 `notes="B"`）在無壓力下通過 `coordinate` 結算後，下一輪正常請求的 tool output 投影明確顯示整組修訂已提交（指向同一 `settlement_ref`），且尾端無重複的 `"Deferred context update outcome"` user 訊息。
2. 測試當包含 `context_update` 的批次在壓縮後才完成結算（該批次已不在 `state["history"]` 中）時，下一輪正常請求尾端確實包含 `"Deferred context update outcome"` user 訊息，且 `apply_handoff` 與 `resolve` 的容量預覽均精確估算該實際呈現方式。
