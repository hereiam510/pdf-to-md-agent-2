### 2. 優先順序一：現有缺陷與造成缺陷的機制分析

#### 發現 1（P2・已重現缺陷）：`Context.compaction_state()` 忽略待處理提案中的「Pin 視圖降級」與「Notes 縮減」，且 `outcome_reserve` 疊加於舊活動政策，導致壓縮啟動前誤觸 `capacity_blocked`

* **問題、優先程度與證據類別**：P2・已重現缺陷（已在獨立暫存環境透過專案 `Store`、`Dispatcher`、`Context`、`ContextUpdates` 實測重現）。
* **具體依據**：
* `src/pdfmd/context.py:143-145`（`Context.policy` 中 `pinned.add(ref); released.discard(ref)`）
* `src/pdfmd/context.py:477-481`（`Context.normal` 在 `state.get("context_waiting")` 時無條件加上 `outcome_reserve`）
* `src/pdfmd/context.py:502-510`（`Context.compaction_state`）與 `515-520`（`Context.compact_request`）
* `src/pdfmd/context_updates.py:83-100`（`ContextUpdates.resolve`）


* **觸發條件、失敗機制及使用者影響**：
1. **場景 A（Pin 視圖降級，例如 `view="full"` 改為 `view="index"` 或小範圍 `start`/`end`）**：
* 假設活動狀態持有一個 10.5KB 的 `big_ref`（`view="full"`），不含歷史時必需輸入為 `27,032` bytes，路由可用輸入上限為 `27,132` bytes（`context_tokens=29,180, output_tokens=2,048`），此時活動政策完全合規（`fits=True`）。
* 在下一輪工具批次中，agent 讀取了兩筆 6KB 證據，並遵循系統提示（`src/pdfmd/context.py:202`：「Choose index, a precise field/range... or explicitly release other pins」）呼叫 `context_update(release=[big_ref], pin=[{"ref": big_ref, "view": "index"}])`（或直接 `context_update(pin=[{"ref": big_ref, "view": "index"}])`），將 `big_ref` 從 10.5KB 全文降級為約 200B 的 `index` 視圖（使必需內容大幅降至約 `16,700` bytes）。
* 在 `Context.preflight()` 中，因該批次剛讀入 12KB 歷史證據，完整正常輸入（`30,111` bytes）超過 `27,132` bytes，故提案被存為 `context_waiting`（`status="awaiting_admission"`）。
* 進入 `coordinate` 節點執行 `ContextUpdates.resolve()` 時：
* 第 83 行檢查提案必需內容 `core["fits"]` 為 `True`（約 `16.7KB <= 27.1KB`），不會進入 `if not core["fits"]:` 分支。
* 第 98 行呼叫 `self.context.compact_request(job, state)` 準備啟動歷史壓縮。
* 然而，在 `Context.policy()`（`src/pdfmd/context.py:144`）中，同一次呼叫先 `release` 再 `pin` 同一 `ref` 會執行 `released.discard(big_ref)`，因此 `proposal["policy"]["released"]` 為空集合 `[]`。
* 接著 `compaction_state()`（`src/pdfmd/context.py:507-510`）只檢查 `set(proposal["policy"]["released"]) - set(state.get("released", []))`，**完全忽略 `proposal["policy"]["pin_views"]` 已將 `big_ref` 從 10.5KB 的 `full` 降級為 200B 的 `index**`，導致 `compaction_state` 原封不動保留了舊的 10.5KB `full` 視圖！
* 更糟的是，此時 `state["context_waiting"]` 已非 `None`，`compact_request()` 第 517 行呼叫 `self.normal(job, {**state, "history": [], "handoff": None})` 時，會在**未降級的舊 10.5KB `full` pin（`27,032` bytes）之上，額外加上 286 bytes 的 `outcome_reserve**`（變成 `27,318 > 27,132`），當場拋出 `StopRun("capacity_blocked", "Required task instructions and pinned objects exceed the configured normal input capacity. Originals and pins are preserved; adjust capacity or explicitly revise the pinned selection.")`！




2. **場景 B（縮減大型 `notes`）**：
* 同理，當活動狀態持有 10.5KB 的 `notes`，而 agent 在歷史壓力下呼叫 `context_update(notes="Compact notes.")` 將筆記縮減為 14 bytes 時，`compaction_state()` 同樣忽略 `proposal["policy"]["notes"]` 的縮減，並在舊的 10.5KB `notes` 上疊加 `outcome_reserve`，導致 `compact_request()` 在未改動任何路由設定的情況下直接因 `capacity_blocked` 停機（或在使用者將 `context_tokens` 調至 `19,000 ~ 29,000` 區間時無法啟動壓縮）。


3. **使用者影響**：Agent 已經主動採取正確的自救行動（將 `full` pin 降級為 `index` 或縮短 `notes`），應用程式卻因壓縮視圖未反映該降級、且把待處理回條預留空間疊加在舊政策上，直接卡進 `capacity_blocked` 並要求人工介入調整容量。


* **根因判斷**：
* `Context.compaction_state()` 的設計初衷是「允許待處理提案中明確釋放空間的操作協助組裝壓縮請求，但不提前激活會增加空間的新增內容」。然而實作時僅考慮了 `released` 陣列，遺漏了同樣屬於「明確釋放空間」的**既有 pin 視圖縮減**（例如 `full`/`raw` 改為 `index` 或更小的區間）與`notes` 長度縮減；同時在檢查活動政策基底時未排除因 `context_waiting` 本身引入的額外預留負擔。


* **建議改善方向与驗證方式**：
* **改善方向**：在 `Context.compaction_state(job, state)`（`src/pdfmd/context.py:502-510`）中，除套用 `proposal["policy"]["released"]` 外，對於仍在 `pinned` 中的每個 `ref`，若 `proposal["policy"]["pin_views"][ref]` 在單獨渲染時的位元組／影像成本小於 `state["pin_views"][ref]`，以及當 `len(encode(proposal["policy"]["notes"])) < len(encode(state.get("notes", "")))` 時，一併納入暫態壓縮視圖（並在 `pending_context_update` 標記中註明此為暫態縮減視圖）。
* **驗證方式**：新增雙協定單元測試，驗證當活動狀態持有 10.5KB `full` pin 或 10.5KB `notes`、且 agent 在歷史壓力下提交 `pin=[{"ref": big_ref, "view": "index"}]` 或縮短 `notes` 時，無需調高 `context_tokens`（或在調低至 22,000 時）皆能順利組裝 `compact_request`、完成壓縮並套用提案。

### 4. 優先順序三：有實際價值的新功能與改善機會

以下建議按對「自主完成轉換與可靠交付」的實際價值排序：

1. **解耦受控子程序（`ocr_page`、`preview_document`）的中斷恢復，並為 `run_script` 設計明確的使用者確認對帳選項**
* **解決甚麼具體問題**：消除掃描／混合 PDF 在 OCR 或預覽截圖中斷後永久卡死在 `local_outcome_unknown` 的問題。
* **現有能力為何不足**：`Dispatcher.execute()`（`src/pdfmd/tools.py:114`）禁止 `ocr_page` 重跑，而 `Dispatcher.skip()`（`src/pdfmd/tools.py:95`）禁止任何 `status == "started"` 的工具在有新指示時被標記為已中止並跳過。
* **對自主性、可靠性或交付品質的改善**：因 `Runtime.run()` 持有跨程序 `FileLock(task-<job>.lock)`，重入時舊子程序必然已結束。對無外部副作用的 `ocr_page` 與 `preview_document`：(a) 無新指示時，可安全封存舊日誌並重新執行該次操作；(b) 有新指示（amendment）時，`skip()` 可封存既有 `stdout.txt`/`stderr.txt` 並回傳 `skipped=true, execution="interrupted_before_completion"` 的配對回條，讓 agent 依新指示自主調整策略（例如改用較低 DPI 或縮小 `region`）。對 `run_script` 則維持預設阻擋，並可選擇性提供明確的 UI/API 使用者確認放行選項（此項屬 `CONTRACTS.md` Q3 契約擴充，需使用者決策是否納入）。
* **如何驗證改善是否成立**：離線故障注入測試模擬 `ocr_page`、`preview_document` 在 `status="started"` 中斷後，直接 Continue 能完成轉換並匯出，帶 amendment 按 Continue 能產生配對跳過回條並由 agent 改選參數完成交付。


2. **在 `Documents.export()` 加入跨檔案系統獨佔寫入回退（`open(target, "xb")` + `fsync` + `verify`）**
* **解決甚麼具體問題**：讓使用者能將轉換完成的 ZIP 直接匯出至 exFAT/FAT32 外接隨身碟、網路共用資料夾或雲端同步掛載區。
* **現有能力為何不足**：`src/pdfmd/documents.py:270-273` 僅處理 `os.link(temp, target)` 的 `FileExistsError`，遇到檔案系統不支援硬連結的 `OSError` 會直接拋錯並留下暫存檔。
* **對自主性、可靠性或交付品質的改善**：在 `except OSError`（非 `FileExistsError`）時，改以 `with target.open("xb") as out:` 獨佔寫入 `temp.read_bytes()` 並執行 `os.fsync(out.fileno())`，並在 `finally` 中確保清理 `temp`，之後同樣執行 `verify(target)`。既保留 100% 的防覆蓋（Exclusive publication）與位元組完整性保證，又消除檔案系統限制。
* **如何驗證改善是否成立**：單元測試模擬 `os.link` 拋出 `OSError(errno.ENOTSUP, ...)` 與 `OSError(errno.EXDEV, ...)`，驗證匯出成功且 `verify(target)` 為 `True`、無 `.tmp` 殘留，且當目標檔已存在時仍拋出 `Conflict`。


3. **在大型證據被容量延後（`omitted_result`）時提供輕量級頁數／容器尺寸導航資訊**
* **解決甚麼具體問題**：當真實模型對多頁呼叫 `inspect_pdf`（如 `mode="blocks"` 或 `"dict"`）或 `ocr_page` 而因結果過大被延後（`body_in_message=false`）時，協助模型精準定位下一步 `read_evidence` 的 `json_pointer` 與範圍。
* **現有能力為何不足**：目前 `Context.omitted_result()`（`src/pdfmd/context.py:325-350`）僅列出頂層鍵名 `result_keys`（如 `["pages", "mode", "warnings", "coverage"]`），模型無法從回條直接得知 `pages` 陣列共有幾項或各頁內容的大致字元／項目數。
* **對自主性、可靠性或交付品質的改善**：在不截斷原始資料、不限制 agent 讀取順序的前提下，於 `omitted_result` 中補充頂層陣列／字串長度（例如 `pages` 長度與各元素的基礎大小概況），減少真實模型在 Stage B 長文件轉換中的盲目試探與額外請求耗用。
* **如何驗證改善是否成立**：單元測試確認 `omitted_result` 的導航資訊準確且不影響完整原文讀取；於獲授權之 Stage B 實測觀察模型讀取行為。



### 5. 架構實質評估

經全面檢視 13 個後端 Python 模組（共約 2,600 行）與 6 個前端／Electron 模組，目前採用的 **「單寫入者小型 LangGraph StateGraph（`coordinate -> prepare -> model -> tools -> compact`）+ `catalog.sqlite` 短交易中繼資料 + 內容定址不可變外部檔案（`objects/`、`versions/`）」** 架構**健全且切合產品目標，不建議更換框架或進行大規模重建**：

* **責任邊界清晰且已解決跨儲存體一致性問題**：拆出獨立的 `coordinate` 節點後，「提案結算／等待觀察（寫入 `catalog.sqlite` 與 `graph.sqlite` checkpoint）」與「組裝並凍結下一筆請求（`prepare`）」已完全解耦；`nexus.py` 的凍結請求與單一發送閘門、`documents.py` 的不可變版本與候選區塊重用、`evidence.py` 的統一未旋轉座標系與原始／顯示影像分離，均運作良好。
