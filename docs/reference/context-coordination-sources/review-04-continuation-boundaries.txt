##### 4. 

$$P2・原碼支持的架構與政策風險$$

 逐筆 `preflight` 准入、缺乏完整候選原子性及「候選處置／結果投遞／自動提交資格」耦合

* **問題、優先程度與證據類別**：P2，原碼支持的架構與契約邊界問題（`src/pdfmd/context.py:149-203`、`src/pdfmd/runtime.py:62, 154-207`、`src/pdfmd/context_updates.py:60-103`）。
* **具體依據與失敗機制**：
1. **中間容量拒絕**：同批分兩筆呼叫 `[pin(Y), release(X)]` 時，第一筆在 `preflight` 因中間狀態 `X+Y` 超量即被拒絕。
2. **部分生效撕裂語義**：同批 `[Call A: 改 notes 指向圖 Y, Call B: pin 圖 Y 失敗]` 時，現行程式跳過 `Call B` 卻保留 `Call A` 生效或待決。
3. **需要 agent 修改候選時缺乏可執行的正常請求路徑**：現行 `runtime.py:98-101` 只要 `context_waiting` 非空且原因不是 `compaction` 就直接 `StopRun`，若不解耦「待處理候選的保留狀態」與「允許用舊有效政策 `A` 發出正常請求讓 agent 修改候選」，agent 將無法在無人工介入下自行修正失敗候選。
4. **新修訂失敗時舊 `Q_prev` 的自動提交風險**：若跨回合已有待處理提案 `Q_prev`，本輪新修訂失敗時若僅保持 `context_waiting` 原指標不變，`coordinate` 會在最新意圖失敗的情況下自動把舊 `Q_prev` 提交生效。


* **建議改善方向與選擇理由（已修正前版第 4 節的未閉合處）**：
* **（1）完整批次候選修訂與 `Q_prev` 資格分離**：
* `Runtime.tools` 依序處理本批所有已接受呼叫（含已完成恢復、未開始 `skip`）。只有當整個批次處理完畢（非半批取消）時，才將本批所有 `context_update` 合組為一個候選修訂 `Q_batch`（支援明確指定 `base="active" | "pending"`）。
* 若本批任一 `context_update` 結構無效（2A）：整組本批 `context_update` 標記為 `invalid_revision`（不部分套用，也不回滾同批其他如 `edit_document` 的成功成果）。此時若先前存在 `Q_prev`，**保留 `Q_prev` 的不可變內容供查閱重用，但取消其自動准入資格（標記為需 agent 明確確認或以 `base="active"`/`base="pending"` 重新提交）**，絕不在本批修訂失敗後自動把舊 `Q_prev` 提交生效。


* **（2）單一協調入口（`tools -> coordinate -> END | prepare`）與四分支嚴格決策表**：
* 在 `coordinate` 中，先恢復已提交的 `context-settlement:<key>`；若未提交且遇新指示（3B），則記錄 `superseded`（不偽造 `instruction_basis`）。
* 對有效候選 `Q` 進行決策時，**先判定候選本身的處置狀態，再規劃投遞與續工路徑**：





| 實際條件 | 候選處置與狀態 | 下一步執行與投遞路徑 |
| --- | --- | --- |
| **① 候選 `Q` 的完整正常請求可准入**（`fits` 且無額外非選取延後） | 提交 `applied` settlement，`Q` 成為新有效政策 `A'` | 若 `terminal`（同批有 `report`）則轉 `END`；否則轉 `prepare` 以 `A'` 組裝正常請求。 |
