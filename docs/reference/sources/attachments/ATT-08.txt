## 一、 四個核心機制的工程收斂（消除近似失真與流程卡死）

### 1. 446 個 Spans 為何高達 147,366 字元？用「100% 無損結構去重」取代「預設合併與量化」

你核對出的數據非常關鍵：該頁 `layout` 只有 41 個 blocks、446 個 spans，卻佔了 **147,366 字元**（平均每個 span 高達 **330 字元**），而 `words` 佔 **39,324 字元**。

* **為什麼 446 個 spans 會膨脹到 14.7 萬字元？**
檢查 PyMuPDF `get_text("dict")` 的結構就會發現，問題不在於 span 數量破千，而在於**極度冗餘的鍵值重複與多層全文重複**：每一個 span 都在重複序列化 `"size"`、`"flags"`、`"font"`、`"color"`、`"ascender"`、`"descender"`、`"origin"`、`"bbox"`、`"text"` 等長鍵名與長浮點數，外加 block/line 層級的 `"wmode"`、`"dir"` 以及與 `text` 欄位完全重複的字串內容。


* **最佳功能設計（預設採用「100% 無損緊湊表示」，不合併 Span、不損失座標精度）：**
既然只有 446 個 spans，我們**完全不需要在預設視圖中冒險合併相鄰 span（避免誤傷表格欄位、公式或圖中標籤），也不需要做 0.5 pt 座標量化（避免在 600 DPI 下產生 2.08 像素的裁切偏差）**！
只要在你的第二種表示法（**可精確還原的緊湊表示，Lossless Compact Representation**）中執行純結構去重：
1. **提取頁面級樣式表（`style_table`）：** 將完全相同的 `(font, size, flags, color, alpha, ascender, descender)` 抽成頂層陣列（一頁通常不超過 10～15 種樣式），每個 span 只存整數索引 `style_id`。
2. **緊湊元組編碼（Tuple Encoding）：** 將每個 span 由冗長的 JSON Object 轉為位置固定的 Tuple：`[style_id, [x0, y0, x1, y1], [ox, oy], "text"]`，並附帶單行 schema 說明。所有原始雙精度浮點數與全部 446 個 span 邊界 **100% 原值保留**，可透過純函數精確還原回原始 `dict`。
3. **消除同次回覆中的重複全文：** 當回傳已包含完整文字的緊湊 `layout` 時，不重複附帶頂層 `text` 巨型字串。




* **實質效果：** 光是消除 446 次重複的 JSON 鍵名、重複樣式字串與重複全文，就能在不丟失任何一個座標位數或 span 邊界的前提下，將 14.7 萬字元大幅壓縮；而「合併相鄰片段與近似座標」則嚴格退居為第三種**可選的簡化視圖（Opt-in Simplified View）**，僅在 Agent 顯式請求快速瀏覽版面概況時提供。

### 2. 批次工具容量分配與「四階漸進式調節（4-Stage Capacity Escalation）」

你指出的四點修正（單份結果可能大於空白 Context、跨過軟水位線不應無腦強制交接、並行工具須統一核算、每個 Tool Call 必須有協定有效結果）非常關鍵。將這四點整合後，App 的單一輸入組裝器（Unified Input Assembler）在整批工具執行完畢後的標準流程應設計為：

```mermaid
flowchart TD
    A["1. 批次工具執行完畢\n原件、操作狀態 (succeeded/failed) 與版本收據落盤"] --> B["2. 統一容量試算\n(現有活躍歷史 + 本批請求表示 + 必備系統/輸出餘量)"]
    B --> C{"是否超過目標容量？"}
    C -- "否" --> D["直接展開本批結果\n組裝下一輪請求"]
    C -- "是" --> E["階梯一：釋放已解除釘選的舊證據\n或切換為無損緊湊表示"]
    E --> F{"容量是否已足夠？"}
    F -- "是" --> D
    F -- "否" --> G{"是否因歷史累積過多\n而需整理舊 Context？"}
    G -- "否 (單純本批結果超大)" --> H["階梯二：直接分段載入 (Chunked Delivery)\n回傳協定有效的完成收據 + 已載入範圍 + 未載入範圍讀取入口"]
    G -- "是 (舊歷史佔用過高)" --> I["階梯三：執行整理前交接 (Pre-Compaction Handshake)\n本批工具先回傳協定有效的『已完成但待展開收據』\n待切換至新 Context 後，再按容量展開或分段讀取"]

```

* **嚴格分離三個狀態欄位，杜絕語義混淆：**
每個工具回覆的結構固定分離為：
1. `operation_status`: `"succeeded" | "failed"`（真實反映底層執行成敗，絕不用容量狀態掩蓋工具錯誤）；


2. `evidence_ref`: 指向已落盤原件的 ID、雜湊與總大小；


3. `delivery_scope`: `"full" | "range_loaded" | "deferred_for_compaction"`（明示本次送入模型的是完整內容、局部範圍，還是因等待 Context 整理而暫緩展開的收據，並附上精確的 `omitted_ranges` 查詢參數）。


* **解決「單份結果大於空白 Context」：** 即使在階梯三完成 Context 整理後，重新評估要載入的內容時，依然走同一個容量分配器——放得下的展開，放不下的（例如一次請求了 20 頁完整 OCR）則自動轉為 `range_loaded`，載入前幾頁並明示剩餘頁面的分段讀取指令，絕不假設整理後一定能 100% 全量塞入。

### 3. 釘選（Pinning）的雙模態契約與「變更影響範圍檢查（Impact-Aware Rebase）」

採納你對釘選與合併的修正，將規則定死在結構化欄位上，消除前後不一致：

#### A. 釘選引用的兩種顯式模式（`pin_mode`）

Agent 在建立釘選時選擇其一（預設為 `follow_latest` 用於結構延續，証拠比對則用 `fixed_snapshot`）：

| 模式 | 適用場景 | 目標區塊／證據更新時的 App 自動行為 |
| --- | --- | --- |
| **`fixed_snapshot`** | 保留有問題的舊 OCR 結果、舊版草稿或特定渲染圖以供比對 | **永遠鎖定原版本（如 `blk_089@v1` 或 `ev_003`）。** 後續無論成果如何修改，始終載入當時的原始快照。 |
| **`follow_latest`** | 跨頁延續中的表格表頭、前文定義的術語表或格式規範 | **僅在「單純文字微調且結構屬性未變」時跟隨新版，並附上變更提示。**<br>

<br>若發生以下任一情況，**不自動靜默替換**，而是同時列出舊快照與新版本差異（標為 `pin_updated_verify_compatibility`）：<br>

<br>1. 區塊被拆分、合併或刪除；<br>

<br>2. 表格欄數、表頭文字或單位改變；<br>

<br>3. 區塊類型改變（如從正文改為註解）。 |

#### B. 候選稿（Candidate）與 Rebase 的關聯檢查

* **Context 不自動掛載所有 Candidate：** 活躍工作集只放當前發布版本（`Published`）的相关區塊；若有未發布的 `Candidate`，只呈現一則輕量的 **「待處理候選稿摘要（含 `candidate_id`、失敗原因、影響頁碼與基於哪個 `base_version`）」**，避免多個草稿塞爆並混淆視窗。


* **超越「Block ID 不重疊」的 Rebase 檢查：** 當 `cand_004`（基於 `v1`）準備合併至 `v2` 時，文件服務除了檢查 Block ID 是否重疊，還會自動檢查三個結構關聯：
1. **頁碼映射重疊：** `v1 -> v2` 是否修改了 `cand_004` 涵蓋或相鄰頁面的 `page_map`？


2. **資產引用連動：** `cand_004` 引用的圖片資產是否在 `v2` 中被刪除或替換？


3. **釘選依賴連動：** `cand_004` 依賴的 `follow_latest` 釘選區塊（如表頭）是否在 `v1 -> v2` 中被修改過？
只要上述任一項為真，就不允許盲目自動合併，而是回傳 `rebase_review_required` 與具體連動項目，交由 Agent 確認語義相容性。

### 4. 無自我衝突的 CAS 切換與「核對紀錄（Verification Record）」局部失效規則

1. **修正 CAS 版本檢查邏輯（分離讀取基底與自身產出）：**
* Handshake 啟動時記錄外部狀態快照：`expected_external = (req_rev: R1, published_ver: V1, candidate_head: C1, pre_handshake_notes_rev: N1)`。
* Handshake 過程中產生的筆記先作為本次整理交易的 **`staged_notes_delta`**（不提前把外部 `notes_rev` 改掉再自己絆倒自己）。
* 提交新 Context 的短交易內：檢查當前系統的 `(req_rev, published_ver, candidate_head, notes_rev)` 是否仍等於 `(R1, V1, C1, N1)`。若完全吻合，則在同一個原子操作內寫入 `notes_rev = N1 + 1` 與新的 `context_manifest`；若有外部變動（如使用者在此期間提交了 `R2`），則將 `R2` 的變更與 `staged_notes_delta` 重新組裝後再提交。


2. **使用者暫停／取消擁有最高優先權：**
* 若使用者發出 `pause` 或 `cancel` 指令，Runtime 在當下網路請求或工具結束的瞬間**立即停止**，直接將目前狀態落盤，**絕不為了「完成交接」而額外發起任何模型請求**。


* 若使用者中途修改了要求（例如將第 15–20 頁改為範圍外，或更改標題格式），系統保留已落盤的來源證據（`Evidence`）與仍適用的來源觀察筆記，但自動將受影響範圍的「待發布 Candidate」與「下一步工作計畫」標記為 `invalidated_by_requirement_change`，要求 Agent 重新評估。


3. **核對紀錄（Verification Records）的精確失效範圍：**
* 核對紀錄以 `(version_id, pdf_pages, checked_aspects, unresolved_issues)` 儲存。當發布新版本 `v2` 時，未受修改影響且無跨頁釘選連動的頁面可沿用既有核對紀錄；但**凡是被修改的區塊、該區塊所在的頁面，以及將該修改區塊列為依賴的後續區塊**，其核對狀態一律自動降級為 `stale_needs_recheck`。

### 對框架選型的關鍵結論（破除「Deep Agents 現成功能多所以比較省工」的迷思）

從這張嚴格基於**公開接口**的對照表可以看出一個非常清楚的架構事實：

1. **為什麼 Deep Agents 看似功能最多，實際上卻省不了 Context 的工？**
因為 Deep Agents 在 LangGraph 之上封裝的兩大核心賣點，就是預設的 `OffloadingMiddleware`（大結果自動轉虛擬檔案）與 `SummarizationMiddleware`（超限自動摘要）。但正如你自己指出的：**「要避免 App 和框架各自獨立決定壓縮、各自維護一份互相競爭的活躍 Context，最終送入模型的內容需要一個明確的決策入口。」**
為了實現我們的「無損緊湊 `layout`、整批工具統一容量分配、整理前交接 Handshake、雙模態釘選（`fixed_snapshot` / `follow_latest`）與 CAS Manifest 切換」，我們**必須透過公開入口把 Deep Agents 預設的 Offloading 與 Summarization 替換成我們自己的 Context 模組**。一旦替換掉這兩塊，Deep Agents 就退化成了普通的 **LangGraph**！


2. **因此，真正的決策並不是「Pi vs. Deep Agents」，而是依據你們對「語言核心」的選擇，在以下兩條最乾淨的路徑中二選一：**
* **路徑一（以 Python 為 Runtime 核心）：直接沿用並重構現有的 Python Controller（或僅引進底層 LangGraph 管理狀態與迴圈），不套 Deep Agents 外殼。**
