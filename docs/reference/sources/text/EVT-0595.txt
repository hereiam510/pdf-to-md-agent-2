**我會保留「正常工作、容量整理、異常恢復、模型切換」四份契約，但不會直接採用這版的全部實作。** 它仍把幾種有用的估算與觀測，寫成了尚未成立的可靠性保證；也有部分機制會增加我們自行維護 runtime 的負擔。

從 app 的最佳功能出發，重點應是：**讓 agent 保持判斷與操作自由，讓框架負責執行延續，讓 app 保證來源、成果與實際輸入可追溯。**

**1. 最重要的修正：程序重啟，不應直接進入新的 Recovery Context。**

提案把「舊 context 已不可用」與「程序崩潰重啟」放在同一類，這會不必要地失去近期工作細節。

合理的順序應是：

1. 載入原有 session／checkpoint。
2. 對帳已完成的文件操作與工具結果。
3. 原狀態仍可用，就從原位置延續。
4. 只有歷史缺失、狀態不合法，或容量問題無法透過正常整理解決時，才組裝新的 Recovery Context。

這也是採用成熟 runtime 應該得到的價值。LangGraph 已提供 checkpoint 恢復，以及公開的 `get_state()`、`get_state_history()`；查核持久狀態不等於自行解析 `checkpoint_blobs`。[LangGraph 官方文件](https://docs.langchain.com/oss/python/langgraph/checkpointers)

因此，文中對「主動查核框架儲存」的反駁，建立了一個不必要的二選一：**我們可以透過公開 API 查核，而不接觸私有儲存格式。**

**2. Lazy Ack 可以簡化常見路徑，但不能單獨保證完整恢復。**

這個設計有用，但「100% 解決兩套儲存時間差」需要撤回，原因有三個：

- **模型輸入中的歷史，不一定是完整持久紀錄。** 工具結果可能已被整理、替換或排除；看不到結果，不能推出工具未完成。
- **在正常執行的 hook 看見結果，不等於它已可靠持久化。** 「觀測到」與「重啟後能讀回」是不同事實。
- **載入 session，不保證 runtime 自動重跑尚未完成的工具。** 這需要核對具體恢復語義。

例如，Pi v1.3.0 的低層 `Agent.continue()`，在沒有排隊訊息且最後一則為 assistant 時會拋出錯誤。因此，不能僅靠 `SessionManager.open()` 加 hook，就推定它具有提案描述的未完成工具重播行為。[Pi 原始碼](https://github.com/earendil-works/pi/blob/v1.3.0/packages/agent/src/agent.ts#L383)

我建議保留 Lazy Ack 作為快捷處理，並讓一個薄的框架適配層透過公開 API 對帳。文件操作則以 app 自己保存的穩定 `operation_id` 和結果收據保證冪等。**任意腳本的副作用不能自動繼承這項保證**，仍須依實際保存的成果判定如何延續。

Pi 也有公開的 `getEntry()`、`getEntries()`、`getBranch()`，並非只能自行讀取其 session 檔案格式。[Pi SessionManager](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/src/core/session-manager.ts)

**3. 操作帳本值得保留，但它應是既有紀錄的查詢視圖，不能代替工作筆記。**

提案指出「最後有效筆記可能太舊」，這個問題成立。然而：

> 「讀過第 15–16 頁、更新過 table_02」

並沒有保存：

> 「第 16 頁首列延續上一頁表格；某個數值仍有字形疑問，所以尚未採用。」

第一種是系統事實，第二種才是接續工作需要的判斷。只增加 Mechanical Delta Log，仍可能保留操作、失去理解。

我會這樣設計：

- 操作時間線直接從既有收據、工具紀錄與成果版本產生，避免再維護一套獨立帳本。
- agent 可以在正常工作中保存重要發現、未解依賴和失敗原因；不必等到整次 compaction。
- 恢復視圖提供近期活動、相關筆記，以及原始訊息／證據／未採用候選成果的精確入口。
- 明確記錄筆記參照到哪個事件位置；單靠 `notes_rev` 並不能判定哪些活動已被整理。

**固定 Epoch 前綴，不妨礙在尾端追加筆記更新。** 因而不應為了前綴快取，讓重要判斷延遲十二個回合才保存。

另外，「只佔幾百 tokens」「精確接回斷點」都只能是特定案例的結果，不能寫成一般保證。

**4. 組件估算與路由校準可以採用，但必須稱為估算，不能稱為保守上界。**

這是提案中另一個需要直接反駁的地方：

\[
\max(\text{近期觀測誤差}) \times \text{安全係數}
\]

不能證明下一個請求一定不超出估算。

例如，校準請求包含大量文字和少量圖片，即使圖片成本低估十倍，整體誤差仍可能很小；下一輪改成圖片為主，原本的係數就可能嚴重失準。以 Base64 長度或像素面積設定初始值，也沒有因此建立視覺 token 的可靠上界。

較實際的設計是：

- 有適用的 tokenizer／圖片計費規則時，優先使用。
- 針對**這次真正組裝的請求**重新估算，包括工具定義、訊息封裝與圖片表示。
- 使用實際 usage 校準，並保留未知與估算誤差。
- 提前留整理空間，同時保留超限後的可恢復處理。

文中的容量公式適合作為**提前整理的規劃條件**。其中 `Expected Tool Receipt Margin` 是預期值，無法約束尚未產生的工具結果；整批結果完成後，仍須依實際大小再決定本次投影。

這不要求一開始就建立複雜的統計校準系統。先使用框架可用的計數機制，加上必要的模型適配與明確誤差，通常更符合減少自訂維護的目標。

**5. 不應把每次釋放證據，都綁定成一次完整交接與新 Epoch。**

這版仍有把 context 管理做得過重的傾向。

兩種動作應能分開：

| 動作 | 所需處理 |
|---|---|
| agent 判斷某份可精確取回的證據暫時不需要 | 更新活躍輸入的選擇，保留原件與取回入口 |
| 舊工作歷史已太長，需要建立新的繼續工作狀態 | 保存必要判斷與依賴，整理歷史並建立新基準 |

前者未必需要額外模型回合，也未必需要重寫全部筆記。若每次移出一張圖片都要求 Handshake，可能增加延遲與成本，反而削弱 agent 自主整理的實用性。

固定基準快照可以是有效的正常模式，但「同一 Epoch 絕對不改寫」最多是該模式的定義。**是否值得開始新視圖或新 Epoch，應服從工作需要與整體成本，不應讓保護快取變成產品的最高規則。**

**6. 分桶索引、模態檢查和 Blob 保護，都應避免變成新的固定流程。**

這三項機制可以保留，但需要限縮其承諾：

| 提案 | 我建議的修正 |
|---|---|
| 每 25 頁分桶，保證精簡常數大小 | 固定桶大小下，`O(N/25)` 仍是 `O(N)`。它是有效導覽方式，沒有保證任意文件都能放進 context。 |
| 只展開目前 1–2 個桶 | 可作預設視圖，不能限制 agent 同時處理多個跨頁範圍。統計數量也不能代替精確覆蓋紀錄。 |
| 無視覺模型遇到視覺依賴便阻擋切換 | 應明確保留未解依賴，阻擋無法完成的操作；其他有用工作仍可繼續。若已有可用的視覺工具／模型，也可由 agent 選擇使用。 |
| `GlyphLessFont` 等特徵觸發視覺核對 | 可以提供診斷訊號，不能單憑字型名稱自動建立每頁必做的核對關卡。 |
| 未過期 Blob 租約可避免清理競爭 | 長操作可能超過租約。要處理續租／仍在使用的狀態；若初期沒有必要，也可先不做執行中的背景清理。 |

尤其是模態判斷：**app 知道模型能否接收圖片；agent 判斷目前問題需要哪些證據。** 兩者要合作，不能讓能力表暗中取代轉換判斷。

**7. Pi 與 LangChain 的比較表，需要修正後才能用來估算修改量。**

我核對到兩個具體問題：

- **一般 `create_agent` 並不預設裝上 `FilesystemMiddleware`。** 官方把 middleware 作為選用擴充；不能把某種 Deep Agents 組合的預設行為，算成使用普通 `create_agent` 必須拆除的成本。[LangChain Agents](https://docs.langchain.com/oss/python/langchain/agents)
- **Pi 的 `context` hook 不能概括成控制整個最終前綴。** v1.3.0 另有 `context_with_system`，在 Pi 恢復 prompt／tool state 後處理完整訊息；還有 provider request 層的接口。實際應在哪一層接管，需要依修改範圍選擇。[Pi 擴充接口原始碼](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/src/core/extensions/types.ts)

所以我不接受表中的「兩者相當」作為已確定結論。**能找到 hook，不代表持久化、恢復及執行順序的工作量相同。**

我會把重構的責任收斂成下面這個分工，而不先要求實作所有新名詞：

| 負責者 | 核心責任 |
|---|---|
| 框架 runtime | agent loop、工具生命週期、session／checkpoint、其公開支援的恢復流程 |
| App 文件與證據服務 | 完整原件、精確讀取、草稿版本、資產引用、操作冪等與發布一致性 |
| App context policy | 組裝實際輸入、容量處理、證據投影、模型能力適配 |
| Agent | 方法選擇、重要發現、未解依賴、證據是否仍需要，以及繼續工作的判斷 |

**如果可靠重啟與減少自訂恢復程式是主要考量，這輪證據讓 `create_agent`＋持久化 LangGraph checkpoint 更值得作為優先設計基準。** Pi 仍是合理候選，但應把需要補上的恢復責任算進成本，不能只比較 context hook 是否方便。這是設計建議，尚不是我們 app 上已驗證的框架勝負。

Nexus 路徑則維持先前約定：由 app／框架完成 context 管理與原件保存，不把上游原生 compaction 當作必要條件。完整重構可以改變實作，但應保留這些責任邊界，避免最後又在所選框架外重建一套自己的 runtime。
