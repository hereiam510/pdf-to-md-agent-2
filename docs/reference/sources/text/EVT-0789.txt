**我會保留 `create_agent`＋持久化 LangGraph Checkpointer＋App 文件／證據服務這個方向，但這版仍有幾項會限制 Agent 自主性或造成恢復錯誤的設計，需要改寫。** 當中「同批次收集局部意圖」值得接受；「引用就必須常駐」「快取粒度等於釋放粒度」及「已達到 100% 恢復閉環」則不成立。

**1. 同批次 Delta Intents 合理，但 `linked_refs` 不能直接變成常駐要求。**

這份提案對我上一輪的反駁有道理：要求 Agent 每次提交完整政策，只是較保守地避開並行衝突，並不能保證語義正確。允許同一批工具提出不同局部變更，再集中結算，是可行的設計。

問題在於這條規則：

> 筆記或釘選區塊引用了某份證據，就自動阻止釋放該證據。

對我們的 App，至少有三種不同關係：

| 關係 | 應有含義 |
|---|---|
| 筆記引用某份證據 | 保留來源與精確重讀入口 |
| 某項工作尚未解決 | 保留待辦狀態、已知問題及相關引用 |
| Agent 明確要求證據常駐 | 在解除要求前，保護指定內容的 context 位置 |

例如，Markdown 草稿中的某個表格引用第 19 頁原圖，可能只是為了日後核對來源。**這不代表每次模型呼叫都需要再次攜帶那張原圖。** 否則，成果寫得越完整、引用越多，就越難釋放 context。

我建議依賴檢查只保證可機械驗證的事情：引用仍有效、版本正確、明確的常駐要求得到尊重。是否仍需看原文，由 Agent 判斷。

同批變更也應按**合併後的目標狀態**檢查。例如 `pin_remove(ev03)`＋`release(ev03)` 可以完全合理；不應因為處理順序而一律「pin 勝出」。真正矛盾的要求則回報明確衝突及實際套用結果。

**2. 恢復設計還缺少「政策啟用本身被中斷」的處理。**

提案描述的 `pending_writes` 情境符合 LangGraph 的恢復方向：已保存的成功任務輸出可以在恢復時沿用，避免重跑。但這項能力不等於 App SQLite 與 Graph State 之間已有共同交易。[LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

仍有這個中斷點：

```text
before_model 在 App SQLite 建立 policy 8
→ 程序中斷
→ active_policy_rev = 8 尚未保存到 checkpoint
```

恢復後，Graph 仍是 policy 7。若再掃描「所有已完成操作」並套用一次，就可能重複推進版本或取得不同的提案集合。

這裡可以沿用既有收據設計：

- 由**當前分支已接受的父 AIMessage／工具批次**確定待結算提案；工具結果攜帶明確的 `proposal_ids`。
- 對「該批次、父政策、提案集合」建立可重用的啟用收據。相同結算重跑時，取得同一結果。
- `before_model` 一次返回新的 `active_policy_rev` 與已結算的批次／啟用識別。
- checkpoint 仍是「目前哪個政策有效」的唯一權威；SQLite 中先建立但未啟用的政策可以存在。

`input_view_id` 適合表示模型看過哪個輸入，**不能單獨承擔哪個工具批次已被當前分支接受的身分**。同一輸入可能牽涉多次嘗試；不能因此把資料庫中相關操作全部納入。

另外，架構圖把大量證據展開和訊息注入一起放入 `before_model`，需要調整。官方區分很清楚：`before_model` 返回的更新會進入 Graph State；`wrap_model_call` 可以只修改本次模型輸入。[Custom middleware](https://docs.langchain.com/oss/python/langchain/middleware/custom)、[Context engineering](https://docs.langchain.com/oss/python/langchain/context-engineering)

建議分工如下：

| 位置 | 責任 |
|---|---|
| `wrap_tool_call` | 核對操作收據、執行或重播完整結果、保存證據及提案引用 |
| `before_model` | 結算政策，更新必要的持久狀態 |
| `wrap_model_call` | 按有效政策展開本次需要的內容、檢查容量、記錄實際輸入視圖 |

這樣才不會為了讓模型看一次圖片或大型 layout，又把全部內容重新塞回持久對話狀態。

**3. 單頁快取值得做，但不應要求所有證據都按頁拆成實體檔案。**

「快取粒度＝釋放粒度」這個推論不成立。應分開考慮：

- **運算單位**：哪些結果能獨立計算、獨立重用？
- **儲存單位**：實體檔案如何保存？
- **輸入選取單位**：這次模型需要哪些頁、欄位或區域？

一個包含六頁的不可變 JSON，仍然可以只讀第 19–20 頁，並讓第 15–18 頁退出 context。現有工具契約已支援用 JSON Pointer 精確讀取證據，並不要求每個片段先存成獨立檔案。[TOOLS 的證據讀取契約](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/TOOLS.md:329)

因此：

- 單頁渲染、獨立單頁 OCR：適合逐頁快取，重疊範圍只計算缺少部分。
- 跨頁表格分析、整段腳本處理：快取單位應跟隨實際運算範圍。
- Context 選取：透過穩定的證據引用加頁碼／欄位／區域選擇即可。

提案保留 OCR 語言順序是正確的，Tesseract 官方確實指出順序可能影響輸出。[Tesseract 文件](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html)

`force_recompute` 產生新版本、保留舊版本也應保留；但「最新產出成為預設」應是清楚的快取選擇規則，不能暗示最新結果品質較好，更不能改寫既有筆記指向的版本。

**4. 雙容量預算正確；固定先載入前 K 項，應降為可選策略。**

分開處理 token 與實際請求 bytes 很重要。不過文中的 15 MB／20 MB、128k／200k 都只是情境假設，不能當成已確認的 Nexus 路由限制。

我會修改三處：

**第一，沒有保證 K 至少是 1。**  
單張圖片就可能超限，或者保護中的必要內容已用掉大部分容量。這時應提供輕量的容量回報、已保存範圍及精確讀取入口，讓 Agent 選擇區域、欄位、其他讀取方式或調整工作集合。若連必要控制資訊都放不下，就明確回報容量限制並保留工作。

**第二，分批不能變成固定工作順序。**  
Agent 可能需要同時比較第 15 與第 19 頁，而不是依序完成 15、16、17、18 頁。系統可以提供預設選取，但必須允許直接選擇跨頁組合，清楚標示哪些內容尚未送入模型。

**第三，容量錯誤不會自動跳回 `before_model`。**  
它是模型呼叫前的 hook，不是通用例外恢復入口。需要明確設計容量錯誤的處理路徑，限制重組嘗試，保留每次輸入與結果；不能只在圖上畫一條返回箭頭就視為已完成恢復。

「不使用傳輸自動重試配額」可以成立，但**實際已發送的請求仍須記錄**，重組後的新請求仍受原有整體預算限制，不能因換了 context view 就獲得額外的無限嘗試。

此外，「較早」「已產生草稿」「工具成功」都不足以單獨證明證據可釋放。優先退避應依 Agent 已表達的可釋放狀態或已同意的容量政策。

**5. Windows 快照方法有用，但錯誤診斷與完成保證說得過頭。**

用讀取 handle 配合 `FILE_SHARE_READ`，並在持有該 handle 時複製內容，是合理的防寫入干擾方式。但原文混淆了兩個參數：

- `GENERIC_WRITE` 是要求寫入存取權。
- `FILE_SHARE_WRITE` 是允許其他開啟者要求寫入；它本身不代表這個 handle 正在寫入。

`ERROR_SHARING_VIOLATION` 表示存取權與共享模式不相容，**不能據此判定有未知後代程序正在寫入**。例如另一個讀取者不允許共享讀取，也可能造成衝突。[Microsoft CreateFileW 文件](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)

所以應回報「共享衝突，無法取得所需快照」，保留原因未知，而不是直接宣稱 `file_still_open_for_write`。

而且：

```text
取得穩定副本 → 格式可完整解碼 → 已核實哪些內容
```

是不同層次。完整解析 JSON 並不證明頁碼、來源對應或要求範圍完整。`verified_pages` 必須來自實際範圍核對，不能只由解析成功推導。

這些可以是救援服務的內部步驟。無須強迫 Agent 每次固定呼叫四個工具；唯讀檢視可以獨立使用，採用選定成果時再執行必要的快照、驗證和登記。

**對我們 App 最有利的收斂，是讓框架管理執行與恢復，讓 App 管理可核對的文件、證據與容量，讓 Agent 決定要看甚麼、保留甚麼及如何完成轉換。** 普通歷史壓縮與證據釋放共用同一套有效政策及輸入組裝機制；Nexus 留在模型接入邊界，這些能力由 App 提供，不依賴上游原生 compaction。

這些修正可以在目前選定的框架方向內完成。完整重構的價值，是把責任界線一次整理清楚，並避免把常駐引用、逐頁拆檔或順序閱讀變成新的產品限制。
