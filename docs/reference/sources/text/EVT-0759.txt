**這版有幾項值得採納的改進，但「所有邊界條件已收斂完畢」仍不成立。最需要修正的是 policy 的啟用權責：SQLite 排好了寫入順序，並沒有因此排好 LangGraph 的狀態更新。**

我仍支持目前的框架方向。以下修改會直接改善續工可靠性、證據重用及 Agent 自主性，不需要再重建一套 runtime。

**1. SQLite 交易不能單獨解決 LangGraph 的並行更新；目前方案重新引入了兩個「當前 policy」。**

提案中的流程是：

- A 在 SQLite 提交 policy 8，回傳 `Command(active_policy_rev=8)`。
- B 在 SQLite 提交 policy 9，回傳 `Command(active_policy_rev=9)`。

即使兩筆資料庫交易完全串行，**兩個 Command 仍可能在同一個 LangGraph superstep 更新同一欄位**。沒有適當 reducer 時，這正是官方列出的並行更新錯誤；如果隨意採用最後寫入者，也沒有保證最後套用的是 policy 9。[LangGraph 官方說明](https://docs.langchain.com/oss/python/langgraph/errors/INVALID_CONCURRENT_GRAPH_UPDATE)

而且，提案新增了 SQLite 裡的 `current_active_rev` 判斷，卻又要求恢復時遵循 checkpoint 的 `active_policy_rev`。當 SQLite 已推進至 9、checkpoint 還停在 7，兩者誰有最終決定權，仍未解決。SQLite 的單一寫交易保證不會自動涵蓋另一套框架提交。[SQLite 交易文件](https://www.sqlite.org/lang_transaction.html)

**我會選擇讓 LangGraph State 保存該執行分支唯一的有效 policy 指標，App 資料庫保存不可變政策內容與提交收據。**

具體可以利用現成 lifecycle hook：

1. 工具保存 context 變更提案，回報「已保存、待啟用」。
2. 在單一 `before_model` 步驟，核對提案的父版本與當前有效版本。
3. 由這個步驟一次更新 `active_policy_rev`，並產生啟用或衝突結果。
4. 下一次模型輸入使用這個已選定的版本。

`before_model` 本來就是 LangChain 提供的循序 lifecycle hook，適合這類狀態更新。OCR、文件修改及其他工具仍由原有 agent loop 排程。[官方 middleware 文件](https://docs.langchain.com/oss/python/langchain/middleware/custom)

另外，**物件 ID 不重疊，不代表變更可以安全合併。** 例如 A 釘選 `blk_12`，B 釋放 `ev_03`，但 `blk_12` 的未解表頭關係可能正依賴 `ev_03`。兩者也可能共同超出容量限制。

我不建議第一版做通用的 `Linear Intent Rebasing`。先讓 Agent 一次提交完整的 context 變更；遇到競爭提案就明示衝突。只有日後確定具有明確合併規則的操作，才加入自動合併。

提案擔心 reducer 錯誤阻止該步推進是合理的，但不能進一步推導「已完成的 OCR 必須重跑」：LangGraph 有 pending writes，App 也應保留工具成果收據。[官方 Checkpointers 文件](https://docs.langchain.com/oss/python/langgraph/checkpointers)

**2. 「已有證據」與「草稿尚待完成」的區分很好，但快取方案尚未解決它舉出的例子。**

這個緊湊狀態值得保留：

```text
Pages 15–20:
draft_pending
available_evidence: OCR, layout
manifest: …
```

它能提醒 Agent 優先查看已有成果，但應只列出實際成功保存的範圍、種類及必要警告，不能把「有 OCR」當成內容完整或正確。

快取則有三個需要補明的地方：

- **`pages=15–20` 與 `pages=15–16` 的參數雜湊不同。** 完全相同參數的快取不會解決這次重複讀取。要重用重疊範圍，需要按實際運算單位建立索引；只有逐頁獨立的處理，才適合直接做逐頁運算重用。
- **快取身分須包含實際運算設定與版本。** 除了來源、工具名稱及參數，還應涵蓋工具實作／引擎版本、OCR 模型或語言資料，以及解析後的預設設定。頁面分割模式、DPI、裁切、註解等設定都可能改變結果。[Tesseract 文件](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html)、[PyMuPDF 文件](https://pymupdf.readthedocs.io/en/latest/page.html#Page.get_pixmap)
- **Agent 必須能明確重算。** 若它正在排查錯誤或比較辨識結果，快取不能讓它永遠拿到同一份有缺陷的舊輸出。

還要區分「結果快取」與「操作重播」：新的工具呼叫可以使用舊 `evidence_id`，但應回傳匹配**當前** `tool_call_id` 的訊息，並記錄成果來源；不能直接搬用舊呼叫的訊息身分。

**3. 容量超限後重新組裝輸入是合理能力，但不能直接等同「移除當批大型證據再重送」。**

這裡有兩個不同問題：

| 拒絕原因 | 需要處理的限制 |
|---|---|
| 模型 context 超限 | token 預算、輸出預留及模型輸入限制 |
| HTTP payload 過大 | 請求內容大小，可能來自代理或伺服器限制 |

HTTP 413 表示伺服器不接受該大小的請求內容，不能據此直接推算模型的 token 上限。[HTTP 官方規範](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.14)

更重要的是，「當批最大」不代表「可以移出」。它可能正是 Agent 剛要求檢查的表格或圖片，也是完成下一步所必需的證據。

我建議把容量修正寫成明確的 context 行為：

- 依現有保留／釋放選擇，重新組裝符合限制的輸入。
- 明示未載入內容及精確讀取入口。
- 保護有效要求、未解依賴及有用工作。
- 需要新的語義取捨時，讓 Agent 在可容納的工作視圖中選擇，而非依資料大小自行判定不重要。
- 若必要內容仍無法容納，保存成果並回報具體限制。

保持同一回合預算、不因換 view 重置計數，這點可以保留。但容量修正應由 context 機制負責；不能只因傳輸層還有重試配額，就自動取得改寫輸入的權限。

這也是新增設計行為：目前專案契約明確不把 context-limit 錯誤當成傳輸故障自動重試。[TOOLS.md](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/TOOLS.md:280)

**4. 成果救援需要驗證，但 `inspect_and_salvage_attempt` 把檢視、終止程序、驗證與採用綁得太緊。**

我支持避免採用仍在寫入或已損壞的檔案，但會作以下調整。

首先，**檢視應保持可讀取性**。Agent 可以查看部分日誌、尚未完成的 JSON 或損壞檔案，以判斷能否修復；不能要求整個目錄全部通過驗證，才准許檢視或救回其中一份正常成果。

正式採用時，才針對選定成果確認：

- 它不再被受控執行程序修改，或已取得一致的固定副本。
- 驗證與納管使用同一份不可變內容，避免檢查完後檔案又改變。
- 格式能由適合的解析器／解碼器讀取。
- 來源、範圍及內容符合這次採用的用途。

只確認原始 PID 已不存在，不足以證明所有後代程序已停止；檢視操作也不應默默終止一個仍正常工作的程序。終止應針對已辨識的舊嘗試，並確認程序已終止，而非等待 handle 被釋放。

格式檢查也應使用成熟函式庫。JPEG 的 EOI、PNG 的結尾或 CRC 檢查，不應單獨被視為完整解碼的替代品。例如 Pillow 明確區分 `verify()` 與實際載入像素的 `load()`。[Pillow 官方文件](https://pillow.readthedocs.io/en/stable/reference/Image.html#PIL.Image.Image.verify)

**格式有效也不代表工作完整。** 一份只有前 30 頁資料的 JSON，可以完全符合語法；不能因此認定原本處理 100 頁的腳本成功完成。

因此，我會避免用單一 `salvaged_resolved` 混合兩種事實：

- 原始操作是否完整完成。
- 哪些局部成果已核對並成功救回。

可以採用可信的局部成果，同時保留原操作未完成或其他副作用未知的記錄。救援動作本身可以有成功收據，不必改寫原始執行歷史。

**5. 「由 checkpointer 決定續跑」應交給框架執行，不應自行把 `StateSnapshot.tasks` 轉成工具排程器。**

`tasks` 是框架的 `PregelTask` 描述，可能包含一般節點、子圖或中斷資訊，並不是一份保證直接可執行的工具呼叫清單。[官方 StateSnapshot 說明](https://docs.langchain.com/oss/python/langgraph/checkpointers#statesnapshot-fields)

我會把實作契約寫得更簡單：

> 使用框架的恢復入口續跑；當框架實際再次呼叫某個工具時，`wrap_tool_call` 才核對操作身分與收據，決定重播或執行。

Snapshot 可用於顯示狀態、診斷及定位 checkpoint。如此能保留前面要求的精確重播，也減少我們自行維護框架內部排程細節。

**我會保留這版的證據進度提示、不可變輸入、Blob-first 保存、穩定回合預算，以及局部成果救援方向。需要改動的設計可收斂為：**

| 部分 | 建議 |
|---|---|
| Policy 啟用 | LangGraph 分支狀態持有唯一有效指標，由單一 lifecycle 步驟更新 |
| 並行 policy 修改 | 明確父版本檢查；先不做通用自動合併 |
| 證據快取 | 按正確運算身分重用，支援範圍查詢與明確重算 |
| 容量恢復 | 由 context 契約重組輸入，保留必要狀態與取回能力 |
| 成果救援 | 檢視、固定成果、驗證、採用分開；局部成功不冒充完整成功 |
| 恢復排程 | 框架負責續跑，工具 wrapper 負責收據重用 |

即使完整重建，我也會沿這個方向設計：讓框架負責執行生命週期，讓 App 提供可靠的文件與證據服務，讓 Agent 保有內容判斷和方法選擇。最需要先定清的，是 **policy 的唯一啟用點與衝突回報方式**，而不是繼續擴充 SQL 欄位。

本輪只做設計審閱與官方資料核對，沒有修改程式或執行模型測試。
