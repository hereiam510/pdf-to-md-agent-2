**這版可以作為架構方向，但仍不宜直接凍結成實作規格。** 我認同穩定前綴、恢復時揭露已提交成果、證據取回索引，以及不可變草稿版本；需要修正的是它對「快取、去重、原子性、證據完整性」的保證。

更重要的是：我們已經討論了很多儲存與恢復細節，**context management 本身的容量計算、整理交接和失敗處理，反而仍未定清楚。**

**1. 穩定前綴與尾端工作狀態值得採用，但不能保證完全保住 cache。**

把經常變動的草稿資訊放在較後位置，是合理方向。OpenAI 官方也建議穩定內容放前面、動態內容放後面，但同時指出：相同前綴未必已有可重用的快取，還取決於快取邊界、有效期和路由。[OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)

附件忽略了一個細節：**尾端注入的工作狀態，下一輪會怎樣處理？**

- 若每輪重新生成、替換或移除，它不一定能延續上一輪完整的訊息前綴。
- 若每輪永久附加完整快照，又會累積大量重複狀態。
- 若工具結果已清楚回報最新修改，再注入同一份內容，也可能只是重複。

我會採取較簡單的原則：

> 穩定規則和工具定義保持穩定；正常修改由工具結果承載；只有恢復、整理後接續或確有資訊缺口時，補入必要的目前工作狀態。

Epoch 可以作為一次 context 整理的版本標識，不必變成「整個 epoch 期間不得重組任何前段內容」的硬規則。使用者修改要求後，也必須立即清楚表達哪些舊要求已被取代。

那次約 84% 的 cached-input 比例，是一個已觀測案例，不能推導為這種新設計的預期收益，更不能直接推算 Nexus 的訂閱成本。**快取是成本優化條件，不能凌駕容量、要求更新及內容正確性。**

**2. 版本衝突代表防護生效；內容 hash 可以改善體驗，但不是「意圖去重」。**

附件描述的情境是：

```text
第一次：expected_rev=3 → 成功產生 rev=4
第二次：新 operation_id，仍要求 expected_rev=3 → 被拒絕
```

這裡沒有發生重複寫入。`expected_rev` 已經阻止了錯誤修改；問題是恢復後可能多花一輪處理衝突。

因此，我支持先改善恢復時的狀態呈現，並在執行寫入前保存已接受的完整工具呼叫與穩定操作身分。這樣可以減少「文件已更新，但執行來源完全消失」的情況。

`(base_revision, payload_sha256)` 可以作為**完全相同操作的額外辨認機制**，但必須包括：

- 文件身分、操作類型及目標區塊；
- 完整修改內容；
- 所引用的固定內容／圖片版本；
- 預期基底版本。

只比較表格內容或檔案 hash 不足夠：相同內容插入不同位置，可能是兩個合法操作。「幾乎相同」的模型重試，也不會有相同 hash。

即使辨認出原操作，也應區分：

> 該操作已產生 rev=4；文件目前可能已經是 rev=5。

不能回傳 rev=4 的收據，就讓模型誤以為 rev=4 仍是目前版本。

還有一點：**某筆工具結果沒有出現在整理後的活躍輸入，不代表它尚未被交付。** 不應每輪掃描精簡歷史，再把所有「不見了的收據」重新貼回來。

**3. SQLite 是合適候選，但「所有關鍵轉移都原子完成」仍然說得太滿。**

我同意：

> 對不可變的基底 revision 做解析與驗證，再以短交易檢查目前版本並提交。

但 SQLite 交易涵蓋的是資料庫內的更新。外部 blob 檔、Pi session 或 LangGraph checkpoint，不會因為用了同一個 app 資料庫，就自動加入該交易。

實作應明確安排：

1. 先完成被引用的不可變檔案。
2. 再提交文件 revision、檔案引用和操作收據。
3. Framework session 可以稍後接收結果；中斷時依收據恢復。

這樣可能留下未被引用的準備檔，但應避免產生「已提交版本指向尚未完成檔案」的狀態。

「持鎖低於 1 毫秒」應撤回為未測量的性能目標。WAL 仍只有一個 writer，checkpoint 和同步設定亦影響延遲與耐久性。[SQLite WAL](https://www.sqlite.org/wal.html)

我也不會現在固定那五張表，因為有幾項責任還混在一起：

| 提案中的欄位 | 建議修正 |
|---|---|
| `evidence_records.retention_state` | 保留／釋放屬於某個 context 的選擇，不是證據本身的永久屬性 |
| `requirements_json` 與 `agent_notes_json` | 分清使用者要求、原始來源和 agent 的工作判斷；筆記不能悄悄改寫要求 |
| `acknowledged_in_turn` | 定義它代表已記錄、已組裝進請求，還是收到回覆；不能表示模型已理解 |
| 每版完整 `blocks_manifest_json` 等 | 不可變版本可以重用未變區塊，未必需要每次複製整份文件 |

**4. 圖片必須可追溯，但不能把「由內建工具產生」變成唯一合法來源。**

附件提醒檔案匯入不能繞過圖片要求，這點正確。但它把「受管資產」和「已證明忠實」混得太近。

合法的腳本可能完成目前內建工具沒有的裁切、組合或格式處理。App 應提供**匯入與登記這些成果的途徑**，按資產種類記錄來源和處理方式，而不是要求 agent 改用指定工具重做。

核對方式亦應隨來源而異：

- 原生圖片：保留原始編碼、尺寸及來源引用；原始 JPEG 可以原樣保存。
- Raster 裁切：關注保留像素、裁切範圍及無損保存。
- PDF 向量／複合圖渲染：關注來源頁、區域、渲染參數和可讀性。

不是每種圖片都需要同一組「頁碼、座標、DPI」才能成立。[專案圖片要求](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/PRODUCT_REQUIREMENTS.md:24)

Metadata 可以證明來源關聯和處理記錄，**不能單靠它證明沒有裁掉圖例、選錯面板或漏掉標籤**。這些仍需要實際內容核對。未確認資訊可以保存在草稿中；完整交付的判斷應對齊真正的品質問題，不能新增一套逐圖批准流程。

**5. Evidence Stub 有用，但它應是檢索入口，不是防遺忘保證。**

我支持釋放大型證據後留下容易理解的線索，例如：

> 第 13 頁；表格候選；底部有小字區；完整 layout／原圖可取回。

但「徹底消除盲目釋放風險」不成立。真正重要的註腳可能沒有被 heuristic 找到，而 100 字元摘要也可能沒有保留關鍵關係。

此外，長文件若每份證據都永久在 context 留下一條 stub，索引本身也會逐漸膨脹。較好的安排是：

- 完整索引持久保存，可依頁、類型、文字或 ID 查找。
- 活躍 context 保留目前工作相關的入口與未解依賴。
- 查找結果可以展開到精確範圍及原始圖片。
- 整理筆記時，必要時仍能讀原件，不能只摘要前一輪的 stub。

附件把 B/C 未使用釋放功能，聯想到「怕遺忘所以全部保留」，也超出了現有證據。那些記錄沒有建立這個動機。

幾何提示可以逐步加入，但不需要先把所有候選偵測器造完。另有兩個小修正：

- `confidence: "heuristic"` 表達的是**方法種類**，不是可信度。
- 單比 `origin[1]` 只適合特定文字方向；旋轉文字需要考慮 line direction。PyMuPDF 的 superscript bit 本身也包含程式偵測，因此較準確的分類是「抽取器回報值」與「app 額外衍生判斷」。[PyMuPDF TextPage](https://pymupdf.readthedocs.io/en/latest/textpage.html#span-dictionary)

**6. 真正應優先補齊的是 context 的運行契約。**

目前提案已足以描述資料放在哪裡，卻還不足以回答以下問題：

| 情境 | App 必須有明確行為 |
|---|---|
| 一次工具結果很大 | 保存完整結果，明確回報容量情況；讓 agent 選擇可用範圍或表示法，避免隱藏截斷 |
| 準備整理 context | 計入規則、工具 schema、歷史、圖片及輸出／交接餘量 |
| 交接筆記失敗或不完整 | 保留可用的舊狀態，不切換到缺少工作資訊的新 context |
| 整理完成 | 實際檢查下一次請求具有有效要求、目前成果、未解問題及精確取回入口 |
| 切換到較小 context 的模型 | 重新評估容量及圖片能力，不假設上一模型的工作集仍然適用 |

圖片檔案的 MB、JSON 字元數，都不能直接當成模型 context token 數。

這些才決定 agent 能否在長文件中持續工作。它們不要求固定百分比、固定頁數，也不要求每次都叫模型另寫一份摘要；可以按實際容量與工作狀態處理。

**7. 公開接口方向正確，但 Pi 的回傳型別仍然寫錯了。**

附件把 Pi 的 session 儲存格式再次拿來當作工具回傳格式。

Pi v1.3.0 的工具 `execute()` 回傳的是 `AgentToolResult`，包含模型可見的 `content` 和結構化 `details`；runtime 再組成 `toolResult` 訊息。不能直接將 `type: "message", role: "toolResult"` 當作工具結果回傳。[Pi 工具型別](https://github.com/earendil-works/pi/blob/v1.3.0/packages/agent/src/types.ts)、[Extension 工具介面](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/src/core/extensions/types.ts)

這也提醒我們：**App 的業務收據應獨立於框架訊息格式。** 重用原收據時，由 adapter 包裝成目前呼叫所需的結果；例如新的 LangChain tool call 必須配對新的 call ID。

測試方面，「終止程序」與「切斷 IPC」亦應分開：後者可能讓子程序繼續完成工作。真實自主性檢查則應看完整成果和方法選擇是否合理，不能要求 agent 必須使用匯入、釋放及預覽修正每一項機制。

**我的設計建議是先確定上述責任與契約，再定資料表和主控語言。** Pi 可以使用 TypeScript runtime，透過工具服務使用 Python／PyMuPDF；`create_agent` 也可以直接在 Python 中接入同一份文件服務。完整重構的自由，讓我們可以按總維護成本選擇，不必先要求你表態偏好哪種語言。

這輪值得保留的主幹已經清楚：成熟 runtime、可靠的文件／證據服務，以及一套由 app 執行、agent 參與決策的 context policy。下一份技術規格應優先寫清楚**模型實際看見甚麼、何時切換 context、失敗時保留甚麼**，其餘快取技巧、幾何提示和額外去重可以按需要加入。
