**我仍支持以「小型 LangGraph StateGraph＋共用 Nexus 請求服務＋文件／證據核心」作為重構設計基準。** 這版有值得保留的改進，尤其是處理歷史中的草稿參數、提供候選內容的局部重用，以及把匯出獨立於模型額度。

但它還不適合直接定為「最終契約」。幾處承諾超出了機制實際能保證的範圍，也有幾個路徑會影響正常轉換。

**1. 草稿參數確實需要納入 context 管理，但「已保存」不應自動等於「立即撤回」。**

文章指出大量正文會留在 `AIMessage.tool_calls` 的參數中，這點成立。只處理 OCR、圖片與工具回傳，確實可能漏掉另一個主要來源。

我建議清楚區分：

- **原始紀錄**：保留實際模型回覆、工具參數及執行結果，供追溯與恢復。
- **下一次模型輸入**：已完成的舊操作，可以使用明確標示的精簡表示與精確引用。
- **目前工作內容**：正在修改的段落、未完成表格及必要前後文，仍可完整留在工作集。

例如，剛保存一段正文、下一輪準備修正其中兩個字，立即把全文撤回可能只會增加重新讀取。是否保留仍應由 agent 的工作需要與 app 的容量管理共同決定。

另外，**保留 `tool_call_id` 並不足以證明修改後的歷史一定符合所有 Nexus 路由的協議要求**。投影不能改掉執行重播所依據的原始呼叫；目前尚未完成的工具呼叫也必須使用完整原參數。

「消滅 90% 膨脹」沒有量測依據，應改成可驗證的設計目標，不能當成預期收益。

**2. 滾動整理的方向合理，但目前的成功條件會阻止它滾動。**

提案一方面允許多輪整理，另一方面要求每輪完成後「總容量低於目標水位」。

假設目標是 80k，第一輪把歷史從 140k 減到 100k：這是有效進展，卻會被後者判定失敗。

應拆成兩個條件：

| 判斷 | 應檢查甚麼 |
|---|---|
| 這次整理能否套用 | 基準仍有效、替換範圍正確、未處理內容保留，而且有有效縮減 |
| 能否恢復正常模型工作 | 最終組裝的指示、歷史、證據、工具定義等，連同輸出預留，能容納於本次請求 |

還有三點要修正：

- 「只摘要尾端、保留前段便完全不會減少容量」不成立。摘要任何區段都可能降低總量。**整理最舊前綴可以是第一版的合理預設，正確性的來源是精確替換範圍與保留未處理內容。**
- 當前版本與筆記錨點應固定到明確版本。摘要中的歷史敘述與「截至目前的工作狀態」要區分，避免把後來完成的事情混成早期事件。
- 覆蓋訊息 ID、基準 revision、錨點版本由程式記錄即可，不需要模型重新生成這些程式已知的資料。

訊息範圍吻合可以證明沒有誤刪未處理的訊息；**它無法證明摘要完整保留了語義。** 有效使用者要求、尚未完成的工作與可取回的原件，仍須受到保護。

**3. `wrap_tool_call` 是可用攔截點，但不能獨自完成原件保存。**

我核對了目前官方程式碼：ToolNode 的 wrapper 確實可以在工具執行及參數驗證前運行，所以用來保存「已解析成工具呼叫、但不符合工具 schema」的參數是合理的。[ToolNode 原始碼](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/prebuilt/langgraph/prebuilt/tool_node.py)

但更早還有 JSON 解析：

- LangChain 會把解析失敗的參數放入 `invalid_tool_calls`。
- 一般 ToolNode 從 `AIMessage.tool_calls` 取得待執行呼叫。
- 因此那些失敗內容不會自動進入同一個工具 wrapper。[工具參數解析原始碼](https://raw.githubusercontent.com/langchain-ai/langchain/master/libs/core/langchain_core/messages/tool.py)

適合我們的分工是：

1. Nexus 接收層保留符合既有保存規則的原生回覆／候選。
2. 共用工具派發器在工具 schema 驗證前保存收到的原參數。
3. 能解析的內容才建立區塊索引與精確重用入口；保存成功與可索引是不同結果。

這也不需要重新引入整套 LangChain agent middleware。現有控制器已經在呼叫 MCP 工具前保存參數；重構應把這個責任整理成共用入口。[現有參數保存](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/agent_tools.py:389)

內容引用與整組操作重用的區分可以保留。不過，**換了 `base_version` 後，舊刪除／替換操作仍須重新檢查適用性**，不能把改版本號當成已完成重定位。

**4. 版本血緣與操作收據各有用途，不能用目前指標代替歷史事實。**

`version_candidate_links` 很適合回答：

> 哪個版本曾引用候選稿的哪一部分？

它不能直接回答：

> 這段內容現在是否仍存在？相關工作是否已完成？

例如 V10 採用了某段，V11 又刪掉它。沿祖先鏈仍能找到採用紀錄，但目前文件已沒有該段。保留這種歷史來源關係即可；目前內容以指定版本為準，待辦事項由小型工作狀態表達。無須要求每個未採用片段都填寫處置報告。

恢復規則也要避免依賴「目前指標仍等於當時結果」：

- 操作 A 成功產生 V12，之後 B 產生 V13；重播 A 應回傳原本的 V12 收據。
- 操作 C 曾選定 V10，之後使用者選了 V11；重播 C 不應把交付指標改回 V10。

因此，收據應記錄**該操作提交時的結果**，並與當次版本／選擇變更一起提交。當前 head 或交付指標可以繼續前進。

讓 SQLite 擁有可變指標是合理的；同時，本次模型請求仍須保存「當時實際看到的版本與內容」。恢復既有請求時，不能偷偷換成最新 head。現有程式已拒絕恢復時輸入與保存請求不同的情況，這項保護值得保留。[現有請求核對](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/agent.py:623)

**5. 圖裡仍有繞過檢查的路徑，也缺少正常等待使用者的出口。**

目前兩條路直接回到模型：

```text
整理驗證成功 → AgentModel
交付條件未滿足 → AgentModel
```

整理本身可能耗盡預算，期間也可能收到取消。因此，**每次真正向 Nexus 發送請求之前，都必須經過共用的預算、取消與實際容量檢查**，包括整理呼叫。

這項檢查最好落在共用請求服務中。LangGraph 從 checkpoint 恢復會依恢復位置繼續執行，不能假設圖頂端的 Gate 必然再次經過。[LangGraph 恢復與重播說明](https://docs.langchain.com/oss/python/langgraph/use-time-travel)

服務應先查是否已有可回收的完成結果；需要真正發出新請求時，才檢查並記錄相應額度。這樣零剩餘額度仍可讀回已完成的結果。

此外，「沒有 tool calls，但文件未完成」也可能是 agent 正在詢問缺失資料。應有 `awaiting_user` 或帶明確原因的停止狀態，不能只因還有額度便再次呼叫模型。

**6. 不經模型匯出是正確方向，而且目前已有基礎；Finalizer 的保證需要收窄。**

目前 `Workspace.export(document, version)` 已可直接打包指定保存版本，CLI 也能直接派發這個操作。已有草稿不會因為模型額度耗盡便永遠無法匯出。[匯出核心](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/core.py:438)、[CLI 直接呼叫](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/cli.py:95)

真正值得改善的是：讓正常完成、額度耗盡及適用的停止情況，都能方便地交付已保存成果。

但圖上的收尾節點不能保證在程序被終止、機器關機或取消直接打斷執行時一定運行。可靠做法是保存匯出意圖與結果，讓宿主可以獨立執行或恢復匯出。

還要保留幾個界線：

- 取消後先停止新模型／工具工作；是否繼續大型打包，依清楚的任務政策處理。
- 自動匯出的最新草稿必須標示為草稿，不能取代原先選定的交付版。
- 「零模型 tokens」仍會消耗時間與磁碟資源。
- 只比對 `manifest.json` 的雜湊，不能證明包內檔案一致；也要核對實際檔案與包成員。
- 目錄與 ZIP 的發布不能籠統當成一次原子替換，亦不能覆蓋不屬於該匯出操作的既有輸出。

目前交付程式已逐項核對 ZIP 內容與保存版本，重構應保留這個程度的驗證。[現有交付核對](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/agent.py:795)

**7. `render` 與 `preview` 的輸入身份必須分開，否則會妨礙 agent 讀取來源。**

提案把兩者都要求為 `version_id` 或 `candidate_id`，這不適用於來源 PDF 的渲染。

應分成：

- **來源渲染**：來源 PDF 身份、頁面、區域、DPI 等參數。
- **成果預覽**：指定文件版本、預覽參數；可渲染的候選稿另行支援。

Agent 必須能在尚未保存任何草稿前查看 PDF。現有 `render` 正是以來源文件、頁面、區域及 DPI 工作。[來源渲染實作](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/core.py:134)

恢復時，圖片雜湊只能證明檔案內容未變；還要核對它是否來自這次需要的來源與渲染參數。

**8. IPC 的「零阻塞」承諾需要撤回，但可以保留實用的目標。**

以下條件不能在接收端無限期停讀時全部成立：

- 記憶體佇列有界；
- 任意數量的控制回覆永不丟失；
- 生產者永不等待；
- 系統持續接受新請求。

獨立 async task 和 ring buffer 不會消除這個限制。Python 官方文件也明確指出，管道填滿可以阻塞子程序。[Python subprocess 文件](https://docs.python.org/3/library/asyncio-subprocess.html)

較合適的契約是：

- 普通進度通知不阻塞轉換核心，可以合併。
- 重要操作結果先持久保存，UI 重連後可按請求 ID 查回。
- 佇列或儲存達到上限時，明確限制新請求。
- UI 透過快照恢復狀態，不依賴每一條進度事件。
- 協議輸出與診斷分離，兩條管道都有人持續讀取。

`os.dup2` 可以是實作選項，但「啟動第一行必須使用它」不應寫成通用契約。具體做法應配合 Windows、MCP 和最終封裝方式驗證。

我會把重構的核心驗收放在一條實際工作情境：**agent 能讀清來源，保存被拒但有用的正文，精確修正局部內容，經過 context 整理或重啟後接續工作，最後匯出指定版本。** 圖負責執行邊界與恢復；讀取方法、OCR 使用時機、修改範圍及證據選擇繼續交由 agent 決定。

這版提出的本地測試可以驗證上述機制，但仍須把「機制正確」與「實際轉換忠實」分開。框架選型可以維持，優先把這些契約說準，便能避免繼續為每個問題增加一層抽象。

本輪僅核對附件、現有程式與官方資料；未修改專案，也未發出 Nexus 模型請求。
