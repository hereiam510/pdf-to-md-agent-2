**我支持這版「保留已有效的核心，集中改善內容重用、編輯與 context」的方向。** 「搶救完整子區塊」也是值得加入的能力。不過，近期原文保留、差集摘要、停止判定及資料歸屬，仍需要調整，才能避免新機制妨礙實際轉換。

我會優先修正以下六點，再定最終 schema。

**1. 我接受「完整子區塊可以搶救」，但要把它定義成精確擷取。**

上一輪「能解析的內容才建立索引」應說得更精確：**整份參數無法解析，不代表其中每個完整子物件都不能獨立解析。** 保存並重用這些片段，確實可以減少重寫。

但一般的 partial JSON parser 不足以證明區塊完整。我用目前環境做了小型離線檢查：

```text
{"blocks":[{"id":"b1","text":"A"},{"id":"b2","text":"B","page":
```

Pydantic 的 `allow_partial=True` 會回傳包含 `b2` 的物件，略去尚未讀完的 `page`。原文中的 `b2` 明明還沒有閉合。LangChain 的 `parse_partial_json` 也會嘗試補上引號或括號；這符合它的用途，但不能直接用來判定「原件中已完整生成的區塊」。[Pydantic partial parsing](https://pydantic.dev/docs/validation/latest/concepts/json/#partial-json-parsing)、[LangChain 解析實作](https://raw.githubusercontent.com/langchain-ai/langchain/master/libs/core/langchain_core/utils/json.py)

我建議的契約是：

- 從**同一次 attempt、同一個工具呼叫**的原生資料擷取，保留原件身份及精確位置。
- 辨識 JSON 字串、跳脫字元與結構邊界，只索引原文中確實完整閉合的子物件；不補字、不補缺失欄位。
- 搶救的是可供重用的內容。原失敗呼叫仍維持失敗／未完成，agent 必須以**新的完整有效操作**引用它，才能提交文件。
- 回報「已保存 13 個可解析完整區塊，其餘未確認」，不能直接宣稱「前 13 個內容正確」或「只需重寫第 14 個」。

最後一點很重要：語法完整不代表來源忠實，後面也可能還有尚未生成的第 15、16 個區塊。

專案確有保存 **8,419 字元不完整工具參數**的紀錄，但那次涉及串流中斷與服務錯誤，不能據此推定「最常見原因是輸出 token 上限」。這個功能有實際相關性，原因與收益仍應按證據描述。[既有紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:266)

另外，讓 agent 自主選擇分批保存、插入與附加，也能降低單次巨大提交的風險；不需要固定每頁或每幾個 block 提交一次。

**2. 「只有被新版取代的草稿才能撤回」仍然太嚴格。**

假設最新版本 V12 本身很大，agent 接下來只修改其中一個表格。如果因為 V12 尚未被取代，就要求其完整草稿參數繼續常駐，context 可能一直無法降到可用容量。

未完成的候選稿也是如此：它值得保存，不代表它的全部正文必須每輪送入模型。

較合適的判準是：

> 原件是否已可靠保存、能否精確取回，以及哪些內容仍對目前工作直接有用。

因此可以保留正在修改的段落、必要前後文與未決關係，其他部分以精確引用保存。這適用於最新版本、舊版本及未採用候選。

近期原文保留可以是良好的預設，但 `K` 不宜成為容量壓力下仍不可調整的硬限制。若逐輪移動固定視窗，還會逐輪修改歷史；若希望保持穩定前綴，「在有需要時集中更新工作視圖」會更清楚。

文章對快取的推論也應收窄：**剛產生的模型工具呼叫，尚未出現在上一輪的輸入請求中。** 在首次回送前投影它，不必然破壞上一輪已有的輸入前綴；修改更早已送過的歷史才是另一回事。實際快取效果仍取決於路由，不能直接保證「最大化」。

同一請求的重播一致性則由保存的請求快照負責，不需要靠永久保留近期原文來保證。

**3. 「只摘要錨點尚未涵蓋的差集」會引入新的依賴。**

這是本版最需要小心的 context 設計。

假設目前筆記已寫著：

> 表格跨到下一頁，後續列仍沿用前頁表頭。

整理模型因此不把它寫入 handoff。稍後筆記被更新，只留下「目前處理到第 18 頁」。如果後續輸入只帶新筆記與差集摘要，那條跨頁關係就不在模型眼前了。

差集摘要可以成立，但必須保證它所依賴的**確切錨點仍會被組裝進後續輸入**，或在替換錨點前把必要資訊合併進新的交接內容。只保存一個可查詢的 `anchor_version_id`，並不等於模型已取得那些內容。

第一版我較傾向：

> handoff 保留可繼續工作的必要狀態；只省略確定仍由其他固定欄位提供的資訊。

也不應把摘要內容限定為「殘留觀察、否定假設、跨頁線索」三類。有效使用者要求、待完成工作、已保存成果的位置、重要取捨，也可能需要保留。

滾動整理另有兩個細節：

- 淨縮減應比較**完整替換後的模型視圖**，包括新增錨點、引用及其他附帶內容；只比較摘要與舊區段可能低估新增開銷。
- 「最多兩三輪」可以是待驗證的可調設定，不能當成普遍充分的界線。應先沿用既有持久預算，並辨識是否一直重複整理同一內容而沒有有效進展。

清楚分段的 prompt 有幫助，但不能「徹底防止」模型混淆時序或遺漏資訊。

**4. 單次提醒可保留，但明確的等待／停止訊號應優先處理。**

文章指出「沒有工具呼叫」不一定代表應停機，這點正確。一次有限提醒可以處理模型只說「接下來開始 OCR」卻沒有實際呼叫工具的情況。

建議判定順序是：

| 已知情況 | 行為 |
|---|---|
| 使用者取消，或 agent 明確提出需要回答的問題／停止原因 | 直接進入相應狀態 |
| 沒有明確停止訊號，交付條件未滿足，而且仍有額度 | 可發一次具體的缺項提醒 |
| 同一停頓已提醒過，仍沒有可繼續的動作 | 保存結果並停止，說明尚未完成的原因 |

`awaiting_user` 應表示確實有等待使用者回答的問題。單純再次沒有工具呼叫，可以是 `stopped_incomplete`，不應一律把處理責任交給使用者。

最好讓 agent 透過可識別的控制訊號表達「等待回答／完成／停止」，例如小型控制工具或明確結果欄位，減少從自然語言猜測意圖。提醒紀錄也應能在恢復後辨識，避免重啟就再提醒一次。

這個機制能降低假性停工，但下一次模型輸出仍不確定，不能保證徹底消除。

**5. 兩種恢復情境已說清楚，但進入下一輪前還要核對整批工具呼叫。**

「重播第 N 輪使用凍結輸入；完成工具後才組裝第 N+1 輪」可以保留。

不過，一個模型回覆可能包含多個工具呼叫。例如：

```text
call A：修改文件，已提交 V12
call B：生成預覽，尚未完成
```

找到 A 的收據，只能證明 A 已完成。必須依已接受回覆中的完整呼叫清單，處理 B 的既有結果、待執行狀態或停止原因，才能正常進入下一輪。現有控制器已保存 `next_call` 與待處理操作身份，這項能力值得保留。[目前工具批次續跑](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/agent.py:660)

圖上另外兩條邊建議修正：

- **`invalid_tool_calls → ToolDispatch`**：應明確分出候選保存／搶救路徑，避免把保存成功當成執行許可。
- **整理套用失敗 → MainReq**：應先重新判斷目前容量與失敗原因。若仍是同一份超量內容，直接進主模型服務只會再次被拒絕。

共用請求服務的最終檢查仍然必要，但圖本身也應表達有意義的後續動作。

**6. 六張表可以是草案，完整性應由資料歸屬與交易邊界判斷。**

目前表格尚未清楚交代幾類重要狀態：

| 資料 | 需要明確的責任 |
|---|---|
| 模型步驟、凍結請求、已接受回覆、attempt 與累積預算 | 由現有 run journal 或指定持久層管理，不能隨 Graph 回退而重置 |
| 目前 context policy、筆記與 context revision | 明確指定當前狀態的擁有者；歷史快照不能成為第二個可變權威 |
| 文件正文、圖片、manifest 與 SQLite 版本紀錄 | 定義哪份是原件、哪份是索引或衍生結果 |
| 匯出意圖與三維終止狀態 | 保存在明確位置，讓宿主可獨立查詢與恢復 |

這不表示一定要增加四張表。現有檔案紀錄或 Checkpointer 可以承擔部分責任，但需要在設計中說明。

尤其現在一方面要保留 `core.py` 的不可變版本檔案，另一方面又在 SQLite 放完整 `blocks_json`，必須避免兩份都成為可獨立修改的正文。

沿著目前實作，我較傾向：**完整內容保留為不可變版本檔案，SQLite 管理版本身份、manifest 雜湊、分支指標及操作收據。** 若要把正文正式遷入 SQLite，也可以，但應把文件保存流程一起重新設計。

「四個模組」也可以只是責任分組；模型通信與文件匯出各自保持清楚的介面，無須為了模組數量放進同一個大型服務。

文章引用的 228 項測試確有紀錄，但屬於當時版本的受影響測試集。它支持保留已驗證能力，不能直接替新的儲存與恢復架構背書。[測試身份與範圍](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:198)

對附件最後提出的先後次序，**我會先定「精確內容重用＋插入／附加＋局部頁碼更新」的契約，同時固定共用請求服務的既有預算與請求快照規則。** Context 投影與整理需要穩定的內容身份、讀取方式和保存結果，這些介面先清楚，後續才容易保持簡單。

完整候選重用應先成立；不完整呼叫中的區塊搶救可沿同一套引用機制加入。最終要驗證的是：正確內容能保存並精確修正，context 整理後仍能繼續完成來源要求，指定版本能可靠交付。這個方向保留 agent 的方法選擇，也讓重構直接改善轉換成果。
