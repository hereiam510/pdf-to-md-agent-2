**我仍支持以 `create_agent`＋持久化 LangGraph Checkpointer 作為優先設計基準，但這份提案還不能直接轉成實作規格。** 其中有兩項框架／實測解讀需要修正，以及一個會讓恢復視圖漏掉資料的筆記水位設計。

也先校正它對上一輪的引用：Pi 的 `Agent.continue()` 限制，只能反駁「載入 session 就必然自動補跑工具」這個假設，**不是判定 Pi 整體不適合的決定性證據**。目前偏向 LangGraph，主要仍是希望減少我們自行維護執行恢復的責任。

**1. 「Superstep 未完成，所以三個工具必定全部重跑」並不符合目前 `create_agent` 的實作。**

我核對的公開原始碼會對每個待執行工具分別建立：

```python
Send("tools", [tool_call])
```

並不是把整批工具視為唯一不可分割的工作。LangGraph 又有 *pending writes*：同一 superstep 中，個別工作已完成且已持久化的結果，可以在恢復時重用。[create_agent 原始碼](https://github.com/langchain-ai/langchain/blob/021dce467195a8c767ec3e1a807eda546c17994c/libs/langchain_v1/langchain/agents/factory.py#L2021)、[LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

所以不能由「完整 checkpoint 尚未推進」直接推出「OCR 一定重跑」。

**不過，保存昂貴工具的完成紀錄，仍然值得做。** 原因是工具產出落盤與框架保存完成狀態之間，仍可能存在時間差。我的建議是：

- 優先使用框架已保存的執行結果。
- App 保存 OCR、渲染等可重用產出，以及文件修改收據，補上跨儲存的空隙。
- 重用前核對來源版本、工具參數及產出是否完整。
- 只有「沒有成功收據」時，不能立即推定操作從未執行，尤其是任意腳本。

另外，**短路應省掉重新運算，不應自動降低結果的完整度**。原本要求完整 OCR，且容量容許，就應從保存的結果交付完整 OCR，而不是重啟後一律只回傳 `evidence_id`。

收據身分也要修正：正文說 `(session_id, tool_call_id)` 唯一，schema 卻寫 `tool_call_id UNIQUE`，兩者不同。應以 app 的穩定操作身分為核心，保留框架呼叫身分及精確輸入的對應；`args_summary_json` 不能獨自承擔一致性核對。

**2. 最需要修正的是：不能在寫入任何筆記時，自動把 `covered_up_to_event_seq` 設成資料庫最新值。**

這會把「資料已經提交」誤當成「agent 已經看過並整理」。

例如：

1. agent 根據截至事件 100 的輸入，發出一則筆記和一個 OCR 呼叫。
2. OCR 先完成，寫入事件 101。
3. 筆記稍後保存，系統自動標成「已覆蓋至 101」。
4. 恢復時只找 `event_seq > 101`。

**事件 101 的 OCR 結果便被排除，但 agent 根本還沒收到它。**

即使沒有並行問題，一則「第 15 頁單位存疑」的筆記，也不代表先前全部工作已整理完畢。

我會分清三件事：

| 紀錄 | 表示甚麼 |
|---|---|
| 筆記寫入位置 | 何時保存這則筆記 |
| 筆記依據的 request／輸入視圖 | agent 形成這則筆記時，實際獲得哪些資料 |
| 歷史整理範圍 | 某次整理實際替換了哪些訊息 |

`event_seq` 可以繼續作為排序與查詢索引，但不能自行證明語義覆蓋。真正整理歷史時，才記錄整理範圍；普通筆記更新不能自動推進這個邊界。

同時，若多個並行工具都可附帶筆記，應採明確的增補／修改操作，或版本衝突檢查，避免兩份完整 `active_notes_json` 互相覆蓋。

**3. 保留 assistant 原文有價值，但提案引用的實測不支持它的主要推論。**

我回查了它引用的那次八輪實測：

- 累計輸入確實是 **636,591 tokens**。
- 累計輸出確實是 **1,587 tokens，包含 137 reasoning tokens**。
- 單次輸入峰值是 **96,996 tokens**，不能把累計輸入當成單一 context 大小。[既有 metrics](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/workspaces/core-delivery-validation/metrics.json:24)

更關鍵的是：**前七輪原始回應的 `assistant.content` 都是 `null`；第八輪才有 508 字元的文字內容。** 前七輪主要透過工具呼叫輸出內容。[原始回應紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/workspaces/core-delivery-validation/workspace/agent-runs/bdc032cac806419b9612c40927dbcf99)

因此，這組資料不能支持：

> 重要語義判斷幾乎都已寫在 `AIMessage.content`，保留它就能恢復。

判斷可能表現在工具參數、候選成果或已公開的文字中，也可能根本沒有外顯。Reasoning token 數量本身，更不代表存在完整、可取得、可跨 provider 重播的工作筆記。

我會採用以下原則：

- 保留確實存在且有用的近期 assistant 文字、完整工具呼叫與候選成果。
- 不能假定所有重要判斷都已被寫出。
- agent 可隨時保存重要發現；必要整理時再建立可繼續工作的筆記。
- 恢復視圖仍須受容量管理，不能永久無條件保留所有 assistant 文字。

至於每個工具都加入 `note_on_previous_step`，我不會立即定案。它會增加 schema 與輸出內容，也引入重播、失敗和並行筆記的處理問題，不能稱為「零成本」。獨立筆記工具也可以與讀取工具在同一次模型回應中發出，**多一個工具呼叫不必然多一輪模型呼叫**。應比較實際使用便利性，而不是從過往未使用直接推定原因。

**4. 圖文分軌估算合理，但「扣掉文字增量，就知道圖片真實成本」仍然過度確定。**

這裡至少有三個限制：

- 「本輪沒有新圖片」不等於純文字請求；歷史圖片可能仍在實際輸入中。
- 本地 tokenizer 精確計算某段文字，不代表精確知道 Nexus 上游的完整訊息／工具封裝。
- 兩輪之間還可能改變工具結果、圖片表示、上下文投影或實際路由，剩餘增量不能唯一歸因於新圖片。

在其他條件穩定且計數方式已知時，增量法可以提供觀測；一般工作回合則只能作校準線索。

**單張預留 1,500–2,500 tokens 也不能當作通用上限。** OpenAI 官方圖像文件本身就有單張圖片達 3,000 tokens 的例子，且不同模型採用不同規則。[官方 Images and vision 文件](https://developers.openai.com/api/docs/guides/images-vision#calculating-costs)

我支持分軌估算，但會把它定義成：

> 已知路由規則＋實際請求組成＋觀測誤差，產生帶有不確定性的容量估算。

這不要求新增付費探測，也不應讓某個尚未校準的係數成為 app 能否正常工作的前置條件。

**5. 延遲釋放、視覺委派與生命週期清理可以採用，但要保留正確的操作語義。**

| 機制 | 我建議的設計 |
|---|---|
| 延遲批次釋放 | 區分「允許 app 擇時移出」與「agent 要求下一輪移出」。後者可能為了減少干擾或移除過時資訊，不能只因容量寬裕而延後。 |
| `query_visual_evidence` | 保留為選用能力；允許局部、整頁或相關多頁，避免強制裁切後失去表頭、圖例與跨頁關係。 |
| 視覺工具結果 | 保存問題、實際圖像／區域、模型身分、回應與不確定性，作為可追溯的模型判讀；原始像素仍是來源。 |
| 啟動／結案清理 | 啟動時先辨識可恢復任務及未完成操作，再清理確定可丟棄的暫存。沒有活躍程序，不代表沒有值得保留的準備成果。 |

延遲釋放是一項可調整的成本策略，不是所有情況都更好。視覺委派則確實能讓文字模型繼續參與工作，但不能把衍生判讀自動升格成已確認的來源事實。

**6. 提案的並行例子，還有一個直接影響交付品質的問題：預覽究竟檢查哪個版本？**

`update_draft()` 和 `view_preview()` 若同時執行，而預覽預設讀取「最新草稿」，便可能拿到修改前的版本。即使沒有崩潰，agent 也可能誤以為已檢查新稿。

我會要求：

- 草稿修改回傳明確的 `produced_rev`。
- 預覽、讀回和匯出都對應明確版本，並回報實際處理的版本。
- 若預覽依賴剛修改完成的稿件，就保留這個依賴；無關的 OCR／讀取仍可並行。

這不需要固定轉換流程。它讓 agent 自己安排工作，同時避免「檢查的是舊稿、交付的是新稿」。

**7. 我會保留目前的分層，讓兩個 middleware 的責任更精確。**

| 部分 | 應承擔的責任 |
|---|---|
| LangGraph | 保存執行狀態、待執行工作及已完成結果；透過公開接口恢復。明確選擇持久化模式。 |
| `wrap_tool_call` | 執行／重用工具操作，保存完整產出、版本身分與收據。 |
| `wrap_model_call` | 看齊整批結果後，組裝本次實際輸入、選擇證據表示、估算容量並保留輸入來源。 |
| App 文件／證據服務 | 管理不可變原件、草稿版本、資產和精確取回。 |
| 工作筆記 | 保存 agent 的發現與依賴，連結其依據的輸入與成果版本。 |

重型 OCR 和圖片資料宜保存在產出儲存中，checkpoint 優先持有穩定引用，避免反覆複製巨大載荷。組裝模型請求時仍可直接補入完整原文與原生圖片，**不因此增加摘要門檻或限制完整讀取**。

恢復也應依框架的待執行工作與中斷狀態處理，不能只檢查最後一則 `AIMessage.tool_calls`。持久化模式同樣影響保證：LangGraph 的 `sync`、`async`、`exit` 對程序崩潰的保障不同，僅指定 SQLite Checkpointer 還不完整。[持久化模式](https://docs.langchain.com/oss/python/langgraph/checkpointers#durability-modes)

**我的建議是維持這個框架基準，先修正操作身分、筆記覆蓋、版本依賴和實際輸入這四項契約，再定 SQLite schema。** 架構已足夠容納需求；目前需要的是把行為定義準確，讓框架提供的恢復能力真正減少自訂程式。
