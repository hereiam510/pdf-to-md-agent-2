**這版已足以固定主要模組邊界：小型 LangGraph、SQLite metadata、不可變檔案，以及共用 Nexus／工具執行服務。** 我會保留這個方向。接下來最需要定清楚的是：壓縮結果如何取代歷史、候選內容究竟採用了多少，以及各種操作如何恢復。

以下幾點會直接影響 app 是否能保住正確成果、可靠續工。

**1. Compaction 有了請求身分，但「覆蓋哪些歷史」和「如何套用」仍未完成。**

提案說撤回大型證據後，compaction 請求就「確定放得進視窗」，這仍不成立。歷史可能主要由長篇使用者要求、agent 草稿和大量工具往返組成；即使撤回 OCR，剩餘內容也可能超量。

「僅載入可容納之歷史範圍」可以實作，但必須回答：**沒載入的部分，之後怎麼處理？**

我建議每次整理至少記錄：

- 本次實際提供給模型的歷史範圍／message IDs。
- 採用的上一份交接摘要及其覆蓋範圍。
- 尚未整理的歷史。
- 本次整理所依據的 context revision。

只有已處理的範圍，才能由新交接內容取代。未處理部分不能因為「已完成一次 compaction」就一起移出活動歷史。切分也須保留完整工具呼叫／結果配對。

LangMem 的實作確實記錄 `summarized_message_ids` 和最後整理位置；但其文件也說明，超過摘要模型容量時可能只取末端部分。因此，這些機制可以參考，不能直接當作完整歷史交接的保證。[LangMem 官方原始碼](https://raw.githubusercontent.com/langchain-ai/langmem/main/src/langmem/short_term/summarization.py)

另外，圖裡缺少 compaction 回覆之後的明確路徑：

```text
準備整理請求 → 模型產生交接內容
→ 檢查覆蓋範圍、格式、容量及基準 revision
→ 套用新的 context → 繼續正常工作
```

不能沿用一般的「沒有 tool calls → delivery check」。空白、被拒、格式無效或已過時的摘要，也不能取代原有 context。

這些檢查可以由程式完成結構與身分核對；**語義上保留甚麼，仍由 agent 判斷**，不需要再加一個隱藏品質裁判。

**2. `block_ops_from_candidate` 重用的是編輯操作，還不是「只重用內容」。**

這是本版最明顯的概念混用。

`block_ops` 可能包含：

- 正文替換。
- 刪除其他區塊。
- 區塊重排。
- 依賴特定舊文字的 patch。

假設候選裡有一段正確正文，以及一個後來不再適用的刪除操作，agent 不能只為取回正文，就被迫重用整組操作。

我會保留兩種明確能力：

| 能力 | 用途 |
|---|---|
| 引用候選中的文字／區塊 | 把正確內容放進新的編輯，重新指定位置、來源對應和 metadata |
| 重用整組候選操作 | 當原編輯意圖仍成立時，重新驗證並執行完整操作集 |

內容引用可以很簡單，例如以 `candidate_id + JSON pointer` 指向已保存正文。這不是跨呼叫的隱式參數合併。

還有一個直接的使用情境：`save_draft` 失敗時保存的是 `blocks`，未必有 `block_ops`。若恢復入口只接受 `block_ops_from_candidate`，初稿保存失敗反而無法自然重用。

前置保存也應先完整保存原參數，再建立可辨識內容的索引；**索引失敗不能導致原候選保存失敗。** 因為這層本來就是用來保護結構不完全正確的輸入。

三個工具表面——`save_draft`、`edit_document`、`select_delivery`——可以保留，沒有必要再為工具數目反覆重設架構。

**3. 候選的採用狀態需要屬於分支，而且不能只有整份採用／未採用。**

把候選生命週期寫清楚，比時間戳判斷好。但目前查詢只有：

```sql
WHERE task_id = ? AND lifecycle_status = 'active_unresolved'
```

在同一任務有多個分支時仍可能出錯：分支 A 採用了候選，並不表示分支 B 也完成了相關工作。

我會分開保存：

- **候選原件：** 不可變，可被多個分支引用。
- **處置關係：** 哪個分支採用了哪些內容、產生哪個版本，或明確放棄哪些內容。

例如候選有三個區塊，只採用兩個，剩下一個仍可能需要處理。此時不能把整份候選標成已解決。也不能僅因新候選涉及相同頁碼，就推定它完整取代舊候選。

不需要先建立龐大狀態機；少量明確引用和採用關係已經足夠。提交版本與登記該次採用關係，則適合放在同一個 SQLite 交易完成。

**4. SQLite 分層合理，但不同操作不能共用同一套「補提交」規則。**

提案將文件版本與任務分支指標分開，我同意。需要補充的是：`save`、`select_delivery` 和 `export` 的成功條件不同。

| 操作 | 恢復時應核對的事情 |
|---|---|
| 保存／編輯版本 | 是否已提交；目標分支的預期基底是否仍成立 |
| 選擇交付版本 | 該版本是否有效、任務範圍是否吻合，以及選擇操作是否已完成 |
| 匯出 | 指定版本的包是否完整、一致，是否已完成指定目的地的交付 |
| render／preview | 是否已有可用結果；未完成時是否可建立新的獨立 attempt |

例如 agent 正在 V12 工作，但選擇匯出 V10，這完全可能是合法行為。匯出不應因工作 head 已前進而被當成過時編輯拒絕。

Graph checkpoint 中若也保留工作版本引用，應把它當作當時的執行上下文；恢復時不能直接用它覆寫 SQLite 中已提交的較新分支狀態。

此外，我不贊成把「刪除未完成 `attempt_dir`」當成重新渲染的必要步驟。裡面可能已有可用圖片或診斷結果。應先對帳並重用完整結果；需要重跑時建立新 attempt，保留原結果及身分。**允許自動重試，不代表需要先清掉舊成果。**

**5. 終止分類應拆開執行狀態、內容聲明與交付狀態。**

提案的五種分類混合了三件不同的事：

| 面向 | 例子 |
|---|---|
| 執行 | 正常結束、等待回答、取消、預算耗盡、效果未能對帳 |
| 內容 | 草稿、指定範圍已聲明完成、仍有必要缺口 |
| 交付 | 未匯出、已匯出、包與選定版本一致性已核對 |

這些狀態可以同時存在。例如任務被取消，但已保存並匯出可用草稿。

`completed_verified_delivery` 容易被理解成內容也已驗證正確。建議讓「verified」明確只指包與版本的一致性；來源忠實度和完成範圍仍須保留相應的檢查／聲明依據。

另外有三個需要修正的規則：

- **無未決候選不應成為普遍交付門檻。** 候選可能是可選的試改方向；真正阻止完成聲明的是當前必要範圍仍有缺口。
- **預算耗盡後，Resume 不會產生新額度。** 若剩餘預算為零，就不能承諾在原限制內繼續模型工作；可以匯出已有成果，或在使用者另行授權後建立新的續工作業。
- **遠端結果未知與本機效果未對帳必須分開。** 已約定的有限自動恢復，在啟用且預算仍有餘額時，允許遠端結果未知的 bounded replay；重構不能把它改回一律停機等待確認。[既有恢復契約](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/TOOLS.md:201)

使用者取消也應有獨立原因，並繼續遵守只有明確續跑才清除取消狀態的規則。

**6. 結構化進度值得做，但不能讓 UI 接收速度控制轉換是否繼續。**

目前技術文件確實選擇非同步 stdio JSON 作為桌面連接方向，但尚未實作，訊息格式仍是開放選擇。[TECHNICAL_STACK.md:26](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/TECHNICAL_STACK.md:26)

我會採用：

- 持久狀態是事實來源，進度事件負責通知。
- 重要狀態提交後才發事件。
- UI 重連時先取得當前快照，靠 revision／sequence 辨識新舊事件。
- 高頻文字進度可以合併，不能因 UI 慢或暫時離線而卡住模型／工具執行。
- 診斷輸出與協議訊息分開。

stdio 管道確實可能因接收端沒有持續讀取而阻塞；Python 官方也記載了這類情況。[Python subprocess 文件](https://docs.python.org/3/library/asyncio-subprocess.html)

進度的語義同樣重要：

> 「OCR 第 12 頁完成」只能表示該次識別完成，不能把第 12 頁直接標成轉換完成或內容已核對。

版本差異預覽則應讀取明確版本的內容來產生。進度事件告訴 UI 有哪個版本變動，不能代替文件資料本身。

**我會把第一版的重點放在四個可觀察的結果：**

- 保存被拒後，能引用正確正文，只修必要部分。
- 分支或恢復不覆蓋其他已完成工作。
- Context 整理有明確覆蓋範圍，成功套用後能接續未完成工作。
- 使用者隨時能知道目前保存了甚麼、為何停止，以及哪個版本可以交付。

路由容量的自動調校、更多工具並行和完整版本比較介面，可以在這條完整流程成立後再擴充。這樣能保留 agent 自主性，也讓新增的每個機制都有清楚用途。
