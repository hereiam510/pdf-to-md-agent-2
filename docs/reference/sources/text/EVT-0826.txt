**這版最值得採納的方向，是把設計重心拉回「證據是否看得清楚、正確內容是否容易保存與修正、長任務是否能接續完成」。** 不過，部分歷史資料被推論得太遠；新增的像素分析、章節子代理，以及沿用舊傳輸程式，也不能直接視為已證明有效的方案。

我的建議仍是以 **LangChain `create_agent`＋持久化 Checkpointer＋App 自有文件／證據服務**作為設計基準，但優先改善文件操作與證據使用，將其他能力保持可選。

**1. 先校正歷史證據，否則容易為錯誤的原因設計功能。**

13 頁試驗確實存在強調格式與字形缺陷，這支持我們改善來源核對、編輯與實際輸出預覽。但另外三個推論需要修正：

- **40 頁試驗不是在 1,200 秒耗盡任務時間。** 對應紀錄的設定是 3,600 秒／100 回合；A2 結束於 HTTP 408 不完整串流，B2 結束於第 57 次請求逾時。工具摩擦、大量 OCR 重讀確實存在，但不能將它們認定為逾時的已證實原因。[40 頁試驗紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:439)
- **9 頁任務沒有主動使用 context 工具，不等於設計失敗。** 那些任務已完成並通過範圍內驗收，也沒有觀察到容量限制。可能是不需要，也可能涉及操作負擔；目前不能確定原因。[自然採用紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:166)
- **短任務的每頁時間不能證明整本書需要特定架構。** 線性外推可以作粗略預算參考，但不能證明單一 Agent 必然失敗、子代理必然較快。

因此，應保留「改善工具人體工學」這個結論，撤回「已找出三大病根」的說法。

**2. 我會把文件編輯與正確內容重用，放在像素分析之前。**

有一項歷史證據很有指向性：40 頁試驗中，`本文件` 在被拒絕的原始候選稿內是正確的，後來重新組織內容時卻變成 `本文作`。[原始紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:471)

這說明部分品質問題發生在**正確內容已經產生之後**。增加 OCR 或視覺提示未必能解決這類退步。

完整重構時，文件核心應自然支援：

- 以穩定區塊 ID 插入、替換、刪除、移動內容，也允許整段／整章重建。
- 從既有候選稿或工作檔匯入精確內容，修正 metadata 時不用重新生成正文。
- 更新局部頁碼對應，由 App 驗證整體一致性，避免每次重傳全書映射。
- 修改附帶所依據的文件版本；若使用者或其他工作已修改相關內容，回報差異並保留候選修改。
- 保存、預覽、重新開啟與匯出都指向明確版本。

這不要求每次只能做小修改，也不要求每次修改都經人工確認。它讓 Agent 自由選擇重建範圍，同時減少因工具限制而重寫正確內容的機會。

**另外，預覽能力應支援直接比較「某個來源區域」與「對應的已保存區塊」。** 粗體問題可能來自來源判讀，也可能來自 Markdown 標記或實際渲染；兩側都容易取得，才能定位問題。是否使用比較工具，仍由 Agent 決定。

**3. 多區域對照圖值得優先考慮；墨跡密度只能先當候選提示。**

我支持 `render_regions([{page, bbox, label}, ...])` 這類能力，尤其適合比較易混淆字形、表頭、上下標及相鄰段落的強調方式。

但工具的價值應建立在以下契約：

- 每個區域都有來源頁、座標及渲染參數，能單獨重讀。
- 標籤放在來源像素之外，保留足夠上下文，避免裁掉字形或關係。
- 可以返回多張獨立圖片，也可以返回拼圖；Agent 可以選擇。
- 保留原始區域與原圖，不把拼圖當作唯一證據。

**一張拼圖並不保證比多張圖片便宜或清晰。** 拼圖過大、字形在整張圖中的比例太小，都可能抵消局部裁切的好處；不能只用檔案大小判斷成效。

對 `pixel_ink_ratio`，我會更保守。數值可以是可重現量測，但它量到的未必是粗體：

- 不同中文字本來就有不同筆畫密度。
- 字級、框選邊界、掃描背景、墨水擴散與二值化都會影響結果。
- 隱藏 OCR 文字框未必精確對齊可見字形。

Tesseract 官方也把背景、雜訊、墨水擴散與影像處理列為辨識品質的影響因素。[Tesseract 影像品質文件](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)

所以它適合先定位為「值得核對的視覺差異提示」，不能直接當成粗體標籤，也不值得預設為每個 span 都產生大量數值。**局部原始像素對照的適用性，比尚未驗證的粗體推測器更直接。**

**4. 長文件應支援分段持續工作，但不必先綁定兩層子代理。**

章節 Episode 是合理選項。不過，提案中的「突破 40 回合／1,200 秒物理瓶頸」需要改寫：

**那些是可配置的執行預算。子代理若共用同一份預算，就不會增加可用時間；若另開預算，則是在改變預算政策。**

真正需要解決的是：

> 做完一部分後，如何帶著必要資訊進入下一部分，而不反覆攜帶全部中間過程，也不遺失跨段關係？

這可以由同一 Agent 切換工作範圍，也可以由專責子 Agent 完成。兩者應共用：

- 有效任務要求及後續修訂；
- 當前文件版本與可重用候選稿；
- 尚未完成的範圍、未解問題及跨段引用；
- 同一份任務預算與操作紀錄。

LangGraph 確實支援每次呼叫重新開始、但在該次執行內保留恢復能力的子圖模式；它並不自動決定應傳入哪些要求、如何合併文件修改或如何判定章節完成。[LangGraph 子圖持久化](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

我會保留 Episode 介面，但不訂「超過幾頁就必須啟用」的規則。Agent 可以根據章節結構、跨頁依賴與任務難度選擇。

另外，提案說把子任務的數百萬字元 OCR／圖片「封存於子分支 Checkpoint」，又混淆了儲存責任：**完整證據仍進 Blob／證據庫，子分支 checkpoint 保存狀態與引用。** 父 Agent 收到的是確切產出、剩餘問題與可重讀入口，而非一個無法核對的「章節完成」摘要。

**5. 降低 context 管理負擔合理，但不能默默把「保存」當成「可以釋放」。**

讓 `update_draft` 順便提交 context 變更，確實能減少額外工具呼叫。但我不建議：

> 未列入 `keep_evidence_ids` 的未釘選證據，預設進入可釋放候選。

這會讓「Agent 沒有填寫某個欄位」變成語義授權。剛寫好的表格仍可能需要原圖核對；已讀過也不代表理解完整。

較清楚的方式是讓保存工具接受選填的變更：

```json
{
  "context_delta": {
    "release_when_needed": ["ev19"],
    "pin": ["ev20"]
  }
}
```

省略這個欄位，就維持原有決定。Agent 也可以單獨管理 context；已同意的容量政策則由 App 自動執行，不必反覆要求同樣指令。

這保留了我們原本的混合方向：**Agent 判斷語義需求，App 執行容量管理。** 容量不足時，App 可以要求整理、展開較小的工作視圖或套用已授權的釋放規則。

同時，這版仍偏重「工具證據」，一般對話壓縮也需要完整位置。使用者修訂、尚未寫入文件的推理結果、決策理由及未解問題，都可能存在於普通訊息中。它們不能因為已有證據庫就被忽略；這也是原先討論已同意保護的內容。[Context 討論紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/CONTEXT_MANAGEMENT_DISCUSSION.md:119)

**6. 自訂 Nexus adapter 是合理起點，但「原封不動繼承 228 項保證」不成立。**

我傾向先重用既有雙協定編碼、完整回覆驗證、圖片配對及診斷能力，再用薄的模型介面接入 LangChain。這符合我們目前已有的程式與 Nexus 路徑。

但不能說 `ChatOpenAI` 必然破壞所有保證。它的重試可配置，也支援圖片及 Responses；真正需要檢查的是實際路由的訊息格式與非標準欄位。官方明確指出，部分第三方擴充欄位不會由通用 `ChatOpenAI` 保留。[ChatOpenAI 官方整合文件](https://docs.langchain.com/oss/python/integrations/chat/openai)

另一方面，我核對原始碼後發現：

- 持久化嘗試帳本在 [`Agent.model_round`](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/agent.py:384)。
- Chat 圖片配對依賴 [`Provider.pending_images` 與 `flush_images`](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/provider.py:798) 的暫存狀態。

因此，只封裝 HTTP 發送函式不會帶走全部行為；直接把舊物件共享給不同執行範圍，也需要處理其暫存狀態。

正確的重構方向是**抽出可重用能力，再接上新生命週期**：請求／批次資料各自隔離，重試只有一個負責者，原生回覆與框架訊息之間有明確映射。228 是既有版本特定範圍的測試結果，不是新組合的自動保證。[測試範圍紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:198)

這裡只需要定好接入邊界；網路恢復的完整設計仍可留待後續討論。

**7. 局部規格還有兩個值得立即修正的地方。**

第一，`settlement_key = hash(current_policy_rev, proposal_ids)` 還不足以辨認「這批提案已結算」。

假如 policy 7 套用提案後成為 8，下次 hook 仍讀到同一批工具結果，卻用目前的 8 重新計算 key，就可能再次結算。應先用**穩定的已接受批次身分**查詢是否完成，再核對原始父政策；政策內容的去重與啟用事件的身分應分清楚。

第二，`salvage_attempt` 內部「自動確認程序已終止或先執行終止」，重新引入了之前已排除的隱含行為。**救回某個檔案不必然代表停止整個嘗試。** 終止應是明確操作或明確參數；可以合併工具介面，但不能合併掉操作意圖。

`wrap_model_call` 內有限次重組則是可行方向，官方允許 wrapper 多次呼叫 handler；仍須確保每次下層呼叫共用原有帳本，不會各自重新獲得重試額度。「最多兩次」是可選政策，並非框架保證。[Middleware 契約](https://docs.langchain.com/oss/python/langchain/middleware/custom)

**若以最佳產品功能排序，我會優先做：可靠的文件編輯與候選稿重用、精確且容易取得的來源／輸出對照、完整的工作狀態與 context 組裝，再接好框架與 Nexus 邊界。** 多區域對照圖是有價值的擴充；墨跡提示與章節子代理保持可選，不作為完成轉換的前置要求。

允許完整重構，讓我們可以消除不合理的介面限制；實際成效仍應看正確內容是否更容易完成、保存和交付，以及使用者是否更少需要介入。

本輪為唯讀審閱，未修改程式、執行測試或發起 Nexus 模型呼叫。
