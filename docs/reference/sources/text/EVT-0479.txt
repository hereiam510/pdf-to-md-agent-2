**可以把優先比較範圍收斂到 Pi SDK 與 LangChain `create_agent`，但我不會直接採納這份完整設計。** Working Draft 是實質進步；P0–P3 保留規則、語義標註視圖，以及把 context manifest 當成全系統唯一真相，仍有會影響轉換品質與可靠性的問題。

完整重構時，我會優先確保：agent 能自由探勘、保存未完成成果、直接核對原件，並在整理後準確繼續工作。框架選型應圍繞這條完整工作路徑。

**1. `create_agent` 值得優先比較，但排除 Deep Agents 的理由需要修正。**

附件有一項版本錯誤：**Deep Agents 自 v0.7 起，task planning／`write_todos` 已是選用功能**，並非必須額外拆掉的預設工具。我也核對了 `0.7.29` 的組裝原始碼，沒有預設加入 `TodoListMiddleware`。[官方說明](https://docs.langchain.com/oss/python/deepagents/overview#task-planning)

更重要的是，通用檔案工具不必然破壞成果契約。它們可以用來：

- 保存長篇草稿與工作筆記；
- 透過腳本整理抽取結果；
- 準備稍後交給文件服務驗證的內容。

真正需要控制的是**正式成果如何產生**：

> 寫進工作目錄的 Markdown 是工作材料；經文件服務驗證並建立版本的內容，才是已發布成果。

不要把通用檔案工具直接指向內部版本儲存，也不要自動把任意檔案當成已發布內容。這樣可以保留有用的自由度。專案本來也允許 agent 選擇腳本與中間檔處理，不能為了讓框架比較簡單而縮減這項能力。

因此，我支持優先比較 Pi 與 `create_agent`，理由是它們可能更容易組合目前需要的功能；**「Deep Agents 必然干擾 PDF 契約」不是已成立的理由。** `create_agent` 的可選組合方式確實值得評估。[官方 agent 文件](https://docs.langchain.com/oss/python/langchain/agents)

**2. `model_layout` 可以提供，但必須區分「底層觀察」與「來源內容判斷」。**

把 bitmask 解碼、顏色轉成易讀格式，是合理的介面改善。但以下轉換不能當成已確認的視覺事實：

- `font flags` →「這段在原頁上是粗體」；
- 透明文字 →「這一定是 OCR 層」；
- 相近位置、相同樣式 →「這些一定是連續正文」。

PyMuPDF 官方明確提醒，字型屬性可能不正確或不完整。[官方說明](https://pymupdf.readthedocs.io/en/latest/textpage.html#span-dictionary)

而我們自己的那個案例更直接：所有 spans 都是 `GlyphLessFont`、flags 12、alpha 0，這些一致的屬性**無法區分原頁實際存在的強調格式**。[既有證據](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:58)

所以我會讓工具清楚表達：

- 字型資料**報告**了甚麼屬性；
- 文字透明度是多少；
- 哪些標籤是推測，以及推測依據；
- 如何取得對應原始資料與頁面像素。

另外，`span_count: 6` 加一個外框，不能還原六個 spans 的內部位置。若保留精確子片段引用，它是**可追溯的簡化視圖**；不能同時宣稱保留完整精確結構。

我支持這種視圖作為日常選項，但保留直接選擇原始結構、局部欄位和圖片的能力。也不必預先認定所有模型都更喜歡這種格式。

**3. P0–P3 可以成為保留傾向，不能成為硬性的頁面生命週期規則。**

這部分是我最想修改的產品政策。

假設 agent 先探勘 30 頁，判斷章節結構、表格延續和圖片位置，再開始重建。如果所有「已讀但未落稿」頁面的證據都自動保留，context 很快就會被探勘資料填滿。這反而懲罰合理的先探勘、後組織工作方式。

同樣：

- 最新請求可能本身就超過模型容量，P0 無法保證全部內容常駐。
- 相鄰一兩頁只是線索；依賴可能在十頁以前。
- 已保存頁面仍可能需要重看。
- 沒有登記未解問題，不代表真的不存在依賴。

我會把這套規則改為：

| 訊號 | 如何使用 |
|---|---|
| 當前請求、明確釘選、已知未解依賴 | 優先保留相關的精確內容 |
| 已讀但未完成 | 保留工作狀態與檢索入口，視下一步需要保留原文／圖片 |
| 相鄰頁、近期使用 | 作為保留傾向，允許 agent 覆寫 |
| 已完成且目前無用途的大型證據 | 優先考慮退出活躍輸入，原件持續保留 |

**需要保護的是可延續的工作，不是把所有未完成頁面的所有資料永久留在輸入裡。**

容量不足時，app 應把限制和可選範圍呈現清楚，讓 agent 調整工作集。頁碼狀態可以幫忙，但不能代替相關性判斷。

**4. Working Draft 值得採用，但草稿也需要穩定版本與失敗隔離。**

這是本輪最有價值的建議。我支持：

- 一份明確的活躍工作草稿；
- 草稿可以不完整，頁碼與內容狀態可以尚待補齊；
- 可以直接讀取、繼續修改及預覽草稿；
- 發布時產生不可變版本。

不過，「所有操作立即落到 Working Draft」仍需要界線：

1. 每次修改帶有預期的 `draft_revision`，避免覆蓋更新的工作。
2. 有效的修改以完整操作提交，產生新 revision。
3. 格式不合法或無法套用的修改，保存其原始內容與錯誤，但不破壞目前可用草稿。
4. 預覽固定對應某個 `draft_revision`，不能一邊渲染、一邊讀到不同 revision 的內容。

這樣「可保存不完整工作」與「草稿仍可可靠讀取」才能同時成立。

對 `follow_latest` 的差異揭露，我也支持，但要避免每輪重貼所有 before／after，造成新的 context 膨脹。應記錄哪些變更已送入先前請求，優先呈現尚未交代的相關變更，完整 diff 保持可取回。

還要指明跟隨的是**活躍草稿**還是**已發布版本**；兩者不能用模糊的「最新」混在一起。

**5. `context_manifest` 不能單獨決定哪些文件操作已經生效。**

我之前所說的單一提交點，是針對 **context 切換**。附件把它擴張成全系統的唯一真相，這會有問題。

例如：

1. 文件服務已保存 `draft_revision=4`，並產生成功收據。
2. context manifest 仍記錄 revision 3。
3. 更新 manifest 前，程序崩潰。

重啟後，不能因為 manifest 還指向 revision 3，就把 revision 4 視為未生效。它可能是已確認保存的有用成果。

我會維持清楚的責任：

| 記錄 | 它負責證明甚麼 |
|---|---|
| 文件版本與操作收據 | 哪些草稿／發布操作已提交 |
| 證據儲存 | 哪些工具結果已保存 |
| Session 記錄 | 實際發生了哪些模型與工具交換 |
| Context manifest | 某次模型輸入採用了哪些版本與內容 |

恢復時需要對帳，必要時更新 context 所引用的成果版本。

**未被某份 context manifest 引用，只代表未納入那份 context；不代表未執行、未保存或沒有價值。**

`ReplaceFileW` 可以是切換指標的實作原語，但它本身不會把多個儲存系統變成共同交易，也不能單憑一次檔案替換就宣稱完整的崩潰恢復保證。[Microsoft 文件](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)

**6. 核對紀錄的沿用，不能簡化為「只改樣式，所以文字 fidelity 仍有效」。**

這個規則仍然過強。

我們要求保留 meaningful emphasis、上下標、註腳及閱讀關係。取消上標、把註腳變正文、改變段落位置，即使底層字元沒有變，也可能改變含義。[產品要求](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/PRODUCT_REQUIREMENTS.md:17)

因此核對紀錄要說清楚原先檢查的是：

- 字元與數值；
- 樣式所承載的含義；
- 閱讀順序與跨頁關係；
- 圖片內容及裁切；
- 實際渲染結果。

未受影響的檢查可以沿用；程式不能僅憑「文字字串相同」宣布整體 `text_fidelity` 有效。也不需要因此建立龐大的通用語義圖，先記錄實際檢查的對象、面向和已知依賴即可。

**我的建議是：優先比較 Pi SDK 與 `create_agent`，保留 Deep Agents 作為可重用機制的對照；產品設計則採用版本化 Working Draft、完整證據儲存、可追溯的多種讀取視圖，以及可調整的工作集。**

下一步的接口評估，最值得驗證的是一條完整路徑：**先跨頁探勘、保存未完成表格、修正 metadata、預覽同一草稿 revision、整理 context，再繼續修改。** 加上「文件已提交但 context 尚未更新就中斷」的情境，才能看出哪個 runtime 真正省工。

我不會把 P0–P3、候選稿自動載入或 `context_manifest.json` 的具體形式先定成不可更改的要求。它們應隨這條工作路徑的需要調整，避免 app 為維護自己的狀態機而限制 agent。
