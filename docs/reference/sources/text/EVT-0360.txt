這份文字就是我上一則建議。重新以反方標準檢查後，**我會保留它的分層思路，但撤回「Pi 預計修改最少，所以應排第一」這個過強的結論。** 我上次對兩個框架採用了不夠對稱的比較方式。

**最重要的遺漏：原始歷史與模型 context 分離，並非 Pi 獨有。**

我重新檢查了 Deep Agents 0.7.29 的摘要實作：

- `_get_effective_messages()` 根據摘要事件組裝模型實際接收的訊息。
- 摘要路徑記錄 `_summarization_event`。
- 原始碼明確說明，歷史透過摘要事件濃縮，而非直接刪除原始訊息。

這並不代表所有內容已永久、安全落盤；仍須正確配置持久化。但它足以修正之前表格中的不對稱：**Deep Agents 也已有「保存的歷史」與「本次模型輸入」分離的實作基礎。** [Deep Agents 摘要原始碼](https://github.com/langchain-ai/deepagents/blob/deepagents%3D%3D0.7.29/libs/deepagents/deepagents/middleware/summarization.py)

LangChain 的官方 context engineering 文件亦明確支援：修改單次請求的 messages，而不改變儲存的 state。[官方說明](https://docs.langchain.com/oss/python/langchain/context-engineering)

Pi 的 `context_edit` 仍然很直接、容易理解，但這只能支持「它的接口很合適」，尚不足以支持「它需要的工作較少」。

**第二個問題：我把 Pi 的客製化算作優勢，卻把 Deep Agents 的客製化算作成本。**

兩者其實都需要處理相同問題：

| 要補上的行為 | Pi | Deep Agents |
|---|---|---|
| 保護仍有效的使用者要求 | Extension／持久狀態 | Middleware／持久狀態 |
| 保留未解依賴與有用草稿 | 自訂整理規則 | 自訂整理規則 |
| 精確引用與重新載入證據 | 自訂工具 | 自訂工具，可重用 filesystem backend |
| 避免不合適的預設截短 | 調整摘要材料／工具設定 | 調整 offloading／摘要設定 |
| 核對原件保存成功 | 自訂保存與引用檢查 | 自訂保存與引用檢查 |

Deep Agents 也提供替換內建 middleware 的公開入口，並不必然要求修改框架內部。[Deep Agents customization](https://docs.langchain.com/oss/python/deepagents/customization)

因此，公平的判準應是：

> **同一項需求，各自能用多少公開設定完成、需要多少自訂邏輯、有沒有被迫依賴內部 API？**

「一個 extension」和「一個 middleware」都可能包含大量程式，不能用模組名稱或數量判斷工作量。

**第三個問題：之前的設計有把需求推得過重的傾向。**

我們同意保護跨頁依賴，不等於 app 必須自行理解表格語義，或建立完整的 PDF 依賴圖。

較輕的起點可以是：agent 記錄「這個表頭仍有用」「這段草稿尚未保存」及精確引用；app 負責保存、容量處理與執行 context 變更。沒有必要先造一個能自動判斷所有依賴的系統。

同樣，需要分清楚三件事：

- **把完整結果存入檔案**：通常可以自動完成。
- **從模型當前輸入移走內容**：需要容量、相關性與取回方式的考量。
- **用摘要取代工作歷史**：需要保護要求、依賴與有用成果。

我之前把 Deep Agents 的自動 offloading 整體視為與自主性衝突，過於籠統。自動儲存、提供明確引用與完整讀取入口，本身可以支持自主性。真正要檢查的是：**它有沒有讓 agent 無法取得所需內容，或在整理時遺漏仍重要的資訊。**

**第四個問題：「保存失敗仍摘要」的批評需要縮小範圍。**

該失敗分支確實值得注意，但不能只看這一段，就推論整個 session 的原件一定永久遺失。還要檢查原始 state、checkpointer，以及我們獨立的 evidence store。

對我們而言，更穩妥的設計是讓工具結果產生時就保存完整原件。如此，後續摘要中的歷史檔案只是另一個取回入口，保存責任不必全部壓在摘要 middleware 上。

這是三種框架都適用的設計，也會降低我們需要改寫 Deep Agents 的程度。

**第五個問題：Nexus 相容性與總整合成本，之前也沒有比較充分。**

Pi 有多種協定與相容設定，是優點；Deep Agents 的模型 integrations 也有對應能力。但目前不能從這些入口推論哪一方在你的 Nexus 路由上保留 reasoning、圖片與 tool-call pairing 更完整。

同樣，不考慮 backward compatibility，確實讓我們可以自由重構；但仍要計算：

- Electron 與 agent runtime 的整合；
- 若保留 Python PDF 工具，跨程序工具呼叫與生命週期；
- session、證據、成果版本之間的一致性；
- 框架升級後自訂部分的維護負擔。

Pi 採用 TypeScript 並不構成障礙，但也不能因為 Electron 使用 TypeScript，就把這些成本當成零。

**我現在會把選型建議改成以下形式。**

| 判斷 | 修正後的建議 |
|---|---|
| **優先減少自行建造通用 context 功能** | **先評估 Deep Agents**：它已有 offloading、摘要、檔案讀取與主動 compaction 工具 |
| **優先直接控制 session 與 context 編輯** | **Pi 是強候選**：接口直接，但領域規則仍須實作 |
| **需要大量自訂執行、分支與恢復語義** | LangGraph 的價值會提高；單為目前 context 需求，直接自建較多 |
| **哪個已證明最適合 Nexus？** | 尚未有足夠整合證據 |
| **哪個已證明總修改最少？** | 尚未證明 |

**如果由我安排下一步，我會先嘗試把我們的要求映射到 Deep Agents 的公開設定和 middleware，再用 Pi 作對照。** 這更符合你「盡量少自建、讓成熟框架承擔通用工作」的優先次序。

比較可以集中在三個具體情境：

1. 巨大 OCR 結果保存後，agent 能完整或按範圍取回。
2. 舊頁表頭仍被下一頁使用，整理後仍知道它的用途與取回位置。
3. 使用者中途更正要求，compaction 後遵守新要求，並保留未完成成果。

先檢查兩者是否能透過公開擴充點完成這些情境，以及各自真正缺少哪些程式。**目前有充分理由保留 Pi；尚無充分理由因為上一份排名，就把整個 app 重構到 Pi。**
