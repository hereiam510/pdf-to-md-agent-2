**這版值得繼續採用，但「五個情境已完全收斂」仍說得太早。** 我支持它減少 agent 維護 metadata 的負擔，也支持工具結果先保存、再決定如何送入 context。不過，幾項自動化規則可能改變資料含義，或令整理流程反覆卡住。

另外，我要修正上一輪表述的一個歧義：**由 app 負責某項產品規則，不代表該項機制必須全部自行實作。** 這直接影響我們如何公平評估 Pi、Deep Agents 和自建方案。

**1. Span 合併與座標量化可以提供，但不能列為預設「無損」轉換。**

附件對資料膨脹的解釋有合理部分，但仍混入未證實的結論：

- 該頁既有紀錄是 **41 blocks、446 spans**，不是已確認有上千個 spans。
- `GlyphLessFont`、透明文字層和重複 metadata，不能單獨建立「Adobe 的碎裂 OCR 就是原因」。
- 「消滅 80% 節點」「座標字元減半」目前都沒有這份資料上的量測支持。[既有紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:58)

更重要的是，**相同樣式不代表位置關係可以安全合併**。同一行、相同字型的片段，仍可能分別屬於表格不同欄、公式、刻意留白或圖中標籤。把多個 bbox 換成一個外框，也會失去內部位置資訊。PyMuPDF 的 span 本來就包含文字、位置、字型和其他屬性；合併時必須說清楚保留了甚麼。[官方結構說明](https://pymupdf.readthedocs.io/en/latest/textpage.html#span-dictionary)

座標量化則明確是近似。以 600 DPI 計算，0.5 pt 的量化間距約為 **4.17 像素**，四捨五入的最大偏差約為每個座標 2.08 像素，不能普遍視作對精細裁切毫無影響。[座標單位說明](https://pymupdf.readthedocs.io/en/latest/app3.html#coordinates)

我建議區分三種資料表示：

| 表示 | 用途與承諾 |
|---|---|
| 原始結果 | 完整保存工具實際產生的資料 |
| 可精確還原的緊湊表示 | 抽離重複樣式、避免重複文字，保留選定資料的原值與關係 |
| 簡化 layout 視圖 | 可合併片段、使用近似座標，但明示轉換及精確來源引用 |

預設優先改善前兩種。簡化視圖可供 agent 選用，精確裁切與位置判斷仍可直接取得原座標。**完整原件留在磁碟，並不會讓簡化後的視圖本身變成無損。**

**2. 支持結果入場檢查，但不必另建一套重複的 context 管理系統。**

附件把「在下一輪請求組裝時檢查」描述成太遲，這不一定成立。

關鍵區別是：**把完整結果寫入持久記錄，不等於把完整結果送入模型。** 只要所有模型請求都經過同一個組裝與容量檢查入口，就可以在發送前選擇展開內容、精確範圍或收據。

我會採用以下流程：

1. 保存工具結果，以及實際操作成功／失敗、成果版本等收據。
2. 在整批工具回覆完成後，統一分配下一次模型輸入的容量。
3. 容納得下的內容按請求提供；其餘回傳明確的引用和未載入範圍。
4. 必要時整理舊工作 context，再重新評估應載入哪些內容。

這裡有四項必要修正：

- **不能保證整理後全部自動展開。** 單份結果也可能比空白 context 還大，必須允許分段讀取。
- **不能每跨過軟水位線就強制交接。** 有時釋放已不需要的證據，或調整當次表示便足夠。
- **並行工具不能各自認為自己還有全部剩餘容量。** 最終輸入需要統一核算。
- **每個 tool call 都要有協定有效的結果。** 可以回傳「已完成、完整結果已保存、內容未展開」，但不能讓未配對的工具呼叫夾在交接回合中。

`Pending Buffer` 可以只是已有證據的持久引用，不必再複製一份大型資料。還應分開記錄「工具執行結果」與「送入模型的範圍」，避免 `saved_partially_loaded` 掩蓋實際的部分失敗。

這能降低溢出風險，但無法提供「無論結果多大，交接永遠 100% 成功」的保證。模型容量、圖片計量及必要指令本身也有限制。

**3. 自動維護釘選 metadata 是對的；自動跟隨所有替換則不對。**

成本估算、版本號、內容雜湊、刪除偵測，應由 app 處理。Agent 主要表達要保留甚麼、為甚麼保留，以及何時可能解除，這點我同意。

但需要明確區分兩種引用：

| 引用方式 | 應有行為 |
|---|---|
| 固定快照：保留當時的原文／證據 | 內容更新後，仍指向原版本 |
| 跟隨目前成果：使用目前採用的表頭／定義 | 符合身分延續規則時，跟隨最新版本 |

例如：

- 「保留被判定有問題的舊 OCR，方便比較」必須固定快照。
- 「繼續這張表格時沿用目前表頭」可以跟隨目前成果。

**一對一替換只能證明編輯關係，不能證明語義用途不變。** 即使區塊 ID 相同，內容也可能從「原文」變成「修正建議」，或改變了單位。不能一律自動推進。

對拆分、合併或刪除，系統可以保存舊快照、提示受影響的依賴，由 agent 更新。附件前半段允許「連續替換」自動推進，後半段又要求拆分後重新釘選，這兩處亦需要統一規則。

候選稿也不宜全部自動掛進工作集。應指出**目前採用哪份工作稿、哪份是已發布版本，以及相關差異**，避免多個候選版本同時佔用 context、造成混淆。

另外，app 能精確知道 bytes、圖片尺寸等本地資料；token／圖片輸入成本通常仍是依模型與編碼方式作出的估算，不能稱作普遍精確值。

**4. 五個情境中，還有三類狀態判斷需要修正。**

**「已讀未存」只能作為提醒，不能代表已理解或漏掉的判斷已獲保護。**

系統可以知道證據已產生、哪些內容曾送進模型、哪些成果引用了它；不能只靠這些紀錄知道 agent 是否理解了某個細節。

保留相關 evidence 清單有用，但重取也不是零成本：可以省掉重新 OCR，仍可能增加模型輸入、延遲及再次判讀。因此它是交接遺漏時的補救能力，不是完整的語義保證。

**「修改區塊不重疊」不足以證明可以安全合併。**

兩次修改即使碰不同區塊，也可能互相影響：

- 一次改表頭單位，另一次新增表格數值；
- 一次重排內容，另一次修改頁碼映射；
- 一次移除圖片，另一次新增該圖片的引用。

`rebase_preview` 有用，但要呈現相關內容與關係的變化，不能只比較 block ID 是否重疊。這也不表示必須建立龐大語義圖；先檢查已知的結構、資產、頁碼和依賴，讓 agent 處理語義上的不確定性即可。

**CAS 必須區分外部變動與交接本身產生的更新。**

附件的例子從 `notes_rev:5` 開始，交接後寫入筆記成為 `notes_rev:6`。若之後仍要求所有 revision 等於原始值，就會把自己的正常更新當成衝突。

應把「讀取時的版本」與「本次打算提交的變更」分開，在短交易內檢查外部變動，並提交筆記及新的 context manifest。

若使用者中途改要求，也不能只把新要求貼到最上面就算完成：

- 來源觀察可能仍然有效，可以保留。
- 舊範圍下的下一步計畫、待發布候選稿，可能需要重新評估。
- 不受影響的證據不用重新運算。
- 如果使用者要求暫停，不應強制先做一次模型交接才能停下來。

這些規則能讓工作延續，同時避免舊計畫繼續支配新任務。

**5. 「Runtime 只剩一個 loop」這個結論，我不同意。**

我上一輪的責任表容易造成誤解，應改得更清楚：

> App 決定產品需要保留甚麼、哪些操作可以提交，以及應如何呈現結果；具體執行機制可以由框架提供。

例如，app 可以定義「跨頁表頭必須保留」，但仍使用框架的訊息狀態、持久化、回合邊界和摘要機制來執行。使用 middleware 也不代表把產品邏輯散落各處：它可以只是呼叫一個集中維護的 context policy。

如果先決定自行重寫所有 session、context、provider 和生命週期機制，再說框架只剩一個 `while`，這個比較會預先偏向自建。

反過來，如果實際接入後確實必須停用、替換大部分框架功能，那麼較薄的 runtime 或自建執行器就可能更合理。**這應由接口對照的結果決定。**

因此，評估標準除了「干擾少」，還要包括：

- 能直接重用多少可靠機制；
- 需要自行維護多少狀態與例外路徑；
- 公開接口是否穩定；
- 出錯時能否定位原因；
- 框架升級會帶來多少修改。

尤其要避免 app 和框架各自獨立決定壓縮、各自維護一份互相競爭的活躍 context。**最終送入模型的內容，需要一個明確的決策入口。**

**6. 可以開始接口對照，但附件列出的 hook 不是全部都屬於公開契約。**

這裡有兩個具體更正：

- Deep Agents 的 `_get_effective_messages` 是內部輔助方法，不應當成穩定公開擴充點。應先使用公開 middleware 介面，例如 `wrap_model_call`、`wrap_tool_call`，以及官方提供的 middleware 替換機制。[公開 middleware 文件](https://docs.langchain.com/oss/python/langchain/middleware/custom)、[Deep Agents 客製化](https://docs.langchain.com/oss/python/deepagents/customization)
- Pi 的 `context`／`context_with_system` 可以改變當次請求內容，但這本身不等於完成持久化與原子切換；`context_edit` 亦是相關記錄機制，不能直接當成 app 的交易保證。[Pi 擴充契約](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/extensions.md)

同樣地，統一訊息格式不必然破壞圖片或 provider 狀態。要檢查的是**必要資訊能否完整往返、最後發出的請求是否正確**，而不是要求完全沒有格式轉換。Nexus 的實際適配仍需獨立確認，不能由 hook 名稱推定成功。

**我的建議是：保留證據先存、輸入按容量組裝、agent 提供延續判斷、候選稿可重用的主架構；把近似 layout、釘選自動跟隨和自動 rebase 做成有明確條件的能力。** 接下來可以對照 Pi 與 Deep Agents 的公開接口，逐項標出「直接重用、設定、薄轉接、需要重寫」。這樣才有依據選出最適合重構、且長期自製與維護工作最少的方案。
