The security posture is mostly strong. The main weaknesses are in cost estimation, streaming persistence and recovery, which are the areas your docs show struggling. I found no credentials in the zip (I scanned 677 text files; the hits were false positives).

## What's done well
- **Local API:** it binds to `127.0.0.1` on a random port, requires a bearer token compared with `hmac.compare_digest`, and has docs endpoints disabled.
- **Electron:** the renderer is sandboxed with context isolation, IPC checks the sender, ids are validated, and the token never reaches the renderer.
- **Preview HTML:** it passes through `nh3`, an in-document CSP, and an iframe with `sandbox=""`. Edits also reject any image that isn't a registered source asset.
- **Storage and requests:** the store is content-addressed with integrity checks and parameterised SQL. Each request attempt is counted before sending, so a crash can't silently double-send. `trust_env=False` and `follow_redirects=False` keep the credential from leaking.
- **Parsing:** Pydantic models use `extra="forbid"`, and replies with duplicate JSON keys are rejected.

## Highest priority

1. **The size estimator is probably 3–4× too pessimistic.** `context.estimate()` counts UTF-8 bytes of the JSON payload as tokens. English text is roughly 4 bytes per token, so your 131k-token route behaves like a ~30k-token window. That pushes the app into compaction early, and compaction is the path that blocked your Nursing run. You already store the provider's `usage` for each attempt. I'd compare `prompt_tokens` against `input_estimate` in your logs, then calibrate with that ratio or use a real tokenizer.

2. **Streaming persists every network chunk expensively.** In `nexus.py`, each chunk goes through `record_chunk()` and `record_observation()` on the event loop. That costs one new object file with an fsync, two SQLite commits at `synchronous=FULL`, and a rewrite of the whole growing `chunks` list. If the gateway sends about one SSE event per chunk, an 8k-delta reply rewrites on the order of a gigabyte of catalog data and creates thousands of tiny files. The streaming test uses 4 chunks (`test_stream_progress.py:79`). Batching chunks into one append-only file per attempt, storing only a chunk count, and flushing on a timer would keep the durability guarantee without the cost.

3. **Pressing Stop during OCR or a script appears to block the task permanently.** `process()` raises `UnknownEffect` and leaves the operation `started`. Both plain Continue (`execute`) and amended Continue (`skip`) then raise `UnknownEffect` again. The app killed that process itself, so the outcome isn't really unknown. I'd settle it as "terminated by user" and treat `ocr_page` as safe to replay, since it only writes to its own directory.

4. **Any non-2xx response is terminal, and its body is discarded.** One transient 429, 502, 503 or 504 stops the task, and you can't tell why. Your own notes record gateway 502s with no cause identified. I'd retain a size-capped body with the token redacted (as `main.ts` already does for stderr) and add bounded retry with backoff that honours `Retry-After`.

## Medium

5. **Exported `document.md` is not sanitised.** The preview is, but the model's raw HTML, which can be steered by an injected PDF, is saved to the export as written. Only `<img>` is validated. Setting `html: False` in `parser()` would fix this, or reject script, iframe, object, event handlers and `javascript:` links at edit time.
6. **Model-controlled resource use is uncapped.** `render_page` allows 1200 DPI on a full page, which is over 100 megapixels, with no pixel limit. A `MemoryError` isn't in the dispatcher's caught exceptions, so it ends the whole run as `internal_error`. There are also no caps on received stream bytes, SSE line length, or PDF size at import.
7. **Parse-error gap.** `parse_reply` is wrapped in `except (ValueError, KeyError, TypeError)`, so an `AttributeError` or `IndexError` from an oddly shaped reply escapes `send()` and leaves the request marked `in_flight`.
8. **Export fails on some filesystems.** `os.link` for exclusive publish doesn't work on FAT/exFAT, some SMB shares and some sync folders. It also leaves a `.tmp` file next to the destination when it fails. Falling back to `open(..., "xb")` and adding a `finally` cleanup would fix both.
9. **Environment leaks.** `run_script` filters by name substring, so `AWS_ACCESS_KEY_ID` passes, and `ocr()` and `preview()` pass the full environment, including `PDFMD_LOCAL_TOKEN`, to a network-capable Node process. An allowlist is safer. Also, `terminate()` doesn't kill grandchildren.
10. **Remembered credential.** Windows encryption protects the key from other users and machines, but not from same-user code, so an enabled script can decrypt it. This is worth stating in the README.
11. **Scaling.** `Documents.version()` re-hashes every file in a version, including all images and original streams, on each call. Each tool call re-reads and re-verifies the whole source PDF. `objects/` has no garbage collection.
12. **Untrusted PDFs are parsed by MuPDF inside the engine process,** which also holds the API key in memory. A worker subprocess would isolate that.

## Low / hygiene
- Six `with self.connect() as db:` blocks in `storage.py` don't close the SQLite connection, because `sqlite3`'s context manager only commits. This relies on refcounting and warns on Python 3.13 and later. Use `contextlib.closing`.
