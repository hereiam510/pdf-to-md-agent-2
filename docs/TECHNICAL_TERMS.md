# Technical terminology and mechanism navigator

Use this page when a term from the discussion is familiar but its explanation is difficult to find. The linked guides own the mechanisms, sequences and examples. This page is a navigator, not another specification or a substitute for those explanations.

Exact spellings matter for locating a discussion, but not every spelling is a required API. The status labels have these meanings:

- **Retained concept** means the responsibility survives.
- **Illustrative name** means the discussion used this field/function without finalizing its schema.
- **Historical** means an earlier design or library observation.
- **Optional** means not a first-version prerequisite.

Library behavior is preserved at its original discussion scope and needs version-specific confirmation before implementation. Q1–Q3 remain open.

| `input_view_id`, `model_input_views`, request fingerprint | Identity/content checks for assembled input. An assembled view is not proof of dispatch, model comprehension or source coverage, and it can be resent in several attempts. | [Input view and causality](design/CONTEXT_AND_EVIDENCE.md#input-view-and-causality) |

| Accepted batch, pending call, `next_call`, batch barrier | Progress through the complete accepted call list. One edit receipt does not settle an unfinished preview call in the same reply. | Frozen-input replay, resume, regenerate, same-job continuation | Different actions. Re-entering an existing request reuses its input. | `interrupted_uncertain`, adoption, process receipt | An external effect cannot be assumed absent merely because the controller stopped. | `awaiting_user`, `waiting_for_user_input`, `stopped_incomplete`, execution stop reason | Illustrative stop labels. Waiting requires a concrete question. | Send gate, durable budget, retry owner, unknown outcome | Normal and compaction sends share persistent accounting and cancellation. A saved complete result can be recovered with no new send.
