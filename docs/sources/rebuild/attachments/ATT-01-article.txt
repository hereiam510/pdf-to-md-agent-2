递归自我改进（RSI）的概念可以追溯到 I. J. Good (1965)，他在论文中将”超智能机器”定义为能够在所有智力活动上超越人类，并设计出更好的机器来改进自身的系统。Yudkowsky (2008) 使用”递归自我改进”这个短语来描述一个特定的反馈循环：AI 使用其当前的智能来改进产生其智能的认知机制。
在现代 AI 中，这种反馈循环可能表现为模型直接重写自身的权重，或者更广泛地说，模型改进*训练流程*和部署系统，进而使下一代模型在经济价值任务上表现更好。AI 研究发展的速度在前沿实验室中已被证明急剧加速（Anthropic；OpenAI）。
我明确提到“部署系统”，是因为原始模型与真实世界上下文之间的这一层似乎与模型的原始智能（即预训练后的评估）同等重要。Harness 是 AI 部署的重要组成部分，正如 Claude Code 和 Codex 等成功的编码 Agent 产品所展示的那样。Harness 是围绕基础模型的系统，它编排执行并决定模型如何思考和规划、调用工具和行动、感知和管理上下文、存储产物以及评估结果。
本文将聚焦于 Harness 工程相关的研究及其对 RSI 的贡献。最近关于自动科研、自我改进 Agent 和进化程序搜索的许多工作都可以围绕这个问题来组织。关于模型自我对弈、合成数据、测试时训练和持续学习等更广泛主题的著作也符合 RSI 的愿景（例如 Yuan et al. 2024、Chen et al. 2024、Zhao et al. 2025、Choi et al. 2026），但这些将不是本文的重点。
Harness 设计模式

与早期的 Agent 框架 “Agent = LLM + 记忆 + 工具 + 规划 + 行动”相比，Harness 工程 additionally 包括工作流设计（例如循环工程）、评估、权限控制和持久化状态管理。它不再只是提示模板，而更接近运行时和软件系统设计：模型如何观察、行动、记忆、自我检查和改进。
设计应该刻意保持简单和通用以实现泛化，可能参考现有的软件工程实践以受益于预训练知识。Harness 与操作系统之间也存在强烈的类比。类似于操作系统，Harness 应该封装复杂的逻辑同时保持界面简单。同时，配置、工具接口和其他协议可能会逐渐在整个行业中标准化。
模式一：工作流自动化

定义一个模型可以在其中操作、测试和迭代的工作流是自动化的关键设计。Karpathy 的 autoresearch 仓库（https://github.com/karpathy/autoresearch）是一个简洁的例子，展示了如何构建这样的工作流。一个常见的工作流遵循目标导向的循环：规划、执行、观察/测试、改进，然后再次执行*直到*目标达成。该过程可能会触发对用户的主动请求，以澄清任务规范或执行偏好。

简化的 Codex Agent 循环：Agent 调用工具，工具响应影响模型的下一次生成。

模式二：文件系统作为持久化记忆

长周期 Agent 系统中一个反复出现的模式是对丰富状态和产物的简单控制。Harness 不应该在上下文中携带整个工作流和所有日志；相反，它应该将持久状态保存在文件中。在长周期 Agent 执行中，实验日志、代码差异、论文摘要、错误追踪和历史轨迹等产物往往比模型训练时的上下文窗口长度增长得快得多。
学习如何读写文件系统（通常通过 bash 命令）是 LLM 的基础技能，因此以文件形式管理持久化记忆自然受益于核心模型能力的改进。
模式三：子 Agent 和后端任务

Harness 可以生成多个子 Agent 并行执行并监控后端任务。当主 Agent 需要搜索多个假设、并发运行实验或委托隔离的子任务而不污染主上下文时，这非常有用。父 Agent 随后需要一个小型进程管理器：启动任务、检查日志、取消失败的运行，并将结果合并回主 Agent 线程。
关键的设计选择是使并行性显式和可检查。如果子 Agent 的输出仅存在于瞬态聊天上下文中，它们会迅速变得过时和隐藏。如果它们存储为文件、日志和状态记录，模型可以在中断后恢复，并推理自己的执行历史。

Harness 层 vs 核心智能？

很难预测 RSI 的未来在多大程度上会依赖 Harness 工程，但近期 RSI 的路径不太可能从模型直接重写其权重开始。我对实用近期路径的预测是：
Harness 工程将朝着元方法论的方向发展（即改进获得更好答案的机制，而非仅仅改进答案本身）。Harness 系统本身成为优化目标，启发式规则更少，通用机制更多。
反过来，成熟的 Harness 实现模型自我改进循环的自动科研，而更智能的模型防止 Harness 过度工程化并保持系统可持续性。
最终，许多 Harness 改进可能会被*内化*到核心模型行为中，但与外部上下文和工具的界面应该保留。我们在提示工程中已经看到了这种模式的较柔和版本：随着指令调优和模型推理的改进，手动提示技巧变得不那么核心，但指定目标、约束、上下文和评估的需求并未消失。
Harness 优化

Harness 系统中优化对象的演进大致是：指令提示 → 结构化上下文 → 工作流 → Harness 代码 → 优化器代码。随着模型变得更智能和强大，我们朝着更复杂的目标和通用方法推进。
上下文工程

简单地将所有工具响应和模型生成附加到上下文中，会迅速失控，因为 Agent 任务范围显著增加。上下文管理是为 LLM 构建更结构化和简洁的上下文并管理持久状态的层。毫无疑问，长上下文研究将持续进步，但目前长上下文智能和上下文工程有时交织在一起。
Agentic 上下文工程（ACE；Zhang et al. 2025）将上下文视为进化的剧本，而非不断延长的提示。它有三个组件来维护一个包含项目符号的上下文剧本，每个都有标识符和描述。
生成器：产生任务轨迹，参考项目符号。
反思器：从成功和失败的轨迹中提炼洞察。
策展人：用增量、条目化的条目更新结构化上下文。

[Figure 03: images/ATT-01-03.webp]

Agentic 上下文工程（ACE）框架。（图片来源：Zhang et al. 2025）
为了防止迭代重写期间的上下文崩溃和简洁性偏差，ACE 中的一个关键设计选择是策展人不重写完整的提示块。它改为输出结构化、条目化的项目符号集合，形式为（标识符，描述），这些项目符号通过确定性逻辑合并到结构化上下文日志中。上下文项目会定期优化和去重。
ACE 从轨迹中学习洞察的事实有助于我们走向自我管理的记忆，但更新规则和整体工作流仍然是手工制作的。为了走向更自我改进的循环，元上下文工程（MCE；Ye et al. 2026）将机制（如何管理上下文）与产物内容（上下文中有什么）分离，在元优化层运行技能进化，在基础层优化上下文。

工作流设计

Harness 工程中的工作流设计可以由领域专家手工制作。以自动科研为例，已经提出和测试了各种框架。AI Scientist 系统（Lu et al. 2026）构建了一个流水线：提出研究想法、编写代码、运行实验、分析结果、撰写手稿和执行同行评审。Meng et al. (2026) 在 ScientistOne 中将可验证性作为中心设计约束，其中每项声明（引用、数值、方法、结论）必须追溯到证据源，并通过证据链检查审核。

[Figure 06: images/ATT-01-06.webp]

AI Scientist 流水线：想法生成、实验、论文写作和评审。（图片来源：Lu et al. 2026）
Autodata Agent（Kulikov et al. 2026）被设计为数据科学家，用于生成训练和评估数据。主 Agent 管理一个挑战者（提出问题）、一个弱求解器、一个*强求解器*和一个验证者/裁判，旨在合成”刚好合适”难度的数据，即强求解器成功但弱求解器失败。
在 Autodata 中，根据求解器和验证者的反馈迭代更新挑战者提示。这里的限制是合成任务用于微调弱求解器而非强求解器；如果循环无法迭代改进强模型，它更像是生成的提示分布上的间接蒸馏，RSI 色彩较少。

[Figure 07: images/ATT-01-07.webp]

Autodata Agentic 工作流设计：围绕挑战者、求解器和验证者角色生成合成训练和评估数据。（图片来源：Kulikov et al. 2026）
工作流的设计空间是巨大的，自然我们可以将工作流设计视为搜索问题，因此我们应该能够通过算法而非仅手工制作来找到好的解决方案。沿着这个方向，Agentic 系统自动设计（ADAS；Hu et al. 2025）将 Agent 设计本身形式化为优化问题，即元 Agent 搜索，其中元 Agent 提出 Agentic 工作流的新设计。
用简单的 Agent（如 CoT 和 self-refine）初始化 Agentic 工作流存档。
要求元 Agent 用*代码*编程新 Agent，受存档中现有解决方案的启发。
 
元 Agent 首先生成新工作流的高级描述，然后用代码实现。
草稿程序然后通过元 Agent 的两个自精炼步骤（即要求模型提供反馈，然后要求同一模型根据反馈精炼之前生成的输出；Madaan et al. 2023）来检查其新颖性。

评估每个新候选者，将成功的添加回存档。
重复步骤 2-3 直到达到最大迭代次数。

Agentic 系统自动设计（ADAS）示意图。

自我改进的 Harness

无论是上下文工程还是工作流设计，都只是 Harness 的一部分。我们需要搜索整个设计空间并一起优化上下文管理逻辑、工作流、权限和许多其他 Harness 组件。正如我们在 Meta-Harness、ADAS 和 AFlow 等工作中看到的，✨代码✨ 是定义程序和系统的通用语言。简而言之，Harness 是编程代码，规定了提示、工具调用、子 Agent、控制流、内存和工作流逻辑如何协同工作。如果 LLM 可以优化执行 Agent 的代码，它可以访问*远大于*手写提示的设计空间。
自我教学优化器（STOP；Zelikman et al. 2023）是递归脚手架改进的早期例子之一。步骤的种子改进器接受初始方案、效用函数和黑盒语言模型，并返回改进的方案，即。STOP 的目标不是直接改进，而是改进改进器本身。

自我教学优化器（STOP）算法。（图片来源：Zelikman et al. 2023）
在 Zelikman et al. (2023) 的实验中，改进的改进器发现了各种策略，如遗传算法、分解和改进部分、多臂提示老虎机、模拟退火、变温度、束/树搜索。这类似于 Harness 工作流如何被表示为优化对象。

他们发现中的一个*警示性*结果是，STOP 在 GPT-4 上跨迭代提高了平均下游性能，但在 GPT-3.5 和 Mixtral 等较弱模型上性能退化。递归结构本身不够。基础模型必须*足够有能力*来改进机制。这暗示 Harness 改进实现了模型的更好部署，但智能仍是核心。
更近的工作，自我 Harness（Zhang et al. 2026），依赖 LLM Agent 通过提出-评估-接受循环来改进自己的 Harness。

[Figure 12: images/ATT-01-12.webp]

自我 Harness 使用弱点挖掘、有界 Harness 提议和验证的循环来更新 Harness。（图片来源：Zhang et al. 2026）
自我 Harness 中的循环有三个阶段：
弱点挖掘：将失败聚类为基于验证器的失败模式。
 
当前 Harness 用于评估任务，收集执行轨迹进行分析。
注意，两次运行可能在错误日志表面共享相同的验证器结果，如超时或缺失产物，而具有不同的因果机制。因此我们需要丰富信息的失败记录，包含终端验证器级原因、相关 Agent 行为的因果状态和轨迹暴露的抽象机制，以发现根本原因。

Harness 提议：基于挖掘的失败模式提出有界的 Harness 编辑。
 
同一模型在作为提议者被调用。
模型被提供有界的提议上下文：（1）当前 Harness 的可编辑表面，（2）来自评估系统的基于验证器的失败模式，（3）应保留的通过行为记录，（4）之前尝试的编辑摘要。
Harness 编辑应该优先选择可解决的重复错误模式（例如非任务特定难度）和可通过窄变更解决的。
Harness 编辑候选应该独特且多样化。

提议验证：验证并合并合格的编辑以创建新 Harness。
 
候选编辑通过在 held-in（测试弱点是否解决）和 held-out（检查是否引入了其他未知问题）分割上的回归测试来评估。
仅当候选在 held-in 和 held-out 数据上都没有回归时才被接受。
接受的候选被合并以更新 Harness 到，而拒绝的候选被记录而不改变活动 Harness。

在 Terminal-Bench-2 上运行 MiniMax M2.5、Qwen3.5-35B-A3B 和 GLM-5 时，自我 Harness 被证明能学习针对不同基础模型不同弱点的模型特定 Harness 指令，并提高 held-out 通过率。
自我 Harness 类型的工作确实引起我的担忧：如果程序被允许编辑操作系统，抽象边界被打破。可编辑表面需要适当设计，权限控制和安全层需要位于此循环之外。奖励黑客等所有挑战仍然存在。
进化搜索

进化搜索是一种受自然选择启发的优化方法（参见我关于进化算法的旧文）。它通过突变进化解决方案群体，并仅保留人群中”适应度”高的。进化搜索在（1）搜索空间广泛或形状怪异；（2）难以用梯度直接优化但易于评估解决方案时派上用场。Harness 搜索似乎很适合这里。
进化搜索已在过去研究中用于提示工程。Promptbreeder（Fernando et al. 2023）通过丰富的突变操作集优化任务特定提示，有趣的是，突变提示（即让 LLM 突变任务提示的指令）本身也通过进化改进。GEPA（Agrawal et al. 2025）将反思式提示与进化搜索结合，使用对试错轨迹的自然语言反思来提出提示更新。
Novikov et al. (2025) 将 AlphaEvolve 作为编码 Agent 进化搜索系统引入，存储候选程序池并提示冻结的 LLM 生成改进的 diffs。随着系统反复评估子程序并保留成功的，它随时间发现更好的解决方案。

[Figure 13: images/ATT-01-13.webp]

AlphaEvolve 如何工作。（图片来源：Novikov et al. 2025）
AlphaEvolve 设计中的几个细节很重要：
提示包括父程序、结果、指令，有时还有元信息。
编码 Agent 可以访问完整仓库，但改进的代码区域用 # EVOLVE-BLOCK-START 和 # EVOLVE-BLOCK-END 明确标记。
元提示与指令和上下文共同进化，如我们进化解决方案程序的方式。
消融显示进化过程、提示中的上下文、元提示、全文件进化和使用更强 LLM 的价值。

消融显示 AlphaEvolve 中几个设计的价值。（图片来源：Novikov et al. 2025）
最近的变体如 ThetaEvolve（Wang et al. 2025）将进化搜索与 RL 和上下文学习结合。另一方面，ShinkaEvolve（Lange et al. 2025）引入了三个新组件来提高 LLM 采样效率：
通过设计父采样来平衡性能排名和后代数量，实现更样本高效的探索。
基于嵌入余弦相似度丢弃与现有人口过于相似的候选，实现代码新颖性拒绝采样。
在元草稿中识别成功解决方案中的好模式以指导未来突变。
与上述关注解决方案改进的方法不同，Darwin Gödel 机器（DGM；Zhang et al. 2025）明确针对 LLM 编码 Agent 的可编辑 Harness-代码仓库的进化。准确地说，此 Agent 被允许修改自己的 Harness。关于 Hyperagents 的后续工作（Zhang et al. 2026）引入了元 Agent 来控制如何修改现有任务 Agent 以创建新 Agent。
从池中的一个编码 Agent 开始。
在每轮迭代中，按性能比例和后代数量反比选择父 Agent，修改并分支以产生新 Agent。
选定的父 Agent 检查自己的基准评估日志，然后提出改进自己的 Harness 代码库以生成编码 Agent 新版本。代码编辑用两个基本工具实现：（1）bash（参数：<bash_command>）和（2）编辑器（参数：view/create/edit <file_path>）。
评估新编码 Agent，仅将足够高性能的添加回池。
重复步骤 2-4 直到满足某些停止条件。
DGM 是固定模型下的 Harness 进化。在使用 Claude 3.5 Sonnet 作为基础 LLM 和简单初始 Harness 配置的实验中，DGM 发现的 Agent 在 SWE-bench Verified（20% 到 50%）和 Polyglot（14.2% 到 30.7%）上达到或优于手工 Agent。
这类方法在候选方案可自动评估且候选适应度易于量化时表现良好，如矩阵乘法、GPU 内核优化、算法竞赛、数据中心调度。在评估慢、模糊或主要基于启发式的领域表现挣扎。进化的计算效率和有效性也是问题。
与模型权重的联合优化

Harness 进化改变了模型周围的非参数系统。为了实现完整自我改进，模型完全可以允许同时更新自己的权重。权重更新可以通过改进训练流程或通过测试时持续学习来实现。持续学习的主题值得未来单独写一篇文。
SIA（Hebbar et al. 2026）是早期尝试在同一优化循环中结合 Harness 改进和模型参数更新，设计中有三个组件：
元 Agent：提出初始 Harness。
任务特定 Agent：执行任务。
反馈 Agent：根据最近轨迹选择更新 Harness 或模型权重。

[Figure 14: images/ATT-01-14.webp]

SIA 中的反馈 Agent 决定下一轮迭代类型。（图片来源：Hebbar et al. 2026）
SIA 实验中的几个混杂选择使结果难以解释。例如，任务特定 Agent 比用于元 Agent 和反馈 Agent 的模型弱得多（gpt-oss-120b vs Claude Sonnet 4.6），基线也太弱，无法与相关方法 clean 地交叉引用。我认为方向有趣，但证据尚不充分。然而许多挑战，如训练稳定性和古德哈特定律，仍然开放。
未来挑战

AI Scientist 系列工作是专家设计的 Harness 可以协调大部分自动科研循环的有力证明，以撰写研究论文的形式实验。但论文生产不同于科学发现。系统可以在仍有伪造引用、实现漂移或弱实验结果的情况下写出看似合理的稿件。
Trehan & Chopra (2026) 测试了 LLM 是否能以最小脚手架和基本工具（即 read_file、write_file、llm_search、list_files）从研究想法到论文。每个想法都有一个专用工作区，Agent 可以在其中生成和读取文档作为上下文的一部分。他们在三个领域（世界模型、多 Agent RL、AI 安全与对齐）实验，每个领域包含 45-50 个高质量种子文档来激发新想法。只有四个想法被人类专家选中运行完整流水线，只有一个被完全执行为论文。他们在实验中观察到六个反复出现的失败模式：
偏向训练数据默认值：使用旧库、过时命令、标准格式，或基于实际仓库或数据集不成立的假设。
执行压力下的实现漂移：当实现变得技术复杂时，模型可能转向常见的更简单的解决方案，而非提出的方法。
记忆和上下文退化：长周期项目除非日志被写为持久产物，否则会丢失关键细节。
过度乐观：模型尽管实验嘈杂或失败仍宣布成功，类似于 Bubeck et al. (2025) 观察到的 “p-hacking 和 eureka-ing” 模式，其中模型可以引入”数字胶带”并在信号仍是噪音时宣布胜利。
领域智能不足：模型缺乏隐性工艺知识，例如预测实现复杂度、判断实验结果是否合理，或知道哪些基线重要。
科学品味弱：实验可能可执行，但无法回答正确的问题。
走向完整 RSI，研究人员取得了真正进展，但几个瓶颈仍然存在。
1. 弱且不明确的评估器。 许多研究声明没有快速精确的验证器，许多真实世界任务也是如此。当前自我改进循环在评估指标可测量和客观时效果最好，类似于RL 的工作原理。
研究品味、新颖性和长期科学价值更难衡量。例如，研究品味通常混合问题框架、实验设计和关于哪些惊喜结果值得追求、哪些失败案例值得重试的判断。
2. 上下文和记忆生命周期。 随着 AI Agent 变得更自主独立，记忆不断增长。有用的 Harness 需要管理上下文和记忆，补充长上下文生成的现有局限，同时最大化长周期任务的成功。由于人类能够终生维持记忆，我看到这里存在类比，上下文工程应该且将成为智能的核心部分，而非停留在软件系统层。
3. 负面结果。 研究人员被激励发表成功结果，因此文献偏向成功。在大量数据（至少目前主要是人类创建的，哈哈）上训练的 LLM 可能难以决定何时放弃假设、报告负面结果，甚至承认失败，由于数据中成功与失败案例的不平衡。研究 Harness 应该使失败尝试易于保留，因为从失败中学习是缩小任务搜索空间的最佳方式。
4. 多样性坍缩。 进化和 RL 循环倾向于利用已知高回报模式。我们需要机制来防止群体坍缩为同一解决方案的变体。这对开放域研究至关重要，最佳路径在当前评估器下最初可能看起来更差。
5. 奖励黑客。 自我改进循环优化给定的任何信号。如果奖励来自单元测试，Agent 可能过拟合到测试；如果来自裁判模型，它可能学到该模型特定的奖励黑客技巧；如果来自基准分数，它可能利用基准产物。
评估器和权限控制可能应该位于进化 Harness 的循环之外，使用 held-out 测试、轨迹审计和人类在关键决策点的审查——多少监督可以扩展和自动化仍是开放研究领域。
6. 长期成功。 外在优化循环作用于我们可以在训练沙盒中模拟的个体轨迹之外的奖励。
以编码 Agent 为例。编码 Agent 已经提高了软件工程的日常生产力，但许多优化目标仍然过于短期。它通常能完成手头的任务，但它应该如何保护由数百或数千工程师共同维护的仓库的长期健康就不那么明显了。标准基于沙盒的 RLVR 风格训练很少捕捉可维护性、所有权边界、迁移成本、向后兼容性或未来调试负担。
7. 人类的角色。 人类应该向上移动堆栈，而不是被移出循环，这意味着人类应在正确的时间、正确的抽象层面提供监督，我们的系统设计应考虑何时以及如何设置此类接触点。
上面列出的许多挑战需要人类的反馈和引导。毕竟，我们正在为人类更美好的未来构建技术，而非相反。

附录：一些有用的基准测试

PaperBench：从零开始复现 20 篇 ICML 2024 Spotlight 和 Oral 论文，包括理解论文贡献、开发代码库和成功执行实验。

每个复现任务被分解为更小的、可单独评分的任务。
总共 8,316 个评分标准，与论文作者共同开发。
当时最佳模型（Claude 3.5 Sonnet，~21%）未能超过 ML 博士生。
包括 PaperBench、PaperBench Code-Dev（较轻版本）和 JudgeEval。

CORE-Bench：评估已发表研究的计算可复现性。

基于计算机科学、社会科学和医学 90 篇科学论文的 270 个任务。
任务涉及从提供的代码和数据复现结果。
包括多个难度级别和纯语言和视觉-语言任务。
当时报告的最佳 Agent（GPT-4o 和 GPT-4o-mini）在最难任务上仅达到 21% 准确率。

ScienceAgentBench：评估用于数据驱动科学发现的 LLM Agent。

从四个学科（数学、化学、生物、地理）44 篇经同行评审的出版物中提取 102 个任务。
涵盖这些领域的基本数据科学任务：数据处理、模型开发、数据分析和信息可视化。

RE-Bench：在现实的 ML 研究工程环境中评估前沿 AI Agent 与人类专家。

7 个具有挑战性的、开放式的 ML 研究工程环境。
每个环境 =（评分函数、起始方案、参考方案）；每个可用 8 个或更少的 H100 GPU 运行。
示例：优化内核、运行缩放律实验、修复嵌入、微调 GPT-2 用于 QA 等。
包括 61 位不同人类专家 71 次 8 小时尝试的数据。
人类专家在 82% 的 8 小时尝试中取得非零分数；24% 达到或超过强参考方案。
最佳 AI Agent 在 2 小时预算下得分比人类高 4 倍，但人类在更长预算下回报更好，在 8 小时和 32 小时设置下超过 Agent。

MLE-bench：在离线 Kaggle 竞赛中评估 ML 工程 Agent。

包含从 Kaggle 精选的 75 个 ML 工程竞赛。
测试训练模型、准备数据集、运行实验和提交预测到评分脚本。
使用 Kaggle 公开排行榜作为人类基线。
论文中最佳设置，o1-preview 配合 AIDE 脚手架，在 16.9% 的竞赛中达到至少 Kaggle 铜牌水平。
包括资源扩展和污染分析。

KernelBench：评估生成的 GPU 内核的正确性和速度。

250 个 PyTorch 任务来评估 LLM 是否能编写快速且正确的内核。
评估指标 fast_p = 正确且比基线快的生成内核百分比。
