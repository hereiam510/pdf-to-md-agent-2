這份審閱非常精準地拆解了前一版在「機械式降級判準」、「前綴快取與動態視圖的結構矛盾」、「跨儲存時間戳空隙」以及「無身分內容尋址」上的邏輯漏洞。將系統行為收斂為 **「正常工作、容量整理、異常恢復、模型切換」四大運行契約**，並撤回「按已落稿頁面自動淘汰證據」的規則，是讓 App 在徹底重構後發揮最佳功能的正確方向。

在採納這些修正的同時，若將你提出的替代方案放到真實極端情境下檢視，仍有**五處設計缺口或過度複雜化的陷阱**需要正面交鋒與補強。

## 一、 完全成立並納入設計基線的五項修正

1. **撤回「已落稿且無錯誤標記＝可安全移出 Context」的機械判準：** 頁面已寫入草稿不代表其原始證據不再是後續跨頁表格、註腳或圖表標籤的解讀依據，且保留全部對話文字與寫入參數本身仍可能塞爆視窗。將「保存事實」與「語義充分性判斷」徹底分開，才符合專案的核心分工原則。


2. **選清「Epoch 基準快照」與「動態重組」的快取取捨：** 前一版一方面宣稱「平時靠工具結果與尾端事件維持穩定前綴」，另一方面又把每輪變動的 `Rollup Map`、草稿與筆記放在對話歷史之前的第二區段（`P2`），確實存在內部矛盾。重構規格應明確選擇 **「Epoch 開始時的固定基準快照（標明版本）＋ 後續改動由工具結果與尾端事件表達」**。


3. **修正交接預留空間的階段公式：** 若正常回合先生成內容與工具呼叫，下一回合才執行交接（Handshake），預留空間不能只取 $\max(\text{Normal Output}, \text{Handshake Output})$，而必須同時容納「本輪正常輸出 ＋ 本輪工具回傳收據 ＋ 交接請求提示與交接輸出餘量」。


4. **區塊必須同時具備穩定身分與內容雜湊（`block_id` + `content_ref`）：** 單純用 `[block_hash_1, ...]` 會在修改表頭時丟失「這是同一張表」的身分追蹤，且無法區分文件內兩段合法重複的文字。改為 `{"block_id": "table_01", "content_ref": "sha256:..."}` 並搭配 `projection_mode` 的具體範圍／欄位記錄，才能同時支援釘選追蹤與不可變內容重用。


5. **外部 Blob 清理必須避開準備中的交易：** SQLite 的原子提交不涵蓋外部檔案，因此在「先寫入 Blob、再提交資料庫引用」的兩階段過程中，剛寫入但尚未提交引用的檔案不能被視為「可隨時清理的孤兒檔」，必須加上準備期保護機制。

## 二、 五個正面交鋒：針對新方案仍留下的工程盲點

### 1. 交鋒一（針對第 1、4 點）：「恢復 Context」若只載入「最後有效筆記」，在長 Epoch 中段崩潰時會造成嚴重失憶

你在第 1 點提出，當交接失敗且舊 Context 已不可用時，應「建立明確標示的恢復 context，載入有效要求、最新成果、最後有效筆記及精確檢索入口，讓 agent 重建所需工作狀態」。

* **盲點分析：** 請對照第 4 點的「Epoch 基準快照」設計——在正常工作中，Agent 為了保護前綴快取，可能連續執行了 12 個回合（讀取了第 15–22 頁、完成了兩次草稿更新、發現了三處字形問題），都還沒有觸發全量筆記整理。如果第 13 回合因為單次大結果或網路問題導致交接失敗、舊 Context 無法繼續使用，此時若只載入「最後有效筆記（停留在 12 回合前）」與「最新成果」，**Agent 在進入恢復 Context 時，完全不知道自己過去 12 個回合讀過哪些證據、做過哪些失敗嘗試，以及最新草稿是根據哪幾份 `evidence_id` 寫出來的！**


* **最佳設計補強（自動附帶「未整理回合操作帳本 Unconsolidated Turn Ledger」）：**
1. 其實「正常 Epoch 切換後的新 Context」與「異常恢復 Context」在結構上完全相同，差別只在於後者缺少了當次 Handshake 的總結筆記。


2. 為了讓恢復 Context 具備最高可接續性，App 在從 SQLite 組裝恢復 Context 時，除了載入「有效要求、最新草稿版本、最後有效筆記」外，**必須由程式自動從操作收據與證據表提取自上次 `notes_rev` 以來的「未整理操作時間線（Mechanical Delta Log）」**（例如：`[Unconsolidated Activity since notes_rev 3: Turn 8 inspected pages 15-16 -> ev_015; Turn 9 updated draft_rev 4 -> 5 (modified block table_02, page_map 15-16); Turn 10 attempted update_draft -> failed validation (staged as cand_07)]`）。這份帳本僅佔幾百 tokens，卻能讓 Agent 在恢復 Context 中精確接回斷點，大幅減少盲目重讀證據的次數。





### 2. 交鋒二（針對第 2 點）：「300 頁奇偶交錯」反例證明的是「一維連續區間摺疊」選錯結構，而非全局進度索引必須放棄固定上限

你用「300 頁中奇數頁已處理、偶數頁未處理會產生近 300 個區間」反駁固定 10–20 行的 Rollup Map，並建議將它拆成「覆蓋／進度索引（完整放外部，活躍輸入用可展開的章節／範圍視圖）」與「工作發現與依賴（Agent 記錄）」。

* **交鋒點：** 將「機械生成的覆蓋／進度索引」與「Agent 記錄的跨頁發現／依賴」拆開是完全正確的；但一維連續區間摺疊（Run-Length Encoding）在奇偶頁交錯時退化成 $O(N)$，不代表活躍輸入中的全局進度索引無法維持精簡常數大小！


* **最佳設計補強（二級分桶覆蓋索引 2-Level Bucketed Coverage Index）：**
* 不要用平鋪的一維連續頁碼摺疊作為頂層視圖，而是改用「固定頁數分桶（例如每 25 頁一桶，或依 PDF 書籤章節分桶）＋ 當前活躍桶展開」的二級結構：
* **頂層分桶摘要（300 頁永遠固定 12 行）：** 即使奇偶頁交錯處理，第 1–25 頁的分桶也只顯示單行統計：`Pages 001-025: [drafted: 13, inspected_only: 0, untouched: 12, open_issues: 1]`。
* **當前焦點展開（僅展開正在處理的 1～2 個分桶）：** 只有 Agent 目前工作所在的區間才展開具體頁碼清單與 `evidence_id`。


* 這樣無論頁面狀態如何碎裂交錯，頂層全局進度視圖在數學上**嚴格保證為 $O(\text{Total Pages} / \text{Bucket Size})$**，既不會塞爆 Context，又不必把全局進度完全藏到外部讓 Agent 額外發起查詢呼叫。



### 3. 交鋒三（針對第 3 點）：既然 `usage` 不能直接跨結構沿用，App 應採用「組件級基準計數 ＋ 路由動態誤差係數」

你準確指出：一旦 Context 被整理、舊訊息被替換、模型切換或圖片表示改變，就不能再直接用「上一輪 `input_tokens` ＋ 新增內容」來推算，且不能假設 Nexus 路由支援官方 Token 計數 API。

* **工程落地的解法：** 如果每次修改歷史或替換訊息都無法沿用上一輪總數，App 該如何在沒有遠端 Token 計數 API 的情況下，給出有證據支持的保守上界？
* **最佳設計補強（Component-Level Estimation with Route Calibration Factor）：**
1. **單訊息／單資產獨立基準估算（Base Component Estimator）：** 系統對每一則訊息、每一個工具 Schema、每一份證據表示法與每一張圖片，在產生時即計算一個**確定性的本地基準值 $B(x)$**（文字採本地標準分詞器加上 UTF-8 / CJK 權重；圖片按該模型家族的公開視覺切塊公式計算，若模型規則未知則按解析度與 Base64/像素面積保守給定初始值，並計入每則訊息的角色與結構封裝開銷）。
2. **路由綁定的動態校準係數（$\alpha_{\text{route, model}}$）：** 每當某個 `(nexus_route, model_id, protocol, image_mode)` 組合收到實際回報的 `usage.input_tokens`（設為 $U_{\text{actual}}$），App 計算當次請求所有實際送出組件的本地基準總和 $\sum B(x_i)$，並更新該路由的觀測比值：

$$\hat{r}_k = \frac{U_{\text{actual}, k}}{\sum_{i \in \text{Req}_k} B(x_i)}$$



系統取該路由近期觀測值的最大上界乘上安全裕度（例如 $\alpha = \max(\{\hat{r}\} \cup \{1.15\}) \times 1.05$）。
3. **結構變更時按組件重算：** 當發生 Context 整理、移除舊訊息或局部替換時，不沿用上一輪的 `input_tokens` 總數，而是直接對**本次準備送出的組件集合**計算 $\alpha \sum B(x_j)$。只要模型或圖片傳遞表示法改變，立即切換或重置對應的 $\alpha$ 記錄。這讓「保守上界」真正建立在該路由的實測誤差證據上，而非盲目加一個固定常數。



### 4. 交鋒四（針對第 5 點）：為了解決 `returned_to_session_at` 的交易空隙而去「主動查核框架內部儲存」，會造成不必要的框架耦合

你指出 `returned_to_session_at` 與框架持久化不在同一交易（可能框架已存但 App 未標記，或反之），因此建議保存對應的 session entry / checkpoint 身分，並在恢復時「按穩定 ID 查核框架的持久紀錄」。

* **交鋒點：** 如果 App 的恢復模組為了對帳，必須自己去讀取並解析 LangGraph Checkpointer 的內部序列化格式（如 `checkpoint_blobs`）或 Pi Session 的內部樹狀結構，就等於讓 App 深度依賴框架的底層儲存實作，違反了我們「只透過公開接口整合、降低框架升級維護負擔」的初衷。


* **最佳設計補強（利用公開 Hook 的「惰性確認 Lazy Ack ＋ 冪等重放」消除跨儲存查核）：**
我們根本不需要讓 App 主動去翻查框架的資料庫，只要把 `returned_to_session_at` 視為「已觀測到進入框架歷史」的標記，並在兩個公開 Hook 中執行對帳即可：
1. **情況 A（框架已保存該工具結果，但 App 來不及寫 `returned_to_session_at` 就崩潰）：** 重啟後，框架載入自己的 Checkpoint 並準備進入下一輪模型呼叫。當框架觸發公開的 `wrap_model_call`（LangChain）或 `context`（Pi）時，**框架傳入的歷史訊息陣列裡本來就已經包含那筆帶有 `tool_call_id` 的 `ToolMessage` / `toolResult`！** App 的 Context 模組看到該 `tool_call_id` 已經在框架歷史中，當場順手將 SQLite 中對應收據的 `returned_to_session_at` 補上，無須注入任何恢復提示，直接無縫繼續。
2. **情況 B（App 已提交文件修改，但框架尚未保存工具結果就崩潰）：** 重啟後，框架從上一個 Checkpoint 恢復，發現該 `tool_call` 尚未執行完成，於是透過公開工具介面重新呼叫該工具（或進入 `wrap_model_call` 時歷史中沒有該結果）。App 透過 `operation_id` / `tool_call_id` 在 `wrap_tool_call` 中直接冪等回傳已保存的原收據（包含 `produced_rev` 與 `latest_draft_rev`），隨即正常走完回合。


* **效果：** 100% 透過公開執行生命週期解決兩套儲存的時間差，**零框架內部儲存耦合**。



### 5. 交鋒五（針對第 6 點）：模型切換應區分「歷史圖片載荷移除」與「任務視覺依賴阻擋」

你指出切換到不支援圖片的模型後，「移除圖片、提示改用 OCR」只解決了 API 請求格式，無法解決粗體、圖例、上下標或圖片完整性的視覺核對需求。

* **最佳設計補強（任務階段的「模態需求檢查 Modality Gate」）：**
在「檢查新模型能力 $\rightarrow$ 準備可移交工作集 $\rightarrow$ 檢查實際輸入 $\rightarrow$ 啟用新模型」的四步切換順序中，第 2 步應加入明確的**工作集模態相容性判定**：


* 若當前活躍工作集包含**尚未解決的視覺依賴**（例如：已釘選待核對的頁面渲染圖、文字層為全透明 `GlyphLessFont` 且尚未完成強調格式視覺核對的頁面、或待執行的預覽截圖檢查），而新模型不具備視覺能力：


* App **不允許靜默把圖片刪掉假裝可以繼續完成視覺核對**；


* 系統應保留舊模型設定並直接向使用者／呼叫端回報「模型能力阻礙（Capability Blocker：目前工作集含未完成之視覺證據核對，目標模型不支援圖片輸入）」，或者僅允許執行不依賴視覺的純文字／腳本整理子任務，同時將所有視覺相關核對鎖定為 `blocked_requires_vision_model`。

## 三、 重構後的核心設計：四大運行行為契約（Runtime Behavioral Contracts）

將我們達成共識的所有規則整理為四份獨立、不預設固定轉換流程（不強制規定先探勘、先 OCR 或逐頁重建）的 Runtime 行為契約：

### 契約一：正常工作契約（Normal Operation Contract）

1. **Epoch 基準前綴與事件流分離：**
* **前段基準快照（Epoch Baseline Prefix）：** 在 Epoch 啟動時固定放入「系統規則、工具 Schema、當前有效要求快照（`req_rev=R`）、Epoch 啟動時的草稿與釘選基準（`draft_rev=D`）、二級分桶覆蓋索引與工作筆記（`notes_rev=N`）」。在同一個 Epoch 期間，此區段**絕對不改寫**，以保護穩定前綴。


* **後段增量流（Append-Only Turns & Deltas）：** 正常草稿修改、證據讀取與伴隨筆記更新，完全由當回合的 `ToolCall` / `ToolResult` 表達。若發生外部變動（如使用者更新要求為 `req_rev=R+1`），則在尾端追加一則**具實質內容的變更事件訊息**（包含新增／修改／廢止的具體要求條文、受影響的頁面範圍，以及哪些舊筆記需重新評估，而非僅貼一個版本號標籤）。




2. **穩定區塊身分與版本化草稿（Working Draft）：**
* 草稿結構採用 `[ {"block_id": "blk_01", "content_ref": "sha256:..."}, ... ]`，分離「邏輯區塊身分」與「不可變內容雜湊」。


* 支援直接傳入內容、引用既有區塊或匯入工作區檔案；任何引用的外部 Blob 寫入時先在 SQLite `staging_blobs(sha256, expires_at)` 登記租約，待短交易正式寫入 `draft_revisions` 與 `operation_receipts` 後才轉為正式引用，背景清理程序嚴格跳過未過期的準備中檔案。





### 契約二：容量整理契約（Capacity Compaction Contract）

1. **分階段容量預留公式：**
每次發送正常模型請求前，以路由校準後的組件估算器檢查：

$$\text{Estimated Current Input} + \text{Normal Output Margin} + \text{Expected Tool Receipt Margin} + \text{Handshake Turn Budget} \le \text{Model Effective Window}$$



一旦預估跨越安全餘量，提前在工具回合邊界啟動整理交接，讓 Agent 主動選擇釋放不再需要的證據並更新工作筆記與跨頁依賴。


2. **整批工具結果容量評估與精確投影收據：**
* 當單個或整批並行工具執行完成後，完整結果先依 Blob-First 協議落盤保存。


* 組裝器合併評估**整批工具結果**的總輸入成本：若能完整容納，直接提供完整讀取結果（不把容量處理變成強制摘要或強制簡化關卡）；若整批超限，回傳明確區分三者的結構化收據：


* `tool_execution_status`: 工具已成功產出並保存完整原件（附 `evidence_id` 與完整結構目錄）；


* `delivered_projection`: 本次模型輸入實際收到的表示法版本、欄位與頁碼／區塊範圍（如 `view: "lossless_compact", pages: [12], fields: ["blocks"]`）；


* `undelivered_scope`: 尚未進入模型輸入的文字範圍或圖片清單及其精確取回方式（絕不將導覽收據標記為「完整證據已交付」）。







### 契約三：異常恢復契約（Abnormal Recovery Contract）

明確區分四種容量與交接異常狀態，不做虛假的「零資訊損失」保證：

| 異常與容量狀態 | Runtime 確定性行為契約 | 對重取證據與工作延續的影響 |
| --- | --- | --- |
| **1. 尚有足夠餘量** | 提前在回合邊界請 Agent 選擇釋放證據、更新工作筆記與跨頁依賴，建立新 Epoch。

 | 正常延續，不丟失活躍依賴。

 |
| **2. 交接失敗，但舊 Context 仍可用** | 保留舊 Context 狀態，依失敗原因（如瞬時網路超時、工具參數格式錯誤）執行有限重試或修正，**不自動淘汰任何已落稿頁面的證據**。

 | 維持原工作狀態繼續。

 |
| **3. 舊 Context 已不可用（如超限且無法在原視窗完成交接，或程序崩潰重啟）** | 保存完整歷史紀錄；建立明確標示為 `[Recovery Context]` 的新 Epoch，載入：**最新有效要求、最新草稿版本與釘選區塊、最後有效工作筆記、自上次筆記以來的「未整理操作帳本（Mechanical Delta Log）」及精確檢索入口**。

 | Agent 可自主重建工作狀態；**明確承認未寫入最後有效筆記的近期細節可能需要透過 `read_evidence` 重新取證**。

 |
| **4. 連必要要求、最小工作索引與恢復操作都無法容納** | 立即保存所有已完成草稿與證據，中止自動迴圈並回報明確的 `capacity_blocker`（列明哪項必需內容或釘選超出當前模型視窗）。

 | 避免無限重試卡死，交由使用者調整範圍或切換更大視窗模型。

 |

### 契約四：模型切換契約（Model Switching Contract）

切換模型或路由時，嚴格依序執行四步檢查：

1. **檢查新模型能力（Capability Check）：** 核對新模型的有效視窗大小、是否支援原生圖片輸入、工具呼叫限制與協定格式（Chat Completions vs. Responses）。若目前任務或活躍釘選含未完成的視覺證據核對，而新模型無視覺能力，直接攔截並回報能力不符，不以「刪圖改用 OCR」掩蓋視覺資訊缺口。


2. **準備可移交工作集（Working-Set Preparation）：** 重置或切換該模型專屬的 Token 校準係數 $\alpha_{\text{route, model}}$；若新模型視窗較小，走「容量整理契約」讓 Agent（或透過顯式標示的恢復／收縮視圖）調整活躍工作集。


3. **檢查實際輸入（Actual Payload Verification）：** 針對新模型完成首個 Request Payload 試組裝，確認工具配對、圖片編碼與總容量合規。


4. **啟用新模型（Activation）：** 檢查通過後才正式切換活躍模型設定，否則保留原模型狀態。

## 四、 圍繞四大行為契約的 Pi SDK vs. LangChain `create_agent` 對照

撤回「按已落稿頁自動淘汰」後，我們用這四大運行契約重新審視 **Pi SDK (v1.3.0)** 與 **LangChain `create_agent` (搭配選用 Middleware)** 的真實適配度：

| 運行行為契約 | Pi SDK (v1.3.0) 公開接口實現方式 | LangChain `create_agent` 公開接口實現方式 | 關鍵取捨與自訂維護負擔 |
| --- | --- | --- | --- |
| **1. 正常工作契約**<br>

<br>（Epoch 基準前綴 ＋ 尾端事件 ＋ 冪等工具收據） | - 工具 `execute()` 回傳 `AgentToolResult { content, details }`。

<br>

<br>- 透過 `context` 擴充點提供固定 Epoch 基準前綴與尾端變更事件。

 | - `wrap_tool_call` 短路攔截重複 `operation_id`，回傳包含 `produced_rev` 與 `latest_draft_rev` 的 `ToolMessage`。

<br>

<br>- `wrap_model_call` 組裝 Epoch 基準前綴與尾端事件。

 | **兩者相當。** 核心的文件服務（`block_id` + `content_ref`、Blob 租約與 SQLite 收據）皆為獨立於框架的 App 核心模組。

 |
| **2. 容量整理契約**<br>

<br>（整批工具容量核算 ＋ 提前交接 ＋ 新 Epoch 切換） | - 在工具包裝層與 `context` hook 統一核算整批工具結果容量，超限時回傳 `delivered_projection` 收據。

<br>

<br>- 透過 `session_before_compact` 攔截預設壓縮，改由 App 的 Epoch 組裝器產生新基準（需停用或覆寫 Pi 預設的截短工具結果與自動縮圖行為）。

 | - 在 `wrap_model_call` 檢視剛產生的整批 `ToolMessage`，統一決定完整保留或轉為容量收據（需確保停用預設無差別的 `FilesystemMiddleware` 自動驅逐，或設 `tool_token_limit_before_evict=None`）。

<br>

<br>- 以自訂 Handshake / Epoch Middleware 執行提前交接。

 | **兩者皆需停用／覆寫預設的盲目截斷 policy**，並接入 App 的「組件校準預算器」與「整批工具容量分配器」。

 |
| **3. 異常恢復契約**<br>

<br>（交接失敗退避、建立 `[Recovery Context]`、崩潰後收據對帳） | - 交接失敗且舊視窗已滿時，寫入新的 Epoch 起點（`context_edit` / compaction entry），載入 `[Recovery Context]` 與未整理操作帳本。

<br>

<br>- 崩潰重啟時透過 `SessionManager.open()` 載入，在首次 `context` hook 與工具呼叫中完成惰性確認與冪等重放。

 | - 交接失敗且舊視窗已滿時，由 Middleware 插入新的 Epoch 分界事件並組裝 `[Recovery Context]`。

<br>

<br>- 崩潰重啟時由 Checkpointer 恢復，在首次 `wrap_model_call`（檢查訊息中是否已有該 `tool_call_id`）與 `wrap_tool_call`（冪等回傳收據）完成無耦合恢復。

 | **無須直接查核或修改兩者的底層持久儲存格式**，即可處理 `returned_to_session_at` 的交易空隙與交接失敗恢復。

 |
| **4. 模型切換契約**<br>

<br>（能力檢查、圖片可用性、工作集重算） | - 支援在 Session 中切換模型與 `openai-completions` / `openai-responses` 設定；需由 App 的 Model Switch 閘門先檢查視覺能力與新視窗預算，通過後才調用 Pi 的模型設定更新。

 | - 支援在 `wrap_model_call` 動態選擇或切換底層 ChatModel 實例；同樣由 App 的 Model Switch 閘門先完成視覺依賴與容量預檢，再注入新模型實例並保留雙協定原生圖片配對。

 | **兩者皆需由 App 實作前段「能力與視覺依賴檢查器」**，框架本身不會知道某頁透明 `GlyphLessFont` 仍需要視覺模型核對。

 |

這套修訂將「四大運行契約」徹底擺脫了脆弱的自動化假設（不再假設已落稿即可刪證據、不再假設 Rollup Map 用一維摺疊永遠 20 行、不再假設時間戳與框架儲存同一交易、不再假設無視覺模型靠 OCR 就能接手所有任務）。

既然我們已經將設計收斂到這四大運行契約，下一步你希望我們先針對這四份契約中最核心的 **「異常恢復契約（特別是交接失敗轉入 `[Recovery Context]` 時，如何組裝『未整理操作帳本』與檢索入口）」** 及 **「整批工具結果的容量分配與投影收據格式」** 進行精確定義與離線案例驗證嗎？
