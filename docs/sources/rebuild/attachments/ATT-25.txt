## 一、 核心架構交鋒：既然 `create_agent` 的預設行為處處需要攔截，直接用 3 節點 `StateGraph` 才是真正的「薄 Runtime」

* **最佳功能設計（直接定義 3 節點 `LangGraph StateGraph` ＋ 共用 `AppToolDispatcher`）：**


這樣設計的好處是立竿見影的：

## 二、 針對其餘關鍵細節的交鋒與修正方案

### 1. 針對第 1、5 點（草稿匯出、分階段驗證與可更正的 Provenance）

* **完全採納的修正：**
1. **草稿隨時可預覽、建快照與匯出：** 嚴格遵循 `PRODUCT_REQUIREMENTS.md` 中「有用的部分成果即是誠實草稿（honest draft）」的規定。`export` 不設「全書必須完成」的阻擋門檻；當匯出尚未完成全部範圍或帶有未解問題的版本時，匯出器正常產出完整的 Markdown／JSON／HTML／資產／ZIP 包，並在 `manifest.json` 與 `document.json` 中明確標記 `delivery_state: "draft"` 與 `unresolved_gaps` 清單（區分「未處理範圍」、「內容存疑」與「技術錯誤」），僅阻擋將其宣稱為 `complete_accepted`。


2. **單一編輯呼叫同時容納正文與選填頁碼：** 不強迫 Agent 拆成兩次工具呼叫。編輯工具（如 `save_or_patch_version`）允許同時傳入區塊修改與已知的頁碼／範圍對應；若頁碼對應尚有缺漏，系統仍原子保存新版本並將缺漏處標為 `unconfirmed`，不退回已寫好的正文。


3. **印刷頁碼與 Provenance 皆為「可隨版本更正的觀測記錄」：** 撤回「印刷頁碼是 68 永遠不會失效」的絕對化表述。只有來源 PDF 的 `sha256` 與總物理頁數是不可變的檔案事實；印刷頁碼（`printed_page`）、區塊對應的 `source_refs`（含 `evidence_id`、頁碼、座標框）與範圍聲明，全部綁定文件版本號（`version_id`），允許 Agent 在後續發現辨讀有誤時提交新版本更正，並保留歷史版本的雙向追溯。

### 2. 針對第 3 點（整份文件解析下的 `data-block-id` 注入與消除捲動截斷）

你用 `區塊 A: See [source][r].` 與 `區塊 B: [r]: [https://example.com](https://example.com)` 證偽「逐區塊獨立呼叫 `markdown-it-py` 渲染」非常精準——除了參考式連結（Reference Links），跨區塊的註腳（Footnotes）在獨立渲染時同樣會壞掉。

* **如何在「整份文件一起解析」的前提下，精確建立 `block_id -> DOM` 對應？**
我們不需要靠脆弱的文字比對，也不需要假設「一個區塊只能對應一個 DOM 節點」：
1. **整份文件拼接並記錄行號區間：** 當組合某個版本的完整 Markdown 時，系統確切知道每個 `block_id` 佔用的起始與結束行號 `[start_line, end_line)`（例如 `blk_01` 為第 0–12 行，`blk_02` 為第 14–35 行）。
2. **利用 `markdown-it-py` 原生 `token.map` 注入屬性：** 將整份 Markdown 一次送入 `markdown-it-py` 解析（因此跨區塊的 `[source][r]` 與註腳 100% 正常解析）。接著透過一個僅約 15 行的 `markdown-it-py` core rule，遍歷頂層 block tokens（以及由 HTML 表格構成的 `html_block` token）：凡是 `token.map` 落在 `blk_k` 行號區間內的頂層產出節點，統一在該 DOM 元素上掛載 `data-block-id="blk_k"`（若單一 `blk_k` 產生多個頂層段落或表格，多個 DOM 節點都會帶有相同的 `data-block-id="blk_k"`，天然支援一對多！）。最後在 `nh3` 清理時保留 `data-block-id` 屬性即可。


3. **從 CSS 源頭消除 `locator.screenshot()` 的捲動遮擋：**
你指出 Playwright 的 `locator.screenshot()` 遇到捲動容器只會拍到可見區域。好消息是：預覽 HTML 的 CSS 完全由我們的 `preview.py` 控制！


* 在生成供檢視截圖的預覽頁面時，CSS 嚴禁對頁面或表格容器設定固定高度與 `overflow: auto / scroll`，並將離屏視窗寬度動態展開至包含最寬表格的 `document.documentElement.scrollWidth`（同時確保無 `position: fixed/sticky` 遮擋物）。
* 當一個 `block_id` 對應多個帶有 `[data-block-id="blk_k"]` 的 DOM 節點時，由渲染器計算這組節點的聯集邊界框（Union Bounding Box）後透過頁面級 `clip` 擷取，若區塊極長則自動分段擷取並回報分段範圍。

### 3. 針對第 6 點（跨重啟穩定的邏輯步驟身分，而非依賴框架 `run_id`）

你在第 6 點問到關鍵細節：**「`(run_id, step_index)` 可以是實作方式，但要明定它是 App 的穩定身分，如何跨恢復維持、如何區分分支；不能直接假定框架每次 invocation 的識別碼具有這些性質。」**

* **實作陷阱確認：** 在 LangGraph 中，每次呼叫 `.invoke()` / `.ainvoke()` 都會產生全新的 `run_id`！因此如果重試帳本或已落盤回覆用 LangGraph 的 `run_id` 當主鍵，程序崩潰重啟後再次呼叫 `.ainvoke()` 時，因為 `run_id` 變了，系統就會找不到崩潰前已落盤的 `accepted_reply_id`，進而重發一次重複的 HTTP 請求！
* **最佳功能設計（由 Graph State 承載的 `(job_id, checkpoint_ns, model_turn_seq)`）：**
1. 在 `AgentState` 中維護一個顯式的整數計數器 `model_turn_seq`（初始為 `1`，僅在 `settle_step` 完成一輪工具與狀態結算、準備進入下一輪模型呼叫時 `+1`）。
2. 當進入 `model_step` 時，App 的模型步驟穩定主鍵定義為 **`logical_step_id = f"{job_id}:{checkpoint_ns or 'main'}:{state['model_turn_seq']}"`**。
3. **無縫跨重啟恢復：** 假設在第 4 輪（`model_turn_seq = 4`），Nexus 已經回傳完整回覆並由 Adapter 寫入本地帳本（綁定 `logical_step_id = "job_1:main:4"` 與 `accepted_reply_id = "rep_004"`），但就在此刻程序斷電，LangGraph 尚未保存第 4 輪的 Checkpoint。
4. 重啟後，LangGraph 從第 3 輪結束時的 Checkpoint 恢復（此時 `state["model_turn_seq"]` 依然是 `4`），重新進入 `model_step`。節點一開始就用 `"job_1:main:4"` 查詢本地帳本，立刻發現 `rep_004` 已經存在且通過完整性驗證，直接從磁碟載入該回覆轉為 `AIMessage` 返回，**零重複網路請求**！

### 4. 針對第 6 點另一半（嚴格隔離 `ToolMessage.artifact` 與 `NexusChatModel` 編碼器）

你指出的這條資料流邊界必須寫成硬性規定：
