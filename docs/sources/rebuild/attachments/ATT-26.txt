## 一、 全局反思與交鋒：砍掉「雙重狀態庫」包袱，補齊「終端交付驗證」

### 1. 全局交鋒一：為甚麼前幾輪不斷出現「跨儲存時間差」？因為我們不該在文件快照與 Checkpointer 之外再造一套複雜的收據資料庫

回顧先前的討論，我們花了大量精力修補「文件已提交但收據未寫入」、「收據已寫入但 Session 未更新」的時序漏洞。你在第 3 點提到的現有程式碼（`core.py:241`）其實已經給出了最優雅的解答：**把 `publication_operation`（操作身分）直接寫進文件版本快照本身！**

* **問題根源：** 當「文件版本」與「操作收據」被拆成兩次獨立寫入時，中間必然存在崩潰空隙。
* **最佳重構設計（Commit-as-Receipt 原則）：**
* **文件修改操作：** 產出新草稿或正式版本時，`operation_id`（連同輸入參數指紋 `input_sha256`）直接作為該版本 `document.json` / 版本 metadata 的內建欄位，透過單次原子檔案替換（如 Windows `ReplaceFileW`）或單一短交易落盤。**版本存在，收據就存在；版本未提交，收據就不存在。** 兩者物理合一，從根本消滅「文件已提交但收據未寫入」的時間差。


* **證據產生操作（`inspect` / `ocr` / `render`）：** 原件落盤後，其不可變證據描述檔（`evidence_meta.json`）本身就內嵌 `(operation_id, input_sha256)`。重啟對帳時只需比對確定性索引，無須維護另一套龐大的事件溯源資料庫。





### 2. 全局交鋒二：破解 MCP SDK (`base.py:152`) 驗證過早的死結——分離「傳輸外殼 Schema」與「領域驗證」

你查出目前安裝的 MCP Python SDK 會在進入註冊的工具函式前，先在 `mcp/server/mcpserver/tools/base.py:152` 執行 Pydantic 驗證——這意味著如果把 `save` / `revise` 的嚴格頁碼映射與結構約束全部寫在暴露給 MCP 的頂層 Pydantic 模型上，只要模型填錯一個 metadata 欄位，MCP Server 就會在 `base.py:152` 直接攔截報錯，裡面的 `AppToolDispatcher` 連一個字都收不到！

要讓內建 Agent、CLI（`call`/`relay`） 與外部 MCP（`serve`） **真正 100% 共享「驗證前先存候選正文」的保護**，有兩條具體工程路徑（建議同時採用）：

1. **在協議入口層攔截（針對內建 Agent 與 CLI/MCP 底層）：** 內建 LangGraph 工具節點與 CLI `relay` 直接接收解析後的原始 JSON dict，先呼叫 `CandidateStore.save_raw_arguments(operation_id, raw_args)`（承接 `agent_tools.py:383` 的設計），再執行領域驗證。
2. **將工具的「傳輸層 Schema」與「領域層 Schema」解耦（徹底解決 MCP `base.py:152` 攔截）：**
* 註冊給 MCP `base.py` 的頂層工具參數模型（Transport Schema）只對 `blocks` / `content` 與 `metadata` 定義寬鬆的基礎容器型別（例如允許 `page_map` 或附加欄位以 `dict[str, Any]` 通過 `base.py:152` 的第一關），讓呼叫必然能進入 `AppToolDispatcher`。
* 進入 `AppToolDispatcher` 後，**第一步先將完整參數與正文落盤為 `candidate_ref**`；**第二步才用嚴格的領域 Pydantic 模型（Domain Schema）執行完整性驗證**。驗證失敗時回傳精確的欄位錯誤與已保存的 `candidate_ref`，讓所有入口獲得完全一致的保護。

## 二、 針對 7 點審閱的深度修正與架構收斂

### 1. 以「保存邊界」定義 4 節點 `StateGraph`：解決分支與續聊的 `model_step_id` 碰撞（回應第 1、2、7 點）


#### 為什麼多一個 `prepare_step` 能徹底消除碰撞？

* **每次需要模型新判斷，必然先經過 `prepare_step`：** 無論是工具執行完進入下一輪、使用者在 `END` 之後追加新訊息，還是從某個歷史點 `update_state` 分支重跑，入口都是 `prepare_step`。
* **雙重綁定（`model_step_id` + `request_fingerprint`）：**
1. `prepare_step` 組裝好本次真正要送出的訊息、系統提示與選中證據清單後，計算內容雜湊 `request_fingerprint`，並生成一個全新的唯一 `model_step_id`（例如 UUIDv7），透過 `durability="sync"` 寫入 LangGraph Checkpoint。


2. 接著進入 `model_step`：
* **若在 `model_step` 收到回覆落盤後、但尚未完成 `model_step` Checkpoint 前崩潰：** 重啟時 LangGraph 會從剛跑完 `prepare_step` 的那個 Checkpoint 恢復，進入 `model_step` 時帶著**同一個 `model_step_id` 與完全相同的 `request_fingerprint**`，因此能 100% 安全重用已落盤的回覆。
* **若是從歷史點修改狀態建立新分支，或使用者追加了新訊息：** 即使 किसी原因重用了步驟名稱，`request_fingerprint` 也必然不同，系統會立即拒絕重用舊答案並發起新請求。
