這份審閱指出的三個核心問題——**以 `max(policy_rev)` 處理並行更新會靜默丟失分支修改**、**被 Compaction 移除的 `ToolMessage.id` 若遭重播會「借屍還魂」重新插入訊息列表**，以及**未水合引用若強制每輪逐項留在活躍輸入會阻礙長章節跨越 Context 邊界**——精準點出了前一版契約在極端並發與長程執行下的破口。

在維持 **LangChain `create_agent` ＋ 持久化 LangGraph Checkpointer** 作為重構基線的前提下，以下先確認六項直接定案的修正，接著針對這些修正落實到執行期時會引發的**四個次生工程問題**進行正面交鋒與補強，最後給出收斂後的執行與資料規格。

## 一、 完全成立並納入基線的六項修正

1. **廢除 `max(policy_rev)`，改用 `parent_policy_rev` 血緣檢查與單一啟用點：** 版本號較大不代表涵蓋了另一並行分支的修改；Context Policy 的推進必須核對預期父版本，且恢復時必須遵循被恢復 Checkpoint 分支所綁定的版本，而非讀取資料庫的全域最大修訂號。
2. **重播嚴格限縮於 Checkpointer 判定待續跑的工作：** 恢復時不掃描資料庫所有成功收據灌回 State，避免將已被 Compaction 移除的舊 `ToolMessage` 重新插入訊息列表；同時將 `parent_ai_message_id` 納入 `operations` 的唯一約束，並明確限定 `framework_state_update_json` 僅序列化 App 工具契約允許的 `Command(update=...)` 欄位。
3. **未水合證據以「待處理範圍＋外部目錄入口」跨越多個 Context：** 遵守「不對未讀原文做無根據摘要」的同時，允許將「工具已產出第 15–20 頁資料」這類操作事實壓縮為範圍狀態與 Manifest 查詢入口，讓未完成的長章節也能順利整理歷史。


4. **分離「回合預算身分（`round_id`）」與「輸入檢視快照（`input_view_id`）」：** 單一模型回合的重試次數上限（如 `1 + automatic_retries` 最多 3 次嘗試）與累積活躍時間預算綁定於穩定的 `round_id`；若重試期間因故更新了輸入快照，產生的新 `input_view_id` 仍共享同一筆回合預算，絕不重置計數。


5. **以 `PROC_THREAD_ATTRIBUTE_JOB_LIST` 消除程序建立空隙，並允許核對後重用腳本成果：** 在支援的 Windows 環境於 `CreateProcessW` 建立當下直接掛載 Job List，消除 `CREATE_SUSPENDED` 與事後指派之間的崩潰視窗；對缺少最終收據的宿主腳本，允許 Agent 先檢查已保存腳本、輸出與副作用，確認合規後再補登重用。


6. **輸入檢視（`model_input_views`）同樣遵守 Blob-First 寫入順序：** 先完成 System Prompt、Tool Schemas 與投影內容的 Blob 落盤與校驗，再於 SQLite 提交引用它們的 `model_input_views` 記錄，並將可重建承諾嚴格界定為「App 在最內層組裝邊界產生的邏輯輸入」。

## 二、 四個深層交鋒：解決修正方案衍生的新執行期陷阱

### 1. 交鋒一（針對第 1 點）：若等到 LangGraph State Reducer 才拒絕 `parent_policy_rev` 衝突，會導致整個並行 Superstep 崩潰

你提出：「啟用新 policy 時，核對它的預期父版本與當前有效版本……不同操作從同一舊版本產生互相競爭的更新，應明示衝突。這個檢查必須發生在實際接受狀態更新的地方。」

* **執行期陷阱：** 在 LangGraph 中，如果兩個並行工具呼叫都回傳 `Command(update={"active_policy_rev": ...})`，所謂「實際接受狀態更新的地方」是 Superstep 結束時的 **State Channel Reducer**。如果我們讓 Reducer 在發現 `parent_policy_rev` 衝突時拋出例外，**整個 `ToolNode` Superstep 就會在框架層直接崩潰**，連同該批次中另一個已經跑完 40 秒的無辜 OCR 工具也無法完成 Checkpoint 推進！
* **最佳功能設計（將「Policy 提交點」收歸 SQLite `BEGIN IMMEDIATE` 短交易，並支援無衝突增量合併）：**
1. **以 SQLite 獨佔寫入鎖作為唯一啟用點：** 任何修改 Context Policy 的工具在回傳 `Command` 之前，必須先在 App 資料庫的 `BEGIN IMMEDIATE` 交易內提交新 Policy。因為 SQLite 寫入交易本身就是嚴格串行化的，兩個並行工具絕對不會同時通過資料庫的 `parent_policy_rev == current_active_rev` 檢查。
2. **非重疊意圖自動線性串接（Linear Intent Rebasing）：** 當操作 A（新增釘選 `blk_12`）與操作 B（釋放舊證據 `ev_03`）同時基於 `policy 7` 發出時：
* 先拿到鎖的 A 建立 `policy 8 (parent=7)`。
* 幾毫秒後拿到鎖的 B 發現當前已是 `policy 8`；但因為 B 提交的是結構化變更意圖（`delta_intents`），服務層檢查發現 A 與 B 操縱的對象完全無交集（Disjoint），即可直接在交易內將 B 基於 `policy 8` 疊加生成 `policy 9 (parent=8)`（同時包含 `blk_12` 釘選與 `ev_03` 釋放）！
* 只有當 A 與 B 修改同一個對象（例如一個釘選 `ev_03`、一個釋放 `ev_03`）時，才讓後到的 B 回傳一則 `status="conflict_rejected"` 的普通 `ToolMessage`（不帶 `Command` 更新），既明示了衝突，又**絕對不會炸毀 LangGraph 的 Superstep**。





### 2. 交鋒二（針對第 3 點）：將未水合證據移出每輪 Context 時，必須防止 Agent 把「已抽取待讀頁」誤判為「未抽取頁」而重複執行 OCR

你指出第 15–20 頁尚未處理時，只需保留「待處理範圍＋不可變 evidence manifest 入口」，不必把每個 evidence 的完整目錄帶進每輪 Context。

* **認知與效能陷阱：** 假設 Agent 在第 4 輪對第 15–20 頁呼叫了耗時的 `ocr_pdf(pages="15-20")`，因容量限制未水合展開；到了第 6 輪執行 Compaction 後，如果活躍視圖只留下一句籠統的 `Pages 15-20: pending, see manifest_04`，Agent 在開始處理第 15 頁時，極可能忘記這幾頁已經做過 OCR，於是再次呼叫 `ocr_pdf(pages="15-16")`（而不是呼叫零運算成本的 `read_evidence`）！
* **最佳功能設計（雙重保護：區分「抽取覆蓋 vs. 草稿覆蓋」＋ 證據服務內容尋址快取）：**
1. **活躍視圖明確標示「已有可用原件範圍」：** 在緊湊進度視圖中，將狀態明確寫為 `Pages 15-20: draft_pending | extracted_evidence_ready: [ocr, layout] via manifest_04`，讓 Agent 一眼看出原件已在庫中，只需按頁讀取。
2. **抽取與渲染工具的確定性快取（Deterministic Extraction Cache）：** 即使 Agent 真的忘記而再次呼叫 `ocr_pdf` 或 `inspect_pdf`，證據服務在啟動子程序前，先計算 `(source_pdf_sha256, tool_name, canonical_params_sha256)`；若 `evidence_blobs` 中已有完全相同參數的成功產出，直接回傳既有 `evidence_id` 的指定範圍內容，不重複啟動 Tesseract 或 PyMuPDF 渲染。





### 3. 交鋒三（針對第 4 點）：在固定 `round_id` 預算下，必須明確規定「何種失敗凍結 `input_view_id`，何種失敗允許降級產生新 `input_view_id`」

你精確指出：相同固定輸入的重試可共用 `input_view_id`；若修改了輸入則應建立新 `input_view_id`，但不能重置原有的回合身分、已消耗嘗試次數及時間預算。

* **必須定清的決策分界：** 當單一回合的第 1 次模型請求失敗、準備消耗第 2 次重試配額時，系統究竟該**原封不動重送同一個 `input_view_id**`，還是**重新組裝一個新的 `input_view_id**`？如果規則不清，會在兩種極端間犯錯：

* **最佳功能設計（依錯誤類別路由的 `Round -> InputView` 重試狀態機）：**

## 三、 收斂後的資料模型與關鍵欄位修訂

結合本輪所有修正，我們不需要增加新表，只需將既有表格的約束與關係調整至完全精確：

```sql
-- 1. 模型回合預算表（承載既有 controller 的單輪重試上限與活躍耗時，不隨 input_view 改變而重置）
CREATE TABLE model_rounds (
```

## 四、 核心執行契約總覽（供實作直接對照）

1. **恢復與重播（Checkpointer-Driven Replay Only）：**
重啟時先由 LangGraph Checkpointer 取得當前分支（Branch）的 `StateSnapshot`（含該分支的 `active_policy_rev` 與待執行 `tasks`）。**僅針對當前 `tasks` 中待執行的工具呼叫查詢 `operations` 表**：若 `(thread_id, checkpoint_ns, parent_ai_message_id, tool_call_id)` 與 `canonical_input_sha256` 吻合且已 `succeeded`，才重播對應的 `ToolMessage` 與 `state_update_patch_json`；絕不掃描歷史收據復活已壓縮的舊訊息。
2. **Policy 變更與衝突處理（Serialized Intent Commit）：**
Context Policy 變更統一在 App 服務的 `BEGIN IMMEDIATE` 交易內核對 `parent_policy_rev`。無交集的並行變更自動線性疊加（`7 -> 8 -> 9`）；相互矛盾的變更在工具層直接回傳衝突說明，不讓 LangGraph Reducer 拋出未捕捉例外中斷整個 Superstep。
3. **跨 Context 進度與證據感知（Manifest-Backed Continuity）：**
整理歷史時，未展開的證據不必逐筆塞入每輪 Prompt，而是收斂為 `pending_extracted_manifests_json` 的範圍摘要（明確標示哪些頁碼已有現成抽取原件可查、哪些頁碼尚未抽取），搭配證據服務的參數雜湊快取，確保長章節跨越多個 Context 時既不塞爆視窗、也不重複執行昂貴的 OCR。



這套架構與契約已經把執行恢復、並發版本控制、重試預算綁定與長文件 Context 延續的所有邊界條件收斂完畢。你希望下一步直接進入這個資料庫與 Middleware 核心層的程式結構設計，還是還有其他邊界條件需要微調？
