**這版最值得採納的是「草稿可以先保存、不必等整份文件完成」，以及把圖片組裝改為每次請求獨立處理。** 但我不建議直接按最後的 Slice 1 表格實作：順序鎖、逐區塊渲染，以及回覆落盤後的恢復，仍有會影響產品正確性的缺口。

也要校準開頭的實測解讀：191,662 字元的 `inspect` 出自一個**通過來源驗收的任務**，能證明輸入負擔，不能證明它造成失敗；十三頁 A 最終剩下的強調錯誤在 16／18／24，C 才包含第 14 頁及「礪→厲」。這些結果支持改善工具與核對能力，但尚未證明所有錯誤都是介面摩擦造成的。[實測記錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:100)、[十三頁結果](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:264)

**1. 草稿與完成驗證應分開；草稿也必須能預覽、保存快照及匯出。**

我同意讓 `write_blocks` 接受尚未完成頁碼整理的內容。這能直接減少「正文正確，卻因 metadata 被迫重新提交」的摩擦。

但提案把嚴格驗證移到 `publish_version`／匯出，仍需區分：

| 動作 | 應保證甚麼 |
|---|---|
| 保存草稿 | 修改沒有遺失，版本與區塊關係一致，未完成資訊有明確標示 |
| 建立快照／匯出 | 產物來自同一版本，清楚標示草稿狀態與已知缺口 |
| 宣稱任務完成 | 使用者要求的範圍已完成，沒有已知重大錯誤或必要未處理內容 |

**未完成不能等於不能匯出。** 服務中斷時，使用者仍應拿得到可用的部分成果；這也符合現有要求。[保存與交付要求](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/PRODUCT_REQUIREMENTS.md:50)

另外，分開驗證責任不必強迫 agent 分兩次呼叫：同一個編輯操作可以同時提交正文與可選的頁碼更新，原子保存；缺少的資料留待補充。

`wrap_tool_call` 作為驗證前保存入口是可行的，我核對的官方實作確實先呼叫 wrapper，再執行工具。不過其 `args` 已是解析後的字典，並非原始回覆位元組；完整原生回覆仍由 adapter 保存。MCP／CLI 也應共享保存契約，不能只有內建 agent 得到這項保護。[ToolNode 原始碼](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/prebuilt/langgraph/prebuilt/tool_node.py)

**2. 並行派發的提醒正確，但「30 行順序鎖」不是可靠恢復方案。**

目前官方 `create_agent` 原始碼確實把待執行工具分別送進 `Send("tools", ...)`；不能假定它沿用舊 controller 的逐項迴圈。[官方實作](https://raw.githubusercontent.com/langchain-ai/langchain/master/libs/langchain_v1/langchain/agents/factory.py)

然而，只靠記憶體中的鎖與完成訊號，有一個直接的恢復問題：

1. 工具 A 完成，工具 B 尚未完成。
2. 程序中斷。
3. LangGraph 恢復時跳過已完成的 A。
4. B 若等待 A 在本次程序重新發出的訊號，就可能一直等待。

框架保存成功節點的 pending writes、恢復時不重跑成功節點，正是官方行為。[Checkpointer 文件](https://docs.langchain.com/oss/python/langgraph/checkpointers)

此外，`reopen` 若排在寫入之前，僅等待「較早的寫入」也不能阻止較晚的寫入搶先改變 `latest`。

我會先消除這類隱含依賴：

- 預覽、重開、匯出綁定明確版本。
- 修改帶 `base_revision`，由共用文件服務原子提交。
- 恢復依據持久操作收據，不依賴某個 wrapper 是否再次執行。
- 確實需要宣告順序的批次，由掌握整批操作的執行器負責。

若選定版本的 `create_agent` 無法簡單滿足最後一點，**使用 LangGraph 的一個小型順序工具節點，是合理取捨**；模型仍自主決定工具與方法，不會因此變成固定轉換流程。沒有必要為維持 `create_agent` 的形式，反而在 middleware 裡重建隱藏排程器。

還有，OCR／render 雖然不修改來源 PDF，實際會建立檔案、資產或啟動程序，不能統稱為無副作用。它們可以並行，但應按實際儲存與資源契約判斷。

**3. `data-block-id` 可以採用；「每個區塊各自渲染」不能直接採用。**

我用專案現有的 Markdown parser 做了一個記憶體內核對：

```markdown
區塊 A：See [source][r].

區塊 B：[r]: https://example.com
```

整份解析會產生正常連結；分開解析再拼接，區塊 A 會留下字面的 `[source][r]`。這符合 CommonMark 的參照連結規則。[CommonMark 規範](https://spec.commonmark.org/0.31.2/#link-reference-definitions)

因此，五行 wrapper 並不能保證預覽與交付內容一致。我建議：

- 按整份文件解析，保留跨區塊語義。
- 利用來源區間與 parser token 的位置資料，建立區塊到渲染結果的對應。
- 在合適的 DOM 節點加入應用程式產生的定位屬性。
- 允許一個內容區塊對應多個 DOM 區域，不強迫一對一。

`markdown-it-py` 已提供 token 的來源行範圍，可作為這項工作的基礎，但不是現成的完整對應方案。[官方 parser 文件](https://markdown-it-py.readthedocs.io/en/latest/using.html)

`locator.screenshot()` 也不保證擷取所有內容：官方明示，捲動容器只會顯示當前可見內容，遮擋也會進入截圖結果。[Playwright 文件](https://playwright.dev/python/docs/api/class-locator#locator-screenshot)

獨立來源圖與輸出圖可以作為便利選項；拼圖也可保留供 agent 選擇，不必把另一種檢視方式全面禁止。

**4. 先做文字 patch 合理，但不需要因此永久撤回 `cell_ref`。**

提案把 `cell_ref` 等同於「必須自建完整 HTML AST 原位編輯器」，這個推論過強。

工具若已能回傳「某格在原始 HTML 的精確片段」，就已經需要可靠定位。把同一定位包成綁定版本的引用，再交給共同 patch 機制，不必然需要另一套編輯引擎。結構性修改則仍可使用較大範圍或多項 patch；單格工具不需要承擔所有修改。

**我會先實作通用 patch，把儲存格介面列為可選便利功能。** 但建議修改這個契約：

```text
patch_block(..., expected_old_text, new_text, occurrence=1)
```

預設 `occurrence=1` 容易靜默改到第一個重複值。較好的規則是：

- 未指定位置時要求唯一匹配。
- 重複時回傳位置與上下文，讓 agent 明確選擇。
- 多項 patch 全部對同一基底版本驗證，再一起提交。
- 修改失敗仍保留候選內容。

它能保證修改位置與原文匹配，不能保證 agent 的語義判斷正確；「處理 95%」目前沒有資料支持。

NFC 的結論也宜精確表述為「不能一概視為無損」，而非每次正規化都會造成可見錯誤。維持不自動改寫正文的方向即可。

**5. 三層資料分工值得採用，但印刷頁碼與 provenance 都要允許更正。**

分開來源資訊、內容對應與完成聲明，比單一頁面狀態清楚。

但「印刷頁碼是 68 的事實永遠不會失效」不夠準確：來源未變，先前的辨讀仍可能有誤。應區分：

- 來源檔案雜湊、物理頁序等可直接確認的身分。
- 印刷頁碼與內容對應等有依據、但可修正的觀察或判斷。

更正應產生新的記錄／版本，保留舊版本當時使用的資料。`block_provenance` 也應保留前面已同意的不可變 `source_refs`；只有頁碼與自然語言備註，會失去已建立的精確取回能力。

範圍擴大時，保留原成果並標示新增或尚未確認的部分是對的。但不必讓所有舊成果都重新審閱；能否沿用，應取決於相關內容、要求與引用是否改變。

**6. 圖片編碼可以沒有請求殘留，但不能繞過 context policy。**

移除共享的 `pending_images`，改成由當次輸入組裝圖片，我同意。模型物件仍可持有設定、連線池和服務引用；需要避免的是跨請求混用的暫存資料，不必追求字面上的「100% 無狀態」。

更重要的是這條邊界：

> 保存的完整 artifact → 本次 context 選取 → 解析所選圖片 → 協定編碼。

編碼器若掃描所有歷史 `ToolMessage.artifact`，把存在的圖片全部重新加入，前面做的 release 就失效了。`artifact` 本身也不會自動送給模型，必須由我們明確選擇與轉換。[LangChain 訊息文件](https://docs.langchain.com/oss/python/langchain/messages)

恢復還要補上一個時間差：

> 完整回覆已落盤，但包含 `accepted_reply_id` 的 Graph checkpoint 尚未保存。

重啟後，Graph 可能仍要重新執行模型節點。因此，節點必須先以持久的邏輯步驟身分查找已接受回覆，再決定是否送出 HTTP。單靠「checkpoint 內有相同 ID」只涵蓋 checkpoint 已保存的情況。

`(run_id, step_index)` 可以是實作方式，但要明定它是 App 的穩定身分，如何跨恢復維持、如何區分分支；不能直接假定框架每次 invocation 的識別碼具有這些性質。

**7. 我會把設計收斂到以下邊界，停止用功能數量擴張 Slice 1。**

| 部分 | 建議責任 |
|---|---|
| 文件核心 | 保留候選、實用草稿、局部修改、版本、來源對應與一致匯出 |
| Agent runtime | 模型／工具迴圈、持久執行狀態、操作恢復與必要執行順序 |
| Context 組裝 | 保護有效要求與工作狀態，選取證據，組裝本次真正送出的內容 |
| Nexus adapter | 協定轉換、請求執行、完整回覆保存；不另決定證據取捨 |
| 預覽服務 | 使用同一文件版本與渲染語義，提供可追溯的整體／局部檢視 |

這版 Slice 1 又同時加入完整編輯介面、雙協定串流、三層資料重構、DOM 對應及並行協調，範圍已再次變大。完整重構仍可以逐步交付：先確保**內容存得住、能修、能拿走、能接續**，再加入局部視覺便利功能與長任務 context 整理。

最後一點尤其重要：只保存輕量引用、提供 pin／release，還沒有完成 context management。仍需處理普通對話歷史、使用者後續修訂、未解依賴，以及單次所選證據已超容量的情況。這些應是明確的後續能力，不宜被「新 runtime 已接好」掩蓋。
