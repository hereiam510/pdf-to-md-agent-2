我建議設計成 **一個 app-owned Context Manager，統一管理證據、工作狀態及每次送給模型的內容**。模型仍負責判斷甚麼重要，Context Manager 負責儲存、容量及正確執行。

不需要向後相容後，可以直接取代目前分開的 `full / agent_selected / checkpoint` 使用模式，建立一個正常運作的流程。以下是建議設計，尚未實作。

**1. 把「完整記錄」與「模型正在看甚麼」分開**

核心結構是：

```mermaid
flowchart TD
    A[使用者要求與工具結果] --> B[完整記錄與證據儲存]
    B --> C[Context Manager]
    D[工作狀態與保留選擇] --> C
    E[模型能力與容量預算] --> C
    C --> F[Provider Adapter]
    F --> G[模型]
    G -->|工具操作與整理決定| A
    G -->|更新工作狀態| D
```

完整歷史是可追溯的原始記錄；每次模型請求則是由它組裝出來的一個工作視圖。

我會保留五類資料：

| 資料 | 內容與責任 |
|---|---|
| `EventLog` | 使用者訊息、assistant 回覆、工具呼叫／結果、context 變更等完整事件 |
| `EvidenceStore` | 原始工具結果、OCR、圖片、精確來源及版本 |
| `TaskContract` | 有效任務、要求及後續修訂；保留使用者原文與出處 |
| `WorkingState` | Agent 維護的進度、未解問題、依賴、必要決策及成果引用 |
| `ContextManifest` | 這次 context 包含哪些事件、證據、工作狀態版本，以及哪些內容已移出 |

**重要改變：使用穩定 ID，不再依賴「歷史陣列第幾個訊息」。** 現有 `EvidenceHistory` 使用訊息位置做映射，重新編排及跨 context 取回時會較脆弱。

第一版可以使用現有 filesystem、JSON／JSONL 和原子寫入能力。現在沒有理由先引入資料庫或向量資料庫。

**2. 證據儲存與 context 呈現各自有自己的狀態**

同一份證據可以一直存在磁碟，但在目前 context 中呈現為：

- 完整內容。
- Agent 選擇的精確欄位、範圍或圖片。
- 移出後的引用及必要診斷。

例如，內部記錄可以是：

```json
{
  "evidence_id": "ev_0042",
  "source_id": "pdf_01",
  "operation_id": "op_0081",
  "scope": {"physical_pages": [18, 19]},
  "content_ref": "objects/...",
  "content_hash": "...",
  "media_refs": ["img_0031"],
  "presentation": {
    "mode": "reference",
    "reason": "released_by_agent"
  }
}
```

`presentation` 不會改寫原始證據。重新讀取時，可以取得原本內容，圖片也必須經 adapter 變成實際模型圖片輸入。

**恢復證據不必恢復整段舊對話。** 可以把原本的證據，帶著正確來源與時間資訊，作為目前的新讀取結果交給模型。這會讓跨 context 的取回更簡單。

所有外部文件、OCR 及搜尋結果仍維持「來源資料」身分，不能因為被寫進摘要便升格為指令。

**3. 工作狀態要有少量結構，但保留自由筆記**

我會採用「小型結構＋自由文字」，例如：

```json
{
  "revision": 12,
  "based_on_event": "evt_0310",
  "current_work": "Reconstruct the table spanning pages 18–19",
  "open_items": [
    {
      "id": "item_07",
      "description": "Verify the unit in the final column",
      "evidence_refs": ["ev_0042"]
    }
  ],
  "artifact_refs": ["document_v8"],
  "retain_refs": ["ev_0042"],
  "notes": "Page 19 continues the header on page 18."
}
```

這個 schema 的目的，是讓 app 能驗證引用、版本及更新衝突；具體內容仍由 agent 決定。

需要分清楚：

- `document_v8` 存在、已成功保存：app 可以確認。
- 表格已核對、內容完整：agent 的判斷，應附相關證據，不能由檔案存在推導。
- 使用者要求：由原始使用者訊息支持，不能讓 agent 自己改寫成新的要求。

工作狀態宜增量更新，避免每次把整份記憶重新摘要。使用者後續修訂也要獨立保留；只有明確被取代的要求才標記為 superseded，不靠摘要模型默默刪除。

**4. Context Compiler 負責組裝真正的模型請求**

Context Manager 裏面需要一個確定性元件，暫稱 `ContextCompiler`。它不判斷文件意思，只按已確認的選擇組裝：

```text
穩定系統指令與工具定義
＋有效使用者要求
＋目前工作狀態
＋需要保留的近期完整互動
＋目前需要的證據
＋必要的取回指引
```

這是邏輯組成，實際角色及訊息順序由 provider adapter 處理，不能全部塞成一個 system prompt。

它必須保證：

- 工具呼叫與結果配對有效。
- 不切開尚未完成的工具互動。
- 圖片、診斷、來源身分保留正確。
- Provider 專有的 reasoning 資料只按其協定處理。
- 切換模型時，不盲目重播另一 provider 的 opaque reasoning。
- 每次送出的內容有 manifest，可查明模型實際看到了甚麼。

這樣，context 決策與 Chat Completions／Responses 的 wire format 就不會互相纏住。

**5. 容量管理採用預算與兩個處理階段**

每條模型路由需要自己的能力設定：

```text
有效 context 上限
最大輸出
token 計數方式及可信程度
圖片成本估算
工具／訊息格式能力
```

不能只從 `model` 字串推斷，因為 Nexus alias 不一定等於實際上游部署。

送出前至少檢查：

```text
估計輸入
＋本次輸出預留
＋估算誤差餘量
≤ 有效 context 上限
```

另外保留足夠空間，讓 agent 能在接近上限前整理：

| 狀態 | 處理 |
|---|---|
| 正常 | Agent 自主工作，也可以主動整理 |
| 接近預算 | 告知剩餘空間與主要佔用來源，讓 agent 選擇釋放或壓縮 |
| 下一次請求無法容納 | 暫緩送出該請求，先完成可容納的整理操作 |

不先指定所有模型一律 80% 或 85%。觸發位置應考慮預留輸出、圖片及下一輪可能增加的資料；整理後也要留有空間，避免每輪都觸發一次。

若 provider 有可靠 token count 可用就使用；否則採估算，並以後續回報校正。估算不能宣稱是容量保證。

Deep Agents 同時提供容量觸發及 agent 主動壓縮，支持這個責任分工；我們不需要照搬它的固定參數。[官方說明](https://www.langchain.com/blog/autonomous-context-compression)

**6. 單次超大工具結果，要在送進模型之前處理**

這是設計中最需要明確處理的邊界。

工具完成後：

1. 先完整保存結果。
2. 計算加入後的請求大小。
3. 放得下就依原要求提供。
4. 若放不下，先嘗試整理舊 context。
5. 若結果本身已超過模型可用容量，回傳明確的容量狀態、完整結果位置、大小及可選取範圍，讓 agent 決定讀取方式。

**不能偷偷只取前十行，卻把它當作完整結果。** 工具執行成功與結果能否完整呈現，也要分開記錄，避免 agent 再跑一次已完成的 OCR。

完整資料始終可取；但若它本身超過單次模型容量，只能分次讀取或由 agent 使用腳本處理。這個物理限制不能透過「full access」消除。

**7. Compaction 應是一個可驗證的 context 切換**

我建議先由正在工作的同一個 agent 產生接續狀態，不額外建立一個便宜的摘要 agent。這樣較符合它掌握目前依賴的情況，也避免先引入另一套模型與預算。

流程：

```text
準備接續狀態及保存引用
→ 建立候選 ContextManifest
→ 驗證引用、版本、訊息結構與容量
→ 保存候選版本
→ 原子切換 active manifest
```

如果引用不存在、輸出不完整或仍超出容量，保留舊 manifest，不把壞的 context 設為生效。

整理期間若使用者有新指示，必須保留並納入下一次請求；不能讓舊狀態覆蓋它。可用 `based_on_event`／revision 判斷候選狀態是否過時。

原始記錄仍然存在。但 app 只能驗證結構與引用，**無法機械地證明摘要沒有遺漏重要語意**。有效要求獨立保護、工作狀態及精確取回，都是為了降低這個風險。

Deep Agents 的原始歷史保存與摘要後取回，是可以參考的實作模式。[官方設計](https://www.langchain.com/blog/context-management-for-deepagents)

**8. 對 agent 暴露少量明確操作**

我會先設計以下能力，名稱可以再調整：

| 操作 | 用途 |
|---|---|
| `context_status` | 查看容量估算、主要佔用及目前保留內容 |
| `context_select` | 保留、釋放或重新載入指定證據 |
| `update_working_state` | 更新進度、依賴、決策與引用 |
| `compact_context` | 提交接續狀態，要求建立新的 context |
| 現有 evidence 讀取／搜尋工具 | 精確找回原始結果、範圍與圖片 |

不要求 agent 每輪先查 status，也不要求每次工具操作後填寫工作筆記。App 在有必要時提供容量資訊；agent 在有意義的工作變化時更新狀態。

**我的技術選擇是：保留一個 Python controller，新增清楚分工的 Context Manager，借鑑 Deep Agents，暫不為此遷移到 LangGraph。** LangGraph 的 persistence 能保存工作流狀態，但 context 的選取、保護與呈現規則仍需要我們設計。[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

不考慮向後相容，最大的好處是可以直接使用統一資料模型與工具契約；既有 raw evidence、圖片和保存成果仍值得保留。接下來最應優先敲定的，是 **`TaskContract` 如何處理使用者修訂，以及 `WorkingState` 如何更新**，因為這兩者決定整理後能否準確接續。
