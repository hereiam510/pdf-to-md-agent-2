**我會採納這版的四個方向：精確局部修補、來源與成品對照、可理解的容量提示，以及多介面共用文件核心。** 但「文件狀態可以共用」與「所有續工方式可以合併成同一機制」仍需分開；局部修補與視覺對照也不能被描述為零風險或必然解決品質問題。

最重要的設計修正如下。

**1. 精確修補應原生支援，但不必把完整表格限制成不可細分的儲存單位。**

提案對產品要求有一個誤讀：

> 保持完整邏輯區塊，不因頁碼標記切斷句子或表格  
> → 整張表必須只有一個 `block_id`

原文位於「Page markers」，是在保護閱讀與來源對應的完整性，並沒有規定資料庫只能用一個不可細分的物件保存表格。[產品要求](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/PRODUCT_REQUIREMENTS.md:32)

我們可以讓表格在輸出中保持完整，同時提供字串、儲存格或子區域的編輯定位；也可以繼續用一段 Markdown／HTML 保存它，再提供精確修補。**不需要先建立完整的結構化表格編輯器，才能避免重寫整張表。**

我支持 `patch_block`，但其保證應是「未指定修改的內容保持不變」，而非「零重寫風險」。`expected_matches: 1` 只能證明找到一次，不能證明找到的是語義上正確的位置。

合理契約包括：

- 綁定文件／候選稿版本，以及目標區塊內容版本。
- 精確比對原文；不默默模糊匹配、繁簡轉換或正規化字形。
- 明確定義多個 patch 的順序與重疊處理。
- 在工作副本完成整組修改與驗證後一次提交；失敗時保留候選內容和原因。
- 修補候選稿產生可追溯的新版本，保留原候選稿。

可以借用 JSON Patch 的前置 `test` 與明確操作序列設計，但字串內替換仍是我們需要自行定義的契約。[RFC 6902](https://www.rfc-editor.org/rfc/rfc6902.html)

另外，修改字形必須根據來源。提案中的 `厲行節約 → 礪行節約` 不能直接成為糾字規則；我們的目標是忠於原稿，不是自動改成模型認為較正確的詞語。

**2. 來源／成品對照值得做，但來源定位本身也需要誠實表達。**

同時看來源與輸出，確實能降低來回查找的負擔。不過，現有紀錄並沒有證明「跨回合視覺記憶」就是那些強調格式錯誤的原因，更不能保證同框後任何錯誤都能一眼看出。

實作上還有一個前提：**穩定的 `block_id` 和頁碼，不等於精確的來源區域。** 現有 Block 只有 `id`、`pages`、`markdown`，沒有 bbox。[目前內容模型](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/models.py:18)

建議採用可逐步增加精度的來源引用：

- 有精確區域：提供對應裁切。
- 只有頁碼：提供來源頁或由 Agent 選區，標示定位較粗。
- 一個區塊來自多頁／多區域：保留多個來源，不硬湊成一對一。
- 輸出截圖綁定確切文件版本；修改後，舊版本的核對紀錄不能直接代表新版已核對。

不需要強迫 Agent 為每個字或儲存格建立 bbox。來源定位應協助工作，不能變成額外的轉換作業。

同樣地，桌面的「同步捲動」應理解為跳到相關來源，而不是要求 PDF 與重新排版的 Markdown 在畫面座標上逐行對齊。

**3. 容量水位計合理，但應量度「本次實際輸入」，不能用原始檔案大小代替。**

我支持讓 Agent 看得見容量狀態。不過提案又把假說寫成了確定原因：

> 不主動釋放，是因為模型不知道容量。

目前證據不足以支持這個因果關係。還有一個明確錯誤：**P 任務的 selective／checkpoint 是關閉的，不能把它的未呼叫算作自然採用失敗。** [P 所屬試驗設定](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/workspaces/bounded-validation/plan.md:27)

水位計應分開呈現三件事：

| 資訊 | 應表示甚麼 |
|---|---|
| 證據大小 | 原始資料或選定片段有多少文字、像素、bytes |
| 活躍輸入貢獻 | 本次選取後，實際準備送入模型的內容及重複出現情況 |
| 容量餘裕 | 依實際路由設定、估算方法及輸出預留計算的剩餘空間 |

例如原始 OCR 有 186 萬字元，但這次只選了其中的 `text` 欄位，就不應把整個原件列為活躍負擔。反過來，同一圖片出現數次，也不能只算一次磁碟檔案大小。

我會把容量報告放在**模型輸入組裝邊界**計算，綁定 `input_view_id`；工具回覆可以提供自身資料大小，但不必每次把完整排行榜永久寫進對話歷史。

另外應保留這些界線：

- Token 數可能只是估算；未知的路由上限不能填成看似精確的 200,000。
- 請求 bytes 與模型 tokens 分開計算。
- 納入工具描述、普通對話、系統要求及輸出預留。
- `drafted` 只表示已有草稿，不代表證據可釋放。
- 60%／70% 可以是可調提示設定，不能聲稱是通用的品質分界。

**水位計的功能是提供決策資訊，不是替 Agent 判斷哪些內容已經不重要。**

**4. Document Continuity Snapshot 有用，但應作為交接資料，而不是取代所有恢復機制。**

這是整版最需要釐清的架構問題。

我同意把文件、候選稿、證據與可重用工作保存於框架之外。但這三種情境仍有不同責任：

| 情境 | 除了文件／工作快照，還需要甚麼 |
|---|---|
| 同一 Agent 整理 context、切換工作範圍 | 有效要求、目前進度、未解問題及新的輸入選取 |
| 派發章節子任務 | 明確任務範圍、繼承資訊、產出與修改權限 |
| 程序中斷後恢復同一執行 | Checkpoint、尚待執行的步驟、操作收據、原有預算及外部修改對帳 |

LangGraph 本身也區分 thread 的 checkpoint 與跨 thread 的持久資料。[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

因此可以共用**資料與交接格式**，但不應把三種生命週期硬合併。否則重啟時只看文件快照，可能遺漏尚待處理的工具結果；反過來，新任務也不應自動承接舊任務的待執行操作。

還有一個容易忽略的範圍問題：**不是所有工作狀態都屬於文件全域。**

例如今天只轉換第 1–10 頁，其他頁屬於這個任務的 `outside_scope`；明天要求整本書，這些頁不能永久維持「範圍外」。任務要求、範圍、工作筆記與未決問題需要保留任務／版本歸屬，不能全部塞進一份無差別的「文件目前狀態」。

我會採用這樣的責任分工：

- **文件與證據服務**：來源、版本、資產、候選稿、精確修改。
- **任務狀態**：有效要求、範圍、進度、未決問題與相關版本。
- **執行狀態**：對話、待執行工作、context 政策、操作與請求帳本。
- **Continuity Snapshot**：從上述資料選出這次續工所需的可核對視圖。

它們可以共用 SQLite，並不需要因此新增多個服務程序。

**5. 多介面可以共用文件能力，但 MCP 不能保證控制外部宿主的 context。**

這是提案尚未處理的邊界。

內建 Agent 的完整請求由我們組裝，所以 App 可以計算容量、投影證據及壓縮歷史。外部 MCP 宿主則自行管理模型、其他工具、對話與輸入；我們的 server 通常只知道自己產生了甚麼結果。[MCP 架構](https://modelcontextprotocol.io/docs/learn/architecture)

因此：

- Electron、內建 Agent、MCP、CLI 可以共用文件與證據操作。
- 外部 MCP 可以取得精確片段、資料大小、版本與候選稿。
- **不能僅因外部呼叫了「釋放證據」，就宣稱宿主舊對話中的內容已被移除。**
- 外部宿主沒有提供容量資訊時，應標示未知，而不是套用內建 Agent 的水位。

這會影響模組位置：`context_footprint` 的全局計算應屬於內建執行層，不能成為 `DocumentService` 在所有介面都保證提供的欄位。

**6. 政策結算仍有一個倒退問題，請求預算也要釐清。**

新提案說：

> 找到舊批次的結算收據後，確保 `active_policy_rev == produced_policy_rev`。

若這批曾產生 policy 8，但分支後來已合法推進到 policy 9，再看到舊批次時強制設回 8，就會撤銷後續決定。

應分成：

- 這批已套用，而且後續狀態仍包含其結果：維持目前政策。
- 正在恢復尚未完成的同一轉移，仍符合原始父狀態：重用既有結算結果完成轉移。
- 狀態來自其他分支或不相容修改：回報衝突，不強制覆寫。

操作重播的身分也不能只靠 `(thread_id, checkpoint_ns, tool_call_id)` 加參數雜湊。不同父模型回覆可能產生同名、同參數的合法新操作；需要保留已接受的父回覆／執行分支身分，或等價的 App 操作 ID。

預算方面，提案把所有請求都限制在 `1 + automatic_retries`，但又希望容量超限後能自動重組。當 `automatic_retries = 0`，第一次已發送的請求遭拒後，按這個定義就沒有第二次額度。

這可以是政策選擇，但必須說清楚。**共用一本請求帳本，不代表容量修正與傳輸重試一定只能共用同一個設定。** 發送前的本地重組不算 HTTP 嘗試；任何實際發送都必須記錄，並受共同總上限約束。

**至於重構順序，我同意產品價值上的優先級，但不建議把 P0→P1→P2 當成隔層完成的施工順序。**

若等所有文件功能與 context 機制都完成後，才接上 Nexus／LangChain，會太晚發現訊息、圖片與工具結果的整合問題。較合適的是逐步完成可用流程：

1. 先讓最小的框架與 Nexus 接入，使用共享工具完成一個完整範圍並保存、重新開啟、匯出。
2. 在同一流程加入候選稿重用、精確修改與來源／成品對照。
3. 再加入容量資訊、證據釋放與普通歷史整理，讓必要工作跨 context 繼續。
4. UI、MCP 與可選子任務沿用已清楚定義的文件契約。

這不是降低成品要求，也不是要求現在重跑實驗。它是讓每一階段都能回答一個具體產品問題，避免把所有建議累積成「核心交付前必須全部完成」的清單。
