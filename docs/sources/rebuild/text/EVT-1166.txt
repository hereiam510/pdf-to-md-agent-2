前幾輪我把實作細節、假設風險和首版必要條件混在一起，讓設計持續擴張。現在收斂：**架構責任已足夠清楚，只保留三項需要正式定案的契約，不再增加機制。**

**目前已定案的架構**

「定案」指設計責任與產品要求，不代表已實作。小型 LangGraph StateGraph＋SQLite 是目前優先重構方案；現有程式仍是 Python 控制器與檔案式版本保存。

| 部分 | 已收斂的責任 |
|---|---|
| Agent 控制層 | 單一 Python 執行控制層。Agent 自主選擇讀取、OCR、圖片檢查及修改方法；不固定轉換步驟。 |
| Nexus 請求服務 | 正常推理與整理共用請求服務、持久預算及取消檢查；保留原生協議與凍結請求，不依賴 provider 原生 compaction、背景查回或遠端取消。 |
| 文件／證據核心 | 保存完整來源、證據、候選內容與不可變版本；提供精確讀取、局部修改、預覽及指定版本匯出。 |
| Context 管理 | 證據取用與歷史整理分開處理。Agent 判斷相關性，app 處理容量；保護有效要求、未完成工作及有用成果。 |
| 保存與恢復 | 驗證前保留收到的原參數；執行重播使用原始呼叫與歷史收據，不重新生成已保存內容或倒退目前版本。 |
| 交付 | Markdown、JSON、HTML、圖片與 ZIP 對應同一指定版本。執行停止、內容完成聲明、匯出一致性分開記錄；已有成果可不經模型匯出。 |

框架名稱、模組數、資料表數不再列為獨立研究問題。接下來只需要把以下三項契約定清楚。

**1. 文件更新與候選引用契約**

**實際觀察：** 曾因完整頁碼映射不合規而拒絕保存；原候選中的正確「本文件」在後續重寫變成「本文作」。目前也缺少直接的純插入／附加與局部頁碼更新介面。這支持改善精確重用，但不能直接歸因於 compaction。[錯字與候選紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:471)、[目前能力](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/CURRENT_STATE.md:25)

**尚未證實：** 自動搶救殘缺 JSON 能帶來多少完整交付收益；它不是這項契約的必要前提。

**我的建議取捨：**

- 首版先支援完整候選的精確引用、插入／附加及局部頁碼更新。
- 局部更新合併後驗證完整文件，不要求模型重傳未修改正文與整份頁碼表。
- 不可變版本檔案作為正文權威；SQLite 管理版本登記、指標與操作收據，避免另一份可獨立修改的正文。
- 殘缺呼叫保留原件；自動區塊搶救退出首版必要清單。

**設計定案條件：** 能明確回答「引用哪份原件、更新哪些欄位、未指定部分如何保留、何時算提交成功」。並能清楚表達三個案例：只修頁碼、插入新內容、引用被拒候選而不重寫正文。

**2. Context 容量與交接契約**

**實際觀察：** 大型 inspect／OCR 結果會佔用大量輸入；既有 checkpoint 曾降低輸入並成功取回先前證據。但這尚未證明普遍成本優勢或無損延續。[既有延續紀錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:270)

**假設情境：** 撤回證據後仍因草稿歷史超量、差集摘要因錨點更新而遺漏資訊。這些是需要定義行為的邊界，不能寫成已觀察到的專案故障。

**我的建議取捨：**

- 每個已選模型路由有可設定的容量與輸出預留；檢查完整組裝輸入，包括圖片、工具定義與工作狀態。
- 先釋放已保存且目前不需要的內容，再整理較舊歷史；最新版本與未完成候選也可部分退出輸入，完整原件仍可取回。
- 首版使用可獨立支撐續作的交接摘要，保留有效要求、未完成工作及精確引用；不採差集摘要。
- 整理可以逐步縮減；只有正常模型請求才必須符合最終容量。失敗保留原紀錄，額度用盡便明確停止。
- 不固定近期 `K` 輪、不要求舊稿先被新版取代，也不先承諾兩三次整理必定足夠。

**設計定案條件：** 對「可以送出、需要釋放、需要整理、仍無法容納」都有明確行為；未處理歷史不會被誤刪，摘要失敗不破壞原件。具體水位可以配置，不需要先研究出通用最佳百分比。

**3. 持久化、恢復與停止契約**

**實際觀察：** 已有保存後繼續轉換，以及 R1／R2 注入故障後完成交付的證據；這不等於任意程序崩潰、自然長時間斷線都已驗證。[驗證範圍](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/CURRENT_STATE.md:59)

**假設情境：** 工具提交成功但 Graph checkpoint 尚未寫入、舊收據重播時 head 已前進。它們需要有限的恢復規則，不需要擴展成通用分散式系統。

**我的建議取捨：**

- 同一任務維持單一活動寫入者。
- 模型請求、工具批次進度、文件版本與操作收據各有唯一權威紀錄。
- 恢復同一模型請求使用凍結輸入；完成整批工具結果後，才組裝下一輪新輸入。
- 已完成操作回傳當時收據；不重置額度、不重複提交、不倒退指標。
- 無法對帳的本地效果停止並保留工作；明確的使用者問題進入等待狀態。
- 已保存版本可獨立匯出；部分成果保持草稿標示。自動提醒與所有退出都自動打包，不列為首版必需。

**設計定案條件：** 把「請求已保存、回覆已接受、工具已提交、Graph 已記錄」四個邊界的恢復行為寫清楚，並指定各資料的擁有者。無須承諾任意舊工作或所有硬崩潰都能無條件恢復。

**我建議就採用上述取捨完成設計定案。** 定案條件是契約一致、責任清楚；實作是否達成，再由適當的離線檢查與指定 PDF／完整章節的來源核對確認。兩者不應混成無止境的前置研究。

獨立桌面 App 的介面、後端整合與 Windows 封裝目前仍未實作；若交付指可安裝產品，它們是既定交付工作，不能省略，但不需要因此重開 context 架構討論。

之後只有實作或實際交付出現會違反上述契約的阻礙，才重新開啟相應設計；其餘假設與優化保留為參考，不形成首版待辦。
