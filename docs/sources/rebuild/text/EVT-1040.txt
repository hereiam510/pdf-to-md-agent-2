**這版的架構方向可以保留，但「全部已落實為無衝突的工程規範」仍然說得太早。** 幾個新增規則會造成實際問題：恢復時覆蓋較新的工作、忽略仍有用的候選稿，以及把 context 整理變成沒有完整預算和恢復保障的模型呼叫。

明確區分恢復／重新生成、保存不可變請求、驗證前保存候選、增量編輯和指定版本交付，這些都值得保留。以下是我會修改的地方。

**1. Context 超限後重新準備輸入是對的，但不能把失敗估算當成「實測上限」。**

假設本機估算輸入有 80,000 tokens，而 Nexus 拒絕請求，這只能證明「這份請求在當時的路由被拒絕」。它不證明模型的 context window 就是 80,000。

可能涉及估算誤差、輸出預留、影像計算方式，或不同類型的請求限制。因此應分開記錄：

- 上游明確回報的錯誤類型、計數和限制。
- 本機估算值及使用的估算方式。
- 當時的模型、API 格式和路由配置。

可以據此調低該配置的暫時安全預算，但不要把本機估算值升格為模型規格，也不要影響其他路由。

「不走網路重試」我同意；**但每次已發送請求，仍須記入實際請求次數、耗時及已知 usage。** 換一個 `model_step_id` 不能重置總預算或降載次數。現有控制器已在發送前保存 attempt，這項保障應繼續保留。[agent.py:384](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/agent.py:384)

提案的「最多 1～2 次」可以是可配置的恢復上限，但應掛在同一次恢復事件及原任務上。

**2. 「觸發緊急歷史壓縮」還需要一條真正可執行的路徑。**

目前提案把這件事藏在 `prepare_step` 裡，容易混淆兩種工作：

- 根據既有 policy 換掉大型證據的輸入表示，是程式可以確定執行的操作。
- 判斷舊歷史哪些內容重要、產生繼續工作的摘要，是模型工作。

後者需要自己的請求身分、預算、完整回覆保存和恢復處理。LangGraph 官方的歷史摘要範例也會實際呼叫模型，不是免費的 state 整理功能。[官方摘要範例](https://docs.langchain.com/oss/python/langgraph/add-memory#summarize-messages)

我會讓 `prepare_step` 負責判斷容量及安排下一步；需要語義整理時，進入可恢復的 context 維護流程，仍使用同一套 Nexus 請求服務。它可以是一個額外節點，也可以是 `model_step` 的另一種請求用途，不必為守住「四節點」而隱藏模型呼叫。

還要處理一個現實問題：**已經超限的完整歷史，不能原封不動再送一次請模型壓縮。**

正常情況應提前整理；緊急情況則先撤回本次超大的證據展開，保留操作結果、精確引用和可容納的工作狀態，再讓 agent 決定如何繼續。有效使用者要求、未解依賴和活躍候選不能因緊急整理而悄悄消失。

**3. Prepared version 可以重用，但不能只憑操作身分吻合就「直接補提交」。**

考慮這個例子：

1. 操作 A 以 V10 為基底，準備了 V11，尚未提交便中斷。
2. 另一個合法操作已把工作版本推進到 V12。
3. A 恢復後找到自己的 V11，直接更新 manifest。

如果這時把工作指標改回 V11，就覆蓋了較新的工作選擇。`operation_id` 和輸入指紋只能證明 V11 屬於 A，不能證明 A 現在仍可更新工作版本。

恢復時應依序判斷：

- 該操作已提交：回傳原有結果。
- 尚未提交，準備檔完整，而且預期基底／目標分支仍吻合：完成提交。
- 工作狀態已改變：保留準備成果，回傳衝突及可重用引用，讓 agent 決定如何整合。

現有程式已經檢查過時的 `base_version`，重構不能把這項保護拿掉。[core.py:254](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/core.py:254)

至於 `document_manifest.json`，它可以作為提交權威，但單次檔案替換本身不會防止兩個寫入者用舊 manifest 互相覆蓋。提交時仍須重新讀取、檢查條件並序列化更新。

**以現在的 metadata 複雜度，我更傾向用 SQLite 管版本登記、操作唯一性和工作指標，大型內容繼續放不可變檔案。** 這是使用現成交易機制，無須自製完整事件溯源系統。[SQLite 原子提交](https://www.sqlite.org/atomiccommit.html)、[交易隔離](https://www.sqlite.org/isolation.html)

同時要收回「一次 `ReplaceFileW` 就保障斷電恢復」的暗示。它不能替整個版本資料夾的資產提供持久化保證，官方也明確列出其 write-through 旗標不受支援。[Microsoft 文件](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)

SQLite metadata 與 LangGraph checkpoint 也仍是不同的提交邊界，兩者繼續靠操作身分對帳。

**4. `edit_document` 值得採用，但「兩個工具」不等於最低認知負擔。**

一個支援多種明確操作的編輯入口，可以減少整篇重傳；這是實際收益。工具數目少，則不一定代表 schema 更短或模型更容易使用。

真正需要定清楚的是以下契約：

| 項目 | 建議規則 |
|---|---|
| 多個 `block_ops` | 依序作用於同一份工作副本；全部通過才提交一個版本 |
| 後續操作的定位 | 明確規定引用前一步結果；避免有時引用原版本、有時引用修改後版本 |
| 候選重用 | 省略欄位表示沿用；覆寫規則明確，尤其是陣列及巢狀欄位 |
| 修正候選 | 產生新的有效參數快照，保留原候選及衍生關係 |
| 更換基底 | 必須重新檢查適用性，不能把舊操作自動套到當前版本 |

例如候選中有第 12、13 頁的更新，這次只修正第 12 頁，究竟是替換整個 `page_map_updates`，還是按頁碼合併？如果不定義，保存正文的好處可能被 metadata 靜默遺失抵銷。

另一條重要規則是：**修正候選是一個新操作，不能沿用原 operation ID 卻更換輸入。** 現有程式會拒絕待恢復操作的參數被修改，這點應保留。[agent_tools.py:389](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/agent_tools.py:389)

頁碼狀態也要分開：印刷頁碼未確認、範圍未確認、尚未處理，是不同資訊。未填寫不應自動變成 `outside_scope`；稀疏更新最後仍須形成完整、誠實的來源對應。

**5. 用「最後一次成功提交之後」判斷活躍候選，會漏掉有用成果。**

這條規則應直接撤回。

例如：

1. 候選 A 包含第一節的正確正文，但頁碼 metadata 有錯，尚未提交。
2. agent 隨後成功保存第二節 B。
3. A 的時間早於 B，因此被排除於未決候選檢查之外。

A 並沒有被修好或放棄，只是另一件事先完成。

候選是否仍活躍，應依據實際的採用、修復、取代或放棄關係，而不是時間先後。可以維持一份很小的活躍引用集合；**無關的成功保存不能清除候選。**

這比再增加複雜候選管理系統更重要。

**6. OCR、render 不是「純讀取」；並行資格與重播安全應分開。**

現有 OCR 會建立批次資料夾、保存請求並啟動程序；render 也會寫入圖片。來源 PDF 不變，不代表整個操作沒有副作用。[ocr.py:71](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/ocr.py:71)、[core.py:161](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/core.py:161)

它們仍然可以並行，但需要獨立輸出位置、資源限制，以及開始／完成紀錄。是否能並行、是否能安全重跑，是不同判斷。

反過來，引用固定版本的 `reopen` 也不需要因工具名稱而永遠被禁止並行。第一版預設依序執行很合理，之後按實際依賴和副作用開放並行即可。

另外，「不傳 version 就使用 working version」仍然是動態引用。應在**該工具按順序開始執行時**解析一次，保存實際綁定的版本；恢復時重用該版本，不再解析一次工作指標。

工具結果的持久索引也不能只靠 provider 的 `tool_call_id`，需要包含所屬任務、已接受回覆或步驟的身分。

**7. 交付選擇應屬於本次任務，工具也要能直接選擇舊版本。**

`selected_delivery` 放進文件的唯一全域 manifest，在只有一個任務時可以工作；但一旦允許分支或同文件的不同任務，交付選擇可能互相覆蓋。

我會把：

- 已提交版本及其來源關係，交給文件核心。
- 本次任務選擇交付哪個版本、哪個範圍，交給該任務的持久交付意圖。

目前 `delivery_selection.select_this_version` 只能選擇本次新版本，還不足以表達「直接交付已存在的 V10」。可以保留它作為一次完成編輯與選擇的便利功能，同時提供明確的既有版本選擇能力，無須為選 V10 再建立一個版本。

終止狀態也應更精確：

| 情況 | 行為 |
|---|---|
| 已選定版本，只缺打包 | app 自動打包及核對 |
| 真正缺少使用者資訊 | 保存成果，等待具體回答 |
| 技術失敗、預算耗盡或取消 | 保存成果並記錄停止原因 |
| 仍有可處理工作且預算允許 | agent 繼續處理 |

「不可自動恢復」不一定表示「使用者需要回答問題」。全部標成 `waiting_for_user_input`，會讓使用者不知道自己究竟要提供甚麼。

我會以 **小型 LangGraph、共用 Nexus 請求服務、SQLite metadata＋不可變內容檔、原子增量編輯、明確候選關係，以及任務專屬交付意圖** 作為重構基準。恢復／重新生成的明確入口可以沿用；`branch_seq` 如有需要可供顯示，不必再成為第二套正確性依據。

最值得優先做好的使用流程是：正文即使因 metadata 錯誤被拒也能保留，修正時只改必要部分，context 整理後仍知道哪些工作未完成，最後交付 agent 明確選定的成果。這些才會直接改善 app 的轉換能力與使用體驗。
