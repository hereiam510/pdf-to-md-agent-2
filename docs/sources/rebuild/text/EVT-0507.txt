**這份建議有可採納的進展，尤其是「以檔案引用匯入草稿」。但我不會直接把它當成實作規格：它仍把幾個合理的設計方向，寫成尚未成立的自動判斷和可靠性保證。**

如果目標是讓 app 發揮最好功能、保留 agent 自主性，而且減少我們要維護的程式，我會作以下修正。

**1. 採納檔案引用匯入，但把它設計成一般內容來源能力。**

這是本文最有價值的新增建議。Agent 已經用腳本準備好大型表格，就應能直接引用成果，避免在下一次工具呼叫重新輸出整張表。

`update_draft` 可以接受幾種平等的來源：

| 內容來源 | 適用情況 |
|---|---|
| 直接傳入內容 | 小段文字、少量修改 |
| 已保存的 artifact 引用 | 重用先前準備好的區塊或表格 |
| 工作區檔案引用 | 匯入腳本或通用檔案工具產生的成果 |

但它是「避免模型重複生成」，不宜稱為技術上的 **zero-copy**。讀取、解析及保存仍可能涉及資料複製；節省多少實際費用，也不能直接套用文中的 API 單價推算你的 Nexus 訂閱成本。

實作順序亦應調整：

> 取得固定內容快照 → 計算 hash、解析及驗證 → 在短交易內檢查草稿 revision → 提交新 revision 和操作收據。

不要把大型檔案讀取、解析全部塞進持鎖交易。驗證與提交必須使用同一份內容，避免檔案在兩者之間被腳本修改。

另外，**匯入 Markdown 不應自動宣稱已知道它對應哪些來源頁、哪些表格關係已完成**。內容、來源對應和未解問題可以一起提交，但草稿必須容許其中部分仍待確認。

**2. Survey View 值得提供；文中的 Focus Decay 仍然過度接管 agent。**

輕量探勘可以幫助 agent 選擇下一步，但以下推論不成立：

> Agent 讀了第 10–15 頁，現在寫入第 10–11 頁，因此只需要保留第 10–12 頁。

第 15 頁可能有整張表適用的註腳，第 13 頁可能解釋前面的縮寫。**寫入範圍是操作事實，不能直接代表思考所需的證據範圍。** 沒有登記依賴，也不能證明沒有依賴。

我會保留我們已同意的分工：

- App 觀察容量、資料大小及使用情況，提出可釋放的候選。
- Agent 決定哪些證據仍與目前工作相關，保存必要筆記和引用。
- App 套用選擇，實際重組輸入，保留原件及精確取回能力。

這不需要使用者逐項批准，也不需要每次寫入草稿就額外做一次整理。

Survey 本身則應清楚區分「已觀測資料」與「候選判斷」。大字級可能是標題，也可能是圖內標籤；掃描頁可能沒有可用文字層。每頁 100–200 字元、30 頁少於 5,000 tokens，只能是待評估的設計目標，不能保證足以建立完整文件地圖。重新讀取已保存證據可以免去重新抽取，但仍有讀取和模型輸入成本。

**3. 「零推測物理視圖」需要改成「清楚標示資料來源與推論」。**

附件有一個明確技術錯誤：在 PyMuPDF 的 span flags 中，`12 = 4 + 8`，對應 **serifed 和 monospaced**，不是 `serif, symbolic`。這也不能直接當作 PDF FontDescriptor flags 解讀。官方文件更指出，字型屬性可能不正確或不完整。[PyMuPDF Span Dictionary](https://pymupdf.readthedocs.io/en/latest/textpage.html#span-dictionary)

因此，對目前案例較準確的提示是：

> 抽取結果的所有 spans 都回報相同字型、flags 和透明度；這些欄位不足以區分原頁可見的強調格式。

不能再擴張成「文字層完全沒有任何可用的上下標資訊」：座標、大小和基線仍可能提供線索。原專案的[證據記錄](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:59)也只支持較窄的結論。

我亦不贊成禁止工具提供所有推測。工具可以提供候選標題、候選表格或可能的閱讀順序，只要標明這是衍生判斷，並能追溯原始資料。這類輔助可能很有用；真正應避免的是把它包裝成確定事實。

**4. 恢復能力應以「文件操作可以安全重試」為核心。**

文件提交後有收據，這個方向正確。但 `tool_call_id` 和 app 的操作身分不能不加區分地互換，也不能只查最後一筆 tool call：一則模型回覆可能包含多個工具呼叫。

我建議文件服務採用以下契約：

- 每個邏輯寫入操作有穩定、具作用範圍的 `operation_id`，執行前保存；可以與模型的 `tool_call_id` 建立對應。
- 操作內容、預期 revision 與收據綁定。
- 新 revision 和成功收據在同一交易內提交。
- 相同操作再次送達，回傳原收據；同一操作身分卻帶不同內容，明確拒絕。

這樣即使框架恢復時再次執行工具，文件服務也能避免再次插入內容。**不必把「框架絕不能重跑工具」當成唯一正確恢復方式。**

保證範圍也要說清楚：這能處理受文件服務控制的同一操作重放；模型另行產生的新操作，或任意腳本的外部副作用，不會自動獲得同樣保證。

既然可以完整重構，我還會減少需要跨儲存協調的狀態：文件 revision、操作收據、artifact 引用可以共用一個 app metadata store，例如 SQLite；大型原件保存在不可變檔案中。資料庫交易可以共同提交相關記錄，但不會自動把外部檔案或框架 session 納入同一交易。[SQLite 原子提交說明](https://www.sqlite.org/atomiccommit.html)

**四種邏輯責任，不必實作成四套獨立的儲存協調系統。**

**5. 框架接口表需要修正，不能據此判斷改動量。**

我核對了附件指定的 Pi v1.3.0：

- 官方恢復例子使用 `SessionManager.open()`，再傳給 `createAgentSession()`。
- Session 的工具結果是 `type: "message"` 裡的 `role: "toolResult"`，不是附件描述的獨立 `tool_use`／`tool_result` entry。

因此，「在 `Session.load()` 前直接補寫 JSONL」不能當作已核實的公開接口方案。應使用框架支援的 session 操作，並確認分支、訊息配對及載入時機。[Pi Session 範例](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/examples/sdk/11-sessions.ts)、[Session 格式](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/session-format.md)

LangGraph 那一欄也過度簡化。`update_state()` 會建立新 checkpoint，更新會經過 reducer，`as_node` 還會影響後續執行。補入一則 ToolMessage，不等於已正確處理所有 pending work。[LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers#update-state)

我的設計偏好是：

> 框架管理自己的執行與 session；文件服務負責安全重試；薄薄的 adapter 把真實收據轉成框架接受的工具結果。

這比自行修改 JSONL，或把有副作用的恢復邏輯塞入 `get_tuple()`，更有機會降低長期維護成本。LangChain 也已有模型和工具呼叫的公開 middleware 邊界，可用來接入這類責任。[Custom middleware](https://docs.langchain.com/oss/python/langchain/middleware/custom)

**6. 「已送出變更」和「已完成核對」都不能過早標記。**

附件有兩個容易產生錯誤狀態的地方。

第一，`last_disclosed_revision` 在請求送出時前進，並不能證明模型已處理該變更。更簡單的設計是：**每次 context 組裝確保目前工作需要的狀態是最新的；diff 只作為幫助理解變更的補充。** Compaction 後重新載入最新表頭即可，不必依賴某個歷史 diff 曾經送過。

第二，`view_preview()` 回傳 PNG，只能建立「這個 revision 已產生此預覽」的記錄。它不能自動建立「排版已核對通過」的記錄。

同樣地，前面文字未變，可以沿用範圍明確的字元比對結果；但新增表格列若改變共同表頭、單位或註腳適用範圍，就不能直接沿用整段語義正確的結論。記錄應描述**實際檢查了甚麼**，不必先建一個龐大的通用品質判定引擎。

**7. 七步路徑適合作為一個測試情境，不能變成產品流程。**

它能測試重要能力，但固定依序呼叫工具的 Mock Model，即使完全不閱讀 compaction 後的輸入，也可能成功跑完。因此，它最多先證明工具串接和部分狀態轉移。

有意義的檢查應包括：

- 整理後實際送給模型的內容，是否包含最新草稿、有效要求和未解問題。
- 證據引用能否取回原資料與所需圖片。
- 同一已提交操作重放時，是否回傳原收據而沒有新增內容。
- 恢復後是否保留所有相關工具呼叫的正確配對。

另外，拋出例外可能仍會執行清理和 flush，不能直接當作程序被強制終止的證據。這些機制檢查，也不等於已證明真實 agent 能自主選擇方法並交付忠實成果。

**我會把重構方向收斂為以下分工：**

| 層 | 應承擔的責任 |
|---|---|
| Pi 或 `create_agent` runtime | Agent loop、工具調度、框架 session 與延續 |
| App 文件與證據服務 | 完整原件、精確讀取、內容引用、版本化草稿、預覽、發布及操作收據 |
| App context policy | 容量管理、agent 的保留／釋放選擇、工作狀態交接、實際輸入組裝 |
| Nexus adapter | 將選用模型的介面接到 runtime，保留所需工具與圖片能力 |

這輪尚沒有足夠證據把 Pi 或 `create_agent` 判定為勝方。比較重點應是：**哪個能透過公開接口完成上述分工，需要我們自行維護的控制邏輯最少。** Deep Agents 的現成機制仍可重用，但應服從同一套 context 決策，避免多個模組各自整理歷史。

我建議採納檔案引用匯入、版本化草稿及可安全重試的文件操作；將 Survey 保留為選用工具，移除按頁號自動淘汰、預覽自動算核對，以及直接修改框架歷史的預設做法。這些修正能讓 agent 保有方法選擇權，同時讓 app 更容易可靠地保存、接續和交付工作。

本輪核對了附件、專案記錄與官方文件；沒有執行 Nexus 呼叫或開始重構。
