**我會採納這版的大部分架構方向，但還不能把它視為已經收斂的重構規格。** 分層讀取、整理前交接、精確釘選、候選稿重用都值得做；需要修正的是幾個過強的保證，以及它們在容量不足、版本改變和品質核對時的行為。

完整重構的前提下，我會優先建立：**可靠的證據與成果儲存、可控制的工作 context，以及能讓 agent 自主選擇方法的工具介面。** 框架應服務這些能力。

**1. 分層讀取方向正確，但「行級資料一定很小而且資訊完整」不成立。**

這次核對到一個重要事實：現有 `inspect` 已經用 `get_text("dict")` 取得區塊、行和 span 結構。那次 191,662 字元的輸出中，`layout` 單獨就佔 **147,366 字元**，`words` 約 39,324 字元。因此，取消詞級資料並不會自然把結果縮成幾千字元。[目前實作](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/src/pdf_to_md_agent/core.py:104)、[既有量測](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/EVIDENCE.md:62)

「首次不知道要讀哪些欄位」確實是工具設計需要處理的問題，但首次沒用 `_select`，不能證明這就是當時的原因。

我建議把改進重點放在**資料表示的設計**：

- 提供容易理解的 `text`、`layout`、`words`、`chars`、圖片／區域讀取方式，避免先猜 JSON Pointer。
- 同一份回覆不必預設重複列出多種完整文字表示。
- 重複的字型、樣式資料可以抽成表，再由文字片段引用。
- 保留局部樣式差異的位置；只提供「全頁字型／透明度統計」會丟失差異發生在哪裡。
- 完整結果、細粒度資料和原始圖片仍可在第一次呼叫直接取得。

尤其不能把 block/line 解讀為「已經知道正確閱讀順序」。PyMuPDF 的文件也明確指出，抽取順序可能與自然閱讀順序不同；span 才承載具體文字及字型屬性。[閱讀順序說明](https://pymupdf.readthedocs.io/en/latest/recipes-text.html#how-to-extract-text-in-natural-reading-order)、[文字結構說明](https://pymupdf.readthedocs.io/en/latest/textpage.html#span-dictionary)

還有一個介面細節：**尚未計算的 `words/chars` 應提供「如何取得」的描述，不能假裝已有精確結果大小和現成 evidence。** 已保存資料的讀取，與需要新運算的抽取，應清楚區分。

**2. 支持整理前交接，但不能等到容量觸頂才開始。**

附件提出的 `Pre-Compaction Handshake` 很有價值，也符合我們已同意的分工：app 在容量壓力下要求整理，agent 判斷哪些工作狀態需要延續。

但交接本身需要一次模型請求及輸出空間。**如果 context 已經塞滿，「先請目前 agent 整理」可能根本無法執行。**

我會這樣設計：

1. 每次組裝請求時，計入訊息、工具定義、圖片與模型所需的輸出餘量。
2. 提前預留整理空間，在安全的工具回合邊界要求交接。
3. 大型工具結果先保存完整原件，再決定這次輸入能容納的表示；超出部分明示並提供精確讀取。
4. 交接失敗時保存所有工作，允許重新組裝或停止；不能無限重試同一個過大的 context。

`working_notes` 隨正常工具呼叫一起提交值得保留，但**也應保留獨立更新入口**。否則 agent 探勘多頁、尚未準備存稿時，仍然無處記錄重要發現。筆記更新亦不應因稿件的頁碼 metadata 驗證失敗而一起消失。

另外，先前 B/C 沒使用 context 工具、P 沒使用腳本，不能合併推論成「agent 必然不會記筆記」。那些紀錄沒有建立這種因果關係。[自然採用的證據界線](C:/Users/laichungling/Documents/ChatGPT/pdf-to-md-agent/docs/ACCEPTANCE.md:107)

整理前交接的價值是**增加明確保留重要狀態的機會**，不能保證補回所有未記錄的判斷。同一模型也可能漏掉資訊，因此精確引用、近期必要歷史和可選摘要仍有各自作用。

**3. 動態釘選值得採用，但必須處理版本、容量和解除條件。**

以原文表頭、術語或原始圖片延續工作，通常比讓摘要重寫它們可靠。這點我同意。

不過，只有 `pinned_block_ids` 還不夠。假設 `blk_089` 的表頭剛被修正，釘選時究竟應保留舊版本還是新版本？

一個有效的釘選記錄至少需要：

| 欄位 | 用途 |
|---|---|
| 精確引用 | 指向某個版本的區塊，或某份 evidence 的具體範圍 |
| 保留理由 | 例如跨頁表格仍需沿用此表頭 |
| 依賴狀態 | 尚未解決、需要重新核對、已完成 |
| 解除條件 | 例如該表格已完整重建並核對 |
| 輸入成本 | 組裝 context 時估計所需文字／圖片容量 |

需要同步處理三種情況：

- **內容更新或被刪除：** 明確更新引用或標記失效，避免悄悄沿用過時內容。
- **釘選總量超出容量：** 讓 agent 調整下一步工作範圍或分批載入；不能暗中縮減被承諾精確保留的內容。
- **依賴已解決：** 可以退出活躍工作集，原件仍保留。

「最後 N 個區塊」可以是方便的近期保留策略，但不應自動等同於必須長期釘選的依賴。

精確釘選能保證的是**引用到的內容沒有被摘要改寫**。它不能保證 agent 選對證據、正確理解，或後續輸出零失真。

**4. Context 事務需要保證持久化與一致性，也要承認語義檢查的限制。**

「先組裝、檢查、再切換」應保留。但附件中有些檢查，程式只能完成一部分：

| 可由程式可靠檢查 | 仍需要語義判斷 |
|---|---|
| 指定版本／證據存在，雜湊吻合 | 是否保留了所有重要發現 |
| 已登記的必要引用全部載入 | 是否漏登記了一項跨頁依賴 |
| 使用者修訂紀錄沒有遺失 | 各項要求如何合併、是否衝突 |
| 請求符合協定與容量條件 | 新 context 是否足以維持轉換品質 |

因此，「目前有效要求」也不能全部當作 app 自動知道的確定性事實。App 能準確保存使用者原話及修訂順序；對要求的整理和解讀應保留來源。

實作上，我建議每次 context 切換保存一份 manifest，記錄它依據的：

`requirements_revision + artifact_version + notes_revision + evidence_refs`

提交切換前再次檢查這些版本。若交接期間使用者改了要求，或成果已更新，就重新組裝受影響部分，避免把過時狀態設為新的工作起點。新 manifest 持久化後，才原子切換活躍指標。

還有一個容易忽略的膨脹來源：**全書頁碼表、所有 candidate、全部 evidence index，不應每次全部放入模型輸入。** 它們完整保存在 app；context 放目前相關項目、進度概況、未解問題和查詢入口。

**5. 候選稿重用應採用，但「三態成果管理」需要改成兩個獨立維度。**

`Candidate → Published` 是儲存／發布狀態；「是否經過來源核對」則是對某個版本、某個範圍的品質判斷。它們不宜變成單向、永久成立的三階段流程。

我會分開記錄：

- **成果狀態：** 候選稿、已發布的不可變版本。
- **核對紀錄：** 核對了哪個版本、哪些來源範圍、哪些內容，以及還有甚麼問題。

原因包括：

- `reopen` 成功只能證明可讀取；`view_preview` 成功只能證明取得了預覽。
- 看過局部表格，不代表整個章節都已核對。
- 修改表頭、頁碼對應或圖片後，相關核對結果可能需要重新評估。
- 使用者應能取得明確標為草稿的部分成果，不必等到某個全局 `SourceVerified` 狀態才能匯出。

這不要求增加固定審核程序；核對仍應依內容需要，由 agent 自主進行。

候選稿方面也要區分：

- 缺 metadata：可以補資料後重新提交。
- `base_version` 衝突：需要檢查並合併，不能只補頁碼就直接覆蓋較新內容。

所以它能**避免重複生成未變內文**，但「零 token 浪費」與「任何失敗都能直接 commit」都不成立。頁碼未知時也應允許明確的 `unknown`，不能為通過驗證而逼 agent 猜測。

**6. 共用預覽管線合理，但 DOM 截圖只是其中一種實作。**

我支持 UI 與 agent 使用同一份版本、渲染元件、CSS 和字型資源，也支持按區塊定位預覽。

CDP 確實提供區域 `clip` 及 `captureBeyondViewport`，所以附件提出的技術方向可行。[官方協定定義](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)

但仍須處理字型／圖片載入、縮放與座標、被裁切的容器，以及過大的區塊；必要時保留分區擷取能力。不能承諾所有內容都能一次完整截圖。

每次預覽應標明**版本、範圍和渲染條件**。預覽像素用來檢查輸出的閱讀效果；交付的來源圖片則仍由資產系統保留原始品質。

常駐 PDF worker 亦合理，但快取 handle 只能減少部分開啟與解析成本，不能據此承諾所有查詢和渲染都達到毫秒級。

**7. 框架試金石應測產品行為，不必要求框架共用某一把鎖。**

附件四項檢查的方向有用，但最後一項把特定實作方式當成了要求。

Pi、Deep Agents 或 LangGraph 不必直接持有 Document Transaction Lock。更清楚的責任劃分是：

| 責任 | 建議擁有者 |
|---|---|
| 規劃、選工具、判斷下一步 | Agent |
| 模型／工具回合與事件生命週期 | 選定的 runtime |
| 證據、候選稿、版本、發布收據 | App 的文件服務 |
| 工作集、容量預算、context 組裝規則 | App 的 context 模組 |
| Nexus 協定編碼與能力差異 | Provider adapter |

框架透過普通工具呼叫文件服務，由文件服務在短交易內完成驗證與發布。**不要把模型推理、OCR 或整個 agent 回合包進同一把文件鎖。**

目前官方介面顯示，Deep Agents 可以替換同名內建 middleware；Pi 也有 context 轉換和回合邊界擴充點。因此，還不能憑這份藍圖斷言哪個必須修改框架內部。[Deep Agents 擴充介面](https://docs.langchain.com/oss/python/deepagents/customization)、[Pi 擴充契約](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/extensions.md)

我會先用幾個具體情境對照公開介面：

- 未存稿的跨頁發現能否經整理後繼續使用？
- 修正表頭後，釘選引用會否過時？
- 候選稿 metadata 出錯能否重用內文？
- 整理期間收到新要求，能否避免切換到舊狀態？
- 超大結果能否完整保存、明示未載入範圍，並直接取回必要內容？

網絡重試及遠端取消仍留待下一輪討論。

**我建議採用這版的四個核心機制：分層證據、整理前交接、具版本的釘選工作集、候選稿重用；同時保留可選摘要和獨立筆記入口。** 下一步最有價值的是釐清這些機制的失敗與更新行為，再對照 Pi／Deep Agents 的公開介面。這會比現在就凍結完整 JSON Schema，更能避免重構後仍被不合適的狀態模型限制。
