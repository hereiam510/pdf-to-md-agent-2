### 1. 本輪討論定位與核心基準

本輪聚焦於 `pdf-to-md-agent-2` 的 **Context 管理政策與設計選擇**（不實作、不修改檔案、不呼叫 Nexus）。我們沿用已核對的原碼事實與 R1／R2／R3 重現證據，並在「責任分離（政策組合、協定計畫與估算、接續決策、持久恢復）」以及「修復 R1/R2/R3」這兩項已無爭議的共識之上，專門針對**三項尚未定案的政策選擇**進行不預設結論的對比與情境推演。

---

### 2. 三項未決政策選擇的深度比較

#### 選擇一：Context 更新的准入與提交單位

這項選擇的核心是：**當一次模型回應包含多筆工具呼叫時，正式改變有效政策 `A` 的「原子提交單位」與「容量准入時點」是甚麼？**（注意：提交時點、工具回條格式、是否附加額外訊息、是否多發模型呼叫是四個獨立維度，以下明確拆開評估。）

| 比較面向 | 政策 P1-Immediate：「逐筆立即生效，容量不足才等待」（現行雙軌改良） | 政策 P1-Batch：「同批次依序組合，批次末整體准入」 |
| --- | --- | --- |
| **准入與提交定義** | 每筆 `context_update` 是獨立的提交單位。執行當下若通過 `preflight`（含後續未執行工具的 placeholder），立即寫入 `context_intent`（`applied=True`）承諾生效；若因歷史壓力放不下但核心合規，存為 `context_proposal` 等待。 | 單筆 `context_update` 執行時只做**語法／引用／範圍驗證**並保存原始回條；等同一回應批次的所有呼叫都處理完畢後，將本批 `context_update` 依序合成**單一候選修訂（Candidate Revision）**，統一在 `coordinate` 以完整已知批次結果執行一次准入並寫入 `context-settlement`。 |
| **1. 對相依更新的影響** | ❌ **跨呼叫無原子性**：若模型在同一批次分兩筆呼叫 `[Call 0: pin(Y), Call 1: release(X)]`，`Call 0` 單獨面對 `X+Y` 中間狀態時會直接因容量超限被拒。模型必須把相關變更寫在同一個 `context_update` 呼叫內。 | ✅ **天然支援同批多步組合**：`Call 0` 與 `Call 1` 先在候選狀態中合成最終政策 `Y`，批次末只對最終 `Y` 檢查容量，中間 `X+Y` 超量不會攔截 `Call 0`。 |
| **2. 對未知後續工具結果的影響** | ⚠️ **承諾與實際批次結果可能脫節**：若 `Call 0` 是 `context_update`，`Call 1` 是 `inspect_pdf(mode="dict")`（產出 1MB 結果），`Call 0` 執行時只看到 `Call 1` 的小 placeholder 而寫入 `applied=True`；但 `Call 1` 跑完後總輸入可能因 `Call 0` 新增的 6KB 筆記而把另一筆原本合規的證據擠成 deferred（違反「不因新更新額外延後既有可見證據」的原則），或直接觸發壓縮。 | ✅ **基於完整事實決策**：准入發生在 `Call 1 (inspect_pdf)` 結果已經落盤之後，系統完全掌握本批所有工具的真實大小，不再需要 `unsettled_operations` placeholder 猜測。 |
| **3. 對中途取消（Stop）的影響** | 在 `Call 0` 完成後、`Call 1` 開始前按 Stop：`Call 0` 若當時無壓力，已經承諾為正式政策；若當時有歷史壓力，則仍為未生效提案（行為取決於當下歷史水位）。 | 在 `Call 0` 完成後、`Call 1` 開始前按 Stop：整個批次尚未完成，`Call 0` 處於「已驗證並保存，但尚未進入批次末正式准入」的一致狀態。 |
| **4. 對恢復、回條與訊息開銷的影響** | • **恢復**：需維持兩套恢復路徑（`Runtime.tools` 恢復逐筆 `context_policy`，`coordinate` 恢復延後 `context_settlement`）。<br>

<br>• **訊息與呼叫**：無額外模型呼叫。 | • **恢復**：只有一套正式政策轉換權威（`context-settlement`）。<br>

<br>• **回條與訊息解耦**：原始 `result:<op>` 保存驗證紀錄；若在緊接的 `coordinate` 即准入通過，組裝下一請求時直接在該批次的 tool output 投影顯示整組修訂已提交，**不需附加額外尾端 user 訊息，也無額外模型呼叫**。 |

#### 選擇二：同批次出現無效更新時的處理

這項選擇的核心是：**當同一批次（或跨回合對既有待處理提案 `Q_prev` 的修訂）中，某筆 `context_update` 因參數錯誤、無效引用／範圍或容量超限而失敗時，同批其他合法的 `context_update` 與先前的 `Q_prev` 是否仍自動生效？**

| 比較面向 | 政策 P2-Partial：「跳過無效筆，套用同批其他合法更新」 | 政策 P2-Whole：「整組 context 修訂不生效，保留內容供 agent 修改」 |
| --- | --- | --- |
| **核心規則** | 失敗的那筆 `context_update` 回傳 `ok=False` 並被略過；同批前面或後面的其他合法 `context_update`（以及上一輪已存在的合法 `Q_prev`）照常組合並自動進入准入／生效。 | 同一批次的 `context_update` 視為一個整體修訂。只要其中任一筆結構無效或合成後容量無法准入，**整組本批 context 修訂均不自動生效**（維持當前有效政策 `A` 不變）。若先前有未生效的 `Q_prev`，**保留 `Q_prev` 與本批所有合法／失敗呼叫的原始內容供查閱重用，但取消 `Q_prev` 的自動准入資格（`auto_admit=False`）**。 |
| **1. `notes` 與 `pin` 語義依賴保護** | ❌ **可能拆散語義**：若 `Call 0` 將 `notes` 改為「已綁定圖 Y，請依圖 Y 修正表格」，而 `Call 1` 綁定圖 Y 時寫錯 `json_pointer` 或因容量被拒，系統會單獨套用 `Call 0` 的新筆記，導致後續上下文出現「筆記聲稱有圖 Y、實際沒綁定圖 Y」的自相矛盾。 | ✅ **不猜測獨立性、不拆散意圖**：App 不自行假設 `Call 0` 可以脫離 `Call 1` 獨立成立。有效政策維持 `A` 不變，並將完整錯誤診斷與已保存的 `Call 0` 內容交還 agent 明確選擇。 |
| **2. 對跨回合既有待處理提案 `Q_prev` 的影響** | 保留 `Q_prev` 的自動准入資格，在下一次 `coordinate` 直接將 `Q_prev`（加上本批其他成功部分）提交生效。風險是：若本批失敗的操作原本是要修正或替換 `Q_prev` 的關鍵部分，自動提交舊 `Q_prev` 會違背 agent 的最新意圖。 | **嚴格區分「內容保存」與「自動執行資格」**：`Q_prev` 的不可變 blob 100% 保留，agent 可隨時讀取或重用；但既然 agent 最新一輪嘗試修改 context 失敗了，系統不擅自把過時的 `Q_prev` 自動提交生效，而是要求 agent 在下一輪明確決定（例如用 `base="pending"` 修補或 `base="active"` 重建）。 |
| **3. 對同批其他工具（如 `edit_document`）的影響** | 不回滾已完成的 `edit_document`、`inspect_pdf`、`extract_image` 等成果。 | **同樣絕不回滾**：此原子邊界僅限於 **context 政策候選**；同批已成功的 `edit_document` 版本、圖片擷取與證據讀取 100% 保留。 |

#### 選擇三：Stop 後加入新指示，如何處理未提交提案

首先明確區分半批 Stop 時的三種狀態：

1. **已提交效果（Committed Effects）**：先前已完成結算的政策 `A`、以及本批 Stop 前已執行完成的 `edit_document`（新版本已寫入）、`inspect_pdf`／`extract_image`（證據已保存）。**無論選哪種政策，這些歷史事實與成果永遠保留、絕不撤銷。**
2. **尚未執行的工具（Unstarted Calls）**：在 Stop 時尚未開始執行的呼叫（如 `Call 1`）。當使用者不加新指示直接 Continue 時，繼續執行 `Call 1`；當使用者**加入新指示（Amendment）後 Continue** 時，`Call 1` 不再執行，而是寫入配對的 `skipped=True, reason="superseded_by_user_amendment"` 回條。
3. **已保存但未正式提交生效的 Context 更新（Saved Uncommitted Context Proposals）**：例如 `Call 0 (context_update)` 已在 Stop 前執行完畢並保存了候選提案，但尚未在 `coordinate` 完成正式政策提交。當使用者在 Stop 後**加入新指示**時，有三種可選政策：

| 政策選項 | 核心機制 | 優缺點與邊界評估 |
| --- | --- | --- |
| **政策 P3-Supersede（預設全部取代未提交提案）** | 凡尚未完成正式提交（未寫入 `applied` settlement）的待處理提案，只要遇到 `proposal["instruction_basis"] != instruction_basis(job)`，在 `coordinate` 一律標記為 `superseded`（`auto_admit=False`），不自動套用。原始提案與參數完整保留於 store 中。 | • **優點**：最安全、不需猜測新指示與舊提案是否衝突，也不會偽造 `instruction_basis`。<br>

<br>• **代價**：若使用者只是在半批按 Stop 補充一句無關的提醒（例如「順便注意第 3 頁註腳」），剛跑完的 `Call 0` 提案也會轉為 `superseded`，需由模型在看到 `superseded` 診斷後決定是否重新提交。 |
| **政策 P3-AutoKeep（已完成保存的工具免受半批新指示取代）** | 認為 `Call 0` 既已在 Stop 前跑完（`operation.status="done"`），就應與同批已跑完的 `edit_document` 一樣保留自動准入資格。 | • **嚴重問題**：1) 若 `Call 0` 還沒正式准入，為了讓它通過 `coordinate` 就必須改寫或忽略 `instruction_basis`，這會掩蓋該政策是在舊指示下提出的真相；2) 若原批次是 `[Call 0: pin(Y), Call 1: release(X)]`，在 `Call 0` 後 Stop 並加新指示跳過了 `Call 1`，自動准入半套 `Call 0` 反而製造了殘缺政策。**不建議採納。** |
| **政策 P3-ExplicitOptIn（預設取代，但提供使用者明確勾選／參數保留，或由 Agent 一鍵重用）** | 引擎預設採用 **P3-Supersede**（不猜測語義、不改寫原始 `instruction_basis`）。但因為 `superseded` 提案的完整內容仍保存在 `proposal_ref` 中，可透過兩種**不需 app 猜測語義**的明確機制銜接：<br>

<br>① **Agent 端零成本重用**：在 `superseded` 回饋中附上該提案引用，並允許 `context_update(base="proposal:<ref>")`（或 `reuse_proposal="<ref>"`），讓模型在新指示下若確認仍需該更新，只需傳一個引用即可完整恢復，不必重寫長 `notes` 或 `pin` 陣列。<br>

<br>② **User 端明確開關（可選）**：Continue API 若未來有需要可支援明確的 `keep_pending_context: bool = False`（預設 `False`），但現階段光靠 ①（Agent 引用重用）已完全足夠且不增加 UI 複雜度。 | • **優點**：兼顧 P3-Supersede 的嚴謹性（絕不自動套用未經新指示確認的半批提案、絕不偽造 `instruction_basis`），又消除了模型重打整串 `notes`／`pin` 的摩擦成本。 |

### 3. 四個具體代表性情境的政策組合推演

以下比較兩種最具代表性的完整政策組合：

* **組合甲（推薦：整體候選與明確處置）**：**P1-Batch**（同批組合、批次末統一於 `coordinate` 准入）＋ **P2-Whole**（同批有錯整組不自動生效，`Q_prev` 保留內容但取消自動准入）＋ **P3-Supersede + Reuse**（未提交提案遇新指示轉 `superseded`，保留引用供重用）。
* **組合乙（改良型逐筆雙軌）**：**P1-Immediate**（逐筆立即 `preflight` 准入，歷史壓力才存提案）＋ **P2-Partial**（跳過無效筆，套用同批其餘更新與 `Q_prev`）＋ **P3-Supersede**（已即時生效者保留，處於 waiting 者遇新指示轉 `superseded`）。

---

#### 情境 1：同批次先 `pin Y`，再 `release X`；中間 `X＋Y` 放不下，但最終 `Y` 放得下

（假設目前有效政策 `A` 綁定大型項目 `X`，本批次為 `[Call 0: context_update(pin=[Y]), Call 1: context_update(release=[X])]`）

| 評估項目 | 組合甲（P1-Batch ＋ P2-Whole） | 組合乙（P1-Immediate ＋ P2-Partial） |
| --- | --- | --- |
| **有效政策與候選** | • `tools` 執行中：有效政策維持 `A (pin X)`；`Call 0` 驗證通過形成暫態 `X+Y`，`Call 1` 驗證通過合成批次最終候選 `Q = {pin: [Y], release: [X]}`。<br>

<br>• 進入 `coordinate`：`Q` 通過完整輸入准入，**有效政策正式更新為 `A' = {pin: [Y], release: [X]}**`。 | • `Call 0` 執行時：`preflight` 檢查 `X+Y` 核心，因超過容量上限當場拒絕 `Call 0`（`ok=False, context_rejected=True`）。<br>

<br>• `Call 1` 執行時：對有效政策 `A` 執行 `release X` 通過。<br>

<br>• **最終有效政策變成 `{pinned: [], released: [X]}`（`X` 被釋放，但 `Y` 遺失！）**。 |
| **已承諾 vs. 僅保存** | • `tools` 結束時：`Call 0`、`Call 1` 的驗證與合成候選 `Q` 為「已保存」。<br>

<br>• `coordinate` 完成時：`context-settlement` 提交，`A'` 為「已承諾生效」。 | • `Call 0` 的拒絕與 `Call 1` 的單獨釋放 `X` 在各自工具完成時即成為「已承諾」。 |
| **Agent 收到的結果與下一步** | Agent 在下一輪請求的 tool output 投影中看到 `Call 0` 與 `Call 1` 均納入已生效修訂（`applied=True`），且 `Y` 已在 `Pinned saved objects` 中，可直接基於 `Y` 繼續編輯文件。 | Agent 收到 `Call 0` 被容量拒絕、`Call 1` 已生效的結果；發現 `X` 沒了、`Y` 也沒綁上，必須額外再花一輪發送 `context_update(pin=[Y])`。 |
| **中斷與重開行為** | • 若在 `Call 0` 與 `Call 1` 之間中斷重開（無新指示）：繼續跑完 `Call 1`，合成 `Q` 並在 `coordinate` 生效為 `A'`。<br>

<br>• 若在 `coordinate` 寫入 settlement 後、checkpoint 前中斷重開：`recover` 直接恢復 `A'`，不重複准入。 | 重開後依 `result:<op>` 恢復「`Call 0` 拒絕、`Call 1` 生效」的半套結果。 |

---

#### 情境 2：`notes` 改為「依據 Y 工作」，但後面的 `pin Y` 因參數或容量問題失敗

（假設目前有效政策為 `A`，若跨回合還有先前待處理提案則記為 `Q_prev`；本批為 `[Call 0: context_update(notes="依圖 Y 核對表格"), Call 1: context_update(pin=[Y])]`，而 `Call 1` 因 range 寫錯或 `Y` 本身超過總容量而失敗）

| 評估項目 | 組合甲（P1-Batch ＋ P2-Whole） | 組合乙（P1-Immediate ＋ P2-Partial） |
| --- | --- | --- |
| **有效政策與候選** | • **有效政策維持 `A` 不變**。<br>

<br>• 本批修訂 `Q_batch` 因 `Call 1` 失敗（結構無效，或合成後 `core["fits"]==False`），整組被判定為**未准入／需修改（`auto_admit=False`）**。<br>

<br>• 若原本有 `Q_prev`，`Q_prev` 的內容保留，但 `auto_admit` 一併設為 `False`。 | • 若 `Call 0` 當時無壓力：**有效政策已被改成 `notes="依圖 Y 核對表格"**`，但 `pinned` 中根本沒有 `Y`！<br>

<br>• 若當時有歷史壓力：待處理提案變成「只有新 `notes`、沒有 `Y`」（或疊加在 `Q_prev` 上），並在壓縮完成後自動把這個半套政策提交生效。 |
| **已承諾 vs. 僅保存** | • **已承諾**：有效政策仍為 `A`；本批修訂的處置確定為 `auto_admit=False`（不會自動生效）。<br>

<br>• **僅保存**：`Call 0` 的新筆記文字保存在 `candidate:<req>:0` 與候選紀錄中，`Q_prev` 也保存在原 blob 中。 | • **已承諾**：`Call 0` 的新筆記已被單獨承諾進有效政策或待自動准入的提案鏈中。 |
| **Agent 收到的結果與下一步** | 系統以有效政策 `A` 組裝下一輪正常請求（若 `A` 受歷史壓力則先以 `A` 壓縮），Agent 收到明確診斷：「`Call 1` 因參數／容量失敗，本批修訂（含 `Call 0`）未生效；有效政策仍為 `A`」。Agent 可修正 `Y` 的範圍後重發，或重用已保存的 `Call 0` 筆記。 | Agent 收到 `Call 0 (applied=True)` 與 `Call 1 (rejected)`；若 Agent 沒注意到需要自己把 `notes` 改回去，後續若觸發壓縮，摘要模型看到 `notes="依圖 Y 核對表格"` 卻找不到圖 Y，容易產生混淆。 |
| **中斷與重開行為** | 由於 `auto_admit=False` 已持久寫入結算／檢查紀錄，任何時候中斷重開（包含調高容量後重開），都不會偷偷把半套 `Call 0` 或舊 `Q_prev` 自動提交，一律維持走「以 `A` 送交診斷讓 Agent 修改」的決定。 | 重開後維持 `Call 0` 已單獨生效（或單獨排隊等壓縮生效）的狀態。 |

---

#### 情境 3：第一筆 `context_update` 已保存後按 Stop，分別「直接 Continue」與「加入新指示後 Continue」

（假設本批次模型回應為 `[Call 0: context_update(U0), Call 1: edit_document(E1)]`，在 `Call 0` 執行完畢、`Call 1` 尚未開始時，使用者按下 Stop）

| 評估項目 | 組合甲（P1-Batch ＋ P2-Whole ＋ P3-Supersede） | 組合乙（P1-Immediate ＋ P2-Partial ＋ P3-Supersede） |
| --- | --- | --- |
| **3a. 直接按 Continue（無新指示）** | • **行為完全一致且自然**：`Runtime.tools` 對帳恢復已完成的 `Call 0`（不重跑），接著繼續執行尚未開始的 `Call 1 (edit_document)`。<br>

<br>• 整批完成後進入 `coordinate`，對 `U0` 執行准入：可容納則正式生效為 `A'`，需壓縮則進入壓縮。 | • `Runtime.tools` 對帳恢復 `Call 0`，繼續執行 `Call 1 (edit_document)`。<br>

<br>• 若 `Call 0` 當初是即時生效則已生效；若當初是 waiting 則進入 `coordinate`。 |
