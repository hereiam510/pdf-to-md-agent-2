## Development credential-file loading

The user selected automatic credential loading for the whole development workflow on 2026-11-06, after placing a credential in ignored `private/api-key.txt`. This supersedes the earlier Task-A-only loader interpretation. Unpackaged Electron launches read that one default file when it exists, including direct `pnpm dev` and isolated development profiles. `PDFMD_CREDENTIAL_FILE` selects another explicit file. `PDFMD_SKIP_CREDENTIAL_FILE=1` disables loading; `tools/dev/start.ps1` exposes `-CredentialFile` and `-NoCredentialFile`, restores its process environment on exit, and rejects those options with `-Packaged`. Packaged Electron ignores both the file and these development controls.

Loading runs in the desktop main process before engine startup, after Electron is ready. The file must be a nonempty UTF-8 regular file, at most 64 KiB, containing one whitespace-free credential after trimming surrounding whitespace. Only ENOENT from initial default-path discovery establishes ordinary absence and leaves remembered/manual entry available. After successful discovery, every read/validation failure, including read ENOENT, blocks engine startup with the fixed safe message and cannot enable remembered fallback. An explicit missing file also fails; raw file/error content is withheld. No directory scanning, provider-configuration import, log/profile credential recovery or provider probe occurs. Loading changes neither connection settings nor task state, and starts no conversion.

The loaded value stays in memory and takes precedence over an older remembered credential. The [CRED-01/02 repair](../reviews/RUNTIME_FINDINGS.md#credential-startup-repair-implementation-and-offline-acceptance-2026-11-06) implements this through one main-process `ConnectionState` owner. It begins initialization before loading the renderer. File and raw connection-settings reads can finish in either order; remembered decryption starts only after file absence or opt-out is established. A valid file excludes remembered decryption entirely. Ordinary settings reads await initialization and queued saves, return only safe metadata, and never restore credentials or rescan the file.

Explicit Connection entry replaces the active key. **Clear credential**, followed by Save, removes it and its remembered persistence. Each accepted replacement/Clear advances a credential revision immediately, so a pending file/decrypt/rotation result cannot restore an older key. Settings saves share a serialized persistence queue; an encryption result for a superseded save does not publish old connection fields or secrets. Save replies and ordinary reads wait for the queue to settle. Refresh, replacement and Clear do not rescan the file; the unchanged file may load again on a later development launch. Remember is an explicit Connection choice using asynchronous OS encryption. When a Remember save has a key to persist, the owner refreshes async capability after initialization inside that queue. It accepts capability metadata and encrypted data only while the save's revision remains current. A rejected capability query is handled as unavailable: manual memory-only use remains available, and a later explicit Remember save can retry. Unchecking Remember retains the session key while removing persisted ciphertext. Unavailable encryption or failed remembered decryption leaves manual entry available; native encryption/save failures use a fixed safe message and permit a subsequent save. Applicable `shouldReEncrypt` rotation stays within initialization and its revision guard. The plaintext owner file remains unchanged and ignored. This is a local development convenience, not isolation against other processes running as the same user. Synthetic Playwright runs disable automatic loading by default and opt in only to fake files.

The renderer disables connection editing and Start until its initial settings reply settles, rather than saving placeholder defaults. It also requires engine readiness before Start. The settings effect ignores replies after unmount; revision comparison rejects older snapshots after newer saves. A selected-file failure returns settled failure metadata and the fixed safe error, with engine startup blocked. Main-process Start waits for initialization and accepted saves, obtains the saved task configuration, then reads the current key and connection defaults again immediately before the local Start call. Configured tasks retain their own route/limits; editing connection defaults does not change task settings. No credential appears in renderer settings replies.

**Reviewed implementation at d370082 (historical evidence).** The [follow-up review](../reviews/RUNTIME_FINDINGS.md#credential-repair-follow-up-review-2026-11-06) found two regressions against the policy above: default-file ENOENT after successful discovery falls back to remembered state, and an initially unavailable encryption capability remains cached through later Remember saves. The original CRED-01/02 race fixes remain supported. The target requirements below address these transitions. Consult [execution progress](../batches/CRED-03-04/tickets.md) and [current batch evidence](../batches/CRED-03-04/verification.md) for the correction; the earlier finite checks alone do not establish these transitions.

### Selected startup repair target (2026-11-06)

**Acceptance basis for the original race repair.** The user selected this bounded CRED-01/02 repair, offline acceptance and record updates. [The selection and rationale](../discussions/REQUEST_CAPACITY.md#credential-startup-repair-selection-and-handoff-2026-11-06), [handoff](../history/20261106_2300_REVIEW_HANDOFF.md#credential-startup-implementation-handoff-2026-11-06) and [execution evidence](../reviews/RUNTIME_FINDINGS.md#credential-startup-repair-implementation-and-offline-acceptance-2026-11-06) retain authority, actual checks and limits. The following selected conditions remain the acceptance basis; the effective mechanism is above. No framework, dependency or credential-policy redesign was needed.

1. **One main-process initialization owner.** Begin a shared initialization promise after Electron readiness and before loading the renderer. Separate raw connection-settings reads from credential restoration. Ordinary `settings()` calls return safe state; they no longer decrypt, assign `apiKey` or rewrite remembered secrets. Initialization must not call the public settings reader recursively.
2. **Deterministic source selection.** File reads and remembered decryption produce candidates, never direct assignments. Publish the valid development-file key ahead of an older remembered key, regardless of completion order. Remembered fallback becomes eligible only when file absence or opt-out is established; an invalid selected file retains the fixed startup failure. A valid file need not wait for an unused remembered result. Candidate preparation order is an implementation detail; correctness must not depend on timing or require unnecessary decryption.
3. **Explicit changes own newer state.** Manual replacement and Clear advance a credential revision, or an equivalent explicit ordering identity. Clear is intentional empty state, not permission to hydrate another key. Older initialization/decryption completions cannot publish over it. Serialize settings persistence and prevent stale encryption/re-encryption from overwriting newer saves, Clear, Remember choices or connection fields. Keep existing OS-encryption behavior, including applicable `shouldReEncrypt` handling, within this ownership boundary. Refresh, replacement and Clear do not rescan the file; a later development launch may load it again.
4. **Settled renderer state.** The initial settings request waits for initialization's terminal outcome. Distinguish loading, ready-with-key, ready-without-key and failure as needed; pending loading is not `hasKey=false`. Enable ordinary Start only after both engine and settings readiness. Ignore older settings responses after a newer save and obsolete/unmounted effects. Connection editing waits for its initial settings rather than saving placeholder route/limit defaults. Failure settles loading and exposes the existing fixed safe error without starting the engine.
5. **Start uses current authority.** Main-process Start waits for initialization and earlier accepted credential changes, then reads the current key at the existing local dispatch boundary. Preserve the route/task-settings boundary. IPC exposes safe metadata such as `hasKey` and any ordering metadata, never the credential. Automatic loading sends nothing.

### Selected credential follow-up target (2026-11-06)

**Adopted follow-up requirements.** The selection event covers both P2 corrections, offline regression checks and records; [local tickets](../batches/CRED-03-04/tickets.md) own their execution state and [verification](../batches/CRED-03-04/verification.md) owns acceptance. [The selection](../discussions/REQUEST_CAPACITY.md#credential-follow-up-repair-selection-and-handoff-2026-11-06) explains sequencing; [the handoff](../batches/CRED-03-04/spec.md) supplies authority and preservation. This is a bounded extension of the existing owner, with no credential-policy, framework or dependency change.

1. **CRED-03: distinguish absence from a failed selected read.** Only an initial default-path discovery ENOENT is ordinary absence. After successful discovery, a read ENOENT is a failed selected file, just like other read/validation failures. Preserve the fixed safe error and block engine startup and Start; do not fall back to remembered credentials. Explicit missing paths still fail. Opt-out and packaged status still bypass file access.
2. **CRED-04: refresh capability for explicit Remember.** Recheck async encryption availability when an explicit Remember save needs to persist the current intended key. Do this inside `ConnectionState` and its serialized save lifecycle, after initialization, and update the safe capability metadata. Capability refresh must not hydrate a remembered key, rescan the file or create another credential owner. Keep the save's intent and revision checks across every new await, so delayed capability/encryption work cannot publish over newer replacement, Clear, Remember-off or connection fields. Continued unavailability leaves manual memory-only use available; native encryption failures retain safe diagnostics and retry behavior.

Primary code is `src/desktop/connection.ts`; production-path regressions belong in `tests/desktop/specs/credential-state.spec.ts` and narrowly extended `tests/desktop/support/credential-host.cjs` instrumentation. Preserve the existing main/renderer readiness path and all original acceptance guarantees. A fresh process solely to recover Remember or a broad settings refresh that rehydrates credentials would not satisfy this target.
