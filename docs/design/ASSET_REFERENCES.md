## Consolidated discussion agreement

These sections are the single current rules for the agreed product direction. Earlier hash-only filenames, routine hash/source/asset suffixes, required title abbreviations, `print`/`pdf` locators, generated figure-label fallbacks and unconditional reuse of an outdated filename are superseded. Full SHA-256 remains internal byte-integrity identity; it does not determine the visible filename or merge separate source occurrences.

### Readable filenames and source locators

The visible filename consists of a source-grounded description, a required page locator, an optional original source figure identifier, an actual-collision suffix only when needed, and the registered image's lowercase extension. Structural separators remain distinct from source punctuation. Ordinary examples are:

- `新聞基本屬性-p58-圖4–2.png`: confirmed printed page and an actual source figure label.
- `新聞基本屬性-p58.png`: confirmed printed page, no usable source figure label.
- `新聞基本屬性-i12.png`: physical position 12 when the printed label is absent or unresolved.
- `新聞基本屬性-p58（2）.png`: a real complete-filename collision with a different asset.

These examples illustrate components and their order, not invented source facts. Use `p` with the source-confirmed printed label, including Roman labels where applicable. Use `i` with the one-based physical position when printed-label state is `none` or `unknown`; keep those states distinct. Always retain the physical source position independently in metadata, even when the filename uses the printed label. Never derive printed numbers from an assumed offset, bookmark, upload filename or viewer hint. Repeated printed labels and multi-page figures retain all actual source-page/region associations; a filename is not the sole page map.

Assemble `description + "-" + locator + optional("-" + source_figure) + optional(collision_suffix) + "." + extension`. Chinese suffix is `（N）`; English suffix is ` (N)` with one leading ASCII space, only for a real conflict. The neutral fallback label is `image`; its stored description/style remains explicit. These generated separators are not added to original metadata strings.

Use compact verified ranges and explicit lists for compound locators:

| Established contributing positions | Filename locator |
| --- | --- |
| Continuous confirmed printed sequence | `p58–p59` |
| Nonconsecutive confirmed printed labels | `p58&p61` |
| Continuous physical fallback positions | `i12–i13` |
| Confirmed printed label plus an unknown/absent printed label at physical position 67 | `p58&i67` |
| One exact compound printed label `3-12` | `p3-12` |

The list connector is the literal ASCII `&`, including in a Chinese filename; it is structural syntax, not a character to convert to `＆`. It replaces the preceding `+` proposal. The en dash marks a verified range only when complete covered membership and labels are established. Never infer an unknown printed label from endpoints or an offset. Keep typed ordered positions and exact source labels in metadata; do not reconstruct them by reparsing an ambiguous filename. Preserve actual compound figure identifiers without inventing panel labels. If mandatory components cannot fit after faithful shortening, return the 180-byte constraint failure rather than reducing the span to its first page.

Keep an actual source figure identifier in its source language, with generated-filename safety substitutions as specified below; preserve its exact original wording in metadata. An absent or unusable identifier is omitted, never replaced with an internal `A004` or invented figure number. The page component is always required for current paginated sources. No default book/article title abbreviation, author/year prefix, `S023` source code or opaque suffix is added. Full established titles and source identity live in embedded metadata. This format-neutral naming direction permits future document types but implements no new importer; a format without stable pages needs a separate pagination decision.

### Punctuation and exceptional filename repairs

Use full-width punctuation in Chinese generated description text and half-width punctuation in English where valid. Record the description's language/style, selected by the agent from its actual linguistic context rather than script counts, the presence of one Han character or the UI locale. If a deliberately bilingual description has no dominant prose language, use the first complete phrase's language as the fallback. Keep the style stable until a deliberate description/style correction. Generated collision brackets follow that style; source-authored figure components retain their wording/typography apart from the agreed safety substitutions. Do not blanket-convert ASCII letters, digits, technical notation or structural separators. For example, `受眾研究（Agenda-setting）-p58-Fig. 4.2.png` can preserve an actual English figure label inside a Chinese-style filename. Original source observations remain separate.

Apply these selected substitutions within generated basename components, including the validity exception for English:

| Prohibited ASCII character | Replacement |
| --- | --- |
| `<` | `＜` |
| `>` | `＞` |
| `:` | `：` |
| `"` | `＂` |
| `/` | `／` |
| `\` | `＼` |
| `U+007C` (ASCII vertical bar) | `｜` |
| `?` | `？` |
| `*` | `＊` |

The actual `assets/` directory separator, structural hyphens, locator `&`/range connectors, page identifiers/digits and extension period are not source-text substitutions. A full-width slash inside the basename is a literal character, never a directory boundary. A description is data, not a supplied filesystem path.

Validate the complete generated filename, including reserved device-name/extension behavior. A source word alone is not a reason to repair it: `CON-p58.png` is not reserved, whereas a truly reserved complete name such as `CON.png` needs an exceptional readable `image-` prefix. Flatten OS-forbidden controls, including line breaks/tabs, into ordinary spaces in the generated components; trim unwanted outer whitespace and terminal ASCII dots from the descriptive stem. Preserve meaningful interior punctuation, joiners and variation selectors. An empty/dot-only description uses a neutral image description plus the required page; it does not invent a source figure label.

Use NFC for generated filename spelling. Do not apply blanket NFKC/NFKD, width-to-ASCII conversion or lowercase rewriting to the visible name. Original source observations are not normalized by this filename policy. Use the separate conservative, case-insensitive and canonically normalized [portable comparison algorithm](#portable-comparison-and-destination-matrix). This comparison can be stricter than one filesystem without claiming that all filesystems compare Unicode identically. Registration, lookup and link serialization must preserve the selected spelling.

### Filename byte budget and meaning-preserving shortening

**The complete final filename must fit within 180 UTF-8 bytes**, including the required page, optional source figure, lowercase extension and any actual collision suffix. The directory path and URI-encoded transport spelling are outside this component budget. This is an adopted product ceiling, not a universal operating-system limit or a target length to fill. Check the destination's whole path separately; do not silently rename assets at export or change global long-path settings.

Keep a fitting description unchanged apart from the agreed typography/safety rules. Reserve the actual structured-component bytes first. If the description is too long, the agent derives a concise source-supported label within the remaining budget:

1. Keep distinctive searchable terms, the depicted subject, relationship/comparison and meaning-critical qualifiers. Negation, direction, relevant population/time/scope, quantities/units and schematic-versus-measured status must survive where their omission changes the reading.
2. Remove genuinely redundant introductory wording or information already expressed by structured filename components. Prefer shorter natural phrasing; do not invent opaque abbreviations, force translation/transliteration or mechanically cut a string at a byte/character/phrase boundary.
3. Preserve complete visible character sequences and keep the shortened label distinct from a source caption. Retain the full original caption, any full agent-authored description and their attribution/derivation in embedded metadata. Full title/source information is not shortened to the filename budget. Existing adjacent searchable Markdown requirements remain in force.
4. Reapply styling, substitution and NFC, then recheck bytes and collisions after any wording change or suffix growth. If required components or a faithful description cannot fit, return the specific constraint and available description budget for correction. Never drop a locator, meaningful qualifier or full metadata to force success. The limit is not silently increased; a later change to the adopted limit would be a new policy decision.

The agent chooses wording within ordinary conversion; app services enforce exact bytes, required components and binding consistency. String length cannot certify semantic fidelity. No routine user naming task, compulsory additional provider round or export-time inference is introduced. A finite filename need not repeat every caption detail, but embedded metadata cannot excuse a misleading visible label. [Capacity calculations and the worked Chinese example](../discussions/ASSET_REFERENCES.md#filename-capacity-and-meaning-preserving-shortening) explain the rationale; the checks there establish arithmetic only.

### Collision-only allocation and identity

Allocate names within the app-controlled task registry. Compare the complete final filename after substitution, normalization, cleanup and shortening, including its page/figure parts and extension. Different page or figure components ordinarily yield different names. For distinct assets requesting the same complete portable name, preserve the existing binding and give only the newcomer the first available copy suffix starting at 2: Chinese `（2）`, English `(2)` before the extension. Recheck each candidate, including existing suffixed names, 9-to-10 growth and any additional shortening. No ordinary file receives a suffix merely to prevent a hypothetical conflict.

An unchanged occurrence can reuse its current path and representation. Corrected naming facts follow synchronized correction below. An identical picture at another real source location has a separate occurrence association even if internal byte storage is shared. A hash proves byte equality, not provenance equality.

Reserve a target binding durably before publishing its references. Concurrent allocation/retry must not assign the same current path to different occurrences. A correction may create a new representation/path for its own occurrence; ordinary allocation cannot rename unrelated assets, renumber survivors or compact suffixes when a reference/source is omitted or removed. Historical version bindings remain authoritative for their versions. Repeating an accepted operation returns its original receipt, not another suffix.

Another operation's pending reservation counts as a conflict at allocation. After a suffixed binding publishes, it keeps its assigned name when the competing reservation settles as a failure. The failed operation's released name becomes available to future saves under the [task-local allocation rules](#document-edit-api-and-operation-semantics).

A source-supported descriptive refinement can avoid a clash when already available, but collision allocation must not require a provider call, title lookup or bibliographic investigation. This is no global filename-uniqueness promise across independent exports. External keep-both renaming can preserve embedded provenance; it cannot repair accompanying Markdown automatically. Existing destination files must not be silently overwritten.

## Standalone embedded provenance and faithful image bytes

Use embedded XMP for each enriched source-image deliverable. Copying or renaming that image alone must leave its established title, citation and source facts readable by an independent metadata reader, without the app database, original document, export manifest, network or companion file. Normal internal inventories/manifests remain permitted; they are not prerequisites for reading the copied image's provenance. Screenshots, re-encoding and metadata-stripping third-party software are outside the ordinary file-copy guarantee.

Use standard descriptive XMP fields plus a small versioned application provenance namespace, both generated from the same versioned source/naming facts. The standard display text and structured values are not independently mutable authorities. Required logical information is defined below; the selected field mapping and embedding boundary follow it.

| Information | Required meaning |
| --- | --- |
| Source identity and citation | Complete source-supported title/citation facts, source identity/digest and source-document kind; retain absent/unconfirmed/conflicting facts honestly. Upload filename, PDF metadata, task title and bookmarks are hints, not sufficient title evidence. Distinguish article/book/container attribution when unclear; do not fabricate or require an external title search. |
| Source location | One-based physical position(s), exact printed-label values and `none`/`unknown` state, original figure identifier when present, occurrence/page/region associations and evidence basis. A displayed printed number never replaces physical position. |
| Image derivation | Corresponding source/extraction/render provenance, coordinate frame/transforms where applicable, pre-enrichment representation identity, associated original image/mask references and relevant processing facts. Source hashes/identities remain useful even without a surviving catalogue. |
| Description and naming | Exact source caption where present, separately attributed full agent description where supplied, derived short filename label and its basis, naming facts/style and assigned filename at creation. An external rename does not make the recorded original filename the current filesystem authority. |
| Representation identity | Metadata schema/enrichment identity sufficient to distinguish the enriched deliverable from the pre-enrichment evidence. The final enriched-file SHA-256 belongs in registry/version integrity records after embedding; embedding a self-referential final file hash is not required. |

Preserve source evidence and the corresponding pre-enrichment asset under the existing retention rules. Metadata enrichment produces a distinct file representation and changes its container bytes/hash. Preserve picture data, dimensions, encoded image content where applicable, color/profile, bit depth, alpha and orientation; introduce no lossy recompression, resize, color conversion or cosmetic change merely to embed metadata. Existing extraction/render limitations remain explicit; enrichment cannot improve or certify fidelity that the prior evidence does not establish. Retained PDF image/mask streams and unchanged source PDFs keep their existing authority.

Finalize metadata, registered path and enriched bytes before immutable save hashes/manifests are finalized. If enrichment cannot preserve the required image representation or provenance, retain the candidate/evidence and return a precise failure; do not quietly deliver a stripped image, sidecar or transformed substitute. Selected saved/reopened/exported deliverable bytes are identical. Metadata correction creates a new representation/version; export only copies that selected version.

An independently retained image remains informative when its source/catalogue is unavailable. This does not promise recovery of a deleted source or reopening a deleted task, establish perpetual retention, or authorize deletion. The full original caption, labels and source-grounded adjacent text still follow [figure delivery](FIGURE_DELIVERY.md#required-outcome); embedded metadata is not their replacement.

### Selected XMP mapping and embedding approach

| Field group | Selected meaning |
| --- | --- |
| `dc:title` | Source-supported image title or explicitly derived image label, with its basis distinguished. Do not silently put the source book/article title here as if it were the image title. |
| `dc:description` | Readable source caption/agent description with attribution, plus a labelled complete source citation and page/figure information. Preserve original source wording/language and distinguish the generated labels. |
| `dc:source` | An established source identifier/digest associated with the structured record. This does not replace the complete bibliographic title/citation fields. |
| Versioned application provenance namespace | Exact source title/citation, source type/identity, ordered physical/printed associations and unknown states, original figure labels, regions/transforms, occurrence/original references, full/short description attribution and derivation. |

Do not infer that the book author created the image. Preserve missing/conflicting facts explicitly instead of populating unsupported standard fields. An independent XMP reader must recover the packet offline; particular file managers/search indexes may expose only some fields, so their full display/search capability requires separate evidence.

### Primary XMP enrichment boundary

**Eligibility.** Enrich source PNGs generated from MuPDF pixmaps and JPEGs copied unchanged from PDF DCT image streams. Require recorded producer and derivation evidence, verify file type and structure, and verify an adopted legacy asset against its task-owned evidence and bytes. An extension or registered path alone cannot establish eligibility. Diagnostic screenshots are evidence only. Reject a reference to one as a source deliverable in a new save with the offending reference identified. Revisit scope if the product adds image import or script-produced source deliverables.

**PNG.** Check the XMP-free generated-PNG input profile before writing. An unexpected XMP-bearing chunk or `caBX` fails this scoped path. Add one uncompressed `iTXt` chunk with keyword `XML:com.adobe.xmp` before the first `IDAT`, with a correct chunk length and CRC. Copy all original chunks and their CRCs in order, including `IDAT` and any encoder-generated resolution or profile information.

**JPEG.** Update the top-level StandardXMP APP1 and only the ExtendedXMP fragments associated with it, treating them as one logical record. Create one primary packet if none exists. Validate segment bounds, complete fragment coverage, lengths, offsets and GUID/digest association before parsing the reconstructed extension. Reject competing primary packets, malformed primary XML, incomplete or ambiguous fragment association, and MPF-bearing JPEGs. Detect MPF before writing and report the unsupported case. Change only the primary APP1 group and its required framing, plus the legacy blanking below. Preserve every other segment, encoded scan and trailer byte, including EXIF, ICC, IPTC/APP13 and JUMBF/APP11.

**Legacy JPEG XMP (B-lite, adopted 2026-11-10).** A top-level legacy XMP value in Photoshop APP13 resource `0x0424` or EXIF IFD0 tag `0x02BC` competes with the primary record in whole-file readers. Overwrite each such value in place with an empty XMP packet of exactly the same byte length, padded with spaces. Do not resize or move anything: segment lengths, IRB sizes, other resources, IFD entries and offsets stay byte-identical. Discard the legacy packet's properties from the delivered image only; the retained original stream keeps them. Reject before writing when the value cannot hold the empty packet, is not valid XMP, sits in an unparseable or split IRB block, or has a TIFF type other than BYTE or UNDEFINED. The [decision record](../discussions/ASSET_REFERENCES.md#t1-f06-qualification-result-and-selection-questions) owns the reasons and the rejected merge variant. Reject when other known position-dependent metadata cannot be kept usable with the allowed splice.

**Validation and preservation.** Validate the exact primary serialization bytes before and after writing within bounded preparation. Require strict encoding and namespace-aware XML checks and valid XMP property semantics. Check the original bytes before any normalization or repair. Only the allowed source properties and necessary packet/container framing may change. Compare the remaining primary properties semantically, including types, arrays, language alternatives, qualifiers and custom namespaces. Copy opaque spans byte-for-byte and in order; the only exception is a blanked legacy value, whose every changed byte must lie inside that value. Older nested XMP in other carriers may remain. Opaque byte equality does not establish packet inventory, nested-XMP equivalence, signature validity or asset binding. Report signature and asset-binding status as unverified. Preserve the PDF, pre-enrichment image and retained streams. A failed validation retains the candidate and source data without publishing an enriched version or advancing head.

Use a separate offline reader to recover the exact complete source record and matching standard fields from the renamed image alone. A fresh packet may be generated from the application allowlist. A merge candidate must preserve existing primary semantics, and both create and merge must support large JPEG records. The [dependency boundary](#dependency-versions-and-helper-boundary) keeps candidate evaluation, qualification and product selection separate. Nested Brotli decoding and complete recursive inventory become dependencies only if a later contract requires reading, comparing, updating or removing nested XMP.

## Synchronized corrections and distinct occurrences

The user explicitly selected **both cases, handled separately**. Correction scope is all affected references and source facts in the current task/document operation and its next saved/reopened/exported version. Earlier immutable snapshots and already exported independent copies remain unchanged.

**Correction:** update the occurrence's source observations and filename-driving facts, derive its corrected full name and resolve genuine collisions. Synchronize all operative image/hyperlink destinations, cross-block reference definitions, affected page/figure/provenance fields, occurrence-to-representation bindings, embedded metadata, inventory, preview and manifest in one coherent new version. A corrected printed-page observation shared by several assets updates every affected current asset. If only non-filename metadata changes, retain the name but version the enriched bytes. Preserve literals, unrelated source text and independently valid occurrences; use parsed reference/source-span correspondence rather than global text replacement. Retain the original received candidate separately from the corrected saved content.

**Genuine additional occurrence:** the same picture appearing at another real page/figure/location receives its own source association, name and embedded provenance. Internal byte deduplication must not merge citations. Existing valid references stay associated with the earlier occurrence; correcting one must not relabel the other.

Prepare corrected bytes/mappings and document changes before conditional publication. Publish all related bindings with the version/head/receipt under the existing task/base/head/conflict/replay guarantees. A failure or stale-head conflict leaves the prior visible version coherent and preserves useful candidates/prepared work. No visible state may pair corrected metadata with stale operative references or another asset's bytes. Rebuild from an explicitly named historical base inherits that base's mappings; it must not silently receive a later mutable correction that was not requested. Replay after a newer head returns the original accepted receipt without another rename or head rewind.

Inside the app, reference synchronization is part of correction/save, not manual user work. Outside the app, Markdown refers to a path, not an embedded-metadata lookup: a file-manager rename can break a separately retained document's links. The app does not search the user's filesystem or rewrite unknown independent copies. Standalone image copying requires no Markdown companion.

### Selected asset-change interface

Extend the existing document-edit responsibility with explicit structured asset changes in one document operation. Distinguish `new occurrence` from `correct occurrence`; supply the operation identity, explicit base/expected head, task-owned occurrence identity, applicable source/image reference and changed naming/provenance facts. The [concrete edit API](#document-edit-api-and-operation-semantics) below defines their names and validation. The stable occurrence identifier stays internal and is not a compulsory filename code. Source/image evidence remains available before naming/citation facts are established, so extraction has no compulsory annotation gate.

The native service owns name reservation, enrichment, targeted reference/source-field synchronization, complete validation and joint publication. Unchanged saves reuse prepared representations. Expensive image preparation occurs outside the short SQLite publication transaction; prepared files and reservations are invisible until accepted version/mapping/head/receipt publication. A reservation alone is not a current binding. Preserve failed candidates/useful files and the prior coherent visible state. Persistent operation identity and task-writer ordering protect replay and competing allocations; an accepted retry returns its original receipt instead of another rename. Historical-base rebuild uses that base's mappings. Shared page/source corrections include all affected current assets, while genuine second occurrences remain independent.

Return the new version and exact affected occurrence/path mappings, or a precise failure. Do not require the caller to manually patch each reference or separately publish an asset rename. Internal preparation can be reused/batched without a compulsory user-visible prepare operation. Export never performs new naming or enrichment.


## Versioned data and embedded schema

These are target wire/storage contracts, not added runtime classes. Objects reject unknown input fields; integers exclude booleans, numeric coordinates must be finite, text must be valid Unicode scalar values, and references must belong to the current task. Arrays preserve order. Omitted patch fields retain the explicit base's value; explicit empty arrays clear lists; `null` is allowed only where declared. No recursive merge or inference from omitted fields is permitted. New occurrence and representation IDs use the existing 32-lowercase-hex UUID convention, independently of byte hashes. SHA-256 fields are exactly 64 lowercase hexadecimal characters.

### Facts, pages and occurrences

| Type / field | Exact shape and rule |
| --- | --- |
| `EvidencePointer` | `{ref: string, physical_page: integer-or-null, region: [x0,y0,x1,y1]-or-null, note: string}`. `ref` identifies preserved source/tool evidence, not an arbitrary path; physical pages are one-based. A region requires a page and the source's unrotated page coordinate frame. `note` explains what supports the observation; it is not itself proof. |
| `TextFact` | `{state: "known"|"none"|"unknown"|"conflicting", value: string-or-null, basis: EvidencePointer[], alternatives: [{value: string, basis: EvidencePointer[]}]}`. Known requires a nonempty exact value and nonempty basis; all other states use null. None requires evidence of absence; conflicting requires at least two evidenced alternatives. Known/none/unknown have no alternatives. Unknown may retain an unresolved hint in its basis note, without promoting it to a title/label. |
| `SourceFacts` | App-supplied `source_ref`, `source_sha256`, `media_type`; editable `kind: "book"|"article"|"document"|"unknown"`, `title`, `container_title`, `publication_date`, `publisher`, `full_citation` (each a `TextFact`), `creators: [{name: TextFact, role: string}]`, and `identifiers: [{scheme: string, value: string, basis: EvidencePointer[]}]`. Missing facts initialize to unknown; lists initialize empty. Source identity comes from the immutable task source and is not caller-reassignable. Current tasks still have one PDF source. |
| Page label authority | `content.pages[physical_page]` remains the single editable printed-label authority. Retain `printed: string`, `disposition` and `note`; add `printed_state: "known"|"none"|"unknown"|null`, `printed_basis: EvidencePointer[] = []`, `printed_alternatives: [{value: string, basis: EvidencePointer[]}] = []`. Known uses the exact nonempty label and evidence; none uses the sentinel `"none"` with evidence; unknown uses `"unknown"`, optionally with unresolved alternatives. Conflicting printed observations therefore use unknown/fallback `i`, never an arbitrarily chosen `p`. Null is solely the untouched legacy-label state described below; new assertions cannot use it. |
| Page patch compatibility | Updating `printed` without a state interprets exact `"unknown"`/`"none"` as those states and every other string as known; an explicit known state permits a real source label literally spelled `unknown` or `none`. A changed known/none observation requires its evidence in the patch. Untouched labels retain their evidence. Setting state alone must validate against the retained label; do not silently discard or invent a value. An untouched legacy string has null state and is retained verbatim, avoiding a compulsory full-map rewrite. For a new image it yields unknown/fallback `i`, with the legacy string explicitly retained as an unconfirmed hint in the embedded page snapshot; an explicit evidenced page patch establishes known/none. Old versions are not rewritten. |
| `Description` | `{full: string, filename: string, language: string, punctuation: "fullwidth"|"ascii", basis: EvidencePointer[]}`. Language is a BCP 47 tag or `und`; punctuation records the agreed contextual choice. `full` is the complete agent-authored description and `filename` its faithful fitting label. An empty/dot-only supplied label uses the agreed neutral image fallback; retain its original supplied value and full description in the record. They remain distinguished from a source caption. The app applies safety/NFC and checks bytes; it never mechanically shortens text. |
| `Location` | `{physical_page: positive integer, region: [x0,y0,x1,y1]-or-null, basis: EvidencePointer[]}`. Region is finite, nonempty and within the existing unrotated source-page frame. Null means whole-page or no more precise region established, as explained in the basis. Store ordered actual contributions; do not deduplicate distinct regions/occurrences merely because page or pixels match. |
| `LocatorGroup` | `{kind: "single"|"range", pages: positive-integer[], basis: EvidencePointer[]}`. Groups cover exactly the unique contributing physical pages, in their first-contribution order. Single has one page; range has two or more and evidence of every member and the continuous printed sequence, or consecutive physical fallback positions. Mixed printed/fallback groups are singles. Omission initially generates singles. A correction that invalidates a previous range expands it to singles; it never invents a newly continuous range. Source labels such as `3-12` are atomic text. |
| `OccurrenceFacts` | `{image_ref, description: Description, caption: TextFact, image_title: TextFact, figure: TextFact, locations: Location[], locator_groups: LocatorGroup[]}`. Locations are nonempty. Missing optional caption/title/figure initialize unknown on create; unknown/none/conflicting figure produces no filename figure component. Image extension/MIME, dimensions and derivation come from validated image evidence, never a caller's desired suffix. |

The app checks evidence ownership, source/page/region consistency and declared processing facts. These checks cannot establish the truth of a caption or semantic shortening; source-led review remains required. The original tool's page/region/transform fields are immutable evidence. A physical-image correction that contradicts them needs a suitable replacement `image_ref`, or separately evidenced association for a genuine repeated occurrence. It cannot edit the original blob's provenance to make it agree. Multiple contributions/transform facts must be supported by the selected representation's derivation; this schema adds no composition or extraction tool.

Page labels are read from the shared page map when building filenames and embedded records. The caller cannot separately edit a printed label inside an occurrence. Source-citation changes similarly use `SourceFacts`, not independent per-image copies. Full facts are copied into each image's metadata at preparation time, so standalone reading needs no source map or database. Their copies are derived immutable snapshots, not additional authorities.

New saves use `document.json.schema_version: 2`, retain the existing job/version/parent/edit-mode/expected-head/source/content/candidate members and add:

Do not add current timestamps or nondeterministic defaults during retries. Allocate new IDs once in the durable operation preparation record. Existing historical versions stay untouched; new references to legacy pre-enrichment evidence require complete new occurrence facts before a schema 2 save can accept them. ### Exact XMP namespace and serialization

Use namespace URI `urn:pdfmd:asset-provenance:1` with preferred prefix `pdfmd`. The URI identifies a schema and is never fetched. Define four app-owned XMP properties: `pdfmd:SchemaVersion` (Integer, 1), `pdfmd:OccurrenceId` (Text), `pdfmd:RepresentationId` (Text), and `pdfmd:RecordJSON` (Text containing the entire structured `provenance_record`). This deliberately keeps the precise schema in one JSON record instead of maintaining a second independently evolving RDF field tree. An ordinary XMP reader can expose its text; a standard JSON decoder recovers the complete typed facts without an app database/configuration file. Standard descriptive properties provide the convenient readable summary.

Serialize RecordJSON with sorted object keys, preserved array order, no insignificant whitespace, UTF-8, JSON escaping for control characters and XML-1.0-forbidden scalars, and no normalization of original text. Reject non-finite numbers and unpaired surrogates. Escape for XML separately; parsing XMP then JSON must recover every original source string, including CR/LF distinctions. This avoids making XML text normalization or full-width filename repair silently change source quotations. The record contains no host absolute paths, credentials, task-store location or required companion pointer. Internal refs are provenance identifiers; complete citation/location/derivation values accompany them.

Write `dc:title` and `dc:description` as XMP Language Alternatives with `x-default`; add an identical-value language entry only when a single applicable language is established. Image title uses known `image_title`, otherwise the derived description label explicitly identified in RecordJSON. Description uses English field labels, exact caption/full description text, every established citation field (including container and creator roles), and all physical/printed/figure positions; render unknown/none/conflicting states honestly and list conflicting alternatives. No truncation. `dc:source` is `urn:sha256:<source_sha256>`; other established identifiers remain in the citation/record. Do not set `dc:creator` from source creators. If a source string cannot appear literally in XML 1.0, its descriptive display uses a labelled JSON-escaped spelling and RecordJSON retains its exact recoverable value.

The allowlist for replacement is these four app properties and the derived `dc:title`, `dc:description`, `dc:source` values. Preserve unrelated useful XMP/EXIF/ICC and other metadata; original versions of any replaced descriptive fields remain in retained pre-enrichment evidence. Clear stale language alternatives in app-generated descriptive fields on correction rather than leaving contradictory text. The app configuration, not document text, defines tags. Reject source-supplied writer options or configuration.

Keep the existing `edit_document` tool and `POST /jobs/{job}/edit`; introduce no separate published rename operation. Existing edit fields, sequential block operations, candidate reuse, explicit base/expected-head, claim and validation remain. Add `asset_changes: AssetChange[] = []` and `source_update: SourceFactsPatch = {}`. Source patch replaces only supplied editable fields as complete typed values; source identity fields are forbidden. Existing `page_updates` supports the new page-label fields above and remains a partial map patch. Asset changes use:

| Action | Input and validation |
| --- | --- |
| Create | `{kind: "create", client_key: string, facts: OccurrenceFacts, legacy_path: string-or-null = null}`. Client key matches `[A-Za-z0-9_-]{1,64}` and is unique within the operation. App allocates occurrence ID; different client keys create separate associations even for equal bytes. Evidence-producing image tools retain `ref`, `image_ref`, `extension`, source/derivation facts and all native-pixel/raw access; expose the immutable pre-enrichment `sha256` and validated `mime` without requiring naming annotations. They do not advertise a new deliverable `asset_path`/`asset_uri` until registration succeeds through the edit operation. Historical hash-path metadata remains labelled historical evidence, not a newly valid enriched binding. The accepted edit result supplies the canonical filesystem path and serialized URI together.

Operation identity remains the Dispatcher's existing outer identity, not an independently editable fact. HTTP callers use an `Idempotency-Key` header of 1–128 ASCII letters/digits/`._:-`, mapped to a namespaced task operation; the desktop creates it before submission and reuses it for transport retries. Tool calls retain their existing operation identity. Bind identity to task, tool and the existing exact-argument hash. Reusing an ID with different arguments conflicts; do not treat semantically similar JSON as a fresh retry. New corrections after a settled failure require a new operation ID. Replaying a settled failure returns that failure/candidate; replaying a committed success returns its original version/mappings even if head is newer.

**Same-operation references:** a create is referenced in candidate Markdown/HTML using the input-only destination `asset:new/<client_key>`. An existing occurrence may be selected with `asset:id/<occurrence_id>`. These opaque handles are valid only in operative destination positions of this edit; they are not URI filesystem paths, filenames or rendered links. The parser must retain them before the normal safe-renderer scheme filter. Resolve them to allocated canonical asset URIs and patch their destination spans before final validation/sanitization. An unknown key/ID rejects. No operative handle may remain in a saved document/export; identical literal text in code/comments stays literal. This closes the naming-before-reference dependency without a compulsory prepare call or exposing internal IDs in filenames.


```json
    "kind": "correct",
```

Apply ordinary document operations against the explicit base first, followed by page/source/fact patches, then resolve affected bindings. Interpret old canonical destinations using the **base** mapping before any renamed target is allocated. Exact corrected target paths may also be used if unambiguous; handles provide explicit identity when a candidate could otherwise select two occurrences. Shared source/page changes regenerate every affected catalog occurrence, including presently unreferenced registrations, while only referenced files enter the delivery inventory. A create may register an unreferenced occurrence, but it cannot bypass fact/enrichment validation. Candidate reuse copies requested content only; it never silently replays an old asset-change list.

Task-local SQLite allocation records enforce a unique `(job, comparison_policy, portable_name_key)` owner. A successfully allocated name stays assigned to that occurrence for the task's retained registry, including after final-reference removal or a rename; the same occurrence may reclaim its own name. This is an actual registered binding conflict, not a suffix added speculatively. Other occurrences cannot take it and make an old task-local path mean a different image. Historical versions still use their frozen path-to-representation mappings. A failed uncommitted reservation is not a permanent occupied name: settle/release its allocation claim atomically with the failed receipt, retaining useful bytes separately. Crash recovery reuses the same pending operation reservation/IDs; another writer cannot steal it while that operation remains unresolved. No new garbage-collection or source-deletion policy follows.

Preparation records bind operation/argument hash, base/head, allocated IDs/names, prepared representations and file hashes. Enrichment runs outside SQLite write transactions under the existing task-writer boundary. After preparation, a short transaction rechecks expected head and reservation ownership and jointly registers immutable version/mappings, promotes reservations and records the receipt. A stale head publishes none of these. File preparation and SQLite are not one physical transaction; only committed registration makes prepared files visible. On restart, an uncommitted preparation may resume idempotently after validation or settle as failure; it cannot be mistaken for a saved version. Failed work is preserved under existing retention rules.

## Reference interpretation and destination policy

### Whole-document analysis

Use the existing whole-document CommonMark/table/footnote rendering pipeline. Analyze effective `img.src` and `a.href` destinations, including supported raw HTML and reference-style links whose definitions are in other blocks. Do not scan individual blocks independently or use a Markdown-text regular expression as the reference authority. Code spans, fenced examples, HTML comments and unresolved reference syntax that remains literal text are not asset references.

The analysis must agree with the safe renderer on tag/attribute interpretation and HTML entities. Before discarding information through sanitization, reject duplicate `src` attributes on an image or duplicate `href` attributes on an anchor as unsupported resource markup; retain the original candidate. This applies even when the duplicates currently contain equal values, so the rule is deterministic. Other markup that would make reference collection and the supported rendered destination disagree must be rejected with useful feedback rather than guessed. Do not broaden this into general source-HTML repair. Image restrictions cannot be bypassed by having sanitization erase an otherwise unsupported image destination.

Build one deduplicated set of asset paths from the complete merged document, retaining whether each occurrence is an image or hyperlink for diagnostics. Saving, saved-version assessment and transient preview binding must use the same reference interpretation. An app-issued preview resource URL is an output of binding, not a source reference to scan back into the document or persist.

For corrections, retain exact source spans for effective destination text while parsing the complete document. Update only those spans, including controlling cross-block reference definitions and supported raw-HTML attribute values, then reparse to verify the new bindings. Preserve unrelated prose, whitespace, code literals and original candidate bytes. Do not globally replace text or reserialize the whole document to implement a rename. Parser line maps alone do not establish exact editable spans; a parser-integrated destination-span collector must be implemented and verified. Ambiguous mapping rejects the operation with its candidate retained; it cannot fall back to broad rewriting or routine manual user repair.

### Destination-span contract

`SourceSpan` is `{block_id: string, start: nonnegative integer, end: integer, expected: string}`: half-open Unicode code-point offsets, with `end >= start` and exact guarded text equality. For an edit it addresses the working block after requested ordinary operations and before automatic asset rewrites; for selected-version assessment it addresses that version's saved block. It never claims offsets into the raw argument JSON. It excludes surrounding angle brackets/quotes and link titles. For a reference link it identifies the controlling definition's destination, not the use label. The analysis record separately keeps each use's role/block and its controlling destination span; one definition shared by images and links is patched once. Duplicate definitions follow the pinned parser's effective-definition rule; inactive definitions remain unchanged. A source span must not point into generated page-marker comments or imaginary flattened offsets.

Build a flattened-document-to-block mapping while composing the existing whole-document Markdown, including generated markers/separators. Track parser input transformations such as CRLF handling, indentation, escapes and inline-table/footnote extraction back to original block code points. Instrument the pinned parser's link, image and reference-destination rules and enabled plugins; its line-only `Token.map` is insufficient. This is a source-map extension of the selected parser, not a second Markdown grammar or broad regex scanner. Apply nonoverlapping destination edits in descending original offset order per block, with expected-text guards, then rerun the same whole-document parser and verify intended occurrence/role bindings and unchanged unrelated content.

| Syntax | Destination edit / interpretation |
| --- | --- |
| Inline link/image, bare or angle-delimited destination, optional title | Replace only destination content with the canonical encoded URI; leave delimiters, title, label and whitespace. Escaped punctuation/entities resolve before URI decoding. |
| Full/collapsed/shortcut reference, including a definition in another block | Patch the effective definition's destination once; preserve reference labels and cross-block scope. Definitions and uses inside table cells/footnotes use the same document environment and exact source correspondence. |
| Markdown linked image | Treat outer hyperlink and inner image as two roles with their own targets/spans. Deduplicate only identical deliverable dependencies. |
| Raw HTML `a[href]` / `img[src]`, double/single/unquoted value | Retain original tag/attribute spelling and quote form; replace the guarded value only. The encoded URI fits unquoted attribute syntax. Collect raw duplicate attributes before sanitization, even equal ones. Compare the parsed target with sanitized rendering; malformed/ambiguous resource markup rejects rather than selecting a convenient interpretation. |
| Code, comments, ordinary autolinks/external URLs, unresolved literal references | No local asset rewrite. Footnote-generated fragment links are renderer output, not editable asset spans. |

An HTML token source-span scanner may use the existing standard-library HTML parser plus raw tag text, but only with equivalence checks against the pinned safe-renderer output; it is not an HTML5 authority for malformed input. Unsupported resource markup that changes parsing meaning must fail explicitly. Local-looking `srcset`, `<picture>/<source>` or other resource forms outside supported `img.src`/`a.href` cannot silently promise additional image dependencies: reject such image-resource input with its candidate retained. This does not broaden ordinary external citation checking or source-HTML repair.

### Supported destinations

A **canonical asset path** is the exact registered relative filesystem path `assets/<readable filename>` returned for this task-owned occurrence/representation. The basename obeys the filename rules above and uses the registered image type's lowercase extension. It contains no extra directory segment, leading slash/dot segment or backslash. Its Unicode spelling and case are authoritative; matching a shape or hash is insufficient. Internal SHA-256 remains byte identity, separate from filename and occurrence identity. This selects no new image format or generic attachment capability.

Distinguish that filesystem path from a Markdown/HTML/URI spelling that represents it. Spaces, Unicode, parentheses, percent signs and other syntax-sensitive text must round-trip through the supported parser/serializer to that exact registered path. Transport escaping is not a filename rename or permission to resolve arbitrary paths. In particular, a literal percent sign in a filename must remain distinguishable from a transport escape; no repeated decoding may turn source text into traversal or a separator. HTML entities are interpreted by the supported parser, with the original Markdown preserved unless an explicit reference correction is requested.

Generate one URI-encoded destination form from the exact registered path: keep literal `assets/`, UTF-8-percent-encode basename bytes except URI-unreserved ASCII letters/digits and `-._~`, and use uppercase hexadecimal escape digits. Return the filesystem path and ready-to-use destination together. The actual filename remains readable and its unencoded UTF-8 basename is what must fit 180 bytes. Markdown and HTML apply their own surrounding syntax/attribute escaping without changing the represented path.

Examples: `assets/News framing-p58 (2).png` becomes `assets/News%20framing-p58%20%282%29.png`; `assets/Comparison-p58&p61.png` becomes `assets/Comparison-p58%26p61.png`; the mixed-locator counterpart uses `p58%26i67`. A literal `%` is encoded as `%25`. The filename stores `&`, never `%26` or `&amp;` as a substitute for that connector.

Separate URI components before decoding, decode the basename once with strict UTF-8, and compare against the exact task/version-registered spelling and case. Do not use form decoding that changes `+` to space, double-decode percent text, reinterpret the decoded `&` as a query separator, or use filesystem fallback lookup. A literal basename containing `%2F` is transported as `%252F`; after one decode it remains literal text. Reject malformed escapes, decoded path separators/traversal, extra directories, queries/fragments and unregistered paths. Parser entity/Markdown escape handling precedes the defined URI lookup boundary; HTML serialization must not create another decode pass. Existing valid authored syntax need not be reformatted wholesale, but must resolve to the same exact registered binding. These accepted transport spellings do not introduce alternate-case/path aliases.

| Parsed destination condition | New-save behavior |
| --- | --- |
| Supported serialized reference to an exact registered task-owned asset, as image or hyperlink | Validate its bytes/provenance/originals and include it once, preserving all reference roles. |
| Missing registration, or asset owned only by another task | Reject with useful task-local guidance; do not search/adopt foreign files. |
| Local reserved-asset variant: leading `./`, `../` or `/`, extra/nested segments, alternate case/spelling, backslash, query/fragment, malformed or traversal-encoding variant | Reject without aliasing, resolving against a host directory or silently ignoring it. Distinguish supported transport escaping from a noncanonical path. |
| Unsupported image destination, including remote/file/data source input | Reject under the local-image rule; sanitization cannot hide the violation. |
| Ordinary external hyperlink, fragment-only anchor/footnote or unrelated relative citation | Keep existing Markdown/sanitization behavior; do not fetch or bundle it. Arbitrary citation availability is outside this batch. |
| Asset-looking text in code, comments or unresolved literal reference syntax | Preserve as text; no dependency or rejection solely from that text. |

Classify reserved-asset variants without filesystem access. Exclude fragment-only links and URLs with a scheme/authority; inspect local path components and supported transport decoding, considering slash/backslash, traversal, query/fragment and case-insensitive `assets` components. Encoded separators or traversal cannot become an accepted canonical path. A remote URL containing `/assets/` remains external. Classification is bounded validation, not a general URL canonicalizer or arbitrary-host-file resolver. Collision comparison is separate: it must not make an incorrectly cased reference silently resolve to a registered asset.

Do not silently convert links to embeds, remove promised links, accept a partial save with an unresolved required asset, include every task image, or infer a replacement image. Reference errors use the existing rejected-edit/candidate mechanism; the error identifies the destination/attribute and the reason, with an actionable correction. It must not expose another task's contents. A model can reuse its retained candidate in a new valid edit under the existing rules.

## Save and immutable dependency preparation

### Portable-link save increment

For new schema 1 saves, resolve the union of operative embeds and local image hyperlinks with the shared interpretation and task-owned registry. Keep existing hash paths and copy each referenced image and its associated original streams exactly once. Preserve Markdown roles and the existing immutable publication boundary. The [T3a acceptance](../batches/R01CAL-A03-DELIVERY-01/spec.md#t3a-portable-link-acceptance) checks newly saved, reopened and relocated results. This increment establishes portable links with retained originals. Standalone XMP and readable naming belong to enriched creation.

Use the existing app-authored blob metadata `purpose: "saved-output diagnostic preview"` to identify diagnostic registrations, including ones already in the task store. Exclude those registrations when resolving a source asset. A destination backed only by diagnostic registrations fails with a message identifying the reference and how to replace it with source evidence. A separately registered eligible source asset can still supply the same hash path. Keep existing diagnostics and historical versions readable. This guard requires no registration schema change or filename heuristic.

### Enriched save flow

For new source-image delivery, model guidance directs `edit_document` to create an occurrence with `asset_changes`, supplying the eligible evidence `ref` as `facts.image_ref` and `asset:new/<client_key>` as the authored image or link destination. The save returns the final relative asset URI. The evidence `asset_path` still identifies the registered source image. A create can explicitly adopt an existing schema 1 hash path through `legacy_path`, as specified in the [edit API](#document-edit-api-and-operation-semantics).

The enriched save flow is:

1. Preserve the received candidate through the existing Dispatcher boundary. Resolve the explicit task/base and apply the requested operations/page changes to the working document.
2. Analyze the complete working Markdown and explicit base bindings to identify operative references and requested corrections. Establish source/naming facts, compute valid final names and obtain durable unique path reservations before embedding path-dependent metadata. Keep preparation invisible; no new name or corrected mapping is published at this step.
3. Prepare the corresponding enriched representations and apply the requested synchronized reference/source-field changes. Then validate the complete merged document and resolve the final image/hyperlink dependency union through its task-owned occurrence/representation bindings. Validate finalized bytes, provenance and associated image/mask originals. Prepare the existing `assets`, `originals` and file/manifest records with the final paths/hashes; no second mutable body or generic attachment registry is introduced.
4. Prepare immutable version files, then conditionally publish the coherent version, occurrence mappings, head and receipt through the existing SQLite commit boundary. Naming/enrichment/reference failure cannot publish a partial update or advance head. File/transaction failure retains useful unregistered work invisibly. In-memory locks alone cannot enforce durable uniqueness; failed preparations must not become current bindings.
5. Return the existing operation result. Replay returns the historical receipt/version without changing a newer head; it does not re-run dependency discovery against a new document or fill old omissions.

The same policy applies to partial and complete content claims, ordinary edits, rebuilds and candidate reuse. A partial claim permits unfinished content; it does not make a deliberately referenced missing image file valid. Metadata-only edits still validate all references in the merged result. Removing the final reference removes that asset and any originals no longer needed from the new version only. Source PDF, old versions, original candidates and task evidence remain preserved.

Associated originals and source provenance follow the [existing image contract](PDF_EVIDENCE.md#pdf-coordinates-and-image-delivery). Enriched display deliverables additionally satisfy the embedded-metadata boundary above. The source PDF is not newly copied into delivery. Reference resolution itself performs no new extraction, resampling, color conversion, OCR or provider work. Metadata finalization is explicit preparation, never export-time healing.

## Saved-version assessment and diagnostics

Saved-version byte integrity and asset-reference completeness are separate checks. Preserve the current integrity gate: a registered version file that is missing or has a different hash is an integrity failure, not a harmless warning. Do not publish a verified ZIP from corrupted registered bytes.

For an integrity-valid version, assess its recorded content against **that version's** asset/original/file inventories and recorded naming policy. Historical registered hash paths remain interpretable as historical mappings; the readable-name/XMP requirements are not retroactively invented for old versions. New schema 1 saves follow the [portable-link contract](#portable-link-save-increment), and new schema 2 saves follow the [enriched contract](#enriched-save-flow). ## Preview binding and return behavior

**Adopted target, AR-S4.3.** Use an app-owned, snapshot-scoped resource protocol for supported display images in both parsed `img.src` and local `a.href`. Create the derived view only after the explicitly selected version passes integrity verification and the shared reference assessment permits binding. The internal protocol replaces data-URL transport for these selected document assets. It is not an OS protocol association, general URL handler or navigation broker. Other source-access tools and their image responses are outside this transport change.

### Verified resource transfer and identity

The document engine owns task/version registration, byte integrity, image-type validation and reference assessment. Its authenticated selected-version load supplies the trusted desktop host with complete verified display-image buffers and exact binding metadata, alongside sanitized document HTML and the out-of-band assessment. Transfer metadata identifies job/version, asset/representation binding, MIME, length and SHA-256. Main checks payload length/hash against the verified binding before accepting it. Carry the verified bytes through this boundary; do not reread mutable task blobs, resolve against head, reextract, resample or substitute another version's image. No separate task-blob read is required for a version-owned file.

Main retains one immutable resource table for the loaded snapshot. Only supported PNG/JPEG display-image members referenced by the shared interpretation and present in that version's verified inventory are eligible. Other version files, originals and unreferenced task images are not exposed as resource routes. Repeated references may share the same payload, while distinct occurrence/representation bindings retain their meanings. The renderer receives the derived preview and matching identity metadata; it cannot register arbitrary paths, supply replacement bytes or choose another task's bindings.

An illustrative URL is `pdfmd-preview://snapshot/<lease>/<asset-key>`. The spelling is an internal detail, not a saved document format. The app issues an unguessable lease for one loaded generation and opaque asset keys. Each entry binds its exact URL to the owning window/session, job, version, load generation, asset/representation identity, registered MIME, full length/hash and immutable bytes. Match issued entries exactly; do not interpret URL paths as filesystem paths or add query, fragment, case, encoding or directory aliases. Recheck an active lease before serving a request. Unknown, forged, foreign and revoked requests fail without revealing host paths or falling back to disk/network lookup.

Use Electron 45.0.0's stable `session.protocol.handle` on the actual window session, returning the complete image as a normal Response body with validated Content-Type, `nosniff` and no-store behavior. Privileged scheme registration occurs before app readiness. Select `standard: true`, `secure: true` and `corsEnabled: true`; leave CSP bypass, service workers, renderer Fetch API support and unrelated privileges disabled. Do not adopt deprecated protocol registration APIs, experimental directory serving, a listening image server or a new dependency for this boundary. The [pinned official API basis](../discussions/ASSET_REFERENCES.md#basis-and-official-guidance) remains the starting reference; check version applicability before eventual framework implementation.

### Sandbox and native request boundary

App-issued resource URLs exist only in the derived preview; saved Markdown/HTML and export keep their original relative asset destinations.

Use supported host request context and frame-navigation guards to establish the owning window/session/frame. The protocol callback alone does not provide frame identity; a matching scheme prefix, referrer or opaque `null` origin does not establish ownership. ### Snapshot lease lifecycle

Use a load generation in addition to `(job, version)`, coordinated through the existing document-session owner and trusted host lifecycle. The lease belongs to the loaded snapshot. Keep it through image viewing, ordinary output-tab changes and Return remounts while that snapshot remains ready; do not release it at the first image `load` or every iframe unmount. Unsaved editor content keeps the existing editing contract.

Revocation prevents new authorized requests but cannot erase bytes already delivered to Chromium or guarantee abortion of every in-flight response. Remove the old frame and reject late generation results at selection boundaries. No-store responses and unique per-generation URLs prevent a retained address from authorizing a different selection.
