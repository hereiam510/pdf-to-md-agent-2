## Task activity and local diagnostic API

The supported renderer detail entry is `readDiagnosticRecord(args: DiagnosticRecordArgs): Promise<DiagnosticRecordResult>` in `src/renderer/diagnosticClient.ts`. Its one required argument contains string `job`, `view`, `kind` and `key`; it has no result generic or fallback overload. `TaskDiagnostics` imports this function, which returns the unchanged bridge action/payload promise. Missing fields cannot fall back to `any` through this client. The generic low-level bridge still permits direct malformed calls; its concrete overload below is not exhaustive protection. [DT01's implementation owner](../verification/20261031_0157_LOCAL_DIAGNOSTICS.md#dt01-implementation-and-verification-2026-10-30) records the real-production-signature controls and delegation/rejection checks. No runtime decoding, extra call, retry, lifecycle or authority change is introduced.

The renderer's `DiagnosticDetail` describes the successful detail envelope and its actual optional projections; `DiagnosticRecordResult` also describes the server's `unavailable`/`stale` failures with reason, task and `refreshable=true`. Other HTTP/auth/query errors reject the invoke promise. The `diagnosticRecord` overload types the actual call result, and only `status='ok'` can enter `DiagnosticDetail | null` state. `links` retains the existing discriminated union; its callbacks infer success-only facts. This is compile-time contract maintenance, not validation of IPC/HTTP JSON. Original catalog/attempt/result/usage/descriptor observations retain unknown content; only scoped display reads narrow raw fields, and complete JSON remains available. Backend integrity/provenance/role and independent commit checks remain the runtime authority. The [typing implementation owner](../verification/20261031_0157_LOCAL_DIAGNOSTICS.md#diagnostic-detail-api-typing-implementation-2026-10-30) explains rationale and verification limits.

The [F02-D03 correction](../verification/20261031_0157_LOCAL_DIAGNOSTICS.md#f02-d03-implementation-and-evidence-2026-10-30) separates raw descriptor observations from validated facts. CURRENT_STATE identifies its actual source/build and finite verification. Whole-query failures remain distinct from local link failures; diagnostic status never authorizes recovery.

Each diagnostic reference keeps the original `ref`. `raw_descriptor`, when readable, contains the exact decoded descriptor observation, including null/array/scalar metadata or absent fields; it is explanatory data. A successful link has `status="available; integrity checked, acceptance not inferred"` and `facts={kind,bytes,meta,...}`. Only `facts` may supply structured ownership, usage or navigation. A failed link has `status="unavailable"`, its earliest applicable `reason`, and no `facts` or top-level kind/meta/bytes/attempt/relation. `DiagnosticLink` in the renderer models this as a discriminated union. This changes only diagnostic response JSON, not persisted descriptor/schema semantics.

`reference` first runs the shared `artifact_facts` integrity/provenance check, then validates the selected role before publishing facts: operation identity for candidate/result attachments, kind/request identity for frozen input, and allowed kinds for explicit request response/stream/accepted pointers. Shared pointers must satisfy all their selected roles. A metadata-shape failure is therefore not replaced by a speculative ownership mismatch. Request blob discovery uses raw fields only to select candidates; every resulting link is checked before use. Generic related and saved-version links use the same result boundary.

An unavailable ancillary link cannot load its result or confirm its owner. The independent inline receipt still runs the existing atomic operation/version/file checks; it supplies a version button only if those checks pass. Contradictory lineage or damaged version files remain unknown. A failed frozen-input link leaves independently readable request/attempt/publication/preparation facts visible. The UI displays local reasons, disables failed-link evidence actions and labels expandable raw observations **not verified facts**. Direct evidence access still uses the existing task/ref/integrity and exact-selection rules; raw observations do not authorize substitute evidence, repair, acceptance or graph readiness.

The [F02-D01/F02-D02 correction](../verification/20261031_0157_LOCAL_DIAGNOSTICS.md#f02-consistency-correction-implementation-and-evidence-2026-10-29) adds a shared factual ownership rule and per-row summary validation. CURRENT_STATE identifies the actual checked source/build and acceptance; the previous review's memory-only reproductions remain historical evidence.

**View activity and diagnostics** opens the existing task's `TaskDiagnostics` panel. Recent/Oldest/Older/Newer navigate a fixed event boundary; Refresh establishes another. The view selector lists requests, operations, versions, context decisions/dispositions/policy, historical resolutions, boundary receipts and evidence descriptors. Lists carry small facts; selected records, joins and exact originals load on demand. [The observability owner](../verification/20261031_0157_LOCAL_DIAGNOSTICS.md#f01f02-implementation-method-2026-10-29) owns rationale and acceptance.

All endpoints use existing loopback bearer authentication:

| Endpoint | Parameters and meaning |
| --- | --- |
| `GET /jobs/{job}/activity` | `limit=100`, validated 1–200; optional signed `cursor`. Returns ascending `events`, stable task/seq `id`, task-filtered `total`, one-based `first`/`last` (0/0 when empty), `boundary_seq`, and `older`/`newer`/`oldest`/`recent`. Cursor binds view, page size, direction and anchor; a foreign task or changed page size cannot reuse it. |
| `GET /jobs/{job}/diagnostics` | `kind`, optional `view`/`cursor`, `limit=50`, validated 1–100. Returns descriptor `items`, `offset`, `total`, optional `next`. A malformed/unsupported row retains catalog `id`, `created`, `diagnostic_status=unavailable` and `reason` in its original position. Total/offset/cursor include that row. Creation order is not graph execution order. |
| `GET /jobs/{job}/diagnostics/record` | Required `view`, `kind`, `key`. Complete selected record plus factual joins and scoped limitations. Requests separate attempts and artifact owners, and directly link frozen input plus explicit earlier proposal/check/feedback/handoff refs from preparation metadata or its context snapshot; same-request aliases do not replace recorded earlier refs. Operations match retained call arguments before claiming request linkage. Document effects check atomic operation/version receipts and immutable files independently of events/envelopes. |
| `GET /jobs/{job}/diagnostics/evidence` | Required `view`, `ref`; `mode=full/index/raw`, optional JSON `pointer` and half-open `start`/`end`. Reuses `Evidence.read`, integrity checking, task ownership, exact bytes/fields/ranges and saved native image pixels. Completeness/units/range describe the chosen selection; index is metadata only. No arbitrary path parameter exists. |
| `DELETE /jobs/{job}/diagnostics/{view}` | Releases only that task's temporary view. Changes no source task data. Renderer closes superseded/unmounted views and ignores late replies; shutdown closes remaining copies. |

The ordinary job projection returns `event_summary={count,latest_seq}` in place of the old embedded oldest-1,000 `events`. It remains a poll indicator, not an exporter cursor. Existing request/version/evidence summaries and compaction-recovery polling otherwise remain. Diagnostic pages, object contents and graph copies are not added to the 1.5-second poll. Filtered SQL counting can still scan event rows; bounded payload does not imply indexed or constant-time counting. F04's existing stopped-compaction inspection cost is separate.

`Diagnostics` initializes no Store/Runtime and opens no original database through SQLite. Explicit opening/refresh copies catalog/main and present WAL into private OS temporary storage, guards capture with two streamed file/hash passes and identity checks, and lets SQLite interpret the copied WAL. It does not copy graph or source SHM. Capture has a five-second read window; catalog query progress has a two-second deadline and service-lock acquisition is bounded. Pages reuse the copy. Up to eight process-local views expire after 15 minutes; cleanup occurs on next access, explicit close/refresh or shutdown. This costs one catalog/WAL copy per retained view and two source file passes per capture, without a durable projection/cache or background scanner. Large-catalog performance is unverified.

Responses label capture time, catalog consistency and graph **unchecked**. Event sequence is global; task counts/ranks use filtered rows. Event coverage is not a snapshot of all mutable records or graph state. Detail/evidence reads return refreshable `stale` when catalog identity changes; expired/busy/unsupported/corrupt views return `unavailable`. Source-page rendering can overlap initial capture; explicitly refresh after that app setup finishes. Independent established facts survive scoped missing/corrupt/mismatch errors; damaged links are disabled. No silent retry, repair, reconcile, context change, attempt or tool execution occurs. The saved acceptance inspector remains the graph/eligibility authority.

Reported zero, unknown and conflicting usage are distinct. Raw native usage is separate from settlement; handoff rejection does not erase accepted native usage. Frozen capacity/projection, context/handoff/repair and resolution records retain explicit refs. Individual fresh-execution/reuse returns are not uniformly logged; the UI says unknown instead of inventing events. Saved/complete claims do not prove fidelity. No new execution timing, provider TTFT, fee or hidden model reasoning is inferred.

`artifact_facts` in `diagnostics.py` is a small pure read check shared by artifact links and both operation-join directions. It checks selected request/task identity, descriptor ref/kind/task/request, retained attempt identity/request and unique membership, canonical `accepted:<request>` versus the published pointer, and retained response/call shapes. The join then checks exact operation index/tool/argument digest. A wrong published pointer is reported even when the selected request also retains valid canonical staging; no alias fallback establishes the join. Each operation returns a structured `request_association` with `confirmed`/`unconfirmed` and publication or reason. Only a confirmed result supplies navigable `request`; unconfirmed request inventory entries retain original IDs/reasons without relationship buttons. A verified document commit/version link remains independently available.

Published and canonical staging-only records both support factual call relationships. The latter displays **unpublished**. Neither that relationship nor the artifact integrity check asserts complete stream validation, native acceptance, executable tools or graph readiness. This helper invokes no parser reconstruction, settlement, reconciliation, recovery action or eligibility check. Request detail can reuse one checked response across its own operations; there is no persistent cache or general read-cost change.

`record_summary` validates only the object and fields used in summaries. Present textual summary fields may be strings/null; a request must retain a list of string attempt identities, including a valid empty list. Missing/null/string/dict attempts are unavailable rather than zero. Optional summary fields can be absent. JSON syntax failures and supported-JSON shape failures affect one row; whole-query/catalog failures remain page-level unavailable, distinct from a successful empty page. Selecting a bad row can return a scoped detail error while other list facts/counts/continuation stay visible. Raw original records are never repaired.

The ordinary task opening/poll projection also reads request display rows individually, preserving bad catalog identities/reasons so that a malformed row cannot block entry to diagnostics. It checks the metadata/capacity/route shapes that this display consumes and reports display limitations. If the existing strict compaction-recovery display read fails, `compaction_recovery` has no request and `diagnostic_limitations` explicitly says unavailable with **no eligibility conclusion**. The underlying `Engine.compaction_recovery`, execution/recovery readers and action eligibility are unchanged. This is failure isolation at the UI entry boundary, not an optimization of F04 or a second recovery authority.
